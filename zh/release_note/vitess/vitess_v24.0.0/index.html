主要变化

新支持

分片键空间的窗口函数下推

此版本引入了一项优化，允许窗口函数在按与唯一 vindex 匹配的列分区时被下推到各个分片。 以前，所有窗口函数查询都需要单分片路由，这限制了它们在分片表上的适用性。通过此更改，现在可以下推 PARTITION BY 子句与唯一 vindex 对齐的查询并在每个分片上执行。 有关示例和更多详细信息，请参阅文档。

查看路由规则

Vitess 现在支持视图的路由规则，并且可以像 vtctldclient ApplyRoutingRules 的表一样应用。当视图路由规则处于活动状态时，VTGate 会重写引用源视图的查询以改用目标视图的定义。例如，给定以下路由规则：

{
  "rules": [
    {
      "from_table": "source_ks.my_view",
      "to_tables": ["target_ks.my_view"]
    }
  ]
}

这个视图定义：

CREATE VIEW target_ks.my_view AS SELECT id, name FROM user;

像 SELECT * FROM source_ks.my_view 这样的查询将在内部重写为：

SELECT * FROM (SELECT id, name FROM target_ks.user) AS my_view;

视图路由规则要求架构跟踪器监视视图，这意味着 VTGate 必须使用 --enable-views 标志启动，VTTablet 必须使用 --queryserver-enable-views 标志启动。目标视图必须存在于指定的键空间中，路由规则才能正常运行。有关更多详细信息，请参阅架构路由规则文档。

通过 USE 语句定位平板电脑

VTGate 现在支持使用扩展的 USE 语句语法通过别名将查询路由到特定平板电脑：

USE keyspace:shard@tablet_type|tablet_alias;

例如，要定位特定的副本平板电脑：

USE commerce:-80@replica|zone1-0000000100;

设置后，会话中的所有后续查询都会路由到指定的平板电脑，直到使用标准 USE keyspace 或 USE keyspace@tablet_type 语句清除为止。这对于调试、每个平板电脑监控、缓存预热以及需要针对特定​​平板电脑的其他操作任务非常有用。 注意：使用平板电脑定位时必须指定分片。与分片定位一样，这会绕过基于 vindex 的路由，因此请谨慎使用。

Binlog 流支持

VTGate 现在通过两种协议支持基于 GTID 的 binlog 流：

  • MySQL 协议：Clients 可以使用标准 MySQL COM_BINLOG_DUMP_GTID 复制协议命令进行连接 — 无需特殊的 VStream 感知适配器或直接 MySQL 访问。
  • gRPC：vtgateservice 中的新 BinlogDumpGTID 流 RPC 为自定义 client 提供本机 gRPC 访问，而无需 MySQL 协议依赖性。 注意：仅支持基于 GTID 的流式传输。基于文件/位置的流式传输无法通过 COM_BINLOG_DUMP 或 COM_BINLOG_DUMP_GTID 获得，并返回错误。 默认情况下禁用此功能。使用 --enable-binlog-dump 启用它。 新标志：
  • --enable-binlog-dump：启用二进制日志转储支持。如果没有此标志，二进制日志转储请求将返回错误。
  • --binlog-dump-authorized-users：授权执行二进制日志转储操作的用户的逗号分隔列表，或 % 允许所有用户。 要求： 启动二进制日志转储连接时，clients 必须指定：
  • 空文件名
  • 文件位置 (filepos) 为 4
  • GTID 位置 对于 gRPC clients，请直接在 BinlogDumpGTIDRequest 中指定键空间、分片以及可选的平板电脑类型或平板电脑别名。 限制：
  • 每个流在单个平板电脑上运行 - 没有跨分片的数据聚合。
  • 无自动故障转移 - 如果目标平板电脑不可用，则流将失败，并且 client 必须重新连接到其他平板电脑。
  • 与 MoveTables 或 Reshard 操作不兼容。对于这些用例，请使用 VStream API。

结构化日志记录

Vitess 现在默认使用结构化 JSON 日志记录。日志输出作为 JSON 发送到 stderr。要配置最低日志级别，请传递 --log-level（debug、info、warn、error 之一；默认 info）。对于具有自动颜色检测功能的人类可读格式，请传递 --log-format=text。要恢复到以前的 glog 后端，请传递 --log-structured=false。 glog 从 v24 开始已弃用，并将在 v25 中删除。

重大变更

默认情况下，外部解压缩器不再从备份 MANIFEST 中读取

默认情况下，恢复时不再使用备份的 MANIFEST 文件中存储的外部解压缩器命令。以前，当未提供 --external-decompressor 标志时，VTTablet 将回退到 MANIFEST 中指定的命令。这带来了安全风险：具有备份存储写入权限的攻击者可以修改 MANIFEST 以在平板电脑上执行任意命令。 从 v24 开始，基于 MANIFEST 的解压缩器将被忽略，除非您明确选择使用新的 --external-decompressor-use-manifest 标志。如果您依赖此行为，请将该标志添加到您的 VTablet 配置中，但请注意安全隐患。 有关详细信息，请参阅 #19460。

小改动

VReplication

--shards MoveTables/Reshard 启动和停止标志

MoveTables 和 Reshard 工作流程的 start 和 stop 命令现在支持 --shards 标志，允许用户在特定分片子集上启动或停止工作流程，而不是立即在所有分片上启动或停止工作流程。 使用示例：

# Start workflow on specific shards only
vtctldclient MoveTables --target-keyspace customer --workflow commerce2customer start --shards="-80,80-"

# Stop workflow on specific shards only
vtctldclient Reshard --target-keyspace customer --workflow cust2cust stop --shards="80-"

针对平板电脑特定错误自动重试平板电脑

现在，当遇到特定于平板电脑的错误时，VReplication 工作流程会自动使用不同的平板电脑重试。以前，没有单元首选项的工作流程将默认为本地单元，并且可能会无限期地重试相同的失败平板电脑。 当平板电脑遇到二进制日志清除（MySQL 错误 1236 或 1789）或 GTID 设置不匹配等错误时，VReplication 会将该平板电脑添加到忽略列表中，并尝试所有单元中的其他平板电脑。尝试完所有匹配的平板电脑后，忽略列表将被清除，工作流程将从头开始重试。 这在多单元部署中特别有用，其中本地单元中的平板电脑可能缺少所需的二进制日志，但其他单元中的平板电脑仍然有它们。

VTGate

删除了 --grpc-send-session-in-streaming 标志

VTGate 标志 --grpc-send-session-in-streaming 已被删除。该标志在 v22 中已通过 #17907 弃用，默认为 true。 现在，会话始终作为 StreamExecute 和 StreamExecuteMulti RPC 的流响应中的最后一个数据包发送。此行为是支持流处理中的事务所必需的，并且无法禁用。 影响：从 VTGate 启动脚本或配置中删除所有 --grpc-send-session-in-streaming 标志的使用。

--legacy-replication-lag-algorithm 标志的新默认值

VTGate 标志 --legacy-replication-lag-algorithm 现在默认为 false，默认情况下禁用处理复制滞后的旧方法。 相反，使用纯粹基于低延迟、高延迟和最小平板电脑数量的更简单的算法，该算法已被证明在许多生产环境中更加稳定。这两种方法的详细解释在此代码注释中进行了解释。 在 v25 中，此标志将被弃用，并且在接下来的版本中它将被删除。同时，可以通过设置 --legacy-replication-lag-algorithm=true 来使用旧行为。此弃用在 https://github.com/vitessio/vitess/issues/18914. 中跟踪

--vtgate-balancer-mode 标志的新“会话”模式

除了现有的“单元”、“首选单元”和“随机”模式之外，VTGate 标志 --vtgate-balancer-mode 现在还支持新的“会话”模式。会话模式在会话持续时间内将每个会话一致地路由到同一平板电脑。 要启用会话模式，请在启动 VTGate 时设置标志：

--vtgate-balancer-mode=session

查询服务

JSON_EXTRACT 现在支持动态路径参数

JSON_EXTRACT 函数现在支持动态路径参数，例如绑定变量或其他函数调用的结果。以前，JSON_EXTRACT 仅适用于路径参数的静态字符串文字。 NULL 处理现在与 MySQL 行为匹配。当文档或路径参数为 NULL 时，该函数返回 NULL。 即使与动态参数混合，静态路径参数仍然经过优化，因此现有查询不会出现任何性能下降。

VTTablet

新实验标志 --init-tablet-type-lookup

VTablet 的新实验标志 --init-tablet-type-lookup 允许平板电脑在重新启动时通过查找现有拓扑记录自动恢复以前的平板电脑类型，而不是始终使用静态 --init-tablet-type 值。 启用后，平板电脑将在重新启动时使用其别名从现有拓扑记录中查找平板电脑类型。这使得平板电脑可以在重新启动后保持其更改后的角色（例如 RDONLY/DRAINED），而无需手动重新配置。如果禁用或不存在拓扑记录，则将使用标准 --init-tablet-type 值。 注意：Vitess Operator 管理的部署通常不会在 pod 替换之间保留拓扑中匹配的平板电脑记录，因此此功能在这些环境中的效果将更加有限。

QueryThrottler 可观测性指标

VTablet 现在公开新的指标来跟踪 QueryThrottler 行为。 添加了四个新指标：

  • QueryThrottlerRequests：查询节流器评估的请求总数
  • QueryThrottlerThrottled：被限制的请求数
  • QueryThrottlerTotalLatencyNs：每个请求在查询限制中花费的总时间，包括评估、指标检查和其他开销（以纳秒为单位）
  • QueryThrottlerEvaluateLatencyNs：做出限制决策所需的时间（以纳秒为单位） 所有指标均包含 Strategy、Workload 和 Priority 的标签。 QueryThrottlerThrottled 指标具有针对 MetricName、MetricValue 和 DryRun 的附加标签，用于识别哪个指标触发了限制以及是否在试运行模式下发生。 这些指标有助于监控限制模式、确定哪些工作负载受到限制、测量性能开销以及在配置更改之前验证空运行模式下的行为。

QueryThrottler 事件驱动的配置更新

QueryThrottler 配置现在传播并存储在拓扑服务器内的 SrvKeyspace 记录中，并使用标准拓扑工具进行管理。以前，平板电脑每 60 秒轮询一次配置更改。平板电脑现在使用事件驱动的监视 (WatchSrvKeyspace) 在查询限制配置更改时立即接收更新。键空间中的所有平板电脑几乎同时看到配置更改，并且拓扑服务器更改是版本化且可审计的。 此更改用存储在拓扑中的 protobuf 定义的配置结构取代了之前基于文件的配置加载器。新配置包括用于启用/禁用限制、选择限制策略以及配置特定于策略的规则的字段。

平板电脑连接池等待上限

VTablet 现在允许用户对等待从连接池获取连接的请求数量设置限制，例如 查询、流和事务连接池。限制是通过以下标志设置的：

  • --queryserver-config-query-pool-waiter-cap
  • --queryserver-config-stream-pool-waiter-cap
  • --queryserver-config-txpool-waiter-cap 以上所有内容都有一个默认值 0，意味着没有限制，从而保留了以前版本的行为。

跟踪

OpenTelemetry 跟踪支持

Vitess 现在支持 OpenTelemetry 作为跟踪后端。要使用它，请在任何 Vitess 二进制文件上设置 --tracer opentelemetry。迹线通过 OTLP/gRPC 导出，可使用以下标志进行配置：

  • --otel-endpoint：OpenTelemetry 收集器端点。如果为空，则使用 OTEL_EXPORTER_OTLP_ENDPOINT 环境变量；如果也未设置，则 OTel SDK 默认为 localhost:4317。
  • --otel-insecure（默认false）：使用与收集器的不安全连接。
  • --tracing-sampling-rate（默认 0.1）：跟踪的采样率（在所有跟踪后端共享）。 任何 OTLP 兼容后端（Jaeger v1.35+、Grafana Tempo、Datadog Agent 等）都可以接收这些跟踪。

弃用基于 OpenTracing 的跟踪后端

从 v24 开始，以下跟踪后端已弃用，并将在 v25 中删除：

  • opentracing-jaeger — 使用已存档的 Jaeger client-go 库。 Jaeger 项目建议迁移到 OpenTelemetry。用户应使用兼容 OTLP 的 Jaeger 端点 (v1.35+) 迁移到 --tracer opentelemetry。
  • opentracing-datadog — 在 dd-trace-go 中使用 OpenTracing 桥。用户应使用 Datadog Agent 的 OTLP 摄取端点迁移到 ZZPH100​​ZZ。 --tracer opentracing-jaeger 和 --tracer opentracing-datadog 选项在 v24 中继续工作，但会在启动时记录弃用警告。以下 Jaeger 特定标志也已弃用，并将在 v25 中删除：
  • --jaeger-agent-host
  • --tracing-sampling-type 迁移：将 --tracer opentracing-jaeger 替换为 --tracer opentelemetry，将 --jaeger-agent-host host:port 替换为 --otel-endpoint host:4317。确保您的 Jaeger 部署接受 OTLP（Jaeger v1.35+ 默认侦听端口 4317）。

VTORc

新 --cell 标志

VTOrc 现在支持 --cell 标志，该标志指定 VTORc 进程在哪个 Vitess 单元中运行。该标志在 v24 中是可选的，但在 v25+ 中是必需的，类似于 VTGate 的 --cell 标志。 如果提供，VTORc 会在启动时验证单元是否存在于拓扑服务中。如果没有该标志，VTORc 会记录有关 v25+ 标志要求的警告。 这使得未来的跨单元问题验证成为可能，VTORc 将能够在采取恢复操作之前要求另一个单元验证检测到的问题。该标志当前已验证，但尚未在 VTORc 恢复逻辑中使用。 注意：如果您在多单元部署中运行 VTORc，请立即开始使用 --cell 标志来为 v25 要求做好准备。

有序恢复执行和半同步部署

VTORc 现在按照定义的顺序对每个分片执行恢复，而不是单独对每个片执行恢复。具有顺序依赖性的问题（例如，半同步配置）首先串行执行，而独立的问题则并发执行。这确保了相关恢复在分片内以正确的顺序发生。 面向用户的主要改进是半同步推出：VTORc 现在确保副本在更新主副本之前启用半同步。以前，在足够的副本准备好之前在主服务器上启用半同步可能会在主服务器等待没有副本准备发送的半同步确认时停止写入。 有关详细信息，请参阅 #19427。

已删除已弃用的 VTORc 指标

DiscoverInstanceTimings 指标已从 v24 中的 VTORc 中删除。该指标在 v23 中已弃用。 迁移：改用 DiscoveryInstanceTimings，它为实例发现操作（后端、实例、其他）提供相同的计时信息。 影响：使用 DiscoverInstanceTimings 的监控仪表板或警报系统必须更新为使用 DiscoveryInstanceTimings。

弃用快照拓扑功能

VTORc 的快照拓扑功能（通过将 --snapshot-topology-interval 设置为非零值来启用）从 v24 开始已弃用，并且计划在 v25 中删除该逻辑。 由于缺乏读取此功能创建的快照的设施，加上 VTORc 后端的内存特性，意味着此逻辑的用处有限。 https://github.com/vitessio/vitess/issues/18691. 中详细解释和跟踪了此弃用 迁移：删除 v25 之前的 VTORc 标志 --snapshot-topology-interval。 影响：VTORc 无法再在其后端数据库中创建拓扑快照。

已删除已弃用的 /api/replication-analysis 端点

/api/replication-analysis 端点已从 v24 中的 VTORc 中删除。请改用 /api/detection-analysis，它提供相同的功能。 迁移：更新调用 /api/replication-analysis 的任何脚本、监控系统或自动化以使用 /api/detection-analysis。替换端点接受相同的查询参数（keyspace、shard）并返回相同的 JSON 响应格式。 影响：对 /api/replication-analysis 的 HTTP 请求将返回 404 Not Found 错误。

指标

通过 Prometheus 扩展 Go 运行时指标

Vitess 现在通过 Prometheus 公开全套 Go 运行时指标。默认的 Prometheus GoCollector 仅公开三个 runtime/metrics（/gc/gogc:percent、/gc/gomemlimit:bytes、/sched/gomaxprocs:threads）加上旧版 go_memstats_* 集。从 v24 开始，所有 Vitess 组件都公开了 Go 的 runtime/metrics 包中的大约 150 个附加指标。 新指标包括：

  • 堆分配直方图
  • GC 循环计数和暂停直方图
  • 内存类别细分
  • Goroutine 状态故障
  • 调度程序延迟直方图
  • 按类别（用户、GC、清理、空闲）的 CPU 时间细分 新的 go_info_ext 仪表还添加了 compiler、GOARCH 和 GOOS 标签，提供了标准 go_info 指标之外的扩展构建环境信息。 受影响的组件：vtgate、vttablet、vtctld、vtorc、vtbackup、mysqlctld 无需配置 — 对于使用 Prometheus 后端的所有组件，指标会自动显示在 /metrics 端点上。

备份和恢复

MySQL 克隆对副本配置的支持

VTablet 和 VTBackup 现在支持使用 MySQL 的本机 CLONE 插件 通过网络直接从捐赠者平板电脑复制数据来配置新副本。物理级数据复制比逻辑备份和恢复要快得多，尤其是对于大型数据集。需要 MySQL 8.0.17+ 和仅限 InnoDB 的表。 新标志：

旗帜 描述
--mysql-clone-enabled 启用MySQL CLONE插件并在MySQL初始化期间创建克隆用户。对于将参与 CLONE 操作的所有平板电脑来说都是必需的。
--clone-from-primary 从分片的主平板电脑克隆数据，而不是从备份恢复。与 --clone-from-tablet 互斥。
--clone-from-tablet 通过别名（例如 zone1-123）从特定平板电脑克隆数据，而不是从备份中恢复。与 --clone-from-primary 互斥。
--restore-with-clone 使用 MySQL CLONE 进行恢复阶段，而不是从备份恢复。需要 --clone-from-primary 或 --clone-from-tablet。
--clone-restart-wait-timeout CLONE REMOTE 完成后等待 MySQL 重新启动超时。默认值：5 分钟。
克隆用户配置：
旗帜 描述
------ -------------
--db-clone-user MySQL 用于克隆操作的用户名（捐赠者身份验证）。
--db-clone-password 克隆用户的密码。
--db-clone-use-ssl 连接到捐赠者进行克隆操作时使用 SSL。
用法示例：
从分片的主分片克隆： 
vttablet \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-primary \
  ...

从特定平板电脑克隆：

vtbackup \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-tablet=zone1-0000000100 \
  ...

注意： 参与 CLONE 操作的所有平板电脑（捐赠者和接收者）必须在 MySQL 初始化期间设置 --mysql-clone-enabled，以确保加载 CLONE 插件并且克隆用户存在。

恢复挂钩改进

扩展钩子覆盖范围：现在，当通过 vtctldclient RestoreFromBackup 触发恢复时，vttablet_restore_done 钩子会触发。以前，此挂钩仅在平板电脑启动或克隆操作期间运行。 新环境变量：该挂钩现在设置 TM_RESTORE_DATA_BACKUP_ENGINE 来指示使用哪个备份引擎。该值来自备份清单的 BackupMethod 字段。 仅当还原从实际备份读取时才设置 TM_RESTORE_DATA_BACKUP_ENGINE，不适用于基于克隆的还原或不使用备份时。挂钩脚本可以使用它来根据还原是否使用 builtin、xtrabackup 还是其他引擎来执行特定于引擎的操作。
