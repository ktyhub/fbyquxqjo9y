vitess v23.0.8

Vitess v23.0.8 发布

总结

不支持的 sql_mode 值被拒绝

VTGate

VTGate 已拒绝启用 Vitess 解析器不支持的模式的 SET sql_mode = ... 语句（ANSI_QUOTES、NO_BACKSLASH_ESCAPES、PIPES_AS_CONCAT、REAL_AS_FLOAT）。检查比较模式名称的文本并且可以被绕过。 VTGate 现在实现了 MySQL 8.x 的 sql_mode 赋值语义，并根据它们验证每个赋值：

  • 即使底层 MySQL 已使用该模式运行（即 SET 不会更改该值），设置不支持的模式也会被拒绝。即使 VTGate 在这些模式下不解析查询，此类语句以前也会成功。组合模式 ANSI 也被拒绝，因为它启用 ANSI_QUOTES、PIPES_AS_CONCAT 和 REAL_AS_FLOAT。
  • IGNORE_SPACE 和 HIGH_NOT_PRECEDENCE 现在也被拒绝。它们是改变 SQL 文本解释方式的剩余两种模式。 Vitess 解析器不支持它们，因此 VTGate 解析查询的方式与会话的 sql_mode 承诺不同。
  • 未知模式名称和无效数值会失败，并出现 MySQL 自身的错误：MySQL 8.0 中删除的模式位的 ER_WRONG_VALUE_FOR_VAR (1231) 和 ER_UNSUPPORTED_SQL_MODE (3899)。
  • 数值根据 MySQL 的 sql_mode 位掩码进行解码。例如，SET sql_mode = 1048576 报告不支持 NO_BACKSLASH_ESCAPES。接受有效的数值。
  • 常量值在计划时验证，没有分片往返。这包括常量表达式，例如基于文字的 CONCAT，并且在禁用 --enable-system-settings 时也适用。一旦非常量表达式的值已知，就会在执行时对其进行验证。

VT平板电脑

VTablet 在其自己的入口点应用相同的验证并返回相同的错误：连接设置、设置池和保留连接以及会话范围的 SET sql_mode 语句。这涵盖绕过 VTGate 验证的 clients，例如尚未升级的 VTGate 和直接与查询服务对话的 clients。 SET_VAR 优化器提示原封不动地转发到 MySQL。 现在，Vitess 创建的每个 MySQL 连接都会从它从服务器全局值继承的会话 sql_mode 中删除更改 SQL 文本解释方式的模式。所有其他模式（例如严格模式和零日期模式）都将保留。这适用于每个组件：查询服务、架构跟踪、心跳、复制管理、在线 DDL、VReplication 和 VDiff，以及与外部 MySQL 服务器的连接。全局sql_mode没有改变。 ####影响

  • 以不受支持的模式运行 SET sql_mode 的 Client（包括 ANSI、IGNORE_SPACE 和 HIGH_NOT_PRECEDENCE）现在会收到错误。当 SET 与后端的当前 sql_mode 匹配时也会发生这种情况。设置模式名称 MySQL 的 Cli 本身也会拒绝接收错误。
  • 在滚动升级期间，VTTablet 通常在 VTGate 之前升级。通过未升级的 VTGate 设置现已拒绝的 sql_mode 的会话已开始从已升级的 VTablet 接收错误。
  • 全局 sql_mode 包含其中一种模式的后端保留它，但 Vitess 会话不再继承它。 有关详细信息，请参阅 #20883。

表 ACL：每个表上具有每个角色的调用者可以运行无法确定其表的语句

v23.0.7 开始在严格表 ACL (--queryserver-config-strict-table-acl) 下拒绝豁免 ACL 之外的每个调用者的表 vttablet 无法确定的语句（DO、CALL、REPAIR、OPTIMIZE、LOAD DATA 和 vttablet 解析器无法完全解析的 CREATE TABLE） （--queryserver-config-acl-exempt-acl）；请参阅 GHSA-w6mx-2f8x-pqf4。覆盖每个表 ("table_names_or_prefixes": ["%"]) 的表组中作为读取器、写入器和管理员的调用者拥有此类语句可能触及的任何表上的每个角色，因此 DO、REPAIR、OPTIMIZE 和部分解析的 CREATE TABLE 现在为其运行。即使这样，CALL 和 LOAD DATA 仍然被拒绝，因为 SQL SECURITY DEFINER 过程以其定义者的权限运行，而 LOAD DATA INFILE 读取服务器上的文件，这两个表 ACL 都没有授予；将他们作为豁免 ACL 中的调用者发出。 对于每个表上具有每个角色的调用者，这些检查在 undetermined-table-set TableName 标签、TableACLDenied 或 TableACLAllowed 中进行计数。对于空运行 (--queryserver-config-enable-table-acl-dry-run)，只有检查会拒绝增量 TableACLPseudoDenied 的语句。 有关详细信息，请参阅 #21349。

连接字符集受限

--db-charset 以及配置了 MySQL 连接字符集的其他位置不再接受 sjis、cp932、gb18030、gbk、big5、ucs2、utf16、utf16le 或 utf32，无论是作为字符集还是作为其排序规则之一给出。配置其中之一的平板电脑无法启动，VTGate 拒绝将 character_set_client、character_set_connection、character_set_results 或 collation_connection 中的 SET 分配给其中之一，或者拒绝不是字符集或排序规则的名称（它用于回答 OK 并忽略），VTTablet 拒绝将会话连接切换到其中之一的设置或 SET 语句。 client 可能仍会在握手时请求其中之一：VTGate 逐字节读取其语句，就像平板电脑与 MySQL 的连接一样，因此它们无法突破文字。 Vitess 逐字节解析和转义 SQL 文本，在这些字符集中，字符的第二个字节可以是反斜杠或反引号，因此其中的文本在通过 Vitess 的过程中被错误解析或损坏。请改用 utf8mb4 作为连接字符集。表和列仍然可以使用这些字符集中的任何一个来声明； MySQL 在它们和连接字符集之间进行转换。 这修复了 GHSA-c28j-qmfx-4gxp。 有关详细信息，请参阅 #21392 和 #21465。

重新生成时，字符集和排序规则名称会被引用

现在，在解析时会对字符集、排序规则、引擎、表空间或全文解析器名称进行解码，并在 Vitess 重新生成语句时将其写回为单个标记：当它是已知的字符集、排序规则、引擎、索引类型或解析器名称时为裸露，否则使用反引号。 用户可见的后果：

  • 带引号的名称被标准化。 COLLATE 'utf8_bin' 重新生成为 COLLATE utf8_bin — 带引号和不带引号的拼写表示相同的名称，并且解码的形式是存储的内容。任何逐字节比较这些语句的打印形式的内容都会看到新的拼写。
  • 仅已知名称保持裸露。 任何 MySQL 或 MariaDB 版本的字符集或排序规则名称、已知存储引擎（例如 InnoDB 或 memory）、BTREE、HASH 和 RTREE 索引类型、ngram 和 mecab 解析器以及 innodb_system 和innodb_file_per_table 表空间按其拼写方式写回。任何其他名称都用反引号括起来：TABLESPACE ts 重新生成为 TABLESPACE `ts` , and so does an engine Vitess does not know or a keyword used as a name. WITH PARSER accepts only a plain identifier, so a known name that is a keyword is quoted there: WITH PARSER `memory` keeps its quoting where ENGINE内存 does not. binary is still bare where the grammar has a BINARY alternative, except directly before the BINARY attribute: 字符集“二进制”BINARY regenerates as CHARACTER SET `binary` BINARY。
  • 表达式中的 ZZPH100​​ZZ 被引用。 expr COLLATE binary 重新生成为“expr COLLATE binary``, because MySQL's expressionCOLLATEonly acceptsbinaryquoted. Column, table and databaseCOLLATE 二进制andCHARACTER SET 二进制”保持裸露。
  • 拒绝空字符集、排序规则、引擎或分区表空间名称。 列、表上的 CHARACTER SET '' 和 COLLATE ''、表或分区上的 ALTER TABLE ... CONVERT TO、CAST/CONVERT、CONVERT ... USING、CHAR ... USING、SELECT ... INTO OUTFILE 和表达式 ENGINE ''，并且分区的 TABLESPACE '' 不再解析。这些位置中的空名称与不存在的子句无法区分，因此它以前会被删除或损坏，并且 MySQL 拒绝的语句可能会成为有效的不同语句。非DDL语句直接得到错误； DDL 回退到部分解析，因此 client 自己的文本被转发，而 MySQL 拒绝它。 SET NAMES ... COLLATE '' 和 SET CHARACTER SET ... COLLATE '' 过去用于解析并丢弃排序规则，现在也是解析错误； MySQL 两者都拒绝。 CREATE/ALTER DATABASE ... CHARACTER SET '' 和 COLLATE '' 未更改：它们仍然解析并写回为 ''。
  • ENCRYPTION 需要带引号的值。 CREATE/ALTER DATABASE ... ENCRYPTION N 不再完全解析，匹配 MySQL，仅接受 'Y' 或 'N' 作为带引号的字符串。这样的语句现在回退到部分解析，而不是重新生成为 MySQL 会拒绝的拼写。 这修复了 GHSA-j8pc-mcwq-qrg6。 有关详细信息，请参阅 #21435。

VTAdmin VExplain 运行语句的模式需要 execute 操作

VTAdmin 的 VExplain API 已获得 get 操作的授权，但 VEXPLAIN QUERIES、ALL 和 TRACE 运行它们解释的语句，因此仅允许读取的参与者可以通过它更改数据 (GHSA-c2r8-grjp-w8c2)。这些模式现在需要对 VExplain 资源执行新的 execute 操作；仅规划语句的PLAN和KEYS，仍然只需要get。对于这些模式，VTAdmin 还只接受不带 INTO 的 SELECT、序列下一个值或建议锁定函数，并在始终回滚的只读事务中运行它们。 Web UI 中的 VExplain 页面现在默认为 PLAN。 迁移：将 VExplain 上的 execute 操作授予应运行 VEXPLAIN QUERIES、ALL 或 TRACE 的参与者。授予所有操作 (*) 和 --no-rbac 的规则已包含它。 影响：在 VExplain 上仅使用 get 的 actor 从 VEXPLAIN QUERIES、ALL 和 TRACE 获得 unauthorized 错误。 有关详细信息，请参阅 #21396。
