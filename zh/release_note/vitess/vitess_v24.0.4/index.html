vitess v24.0.4

Vitess v24.0.4 发布

总结

lz4备份引擎：库升级和--compression-level映射

lz4 压缩引擎现在使用 pierrec/lz4/v4 库而不是 pierrec/lz4 v2。这修复了 v2 库中 amd64 上损坏的块解码。帧格式不变，因此旧 Vitess 版本写入的备份仍然可以恢复，并且该版本写入的备份也可以由旧版本恢复。 此次升级改变了 lz4 引擎对 --compression-level 的解释方式。值0和1，包括默认的1，选择快速压缩器； 1 之前请求的哈希链搜索深度为 1。值 2 到 9 现在选择 lz4 的命名哈希链级别（Level2 到 Level9），而不是使用原始值作为哈希链搜索深度，因此较高的值会以更高的 CPU 成本产生更好的比率。负值（之前请求无限制搜索）和高于 9 的值（用作搜索深度）选择 Level9。其他压缩引擎不受影响。 有关详细信息，请参阅 #20778。

无法根据配置的 CRL 检查其证书吊销的连接将被拒绝

使用 --grpc-crl、--mysql-server-ssl-crl、--tablet-grpc-crl、--vtgate-grpc-crl 和其他 *-crl 标志配置的证书吊销列表现在在每个 SSL 模式和恢复的 TLS 会话中强制执行，请参阅 GHSA-fxqj-c35w-x6rq。对等方已验证链的每个证书（链结束处的 trust 锚点除外）都会根据其颁发者（链的下一个证书）签名的 CRL 进行检查。

现在被拒绝的连接

在 preferred 和 required SSL 模式下，不会验证服务器的证书链。具有 CRL 的 client 现在会将该链构建到已配置的 CA，或者在未配置 CA 时构建到系统根，并在无法构建或验证链时拒绝连接，而不是不检查 CRL。例如：

  • required 模式下的 client 具有 CRL 但没有 CA 文件，连接到其证书由私有 CA 颁发的服务器。
  • 配置了 CRL 和根 CA 的 client，连接到提供其证书的服务器，而无需颁发该证书的中间 CA。
  • 具有 CRL 的 client 连接到其证书已过期或对服务器身份验证无效的服务器，这些模式在没有 CRL 的情况下接受该证书。 要保持此类连接正常工作，请配置服务器链通向的 CA，让服务器提供其整个链和有效证书，或者删除 CRL。 配置了 CRL（--tablet-grpc-crl、--vtgate-grpc-crl、--vtctld-grpc-crl 和其他 *-grpc-crl 标志）的 gRPC client，但 client 证书和 CA 现在均不与 TLS 连接，根据系统根验证服务器，而不是以明文形式静默忽略 CRL。配置 CA 和 CRL，或删除 CRL。

启动时被拒绝的配置

现在，在启动时构建 TLS 配置时，以下配置将被拒绝，因为 CRL 无法按配置应用。他们中的大多数过去常常在默默忽略 CRL 的情况下运行。

  • 没有匹配 CA（--grpc-ca、--mysql-server-ssl-ca）的服务器端 CRL（--grpc-crl、--mysql-server-ssl-crl）。如果没有 CA，则不会请求 client 证书，因此无法应用 CRL。配置 CA，或删除 CRL。
  • 没有匹配证书和密钥（--grpc-cert 和 --grpc-key、--mysql-server-ssl-cert 和 --mysql-server-ssl-key）的服务器端 CRL（--grpc-crl、--mysql-server-ssl-crl）。然后，服务器根本不配置 TLS：gRPC 服务器用于以明文启动，而 MySQL 服务器没有 TLS，并且 CRL 会被默默忽略。与 CA 一起配置证书和密钥，或删除 CRL。
  • 不包含 CRL 的 *-crl 文件。将标志指向至少包含一个 X509 CRL 块的文件，或者删除该标志。
  • CA 文件中其颁发者的证书未验证的 CRL：其签名未针对该证书进行验证，或者该证书缺少 cRLSign 密钥用法。重新颁发 CRL 或带有 cRLSign 的 CA 证书。当此类颁发者仅在对等方的链中找到时（作为对等方提供的中间 CA），该对等方的连接将被拒绝。
  • CRL，其授权密钥标识符指定的密钥与其颁发 CA 证书的密钥不同，尽管该证书的密钥对其进行了签名。否则它就会被忽略。使用证书的主题密钥标识符作为其颁发机构密钥标识符重新颁发它。
  • 使用不受支持的算法签名的 CRL。
  • 颁发者名称的编码方式与签名 CA 文件中的 CA 证书主题不同的 CRL，就像由除 CA 之外的其他工具编写的 CRL 一样。这些名称是逐字节匹配的，因此不会应用 CRL。使用证书的主题作为其颁发者重新颁发 CRL。
  • 增量 CRL、间接 CRL 或其发行分发点限制为最终实体证书、CA 证书、属性证书或某些吊销原因的 CRL：仅支持完整的 CRL。接受指定其分发点但不限制自身的 CRL，并且应用发行者 CRL 的每个此类分区。
  • 在列表或条目上携带除发布分发点之外的关键扩展的 CRL。
  • thisUpdate 位于未来五分钟以上的 CRL，因此提前上演的 CRL 无法取代当前的 CRL。提供当前的 CRL，并检查时钟。

CRL 应用方式的其他更改

  • 当任何已验证的链不持有吊销的证书时，对等点通过，因为验证本身接受任何有效链上的对等点；每条链条过去都必须干净。由两个根交叉签名并被其中一个根撤销的中间 CA（如在 CA 翻转期间）仍然通过另一个根承载对等点。
  • trust 锚点（即链结束处的 CA 文件中的 CA 证书）按配置进行 trust 处理，并且未根据其颁发者的 CRL 进行检查。例外情况是，其颁发者也在 CA 文件中，并且其颁发者的 CRL 列出了该锚点，或者通过 CA 文件中的 CA 证书在以这种方式列出的 CA 证书下颁发的锚点。以此类锚点结束的每一条链都会被拒绝，无论对等方是否提供它，并且在构建配置时会出现警告命名 CA 证书。不根据根的 CRL 检查未配置其根的中间 CA。
  • 当一个 CRL 文件包含来自一个发行者的多个完整 CRL 时，仅适用最新的 CRL，因为完整的 CRL 会取代之前发布的 CRL；它们曾经是结合在一起的。
  • CRL 仅当链中发行者的证书对其进行验证时才适用。因此，不支持使用同名的单独证书签署其 CRL 的 CA。
  • 其授权密钥标识符指定的密钥与 CA 证书的密钥不同的 CRL（如重新设置密钥的 CA 的前身的 CRL 那样）不会针对该 CA 的证书进行保留。 有关详细信息，请参阅 #21054 和 #21153。

表ACL：严格表ACL下拒绝无法确定表的语句

在严格的表 ACL (--queryserver-config-strict-table-acl) 下，vttablet 根据其规划器为其派生的表检查语句。 DO、CALL、REPAIR、OPTIMIZE 和 LOAD DATA 被解析为丢弃其表承载文本的节点，因此不会为它们派生任何权限，并且检查也无需强制执行：任何经过身份验证的调用者都可以使用 vttablet 自己的 MySQL 权限对 ACL 拒绝的表运行它们 - 携带表读取的 DO子查询或 CALL 放入过程体中进行读取，服务器端 LOAD DATA INFILE 进行写入。请参阅 GHSA-w6mx-2f8x-pqf4。 vttablet 现在无法关闭：当它无法确定语句的表时，它会在严格的表 ACL 下拒绝该语句，而不是跳过检查。在启用严格表 ACL 的情况下，对于豁免 ACL (--queryserver-config-acl-exempt-acl) 之外的每个调用者，这五个语句都会被拒绝，包括其表授予本来就足够的调用者，因为平板电脑无法确认该语句涉及哪些表。需要它们的运营商应将它们作为豁免 ACL 中的呼叫者发出。对于空运行 (--queryserver-config-enable-table-acl-dry-run)，仅记录拒绝并运行语句。严格的表 ACL 关闭后不会发生任何变化。 这些拒绝没有可命名的表，因此它们在 TableACLDenied 中的新 TableName 标签 undetermined-table-set（带有空 TableGroup）下进行计数。试运行后，无论严格表 ACL 是否打开，来自携带呼叫者 ID 的请求的每个非豁免 DO、CALL、REPAIR、OPTIMIZE 和 LOAD DATA 都会在该标签下递增 TableACLPseudoDenied，因此调整严格 ACL 部署大小的操作员将看到出现一个新系列。 导出的 planbuilder.BuildPermissions 现在会返回第二个结果 tablesUndetermined bool 以及权限。这会故意破坏任何树外调用者：单一结果兼容性包装器将继续为这些语句返回“无权限”，而无法获悉表集尚未确定，因此留在其上的调用者将默默地保持此修复关闭的行为。调用者应该接受新的结果，并在该陈述为真时否认该陈述。 这涵盖了陈述。在表达式（SELECT f()、WHERE 子句、DML 中的 SET）内调用的存储函数不是 CALL，因此它仍然以 vttablet 的 MySQL 权限运行其函数体，而 ACL 仅检查语句本身命名的表； Vitess 不解析 CREATE FUNCTION，因此这适用于直接在 MySQL 中定义的函数。该差距在 #21134 中进行跟踪。 有关详细信息，请参阅 #21053。

表 ACL：在严格的表 ACL 下检查嵌入在 DDL、EXPLAIN、SHOW、SET 中的读取以及针对 dual 的查询

这完成了对 GHSA-w6mx-2f8x-pqf4 开始的修复上面：该更改在解析器丢弃其表的语句上失败关闭；这个获取嵌入在规划器解析但从未检查的语句中的读取权限，因此没有表授权的调用者可以通过它们读取它。现在，每个读取都会像相同表的普通 SELECT 一样在严格的表 ACL (--queryserver-config-strict-table-acl) 下进行检查，并具有与任何其他表 ACL 检查相同的空运行和豁免 ACL 行为：

  • CREATE TABLE ... AS SELECT 除了其创建的表上的 ADMIN 之外，还需要 SELECT 读取的表上的 READER（通过 CTE、连接和联合）。 CREATE VIEW ... AS SELECT 和 ALTER VIEW ... AS SELECT 在其源表上需要相同的 READER：视图在定义时不读取任何内容，但每当查询时，它都会以平板电脑的 MySQL 用户身份读取其源，然后 ACL 只能看到视图的名称，因此在定义视图时会检查源，因为 MySQL 需要 SELECT。
  • EXPLAIN（任何格式）和 DESCRIBE <statement> 现在需要解释语句的权限，WRITER 在包含的 DML 目标上，因为 MySQL 需要解释语句的权限。 EXPLAIN ANALYZE 执行该语句，普通的 EXPLAIN 也会读取：MySQL 读取单行表并在优化时评估不相关的子查询，并且计划显示结果 (Impossible WHERE)，因此 EXPLAIN 回答有关数据的是/否问题。
  • SHOW ... WHERE <expr> 需要过滤器中任何子查询读取的表上的 READER，MySQL 会对其进行评估。 SHOW 自己的主题（SHOW COLUMNS FROM t 的表）保持未选中状态。这也包括 SHOW VITESS_MIGRATIONS ... WHERE。
  • SET 在其表达式中的任何子查询读取的表上需要 READER。
  • 针对 dual 的查询需要在其中任何子查询读取的表上使用 READER，例如 ZZPH100​​ZZ。 vttablet 完全从表 ACL 中免除了针对 dual 的查询，包括子查询；现在只有除了 dual 之外什么也不读取的查询可以豁免。 vttablet 解析器无法完全解析的 CREATE TABLE 将作为 client 的原始文本转发到 MySQL，规划器只知道 CREATE TABLE <name> 前缀。某些此类语句从规划器从未见过的表（CREATE TABLE t (SELECT ...)、CREATE TABLE t AS TABLE src、EXCEPT 或 INTERSECT 源）复制行，并且规划器无法从 Vitess 缺乏的语法中的有效语句中辨别它们。因此，对于豁免 ACL 之外的调用者，每个部分解析的 CREATE TABLE 都被视为一条语句，其表无法以相同的方式确定和拒绝； vttablet 语法中的 CREATE TABLE 无法解析，必须由豁免 ACL 中的调用者发出。在 #21138 中跟踪对这些源的解析。 现在，以这种方式标记的语句具有规划器首先检查的权限，因此在部分 CREATE TABLE 创建的表上缺少 ADMIN 的调用者将在该表上按名称被拒绝，并且试运行会记录该拒绝和未确定的拒绝。 连接设置（vtgate 附加到会话查询的 SET 语句以及预留的预查询）应用于没有表 ACL 检查的连接。在严格的表 ACL 下，vttablet 现在拒绝其表达式包含子查询的设置，以及它无法解析为 SET 的保留预查询：设置携带常量，而 vtgate 只发送值。如果没有严格的表 ACL，每个设置都会像以前一样被接受，因为检查没有任何内容需要保护。对于表 ACL 试运行 (--queryserver-config-enable-table-acl-dry-run)，该设置也会被接受，因为试运行允许表 ACL 拒绝的任何请求，并且 vttablet 会记录一条限制警告，命名严格表 ACL 将拒绝的设置（对于 --sanitize-log-messages，仅其设置的变量）。因此，目标会话的设置也是常量，vtgate 现在会在存储之前评估系统变量的目标 SET；请参阅下面（#vtgate-a-targeted-sessions-set-of-a-system-variable-is-evaluated-once）。 有关详细信息，请参阅 #21139。

VTGate：系统变量的目标会话的 SET 被评估一次

现在，在目标分片上对目标分片 (use ks:-80) 会话中的系统变量 SET 进行一次评估，平板电脑的表 ACL 检查任何读取，并且会话应用并存储结果值，就像非目标会话一样。以前，此类会话会存储所编写的表达式，并在每个保留的连接上重新评估它。结果：

  • 在非恒定目标 SET 之后的 SELECT @@var 现在返回值，而不是无法评估存储的文本。
  • 失败的目标 SET 不再在会话中留下其值。
  • 每个目标 SET 都会额外花费一次到分片的往返费用。 兼容性说明： 没有此更改的 vtgate（在 v23.0.7 或 v24.0.4 之前）仍按写入方式存储目标会话的 SET 表达式。针对在没有试运行的情况下运行严格表 ACL 的 v24.0.4 vttablet，在目标时运行 SET @@var = (<subquery>) 的此类 vtgate 上的会话会在以后的每个查询中拒绝该设置，直到 client 重新连接。在通常的升级顺序中，vttablet 在 vtgate 之前，只要升级持续，这就适用：避免在目标 SET 语句中使用子查询，直到每个 vtgate 都升级，或者首先升级 vtgate。如果没有严格的表 ACL，此类会话不会发生任何变化。 有关详细信息，请参阅 #21139。

旧版 vtctld HTTP API 已删除

vtctld 在 /api/ 下提供服务的 HTTP API 已被删除，因为它是暴露安全攻击面的死代码。它是为 vtctld Web UI 构建的，VTAdmin 在 v16 中取代了 vtctld Web UI。从那以后，没有任何东西服务或调用它，并且 VTAdmin 通过 gRPC 到达 vtctld。剩下的是未经身份验证的 HTTP 表面，它提供拓扑数据、平板电脑运行状况、任意 vtctl 命令、模式更改以及键空间和分片验证。它的 --security-policy 覆盖范围从一个端点到下一个端点都不同。删除它会删除该表面，而不是逐个端点地修补它。 删除的端点为 cells、keyspaces、keyspace、shards、srv_keyspace、tablets、tablet_statuses、tablet_health、topology_info、topodata、vtctl、schema/apply 和features，以及它们背后的键空间、分片和平板电脑操作端点。配置 API 的 vtctld 和 vtcombo 的 --cell、--proxy-tablets、--action-timeout 和 --tablet-health-keep-alive 标志现在已弃用无操作，因此用它们启动的进程仍会启动。它们将在 v26 中被删除。 迁移：使用 vtctldclient 或其调用的 VtctldServer gRPC 服务来执行脚本针对 /api/ 执行的任何操作。从 vtctld 和 vtcombo 启动参数中删除 --cell、--proxy-tablets、--action-timeout 和 --tablet-health-keep-alive。 /debug/health 和 /debug/status 端点保持不变。 影响：vtctld 的 HTTP 端口上对 /api/ 的请求返回 404 Not Found。传递四个标志之一会记录弃用警告，并且没有任何效果。对于任何在 Go 软件包上构建的人来说，vtctld.InitVtctld、vtctld.ActionRepository、vtctld.ActionResult 和 vtctld.TabletWithURL 都已经消失了。 请参阅 #21171 了解如何删除 v26 中的标志，以及 #21170 了解如何删除 v26 中的标志。

可选 gRPC TLS：连接按传输计数

以 --grpc-enable-optional-tls 启动的 gRPC 服务器现在通过传输、tls 或 plaintext 以两个新统计数据报告其连接：GrpcOptionalTlsOpenConnections（当前打开的连接）和 GrpcOptionalTlsConnections（迄今为止握手的连接）。可选 TLS 提供未经身份验证的纯文本连接，以便一次可以将 client 移动到 TLS，包括设置 --grpc-ca 时，其 client 证书检查仅适用于 TLS 连接。统计数据是删除 --grpc-enable-optional-tls 之前要检查的证据：第一个显示纯文本 client 现在是否已连接，这很重要，因为 gRPC 连接是长期存在的，很久以前连接的 client 不会再次握手，第二个显示最近是否有任何连接。两者都没有显示 client 离线或仅偶尔连接，因此他们支持该决定而不是证明它。具有这两个标志的服务器现在也在其启动警告中这么说。 有关详细信息，请参阅 #21162。
