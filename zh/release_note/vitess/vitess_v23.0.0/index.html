主要变化

重大变更

已删除的 VTGate 指标

v23.0.0 中已完全删除四个已弃用的 VTGate 指标。这些指标在 v22.0.0 中已弃用：

指标名称 组件 已弃用于
QueriesProcessed 虚拟门 v22.0.0
QueriesRouted 虚拟门 v22.0.0
QueriesProcessedByTable 虚拟门 v22.0.0
QueriesRoutedByTable 虚拟门 v22.0.0
影响：使用这些指标的任何监控仪表板或警报系统都必须更新为使用 v22.0.0 中引入的替换指标：
  • 使用QueryExecutions代替QueriesProcessed
  • 使用QueryRoutes代替QueriesRouted
  • 使用QueryExecutionsByTable代替QueriesProcessedByTable和QueriesRoutedByTable 有关新指标的详细信息，请参阅 v22.0.0 release notes。

ExecuteFetchAsDba 不再接受多语句 SQL

TabletManager 中的 ExecuteFetchAsDba RPC 方法现在显式拒绝包含多个语句的 SQL 查询（截至 PR #18183）。 影响：之前将多个分号分隔的 SQL 语句传递给 ExecuteFetchAsDba 的代码或自动化现在将收到错误。每个 SQL 语句必须在单独的 RPC 调用中发送。 迁移：将多语句 SQL 拆分为单独的 RPC 调用：

// Before (no longer works):
ExecuteFetchAsDba("CREATE TABLE t1 (id INT); CREATE TABLE t2 (id INT);")

// After (required in v23+):
ExecuteFetchAsDba("CREATE TABLE t1 (id INT);")
ExecuteFetchAsDba("CREATE TABLE t2 (id INT);")

gRPC TabletManager 错误代码更改

vttablet gRPC tabletmanager client 现在返回由内部 go/vt/vterrors 包封装的错误 (PR #18565)。 影响：依赖 google-gRPC 错误代码的外部自动化必须更新为使用 vterrors.Code(err) 来检查错误代码，这会返回 proto/vtrpc.proto 中定义的 vtrpcpb.Code。 迁移：

// Before:
if status.Code(err) == codes.NotFound { ... }

// After:
if vterrors.Code(err) == vtrpcpb.Code_NOT_FOUND { ... }

GTID API 签名更改

作为 GTID 性能优化的一部分，PR #18196 中更改了几个与 GTID 相关的 API 签名： 更改：BinlogEvent.GTID() 方法签名 影响：直接使用GTID解析APIs的代码可能需要更新。大多数用户不受影响，因为这些是内部 API。

GenerateShardRanges API 签名更改

PR #18633 中的 key.GenerateShardRanges() 函数签名已更改，添加了新的 hexChars int 参数来控制生成的分片名称的十六进制宽度。 影响：必须更新直接调用 GenerateShardRanges() 的代码才能传递新参数。 相应的 vtctldclient 命令获得了一个新的 --chars 标志来控制此行为。

标志命名约定迁移

Vitess v23.0.0 包括所有二进制文件中 CLI 标志命名约定的主要标准化。 PR #18280 和相关 PR 中的 989 标志 已从下划线表示法 (flag_name) 迁移到破折号表示法 (flag-name)。

向后兼容性

  • v23.0.0 和 v24.0.0：支持下划线和破折号格式。下划线格式已弃用，但仍可用。
  • v25.0.0：下划线格式将被删除。仅接受破折号格式。

自动标准化

标志标准化在 pflag 级别自动发生（PR #18642），因此两种格式都可以接受，无需在 v23/v24 中更改代码。

标志重命名示例

受影响的常见标志（PR #18280 中提供了 989 个标志的完整列表）： 备份标志：

  • --azblob_backup_account_name → --azblob-backup-account-name
  • --s3_backup_storage_bucket → --s3-backup-storage-bucket
  • --xtrabackup_root_path → --xtrabackup-root-path 复制标志：
  • --heartbeat_enable → --heartbeat-enable
  • --replication_connect_retry → --replication-connect-retry gRPC 标志（PR #18009）：
  • 所有 gRPC 相关标志标准化（30 多个标志）

需要采取行动

在升级到 v25.0.0 之前，用户应更新配置文件、脚本和自动化以使用基于破折号的标志名称。迁移在 v23 和 v24 中向后兼容，允许逐步更新。

新的默认版本

升级到 MySQL 8.4

我们的 vitess/lite:latest 映像使用的默认主要 MySQL 版本是从 8.0.40 到 8.4.6。 此更改已合并到 #18569 中。 VTGate 还默认宣传 MySQL 版本 8.4.6，而不是 8.0.40。如果这不是您正在运行的版本，您可以设置 mysql_server_version 标志来通告所需的版本。

⚠️ 使用 vitess-operator 升级到此版本：

如果您使用的是 vitess-operator，考虑到我们正在将 MySQL 版本从 8.0.40 升级到 8.4.6，您将需要手动升级：

  1. 将 innodb_fast_shutdown=0 添加到 YAML 文件中的额外 cnf 中。
  2. 应用此文件。
  3. 等待所有 pod 都健康。
  4. 然后更改您的 YAML 文件以使用新的 Docker 图像 (vitess/lite:v23.0.0)。
  5. 从 YAML 文件的额外 cnf 中删除 innodb_fast_shutdown=0。
  6. 应用此文件。

仅当从最新的 8.0.x 升级到 8.4.x 时才需要一次。一旦您使用 8.4.x，就可以在 8.4.x 版本之间升级和降级，而无需运行 innodb_fast_shutdown=0。

新支持

多查询执行

Vitess v23.0.0 通过新的 ExecuteMulti 和 StreamExecuteMulti API (PR #18059) 引入了对在单个 RPC 调用中执行多个查询的本机支持。 此功能提供更高效的批量查询执行，无需手动查询拆分或多次往返。 使用示例：

queries := []string{
    "SELECT * FROM users WHERE id = 1",
    "SELECT * FROM orders WHERE user_id = 1",
    "SELECT * FROM payments WHERE user_id = 1",
}
results, err := vtgateConn.ExecuteMulti(ctx, queries)

配置：使用 VTGate 上的 --mysql-server-multi-query-protocol 标志启用。

交易超时会话变量

添加了新的 transaction_timeout 会话变量 (PR #18560)，允许按会话控制事务超时持续时间。 用法：

-- Set transaction timeout to 30 seconds for this session
SET transaction_timeout = 30;

-- Begin a transaction that will automatically rollback if not committed within 30s
BEGIN;
-- ... perform operations ...
COMMIT;

与全局服务器设置相比，这提供了更精细的超时控制，可用于：

  • 需要延长超时时间的长时间运行的批处理操作
  • 应该快速失败的交互式会话
  • 每个应用程序工作负载的超时要求不同

实验：查询节流器

Vitess v23.0.0 引入了一个新的实验性查询节流器框架，用于限制传入查询的速率（RFC 问题 #18412、PR #18449、PR #18657）。这种新型节流阀的开发工作正在进行中，未来可能会发生重大变化。 对此实验性功能的反馈欢迎在 GitHub 问题或 Vitess Community Slack 的 #feat-handling-overload 频道中获得。 特点：

  • 基于文件的限制规则配置
  • 空运行模式，用于测试节流而不强制执行
  • 动态规则重新加载 配置：
  • --query-throttler-config-refresh-interval - 重新加载油门配置的频率 试运行模式：在不实际阻止查询的情况下测试限制规则，对于在执行之前验证配置很有用。

多查找 Vindexes 支持

现在通过 --params-file 标志支持在单个工作流程中创建多个查找 vindex（PR #17566）。 用法：

# Create multiple lookup vindexes from JSON configuration
vtctldclient LookupVindexCreate \
  --workflow my_lookup_workflow \
  --params-file /path/to/params.json \
  commerce

params.json 示例：

{
  "vindexes": [
    {
      "name": "user_email_lookup",
      "type": "consistent_lookup_unique",
      "table_owner": "users",
      "table_owner_columns": ["email"]
    },
    {
      "name": "user_name_lookup",
      "type": "consistent_lookup",
      "table_owner": "users",
      "table_owner_columns": ["name"]
    }
  ]
}

这显着提高了设置多个 vindex 时的工作流程效率，减少了所需的单独操作的数量。

Materialize 工作流程中的参考表

现在可以使用新的 Materialize ... update 子命令 (PR #17804) 将参考表添加到现有的具体化工作流程中。 用法：

# Add reference tables to an existing workflow
vtctldclient Materialize --workflow my_workflow update \
  --add-reference-tables ref_table1,ref_table2 \
  --target-keyspace my_keyspace

用例：增量添加引用表来运行具体化工作流程，而无需重新创建整个工作流程，从而提高操作灵活性。

在线 DDL 分片特定完成

现在可以使用新的 COMPLETE VITESS_SHARDS 语法（PR #18331）在每个分片的基础上完成在线 DDL 迁移。 用法：

-- Complete migration on specific shards only
ALTER VITESS_MIGRATION '9e8a9249_3976_11ed_9442_0a43f95f28a3'
  COMPLETE VITESS_SHARDS '-80,80-';

-- Complete migration on all remaining shards
ALTER VITESS_MIGRATION '9e8a9249_3976_11ed_9442_0a43f95f28a3'
  COMPLETE;

好处：

  • 跨分片逐步推出架构更改
  • 能够在全面推出之前验证分片子集的更改
  • 更好地控制迁移时间和影响

使用递归 CTE

Vitess 现在支持 WITH RECURSIVE 公用表表达式 (PR #18590)，从而能够对分层数据进行递归查询。 示例：

-- Find all employees in a management hierarchy
WITH RECURSIVE employee_hierarchy AS (
    SELECT id, name, manager_id, 1 as level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    SELECT e.id, e.name, e.manager_id, eh.level + 1
    FROM employees e
    INNER JOIN employee_hierarchy eh ON e.manager_id = eh.id
)
SELECT * FROM employee_hierarchy ORDER BY level, name;

这是针对具有分层或类似图形数据结构的应用程序的主要 SQL 兼容性增强功能。

创建表…选择支持

SQL 解析器现在支持 CREATE TABLE ... SELECT 语句 (PR #18443)，提高了 MySQL 兼容性。 示例：

-- Create a table from a query result
CREATE TABLE recent_orders
SELECT * FROM orders
WHERE order_date > DATE_SUB(NOW(), INTERVAL 30 DAY);

修改后的指标

使用键空间/分片标签增强 VTORc 恢复指标

除了现有的 RecoveryType 标签之外，以下 VTORc 恢复指标现在还包括 Keyspace 和 Shard 标签 (PR #18304)： 1.FailedRecoveries 2.PendingRecoveries 3.RecoveriesCount 4.SuccessfulRecoveries 影响：使用这些指标监控查询和仪表板可能需要更新以考虑其他标签维度。 好处：

  • 更精细地观察键空间/分片遇到的恢复问题
  • 能够针对每个密钥空间/分片的恢复模式发出警报
  • 更好地解决集群特定问题 PromQL 查询示例：
# Before (v22): Recovery count by type only
sum(rate(RecoveriesCount[5m])) by (RecoveryType)

# After (v23): Recovery count by type, keyspace, and shard
sum(rate(RecoveriesCount[5m])) by (RecoveryType, Keyspace, Shard)

VTGate QueryExecutionsByTable 行为更改

QueryExecutionsByTable 指标现在仅计算成功的查询执行次数 (PR #18584)。以前，它会计算所有查询尝试，无论成功/失败。 影响：

  • 如果您的工作负载出现严重的查询失败，指标值可能会减少
  • 更准确地表示成功的查询量
  • 通过错误指标单独跟踪失败的查询

增强的 CREATE PROCEDURE 语句解析（PR #18142、PR #18279）：

  • 更好地处理各种格式的 DEFINER 子句
  • BEGIN...END 块和 START TRANSACTION 语句之间的区别
  • 支持程序体内的 SET 语句
  • 改进了过程定义中分号的处理

运算符优先级修复

  • 修复了 MEMBER OF 运算符与 AND 的优先级（PR #18237）
  • 将 JSON 操作与布尔逻辑结合时确保正确的查询评估

查询计划改进

单分片查询中的窗口函数

现在可以将窗口函数下推到单分片查询（PR #18103），从而提高分析工作负载的性能。 v23 之前：窗口函数始终在 VTGate 级别执行，即使对于单分片查询也是如此。 v23之后：当查询针对单个分片时，窗口函数被下推，减少数据传输并提高性能。 示例：

-- This query now executes entirely on the target shard
SELECT
    user_id,
    order_date,
    amount,
    SUM(amount) OVER (PARTITION BY user_id ORDER BY order_date) as running_total
FROM orders
WHERE user_id = 12345;  -- Single-shard query

UNION 查询合并改进

UNION 查询优化已得到显着增强（PR #18289、PR #18393）： 扩展 UNION 合并：使用 Equal 和 IN 操作码的 UNION 查询现在可以更积极地合并，生成更简单的 SQL。 派生表消除：UNION 查询避免了不必要的派生表换行，从而生成更干净、更高效的 SQL。 示例：

-- Query:
SELECT * FROM t1 WHERE id = 1
UNION
SELECT * FROM t1 WHERE id = 2;

-- Before v23: Wrapped in derived table
SELECT * FROM (
    SELECT * FROM t1 WHERE id = 1
    UNION
    SELECT * FROM t1 WHERE id = 2
) AS dt;

-- After v23: Direct UNION (simpler, more efficient)
SELECT * FROM t1 WHERE id = 1
UNION
SELECT * FROM t1 WHERE id = 2;

SINGLE 模式下的多分片只读事务

使用 SINGLE 事务模式时，只读事务现在可以跨越多个分片（PR #18173）。 v23 之前：SINGLE 模式将所有事务限制为单个分片，甚至是只读分片。 v23之后：只读事务可以以SINGLE模式访问多个分片，在不牺牲一致性保证的情况下提高灵活性。 影响：使用 SINGLE 事务模式的应用程序现在可以在事务内执行多分片读取查询，而无需升级到 MULTI 或 TWOPC 模式。

准备语句的延迟优化

准备好的语句现在支持延迟优化 (PR #18126)，即使在计划生成需要运行时值时也允许准备成功。 好处：

  • 更多准备好的语句在准备时成功
  • 通过参数相关的优化更好地支持查询
  • 减少了 PREPARE 语句失败导致的应用程序错误 行为：当准备好的语句在准备时无法完全优化时，优化将推迟到绑定变量值可用时的执行时。

即时 DDL 的查询缓冲

已针对 INSTANT DDL 操作实现查询缓冲（PR #17945），从而减少架构更改期间的查询失败。 特点：

  • 在 INSTANT DDL 执行期间自动缓冲查询
  • 强制终止阻塞交易
  • 对应用程序透明 影响：应用程序在架构更改期间遇到的查询错误更少，从而提高了 DDL 操作期间的可用性。

多个组件中使用的 --consul-auth-static-file 标志现在要求可以从提供的 json 文件加载 1 个或多个凭据 (PR #18152)。 影响：具有空或无效凭证文件的配置现在将在启动时失败，而不是在不进行身份验证的情况下静默继续。

VTORc

已删除聚合发现指标 HTTP API

VTORc 未记录的 /api/aggregated-discovery-metrics HTTP API 端点已被删除（PR #18672）。记录的 VTORc API 列表可以在此处 找到。 我们建议使用标准 VTORc 指标来收集相同的指标。如果您发现标准指标中缺少某个指标，请提出问题或 PR 来解决此问题。

基于 EmergencyReparentShard 的恢复的动态控制

注意：禁用基于 EmergencyReparentShard 的恢复会带来可用性风险；请极其谨慎使用！如果您经常依赖此功能（例如在自动化中），这可能是反模式的迹象。如果是这样，请提出一个问题来讨论在 VTORc 中本地支持您的用例。 引入了新的 vtctldclient RPC SetVtorcEmergencyReparent（PR #17985），以允许在每个密钥空间和/或每个分片的基础上禁用涉及 EmergencyReparentShard 操作的 VTORc 恢复。在此版本之前，只能全局/每个 VTORc 实例禁用基于 EmergencyReparentShard 的恢复。 VTORc 现在将考虑每次恢复时从拓扑刷新的键空间/分片级别设置。通过首先检查键空间，然后检查分片状态来确定禁用状态。删除键空间级覆盖不会删除每个分片的覆盖。 为了在禁用基于 EmergencyReparentShard 的 VTORc 恢复的情况下提供键空间/分片的可观察性，添加了 EmergencyReparentShardDisabled 指标。此指标标签可用于创建警报，以确保基于 EmergencyReparentShard 的恢复不会在不需要的时间段内被禁用。 示例：

# Disable ERS recoveries for a keyspace
vtctldclient SetVtorcEmergencyReparent --keyspace commerce --enabled=false

# Disable ERS recoveries for a specific shard
vtctldclient SetVtorcEmergencyReparent --keyspace commerce --shard 80- --enabled=false

# Re-enable ERS recoveries
vtctldclient SetVtorcEmergencyReparent --keyspace commerce --enabled=true

包含密钥空间/分片的恢复统计信息

以下与恢复相关的统计信息现在包括键空间和分片的标签（PR #18304）： 1.FailedRecoveries 2.PendingRecoveries 3.RecoveriesCount 4.SuccessfulRecoveries 在此版本之前，标签中仅包含恢复“类型”。有关更多详细信息，请参阅修改的指标。

/api/replication-analysis HTTP API 端点现已弃用，并替换为 /api/detection-analysis (PR #18615)，它当前返回相同的响应格式。 时间表：/api/replication-analysis 端点将在未来版本中删除。用户应迁移到 /api/detection-analysis。

托管 MySQL 配置默认为 caching-sha2-password

MySQL 8.0.26 及更高版本的默认身份验证插件现在是 caching_sha2_password 而不是 mysql_native_password (PR #18010)。进行此更改是因为 mysql_native_password 已弃用并在未来的 MySQL 版本中删除。 mysql_native_password 仍启用向后兼容。 此更改特别影响复制用户。如果您的用户配置了显式密码，建议在升级到 v23 后确保使用如下语句升级该用户：

ALTER USER 'vt_repl'@'%' IDENTIFIED WITH caching_sha2_password BY 'your-existing-password';

在未来的 Vitess 版本中，将为托管 MySQL 实例禁用 mysql_native_password 身份验证插件。

MySQL 时区环境传播

修复了 TZ 等环境变量未从 mysqlctl 传播到 mysqld 进程的错误 (PR #18561)。 因此，环境中的时区设置之前被忽略。现在mysqld正确继承环境变量。 ⚠️ 部署影响：依赖旧行为并显式设置非 UTC 时区的部署可能会发现 DATETIME 值的解释方式发生变化。为了保持兼容性，请在 MySQL Pod 中显式设置 TZ=UTC。

gRPC tabletmanager client 错误更改

vttablet gRPC tabletmanager client 现在返回由内部 go/vt/vterrors 包封装的错误 (PR #18565)。依赖 google-gRPC 错误代码的外部自动化现在应该使用 vterrors.Code(err) 来检查错误代码，该代码返回 proto/vtrpc.proto protobuf 中定义的 vtrpcpb.Code。 请参阅重大更改 了解迁移指南。
