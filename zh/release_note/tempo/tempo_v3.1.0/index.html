tempo v3.1.0

这个项目是干啥的：一个分布式链路追踪后端，把海量调用记录存下来供事后排查故障，给需要看清请求在哪一环变慢的运维和SRE用。

Grafana Tempo 3.1.0 添加了基于查询的跟踪编辑、TraceQL 指标算法和采样感知外推、Kafka 连接改进以及用于比较和修剪跟踪的实验工具。 它还使 vParquet5 成为新写入块的默认格式。

变更架构图

亮点

  • 按查询进行编辑： 使用 TraceQL 选择器提交编辑作业，而不是枚举跟踪 ID，并具有可选时间窗口和编辑可靠性改进。
  • TraceQL 指标： 将聚合与算术结合起来，并选择使用跨度中记录的采样概率进行外推。现在默认启用更快的仅跨度获取路径。
  • 指标生成器和服务图： 使用选择加入的连接信息量规检测重采样下的服务拓扑，识别 db.system.name，并减少跨度指标和服务图处理开销。
  • 实验性跨度修剪： 通过请求级别选择加入和可配置的默认值，减少按 ID 跟踪 v2 响应大小。
  • Kafka 连接： 配置额外的 SASL 机制、TLS 和双向 TLS、机架感知获取和生产者压缩，包括用于 Azure 事件中心的 gzip。
  • 实验跟踪差异和摘要： 通过 API、tempo-cli 和 MCP 与完整补丁和紧凑摘要格式比较跟踪。
  • vParquet5 默认情况下： 在 vParquet5 中写入新块，同时继续读取现有 vParquet4 和 vParquet3 块，无需数据迁移。 下面详细的 changelog 包括经过审查的 RC1 注释和后续向后移植， 包含 PR 参考、贡献者信用、安全标识符和升级指南。

特点

  • backend-scheduler：可以使用 TraceQL 查询选择器而不是显式跟踪 ID 列表来提交编辑作业，因此可以将大量删除表示为查询。 (#7663) (@zalegrala)
  • metrics-generator：添加 service-graphs-* 子处理器和可选的 traces_service_graph_connection_info 存在量规，用于在大量采样下进行拓扑检测。 (#7202) (@jcreixell)
  • operations：通过 Prometheus 触发器在持有的预期字节上添加 KEDA 自动缩放功能以进行实时存储。通过 live_store.keda.enabled: true 启用。 (#7154) (@zachfi) 使用 block_builder.keda.enabled: true 单独启用块构建器自动缩放，并选择使用 block_builder.keda.scaling 的方法。 默认值 'rollout-operator' 镜像实时存储区域 a 副本，并需要启用实时存储 KEDA。 'keda' 方法使用 kubernetes 工作负载触发器，并且可以在有或没有实时存储 KEDA 的情况下工作。 启用实时存储 KEDA 会自动启用 rollout_operator_replica_template_access_enabled。
  • operations：使用新的 Grafana 仪表板监控 Tempo 现场商店的健康状况和绩效。 (#7287) (@javiermolinar)
  • query-frontend：向trace-by ID v2端点添加实验性跨度修剪。 (#7566、#7628、#7693) (@ie-pham) 对于省略 span_pruning 的请求，默认使用 span_pruning_enabled_by_default 启用修剪， 或使用 span_pruning_enabled 覆盖配置每个租户的默认值。 检测到已在写入路径上修剪的迹线，并且不会再次修剪。
  • query-frontend：添加用于比较两个跟踪的实验端点，并由租户的 max_bytes_per_trace 设置强制执行组合输入大小限制。 (#7523、#7539、#7564) (@javiermolinar)
  • query-frontend：添加trace-summary-v0-composed作为可选的实验跟踪差异API和tempo-cli格式。响应始终包含紧凑的摘要，并包含最多 64 KiB 的完整补丁；较大的补丁报告该补丁被省略。默认值仍然是trace-patch-v0。 （[#7593]（https://github.com/grafana/tempo/issues/7593））（@carles-grafana）
  • tempo：添加 client_rack Kafka 配置选项以启用机架感知抓取 (KIP-392) 并减少跨区域 Kafka 流量。 (#7594) (@AvivGuiser)
  • tempo：支持 TraceQL Metrics 中的算术运算 (#6866、#7199、#7409) (@ruslan-mikhailov)
  • tempo-cli：向 tempo-cli 跟踪差异添加实验性跟踪摘要-v0-本机格式。它提供了延迟、总跨度持续时间、错误、结构变化和受影响服务的紧凑概述。 (#7510) (@carles-grafana)
  • tempo-cli：添加实验性跟踪 diff 命令，该命令比较两个本地跟踪 JSON 文件并发出 Trace-patch-v0 输出。 (#7468) (@javiermolinar)
  • traceql：TraceQL 指标查询可以根据 W3C 跟踪状态采样概率推断计数。通过 with(extrapolate=true) 提示选择加入每个查询。 (#7452) (@csmarchbanks) 当跨度在其跟踪状态中携带 OpenTelemetry 概率阈值时 (ot=th:...)，每个匹配跨度贡献 1 / sampling_probability rate、count_over_time、sum_over_time、avg_over_time、 histogram_over_time、quantile_over_time 和 compare 骨料 — 匹配指标生成器现有的每跨度乘数行为。 min_over_time 和 max_over_time 不受影响。仅支持 vparquet4 及更高版本。

增强功能

  • backend-scheduler：公开每个租户和作业类型的待处理后端作业，并启用后端缓存项大小的本机直方图。 (#7772) (@zalegrala) tempo_backend_scheduler_jobs_pending{tenant, job_type} 统计等待调度的作业， 提供用于监控和自动缩放的队列深度信号。 tempodb_cache_store_size_bytes 现在支持本机直方图。
  • backend-scheduler：添加 tempo_backend_scheduler_redaction_traces_found_total{tenant, mode} 指标 — 与每个租户的修订作业匹配的跟踪，其中 mode=apply 计算实际删除的跟踪，mode=dry_run 计算试运行的预览爆炸半径。 (#7699) (@zalegrala)
  • backend-scheduler：通过索引每个租户的挂起作业和繁忙块来减少后端调度程序作业查找开销。 (#7141) (@zalegrala)
  • backend-scheduler：将可选的 [start, end] 时间窗口添加到密文 (tempo-cli redact --start/--end)，将其范围限定为重叠块并限制每块扫描。 (#7702) (@zalegrala) 窗口式编辑可以让大租户分片进行编辑，而不是对每个块进行一次编辑，因此整个运行过程中不会推迟压缩。两个边界都是必需的并且必须订购；省略它们会像以前一样编辑整个租户。 client 将边界解析为绝对时间戳，因此长的编辑不会向前漂移到新摄取的数据中。 该窗口限制了 --query 选择器的扫描。它不能与 --trace-id 结合使用，--trace-id 可以无时间限制地解析跟踪：该对将仅从与窗口重叠的块中删除每个列出的跟踪，并在报告成功时将其余部分保留在原处。 当调度程序和工作线程运行不同版本时，请勿提交窗口化编辑。在此更改之前的工作人员会忽略窗口字段，并删除给定的每个块中的每个查询匹配项，无论时间戳如何，都不会出现错误，也无法恢复数据。
  • block-builder：添加 tempo_block_builder_flush_size_bytes 本机直方图，记录块生成器刷新的块的大小。 (#7773) (@zalegrala) 与 tempo_live_store_local_flush_size_bytes 一起使用 tempodb_compaction_output_block_size_bytes 用于比较写入路径上的块大小 并调整压实的 max_input_blocks 设置。
  • cache：将 connect_timeout 和 min_idle_conns_headroom_percentage 选项添加到 memcached client 以调整连接行为。 (#7671) (@mapno) connect_timeout 与 timeout 分开绑定连接建立（请求 往返），未设置时默认为 timeout。 min_idle_conns_headroom_percentage 控制空闲连接 reaping：负值（默认）从不关闭空闲 连接数，正值保持空闲连接相对打开的百分比 最近使用的数量。
  • cache：为 Redis 强制执行可配置的 MaxItemSize。 (#7311) (@electron0zero)
  • compactor：添加tempodb_compaction_output_block_size_bytes本机直方图，记录压缩产生的块的大小。 (#7773) (@zalegrala) 没有现有的指标捕获压缩输出块的最终大小（现有的 tempodb_compaction_bytes_written_total 是每个行组刷新的累积计数器，而不是 每个成品块的大小）。这为操作员提供了调整 max_input_blocks 和 TCO 的原因。
  • distributor：添加 ingest.kafka.producer_compression 配置以允许覆盖 Kafka 生产者的压缩编解码器。 (#7691) (@fleighton) 一些兼容 Kafka 的后端仅支持某些压缩编解码器， 特别是 Azure 事件中心，它仅支持 gzip。支持的值为 none、gzip、snappy、lz4、zstd（不区分大小写）；未设置的 值使 Kafka client 自己的默认编解码器首选项保持不变。
  • distributor：添加每个租户推送形状指标：tempo_distributor_push_duration_seconds 上的租户标签，以及新的 tempo_distributor_push_bytes 和 tempo_distributor_received_traces_total (#7865) (@zalegrala)
  • distributor：添加Kafka SASL机制选择和TLS支持。 sasl_mechanism 选项选择 SASL 机制（PLAIN（默认）、SCRAM-SHA-256、SCRAM-SHA-512、OAUTHBEARER 或 AWS_MSK_IAM），带有 tls_* 选项的 tls_enabled 为 Kafka client 启用 TLS 传输和双向 TLS。 (#7586) (@heytrav) OAUTHBEARER 和 AWS_MSK_IAM 凭证可以从 JSON 文件静态提供，或者通过 Unix 域套接字获取。现有配置不受影响，因为在未设置用户名或密码时，默认机制仍为 PLAIN，并禁用 SASL。
  • distributor：在 2 × distributor.ring.heartbeat-timeout 之后自动忘记分配器环中的不健康实例，从而无需在非正常 Pod 终止后在 /distributor/ring 上手动进行 click“忘记”。 (#7098) (@oleg-kozlyuk-grafana)
  • docs：正确的有关 Redpanda 和 Kafka 要求的单二进制快速入门文档。 (#7704) (@veenoise)
  • docs：添加有关配置 Tempo 微服务部署使用的 Kafka 兼容后端的指南。 (#7714) (@javiermolinar)
  • docs：为人工智能辅助文档创作添加共享文档技能、项目上下文和发行说明工作流程。 (#7447) (@knylander-grafana)
  • live-store：将查询检查的字节公开为指标。 (#7162、#7163) (@zhxiaogg)
  • live-store：通过消除并发评估的 WAL 块之间的锁争用来提高 TraceQL 指标查询性能。 (#7867) (@ruslan-mikhailov) 现在，每个块都使用自己的指标评估器进行评估，每个块的结果是 求和，而不是所有 WAL 块共享一个由互斥体保护的求值器。
  • live-store：通过使范围不同的字符串收集器无锁来减少标签搜索中的互斥争用。 (#7492) (@zhxiaogg)
  • metrics-generator：默认跨度类型正则表达式的快速路径跨度过滤器匹配，并在属性过滤器之前评估内在过滤器。 (#7465) (@carles-grafana)
  • metrics-generator：识别服务图中的db.system.name属性，用于数据库节点检测和虚拟节点命名。 (#7697) (@iamrajiv) OpenTelemetry 语义约定 v1.30.0 将 db.system 重命名为 db.system.name。跨度从 仅发出新属性的检测不再被识别为数据库请求 并且无法命名虚拟节点。 db.system.name 附加到 peer_attributes 和 peer_attributes 的默认值中 database_name_attributes，继db.system之后。因为列表是按顺序搜索的 较旧的属性仍然列在前面，携带 db.system 的跨度继续生成节点名称 今天他们这样做了。每个租户仍然可以覆盖这两个默认值。
  • metrics-generator：减少跨名称清理器 CPU 和重复确切名称的分配。 (#7794) (@carles-grafana) Drain 现在拥有保留的令牌字节，重用令牌生成器状态，在匹配期间删除陈旧的候选者， 并使用由大叶子的完整跨度名称作为键控的有界精确匹配索引。生成的跨度度量 标签和现有的图案固定装置保持不变。
  • metrics-generator：通过注册表的池借用标签路径构建系列标签，减少跨度指标处理器中的每个跨度 CPU 和分配。 （[#7584]（https://github.com/grafana/tempo/issues/7584））（@carles-grafana） 跨度指标处理器现在在注册表拥有的池缓冲区中构建系列标签，使用预先计算的标签哈希更新指标，并为每个资源构建一次 target_info 而不是每个跨度构建一次。指标名称、标签和值保持不变。
  • metrics-generator：添加 skip_stale_backlog_on_startup 以在启动时将分区向前寻找到摄取松弛水平，而不是重放松弛将丢弃的积压，从而在重新启动时保持分区滞后指标诚实。 (#7611) (@zalegrala)
  • metrics-generator：通过使用不匹配的跨度类型标记过期边缘来改进服务图故障排除。 (#7709) (@javiermolinar)
  • metrics-generator：通过注册表的池借用标签路径构建系列标签，减少服务图处理器中的每边缘 CPU 和分配。 （[#7587]（https://github.com/grafana/tempo/issues/7587））（@carles-grafana） 服务图处理器现在使用计数器、直方图和连接信息量表的借用标签更新；对标准跟踪和跨度 ID 使用固定大小的键；重用跟踪 ID 缓冲区；将经典示例编码推迟到收集；并为本机直方图的每条边共享一种编码。指标名称、标签和值保持不变。
