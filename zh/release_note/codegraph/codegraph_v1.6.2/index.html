codegraph v1.6.2

[1.6.2] - 2026-10-03

亮点

  • 每种语言中的错误链接都少得多。 调用、导入或类型现在解析其语言范围名称的方式 - 通过导入、包、命名空间和它所编写的类 - 因此它不再登陆仅共享其名称的不相关符号。这涵盖了 TypeScript 和 JavaScript、Python、Java、Kotlin、Scala、C#、VB.NET、Swift、Objective-C、Go、Rust、C 和 C++、PHP、Ruby、Dart、Lua、R 等，并使调用者、影响和 codegraph_explore 答案更有价值。
  • 重载、super 和递归正确解析。 调用达到其参数适合的重载，super 调用达到父级的方法，并且调用另一个重载的方法或另一个同名对象的方法看起来不再像调用自身。
  • 更多框架的路由。 Angular（包括 Nx 库）、Vue Router 管理应用程序、Rails 嵌套路由、Flask 的 add_url_rule、ASP.NET FastEndpoints、Play 子项目、Vapor 关闭路由和 Expo Router API 路由均已找到。 NestJS 和 Laravel 路由由请求实际采用的路径命名，通过 URL 调用路由的 Spring 或 Laravel 测试算作覆盖它。
  • 图中的更多代码。 Vue 选项 API 组件、带主体的 Java 和 Kotlin 枚举常量、流类型 JavaScript、Kotlin 中缀调用、React Native 本机视图和事件、Expo 模块、基于标签的 CFML 和 Delphi .inc 文件现在都已编入索引。
  • Windows：无闪烁窗口，无随机崩溃。 后台服务器工作时不再弹出控制台窗口，索引或关闭时偶发的访问冲突崩溃（退出代码 3221225477）已修复，并且 codegraph upgrade 在代理会话使用 CodeGraph 时工作。
  • 更稳定的后台服务器。 较新的MCP client例如Antigravity再次连接，Claude Code看到codegraph_status的全文，丢失共享服务器的会话自行重新连接，通过projectPath查询的项目在10分钟空闲后被释放。
  • 索引完成。 大型 C 和 C++ 项目在解析引用时不再耗尽内存，COBOL 文件不再停止索引，并且 codegraph sync 保留多次定义的名称的每个调用者。
  • **升级：**在此版本后重新索引您的项目 - 大多数修复都是在索引时编写的。

新功能

  • 在 Nuxt 和 Astro 项目中，文件路由页面现在链接到其文件定义的组件。 Astro 端点链接到它导出的 HTTP 动词处理程序，例如 export const GET。之前，像 Nuxt 的 pages/admin.vue 或 Astro 的 src/pages/about.astro 这样的页面路由没有任何链接，因此呼叫者、影响和流量都在该路由处停止。
  • 通过路由配置对象编写的 React Router 链接和 navigate(…) 调用（如Bulletproof-react 的 paths.app.discussion.getHref(id)）现在可以到达它们打开的路由。在 to 之前具有箭头功能属性的 <Link>，例如 onMouseEnter={() => …}，也会被读取。
  • React Router 数据路由器路由由其完整路径命名：嵌套的 children 路径连接到其父级路径，读取 path: paths.app.root.path 常量，并且 lazy: () => import('./routes/x') 路由链接到模块的组件。像 <ProtectedRoute> 这样的保护包装器不再代表页面。在bulletproof-react上，每条路线现在都有其真实的路径和页面。
  • 现在可以找到其处理程序是尾随闭包的 Vapor 路由（如 app.get("hello") { req in … }）、WebSocket 路由（如 app.webSocket("chat") { req, ws in … } 和 routes.on(.POST, "x", use: handler) 注册），并且闭包路由链接到闭包调用的内容，就像 Express 内联处理程序所做的那样。之前，仅读取具有 use: 处理程序的路由，并且关闭路由不链接任何内容，因此调用者、影响和流量都停止在该处。
  • 流类型的 JavaScript 文件（标题注释中带有 @flow 的文件）现在像 TypeScript 一样进行解析，因此像 render(): React.Node 这样的类型注释不再缩短类。这主要影响 React Native 代码：在 React Native 自己的库上，该图获得了超过 8,000 个链接，并且组件类保留了它们的方法。没有编译指示的文件不会发生变化。 Re-index after upgrading.
  • 由框架或桥解析器创建的链接现在记录是哪个链接创建的（metadata.framework，例如 swift-objc-bridge 或 react-native-bridge），如自述文件所述。之前，仅对合成事件和视图通道进行命名。
  • 使用 FastEndpoints 构建的 ASP.NET 应用程序现在拥有自己的路由：Configure() 中的每个端点类的 Get(…) / Post(…) 成为链接到其自己的 HandleAsync / ExecuteAsync 的路由，包括保留在请求类的 Route 常量中的路径。 ardalis/CleanArchitecture 从无路由增加到 24 条。不带前导斜杠 (app.MapGet("api/todos", …)) 的最小 API 路由现在命名为 /api/todos。
  • 保存在子目录中的播放项目被识别，因此每个项目的 conf/routes 都会被读取。根部没有 Play 构建的存储库（如 playframework 的示例）从没有路由增加到超过 130 条。
  • Rails 路线现在通过其嵌套进行读取：namespace 和 scope 添加其路径和控制器模块，嵌套的 resources 位于其父级 :id 下方，而 member / collection 块添加其操作。命名空间路由现在链接到其自己的模块的控制器。 Rails 引擎的 config/routes.rb 中的路线也被发现了：solidus 从没有路线增加到超过 600 条，mastodon 的路线到动作链接几乎增加了两倍。
  • 现在可以找到用 add_url_rule(…) 注册的 Flask 路由，并将其链接到其视图函数或基于类的视图。通过项目自己的帮助程序注册的路由也是如此，该帮助程序传递路径列表和 view_func=。 Flaskbb 以这种方式记录每个视图，从没有路线增加到超过 100 条。
  • 使用选项 API (export default { methods: {…}, computed: {…}, watch: {…}, mounted() {…} }) 编写的 Vue 组件与每个 Vue 2 应用程序一样，现在在图中都有其方法、计算属性、观察者和生命周期挂钩。每个都有自己的调用者和调用，模板的 @click="handleLogin" 链接到它运行的方法。在 vue-element-admin 上有超过 800 个新链接，其中组件的调用过去属于整个文件。
  • 名称保存在常量中的 React Native 事件现在将本机代码链接到侦听它们的 JavaScript，例如 NetInfo 的 addListener(PrivateTypes.DEVICE_CONNECTIVITY_EVENT, …) 或 Java .emit(PROGRESS_EVENT, …)。常量以语言范围的方式读取，从同一文件、导入或其所属类，因此碰巧共享常量名称的参数永远不会被误认为是常量。
  • 使用 requireNativeComponent('X') 声明的 React Native 视图（react-native-maps 和分段控制使用的较旧的 Paper 样式）现在从 JavaScript 链接到其本机 iOS 和 Android 实现，正如 Codegen 规范已经做的那样，包括在纯 .js 文件中。使用与其组件不同的名称编写的 JSX 标记（例如 import Autocomplete from './autocomplete.vue' 的 <Autocomplete>）现在链接到它呈现的组件。
  • Expo Router API 路由 (app/hello+api.ts) 现在是端点，每个导出方法一个，如 GET /hello，绑定到处理它们的函数。 They used to show up as a screen named /hello+api.在其根目录为示例应用程序声明 Expo Router 的存储库中，其自己的文件夹中的 Next.js 应用程序（如react-native-true-sheet 的 docs/）不再获取从其文件制作的 Expo 屏幕。
  • 即使 JavaScript 将模块命名为其他名称（例如将 expo-camera 的 CameraManager 命名为 requireNativeModule('ExpoCamera')），对 Expo 模块的调用现在也可以到达模块的本机函数。 iOS 和 Android 实现都是链接的。 expo-camera 的调用用于链接回进行调用的同名方法，因此一个方法看起来像是调用自身。
  • Angular 应用程序分布在 Nx 库中，例如 Angular-spotify，现在拥有自己的路线和导航。一条写入 async () => (await import('@app/home')).HomeModule 的延迟加载路由通过库的 index.ts 到达它重新导出的模块，并且一个库中的 routerLink 现在到达另一个库中声明的屏幕。从类常量 (RouterUtil.Configuration.Lyrics, `issue/:${ProjectConst.IssueId}`) or an enum are now read. A redirect in a routes file that only lazy-loads others now counts, and router.navigate(['project', 'issue', id]) without relativeTo 构建的路由路径是从根读取的，与 Angular 一样。升级后重新索引 Angular 项目。
  • React Router 应用程序现在显示以 React Router v5 的 <Redirect to="/login" /> 形式编写的导航，并通过样式化的链接，例如将 React-boilerplate 的 HeaderLink = styled(Link) 用作 <HeaderLink to="/features">。以这种方式构建的应用程序有路线，但屏幕之间没有链接。
  • SvelteKit 路由现在按浏览器要求的地址命名。 (group) 文件夹（如 (app) 或 (marketing)）不再是路由路径的一部分，并且带有匹配器的参数（如 [id=integer]）只是 :id。因此，goto('/blocks') 和 <a href="/blocks"> 现在到达了位于 src/routes/(app)/blocks/ 的页面，而在此之前他们什么也没到达，应用程序的屏幕也没有显示任何导航。 Re-index SvelteKit projects after upgrading.
  • 像 vue-element-admin、vue-admin-template 或 vben 这样构建的 Vue Router 应用程序现在拥有自己的路由和屏幕。现在可以读取命名表（export const constantRoutes = [...]、const routes: RouteRecordRaw[] = [...]）、每个模块路由文件中或通过 new Router(...) 声明的路由。子路由连接到其父路由的路径上，父路由的组件是它们周围的布局。延迟加载的视图 (() => import('@/views/dashboard/index')) 绑定到它命名的文件，this.$router.push(...) 算作导航。 Nuxt 基于文件的路由现在仅来自 Nuxt 应用程序，因此普通 Vue 应用程序的 pages/ 文件夹不再变成虚构的屏幕，并且位于其存储库根目录的 Nuxt 应用程序现在获取其路由。 Re-index Vue projects after upgrading.
  • NestJS 路由现在按请求所采用的路径命名：应用来自 app.setGlobalPrefix('api') 的全局前缀及其 exclude 列表，以及来自 app.enableVersioning(...) 的 URI 版本控制，并考虑 @Version、VERSION_NEUTRAL 和控制器自己的 version。以前显示为 GET /user 的路由现在是 GET /api/v1/user，因此前端的 this.http.get('/api/v1/user') 或 fetch 调用连接到为其提供服务的控制器方法。 Re-index NestJS projects after upgrading.
  • Laravel 路由现在按请求所采用的路径命名：在路由文件忽略的地方添加前导 /，应用 Route::prefix() 和 Route::group(['prefix' => …]) 组，并且 ZZPH100​​ZZ 中的路由带有 /api 前缀 Laravel 在其下提供服务，从 RouteServiceProvider、bootstrap/app.php 或任何挂载路由文件的文件中读取。前端 fetch('/api/…') 现在连接到为其提供服务的 Laravel 路由。升级后重新索引 Laravel 项目。
  • Spring 或 Laravel 通过 URL 测试的控制器现在算作已测试。其中包括 MockMvc 的 perform(post("/owners/new"))、WebTestClient、TestRestTemplate、RestAssured、Laravel 的 $this->postJson('api/me')、Pest 的 get('/about') 以及基于它们构建的项目自己的请求助手。 codegraph_explore 现在命名了达到这一终点的测试套件，而之前它们中的每一个看起来都未经测试。升级后重新索引 Spring 和 Laravel 项目。
  • 在 Angular 应用程序中，模板调用的方法（例如 (click)="toggleFavorite()" 或 (ngSubmit)="submitForm()"）现在从其组件链接。这些方法过去根本不显示任何调用者，因此影响和调用者的问题就停止在这些方法上，死代码检查可能会将它们列为未使用。升级后重新索引 Angular 项目。
  • Angular 应用程序现在在图表中具有路线和导航。 Routes 数组中的每个屏幕都是由其完整路径命名的路由，包括子项、延迟加载的 loadChildren 文件和 NgModule、写为路由常量或 $localize 字符串的路径以及重定向。每条路线都链接到其组件。 router.navigate([...])、navigateByUrl、警卫的 createUrlTree 和组件模板中的每个 routerLink 链接到它们打开的屏幕，模板的子组件 (<app-article-list>) 链接到渲染它们的组件。像“这个按钮去哪里”和“什么呈现这个组件”这样的问题现在在 codegraph_explore 中有答案。升级后重新索引 Angular 项目。
  • Delphi 和 Free Pascal 包含文件 (.inc) 现在被索引为 Pascal。之前，它们被读取为 PHP，结果却是空的。带有 <?php 标记的 .inc 文件仍然是 PHP，而 .inc 的 codegraph.json 映射仍然获胜。感谢@ijbranch 的报告。 (#2279)
  • 在基于标签的 CFML 中，现在链接在标签中编写的调用：在 <cfset>、<cfif>/<cfelseif>、<cfreturn>、<cfloop condition> 和 #…# 表达式中。之前，仅读取 <cfscript> 和 <cfquery> 代码，因此调用者和影响者在基于标签的组件中几乎找不到任何内容。包含在 <cfprocessingdirective> 或 <cfsilent> 等标签中的函数现在也被索引，并且 <cfinterface> 被索引为 implements 链接到的接口。升级后重新索引 CFML 项目。感谢@HarryMuc 的报告。 （#2091）
  • Java 枚举常量和 Kotlin 枚举条目拥有自己的主体，现在在图中拥有它们的方法。例如 PLUS { int apply(…) { … } } 和 NewBuffer { override fun pipe() … }。以前，这些方法缺失，并且其中的每个调用都被丢弃。 jsoup 的 HTML 分词器和树构建器就是这样编写的，因此它们的 2,000 多个调用是不可见的。重新索引以获取此内容。
  • Kotlin 中缀调用（例如 Users.id eq id1 或 koin 的 single { … } bind MyApi::class）现在记录为对中缀函数的调用。以前，他们根本没有来电者。在 Excessed 上，eq 现在显示超过 1000 名来电者。对数字（x and 0xff、h shr 8）的位操作留给 Kotlin 自己的运算符，即使项目定义了同名扩展也是如此。升级后重新索引。

修复

窗口

  • 在 Windows 上，当 CodeGraph 在后台运行时，终端窗口不再闪烁打开和关闭。自 1.6.1 起，后台 MCP 服务器在启动时多次弹出控制台窗口（如果是默认终端，则为完整的 Windows 终端窗口），并且每次重新同步更改的文件时都会再次弹出。 CodeGraph 的所有 git 调用现在都隐藏运行。感谢@Suharaz、@23q3、@A-Van-Gestel、@HarryMuc 和@MzaGuille。 （＃2094，＃2096，＃2312）
  • 在 Windows 上，使用不同驱动器号或文件夹名称大小写打开的项目（例如 d:\work\app 和 D:\Work\App）现在会加入已为其运行的 CodeGraph 后台服务器。之前，每个拼写都会启动一个自己的服务器并立即退出，因此会话会自行悄悄地提供图表，没有共享文件监视或自动同步，并且 codegraph list 显示了该项目两次。谢谢@greatjackzhou。 (#2278)
  • 在 Windows 上，当代理会话使用 CodeGraph 时，codegraph upgrade 不再中断安装。它曾经中途停止并导致 CodeGraph 无法启动；现在，它会在 CodeGraph 运行时交换新文件，并在出现任何问题时恢复以前的版本，并且重新运行 PowerShell 安装程序的工作方式相同。如果早期的升级已经破坏了您的安装，请重新运行 irm https://raw.githubusercontent.com/colbymchenry/codegraph/main/install.ps1 | iex 来修复它。感谢@tippmar-nr 的报告。 (#2185)
  • 在 Windows 上，CodeGraph 不再有时会在繁忙的计算机上崩溃并出现退出代码 3221225477（访问冲突）：在 codegraph init、codegraph index 和后台同步中解析后，或者在后台服务器关闭时。在它仍在启动时或在完成内存清理之前停止其辅助线程之一（解析文件、解析引用、写入索引并计数 codegraph_status 更改的线程）会导致整个进程停止运行。线程现在在退出之前完成启动和清理。

后台服务器、会话和 CLI

  • Claude Code 提示挂钩不再在 Claude Code 用于将子代理的报告传回主会话的消息上运行。以前，如此长的报告可能会使钩子在 Claude Code 的 30 秒钩子超时之后保持忙碌，并注入与您所要求的内容无关的上下文。感谢@danusha2345 和@tippmar-nr 的报告。 (#2184)
  • 较新的 MCP client（例如 Antigravity 2.5）再次连接：服务器现在立即以“找不到方法”应答其 server/discover 探测，因此它们直接进行常规握手，而不是等待可能需要几秒钟或永远不会出现的答复。感谢@danusha2345 和@samem26 的报告。 (#2084)
  • 通过 projectPath 查询另一个项目的 CodeGraph 会话在运行期间不再保持该项目锁定：10 分钟后没有查询，它会让项目继续运行，因此项目自己的会话和 codegraph index 可以再次接管（使用 CODEGRAPH_PROJECT_IDLE_TIMEOUT_MS 进行调整，0 保持其打开状态）。感谢@danusha2345 和@bompus 的报告。 (#2087)
  • Claude Code 现在向模型显示 codegraph_status 和 explore 的陈旧索引拒绝的全文。两个结果也都携带 structuredContent，并且 Claude Code 显示结果的 structuredContent 代替其文本，因此模型只看到新鲜的 JSON 对象：没有拒绝消息，没有重试指导，也没有状态报告。两个结果现在都只是文本。谢谢@bompus。 （#2088）
  • 当代理向 CodeGraph 询问嵌套在索引项目中的单独 git 存储库时，项目的索引遗漏了一个（例如，因为父项目的 .gitignore 排除了它），它现在得到通常的“未索引”指导，而不是来自父项目代码的答案。父级索引的嵌套存储库（例如子模块）像以前一样工作。感谢@wstczyw 的报告。 (#2110)
  • 代理会话失去与 CodeGraph 共享后台服务器的连接，或者在启动时无法访问它，不再阻止该服务器在会话的剩余时间内运行。一旦服务器可以启动，它就会自行重新连接，因此同一项目上的其他会话会自动同步回来，而不是以只读方式运行。感谢@ijbranch 的报告。 (#2277)
  • 当后台服务器仍在完成关闭时，codegraph index 不再因“无法验证活动的 CodeGraph 守护进程已停止”而放弃，并且 codegraph daemon 不再将此类服务器报告为无法停止的服务器；现在，两者都等待它退出，时间长达大约 20 秒。由于后台服务器不可用，本身为 CodeGraph 提供服务的代理会话现在也会等待该工作停止后再退出，而不是中途退出，这可能会在 Windows 上崩溃。谢谢@bompus。 (#2311)
  • 匿名使用遥测现在按记录发送每个工具或命令的每日计数，而不是每个代码图进程发送一个计数。之前，每次 MCP 服务器启动时，CLI 命令和提示钩子都会将其自己的条目排队，因此繁忙的机器每天都会上传数千份相同数量的副本。如果您关闭了遥测功能，则不会发生任何变化。

索引和同步

  • 最后一行在序列区域（第 1-6 列）内结束的 COBOL 文件，例如仅缩进四个空格的结束句点，不再使索引停止超过一分钟，然后在没有符号的索引中结束。
  • 编辑多次定义相同名称的文件（例如每个都有 execute 方法或方法重载的两个类），在 codegraph sync 期间不再将其他文件中的每个调用者移动到其中一个文件。文件中途中断的同步也不会再丢失这些调用者，直到完全重新索引为止。感谢@ijbranch 的报告。 (#2276)
  • 索引大型 C 或 C++ 项目不再在“解析引用”过程中耗尽内存。包含保护被写为 #define X_H 1 的标头（如 OpenSceneGraph 和 osgEarth 中），或者包含在构建标志代码图下的标头无法识别，通常会在每个包含路径上重新读取，该包含路径随着包含树的深度呈指数增长。现在，每个包含状态都会读取一次，并且硬限制会停止对任何仍然太大的包含树的检查。感谢@danusha2345 和@coolhitmanleon 的报告。 (#2127)
  • 在繁忙的计算机上，索引或同步小项目不再启动额外的后台线程来解析它无法使用的引用。在重负载下，较慢的速度使得十个文件的项目看起来足够大，需要它们，这增加了运行时间并保留了额外的内存。

跨语言

  • 扩展同名的另一种类型的类型现在链接到该其他类型而不是其自身。当来源拼出限定符时，该限定符会在同名候选人之间进行选择。之前，cats 的 trait BigDecimalInstances extends cats.kernel.instances.BigDecimalInstances 和每个 trait AllOps … with Functor.AllOps[…] 都指向声明性状，而 Newtonsoft.Json 的 JsonConverter<T> : JsonConverter 则扩展了自身。
  • Django、FastAPI、Flask、ASP.NET、Gin、SwiftUI 和 Vapor 的框架名称约定现在仅选择参考可以看到的类。这些约定的示例包括“…View 是视图”、“…Service 是服务”和“capi 化名称是模型”。选择从引用自己的文件开始，然后是它的包，并且从不采用在某个函数内声明或嵌套在另一个文件的类中的类。之前，Django REST 框架的测试将每个文件自己的 MockView 和 Serializer 链接到另一个文件的，而 netbox 的测试将 TestForm() 链接到在不同测试函数中声明的表单。
  • 在任何语言中，对另一个表达式的结果调用同名方法的方法不再链接到其自身。例如，Scala 的 requestToArmeria(request).execute() 位于 execute() 内，Rust 的 self.0.into_route(state) 位于 into_route() 内，以及来自内部对象的 Kotlin 的 this@Buffer.write(…)。其初始值设定项链调用同名方法的值（例如 sttp 的 val response = basicRequest.get(…).response(…)）也不再链接到其自身。
  • 将其调用交给另一个对象的方法不再链接到其自身。在 TypeScript 和 JavaScript 中，仅当字段声明为方法自己的类时，通过 this.<field> 或 window.<x> 的调用才算作递归。仅根据接收者的名字进行猜测永远不会落在调用方法上。之前，BookStack 的 toggle() 做 this.container.classList.toggle('open')、listen() 做 window.$events.listen(…)、FileStorage::delete 做 $storage->delete($path) 各自指向自己。
  • 作为值传递的函数或名称现在解析为其写入范围内的内容。嵌套在另一个函数中的函数只能从其内部访问。在 Python 中，同名的参数或局部就是那个局部。 pytest 夹具是仅在其自己的模块中或其 conftest.py 下的测试参数。之前，httpx 的 self._build_auth(auth) 链接到测试在另一个函数中定义的 auth，而 auth_flow(self, request) 将 request 链接到包的 request() 函数。
  • 在 Java、C#、Kotlin、Swift、Scala、Dart 和 VB.NET 中，调用现在会到达其参数适合其参数的重载，而不是首先索引的同名重载。例如，HashCodeBuilder.reflectionHashCode(this) 现在使用可变参数达到单参数过载，而不是三参数过载。每个重载的调用者现在都是它自己的。
  • 调用其自身的另一个重载的方法现在链接到该重载而不是其自身。一个示例是 toInstant(instant) 返回 toInstant(instant, Instant.EPOCH)。更完整的重载现在在其调用者中列出了其便利重载，因此其影响包括它们。这适用于 Java、C#、Kotlin、Swift、C++、Scala、Dart 和 VB.NET。真正的递归没有改变。
  • 生产代码不再链接到测试套件内的同名符号，因为测试未内置到程序中。之前，typeorm 的 Record<string, …> 类型到达了一个名为 Record 的测试实体，okhttp 的示例 @Override 注释到达了测试的嵌套 Override 类。项目附带的测试支持代码（例如 testing/ 文件夹或 *-test 模块）仍然触手可及。
  • 对变量的方法调用不再仅仅因为双精度具有该名称的唯一方法而被猜测为测试双精度的方法。这涵盖了名为 Mocked…、Fake…、Stub… 或 Dummy… 的类：django-allauth 的 resp.json() 调用都转到了 MockedResponse。命名双精度的测试仍然调用它。
  • 通过类名（例如 THorse.Get(…)、MyView.as_view() 或 ColorChoices.values()）的调用现在可以到达类继承的类方法。在 Pascal、Python、Ruby、PHP、TypeScript/JavaScript 和 Java 系列中，继承是从类声明本身读取的。以前，这样的调用都是通过名字猜测来解决的。在马匹上，THorse.Get('/ping', …) 曾在航线组接口的 Get 上着陆 120 次。升级后重新索引。
  • 从接收者名称猜测的方法不再落在 Web 框架分派到的请求处理程序上，例如 Django 或 DRF 视图的 post / get 或控制器的 update / destroy。它也不再落在调用文件从未提及的测试替身上。在 django-allauth 上，测试的 client.post(…) 曾在 ClientRegistrationView 上着陆 425 次。在mealie上，response.json()曾在测试的_FakeHTTPResponse上着陆424次。在Python中，site = Site.objects.create(…)现在使site成为Site，因此site.save()达到了模型自己的save。升级后重新索引。
  • 在 C#、Java 和 Kotlin 中，通过字段、属性或参数的调用现在会落在声明它的类型的方法上。这包括从基类继承的类型（填充了类型参数）、泛型或 for-each 声明、C# using 别名以及类型参数的绑定。调用不再退回到对某些项目类的同名方法的猜测，并且来自项目外部的类型不提供链接。在 Newtonsoft.Json 上，写入器包装器内的 _innerWriter.WriteValue(…) 用于落在包装器自己的 WriteValue 上，而 TextWriter 的 Write(…) 则落在测试写入器的 Write(…) 上。在 commons-lang 上，DateFormat 油田的 parse(…) 曾在项目的 DateParser 上着陆过 284 次。
  • 对使用项目外部类型声明的变量（List<String> list、var sb = new StringBuilder()、signer = TimestampSigner()）的调用不再落在具有相同名称的项目类型的方法上。在 gson 上，list.add(…) 曾经登陆项目列表包装器；在 commons-lang、s.length() 和 buffer.append(…) 项目类上。在 Python 中，调用 (prefix=IPNetwork(…)) 内的关键字参数不再用于对该名称的赋值。
  • 从项目外部调用类型，如 Integer.valueOf(…)、Arrays.asList(…)、Object.assign(…) 或 Delphi 的 Exception.Create(…)，不再使用该名称的项目自己的方法。在 commons-lang 上，Integer.valueOf 曾经登陆过 StringUtils.valueOf 超过 800 次。 Go 的导出变量和 Pascal 的 capitalized 参数和局部变量不会被误认为类型名称。
  • 在 PHP、CFML、Pascal、COBOL 和 VB.NET 中，现在解析以与其定义不同的大小写编写的调用，例如 FormatPrice 的 formatprice() 或 toMatchWithCase 的 CFML 的 ToMatchWithCase()。这些语言忽略名称中的大小写，但此类调用过去常常在解析之前被删除。
  • 在 Java、Kotlin、Swift、C#、C 和 C++、Go、Scala、Ruby、Dart 和其他区分大小写的语言中，名称不再链接到名称仅大小写不同的符号。在 jsoup 上，JUnit 的 @Test 将每个测试链接到 test 方法； new CookieManager() 已链接至 cookieManager() getter，Method 类型链接至 method()。 PHP、Pascal、CFML、COBOL 和 VB.NET（它们的名称确实忽略大小写）没有改变。
  • 重写方法中的 super 调用（例如 super.viewDidLoad()、[super init]、base.Handle()、parent::setUp() 或 super().dispatch(…)）不再使该方法看起来像是在调用自身。该调用将转到父版本，因此覆盖将停止显示为递归，并且不再将其自身列在其自己的调用者中。
  • 通用类型参数（例如 def zipWith[A, B](…) 中的 A、<T> T max(…) 或 class Foo<T> 中的 T）不再链接到恰好共享其名称的项目符号。在猫方面，一台 implicit def A 拥有来自图书馆中每台 A 的数千个虚构家属。 Rust、Dart、TypeScript、Java、Kotlin、Swift、Go、C# 和 C++ 也是如此。函数内部声明的类或其他类型只能从该函数内部链接。在 Scala 中，def 自己的参数（如 (f: A => B) 中的 f）不再链接到其他地方的同名字段。裸名称不再到达嵌套在另一个类型中的类型，除非代码位于该类型内部、扩展它或导入其成员；相反，作用域中的类型是链接的，就像猫自己的 FlatMap 代替了 Eval 的嵌套 FlatMap 一样。升级后重新索引这些语言的项目。

JavaScript 和 TypeScript，带有 Vue、Svelte、Astro、React、Express、NestJS 和 Hono

  • 在 Vue、Svelte 和 Astro 文件中，组件现在拥有其脚本，<script setup>、Svelte 实例脚本或 Astro frontmatter 在其顶层所做的事情就是组件所做的事情。其中包括 Nuxt 页面的 useAsyncData(…)、Svelte 页面的 onMount(…) 和 Astro 的 await getCollection(…)。导入和模块级脚本保留在文件中。以前，这些调用属于该文件，因此来自组件的调用者和流什么也找不到。该组件也被记录为包含其自己的文件，而没有脚本的文件根本没有文件节点。
  • 在 JavaScript 和 TypeScript 中，CommonJS require('./application') 现在被视为该文件的导入，就像 ESM import 一样。模块路径还解析 Node 和捆绑器找到它的方式：扩展、index 文件和路径别名。之前，CommonJS 文件在文件级别上不依赖任何内容，因此 Express 自己的 lib/express.js 显示没有导入，并且影响分析错过了它加载的文件。像 import './polyfills' 这样的无扩展副作用导入也会在其自己的导入语句处停止，而不是到达文件。
  • Express 路由的处理程序内联编写为 function (req, res) {…}（Express 自己的示例使用的形式），现在链接到该处理程序调用的内容，就像箭头处理程序一样。处理程序是路由的最后一个参数，因此命名处理程序之前的内联中间件不再代表它，并且像 asyncHandler(async function (req, res) {…}) 这样的包装器和尾随逗号都可以工作。之前，诸如 POST /login 之类的路线没有任何链接。
  • 在 NestJS 项目中，提供程序命名约定（…Service、…Controller…）现在仅从引用自己的文件中选择一个类。另一个文件的提供者可以通过其导入或通过首选最近声明的普通名称匹配来到达。之前，约定对 *.service.ts 文件的偏好将 Nest 自己的规范“TransientService 和 TestService”发送到不相关示例应用程序中的同名类。
  • 在 Astro 项目中，组件名称约定现在仅适用于使用组件的 .astro 文件内。之前，带有组件名称的 TypeScript 类型链接到该组件：在其类型声明中为 astrowind 的 image?: Image 和 callToAction?: CallToAction，在其测试中为 starlight 的 Playwright page: Page。
  • 在 JavaScript 和 TypeScript 中，中间件（validate…、auth、logger 等）、控制器和服务的 Express 约定现在仅选择调用文件自己的声明。另一个文件只能通过 import 或 require 访问。之前，SvelteKit 的远程功能将 validate(arg) 链接到另一个包中的配置加载器的 validate，而 Express 的示例将 logger('dev') 链接到一个示例的 logger。
  • 在 JavaScript 和 TypeScript 中，钩子 (use…) 和上下文 (…Context、…Provider) 的 React 约定现在仅从引用自己的文件中选取。另一个文件的钩子或上下文只能通过导入来访问。像 onSuccess?.(…) 这样的可选调用现在获得与普通调用相同的范围规则。之前，trpc 的 WebSocket 适配器的 createContext?.(…) 选项链接到示例应用程序的 createContext，zod 的 schemas.ParseContext 链接到 v3 副本而不是 v4，而bulletproof-react 的应用程序将 useUser() 链接到彼此的。
  • Svelte 组件的实例 <script> 或 Vue 组件的 <script setup> 声明的内容现在对该组件是私有的。只能从另一个文件访问 Svelte <script module>、普通 Vue <script> 或 <script setup> 导出的类型。之前，shadcn-svelte 的 <Item.Root> 链接到一个示例组件为其自身声明的 type Item，而 halo 的 isActive 从其编辑器核心导入，链接到选项卡组件的本地值。
  • 在 JavaScript 和 TypeScript 中，调用函数将自身绑定为参数或引用上方的普通 var/let/const 的名称，现在意味着本地而不是文件中其他位置的同名函数。之前，每个 lodash 助手的 object 参数都链接到 runInContext 内声明的 function object() {}，而当 Class 是函数的参数时，zod 的 new Class(…) 链接到不相关的 Class。像 const { t } = useI18n() 这样的解构挂钩结果仍然链接到它们来自的函数。
  • 在具有 React 前端的项目中，钩子 (use…) 和上下文 (…Context、…Provider) 的 React 规则不再适用于后端代码。在 halo（带有 React UI 的 Spring 应用程序）中，SecurityContext 和 ObjectProvider 等 Java 导入已作为 React 上下文进行处理。
  • 在具有 Vue 前端的项目中，后端的调用不再落在 Vue 组件上。 mealie 的 Python QueryFilterBuilder(…) 已链接到 QueryFilterBuilder.vue 组件。 Vue 规则（编译器宏、Nuxt 自动导入、按名称排列的组件）现在仅适用于应用程序的脚本。
  • 您自己的 JavaScript 中的调用不再链接到供应商的缩小脚本内的同名函数，例如 *.min.js 或由几行巨大的行组成的包。这些名字都被破坏了。在健康检查中，每个 jQuery $(…) 调用都转到 bootstrap-native.min.js 内的一个字母帮助程序。
  • 内联路由处理程序内的调用现在保留其接收者，因此它们像任何其他方法调用一样解析。之前，Hono 的 app.get('/', (c) => c.text('Hello')) 将路线链接到项目中的另一种 text 方法，即其 client 的 ClientResponse.text；超过 400 条路线都发生过这种情况。像 userService.lookup(id) 这样的调用会到达它指定的服务。
  • 桶的export * as core from './core'现在仅出口core，而不是./core中的所有东西。在 zod 中，z.string() 和 z.number() 一直在其核心模块深处使用同名的正则表达式常量，而不是模式函数。通过 import * as ns 进行的呼叫还可以找到按姓名 (export { safeParse } from '../core') 转发的会员。它们也遵循 z.coerce.number() 之类的命名空间路径。
  • 通过 CommonJS require 绑定的 JavaScript 调用现在可以到达正确的函数。 var express = require('../') 通过 index.js 跟随 module.exports 到达其导出的函数，并且读取 var a = require('x'), b = require('y') 列表中的每个绑定。 require('./utils').setCharset 意味着模块的 setCharset 而不是其第一次导出，并且从项目外部调用包（supertest、node:assert）不再是局部变量的优势。在 Express 上，目前有超过 700 个 express() 呼叫到达 createApplication。
  • 通过 tsconfig 或 jsconfig 路径别名导入现在使用最接近导入文件的配置，因此 monorepo 中的每个应用程序都会解析自己的 @/… 或 ~/… 别名。在bulletproof-react 和 trpc 的示例中，这些导入曾经失败或登陆到不同的应用程序中。
  • 在 JavaScript、TypeScript 和 Vue 中，通过从可组合或自定义挂钩（如 const { getDefaultActivityRoute } = useDefaultActivity() 或 const { t } = useI18n()）解构的名称进行的调用现在可以到达挂钩返回的函数。这些呼吁过去都没有得到解决。 mealie、elk、halo 和 excalidraw 各自获得了几十到一百多个这样的链接。
  • 在 JavaScript 和 TypeScript 中，模块不导出的模块的顶级函数、变量或类型不再与其他文件链接。每种导出形式仍然很重要：export 关键字、export { … } 列表、export default 和默认导出的对象。在typeorm上，测试夹具的本地ColumnMetadata用于捕获import { ColumnMetadata } from "typeorm"；在 sveltekit 上，未导出的 resolve 收集了其他文件的 resolve(…) 调用；在zod上，本地z收集了zod包导入。
  • 对文件导入的内容（例如 fireEvent.click(…) 或 util.omit(…)）的 JavaScript 或 TypeScript 调用不再链接到调用文件本身中声明的同名方法。
  • TypeScript 的 import type { X } 不再读取为名为 type 的导入，并且 import { a, type B } 绑定 B，而不是 type B。因此，仅类型导入现在链接到它命名的模块，它过去常常链接到具有该名称的任何项目符号。从包导入的类型（例如从 @rsbuild/core 导入的 RsbuildConfig）不再链接到项目符号，并且 JavaScript 和 TypeScript 名称不再与名称仅大小写不同的符号匹配（Mock 不是 mock）。
  • 在带有 Expo 应用程序和 Next.js 应用程序旁边的 monorepo 中，例如 create-t3-turbo 或 tamagui 的启动器，每个路由器现在只读取自己的应用程序。 Expo Router 也曾经读取 Next.js 应用程序的文件，因此 layout.tsx、page.tsx、_components 文件夹和 API 路由显示为名为 /layout、/page 或 /_components/posts 的屏幕，并且共享包的文件也成为屏幕。升级后重新索引此类 monorepos。
  • Vue、Svelte 和 Astro 组件中的调用现在遵循与 JavaScript 和 TypeScript 相同的规则。 useI18n() 中的 t('…') 或 vue 中的 ref(…) 用于链接到项目中其他地方的接口属性或同名局部变量，因此两个不相关的符号各自有超过一千个虚构的调用者。当在嵌套应用程序的 package.json 或 Deno 导入映射中声明包时，从包导入的调用也不再被误认为是项目符号。无法遵循通过别名 CodeGraph 进行的导入，例如 SvelteKit 的 $lib/… 或嵌套 Nuxt 应用程序的 ~/…，仍被视为项目代码。升级后重新索引 Vue​​、Svelte、Astro 和 JavaScript/TypeScript 项目。
  • 现在，即使未命名为 .min.js，缩小或捆绑的 JavaScript 文件也会被识别为已生成，例如文档站点的 bundle.js、可读的 Webpack 版本或供应商的 underscore-min.js。现在，它的单字母函数在搜索和 codegraph_explore 答案中的排名低于您自己的代码。
  • JavaScript 和 TypeScript 呼叫不再链接到仅共享姓名的集体成员。对名称空间导入的调用，如 zod 的 z.string() (import * as z from 'zod')，或从 npm 包导入的内容，用于链接到项目中具有 string 成员的任何类，以及对接口的 it 属性或类的 describe 的裸调用，如 mocha 的 it(…) 或 describe(…)场。在 zod 上，一位测试助手的 getter 有数千个虚构的来电者，并且名列最受依赖的名单之首。从包导入的 React 钩子或组件（例如 @tanstack/react-query 中的 useQuery）不再链接到项目中的同名钩子或组件，并且嵌套在另一个函数中的钩子根本不再是目标。升级后重新索引 JavaScript 和 TypeScript 项目。

Java、Kotlin 和 Scala

  • 在 Java 中，裸类型名称现在仅解析为可达的类型。这是同一包中的一种类型，通过名称或使用 .* 导入的类型，或者从其所有者内部、子类（包括匿名类）使用的嵌套类型，或者通过其所有者编写的类型，如 Outer.Inner 中所示。构造函数不再代表其类，枚举常量只能通过其枚举内部、case 标签中的裸名称或通过静态导入来访问。之前，retrofit 的 new Retrofit.Builder() 链接到 RequestFactory.Builder，halo 的千分尺 Counter 链接到它自己的 Counter 类，jsoup 的 java.lang.Class<?> 链接到嵌套选择器类。
  • Gradle Kotlin 脚本 (build.gradle.kts) 中的裸调用（例如 plugins { }、dependencies { } 或 api(…)）不再链接到项目自己的类之一的方法或属性。在 Gradle 类型上构建逻辑的扩展函数仍然可以解析。之前，nowinandroid 的构建脚本将每个 plugins { } 和 dependencies { } 块指向其构建逻辑的 Graph 类，并将每个 api(…) 指向 lint 注册表的 api 属性。
  • 在 Scala 中，包对象的成员现在仅解析其范围内的位置：在其自己的包中、其下的包中或通过该包导入的文件中。之前，猫法则将 Eq、Order 和 Monoid 解析为 algebra 包对象的别名，而不是 cats 包对象的别名，并且 sttp 的 akka 测试达到了 zio 包对象的 whenRequestMatches。
  • 在 Spring 项目中，类名现在在通过文件夹约定进行任何猜测之前解析为引用自己的文件或包中的类名。嵌套在另一个文件的类中的类永远无法通过其裸名称访问。之前，mall 中的每个 MyBatis Example 类的 new Criteria() 都链接到第一个 Example 的嵌套 Criteria，而 halo 的 Lombok @Builder 链接到其他地方的嵌套 Builder 类。
  • 在 Scala 中，类型中的种类投影仪占位符（如 Align[Either[A, *]]）不再链接到名为 * 的运算符方法。类型中的符号名称（如猫的 F ~> G）现在仅解析为类型。
  • DSL lambda 内部的 Kotlin 调用现在到达 lambda 自己的接收器。该接收器来自 lambda 传递到的函数，即使通过像 koin 的 Definition<T> = Scope.(…) -> T 这样的类型别名也是如此。它还胜过该项目在其他地方用作 lambda 接收器的其他类型。同样，single { … } 中的 2,000 多个 get() 呼叫现在到达 Scope.get，而不是 Koin.get；在暴露时，表对象内的 varchar(…) 达到 Table.varchar；在 kotlinx.coroutines 上，launch { } 达到 CoroutineScope.launch。
  • 像 xs.map { … } 这样的 Scala 链式调用不再落在恰好名为 map 的对象上，就像猫的 alleycats.std.map 及其 syntax/instances 对象一样。链中的类型或对象仅当接收者命名其持有者时才匹配，如 sttp.client4.Response(…) 中。
  • Kotlin 导入现在决定名称的含义，就像 Java 导入已经做的那样。 import java.net.Proxy 或 import org.mockito.Mockito.mock 不再链接到同名项目符号，并且文件声明自身的成员仍然排在第一位。 import x.Foo 从几个同名类中选择正确的一个：在 okhttp 上，MockResponse.Builder() 和 Request.Builder() 现在到达它们的类。像 import …internal.unsafeFlow as flow 这样的重命名导入意味着它命名的函数。
  • 在 Java 中，从项目外部导入的类现在拥有其名称。在 import java.lang.reflect.Field; 之后，文件的 Field 不再链接到恰好共享该名称的项目类。在 gson 中，这是一个测试的嵌套 Field 类； jsoup的W3C转换器中是jsoup自己的Document和Element。像 import static org.mockito.Mockito.verify; 这样的静态导入也以相同的方式进行。
  • Scala 调用不再落在另一个测试的本地值上。在一个 test("…") { } 块内编写的 val f 被选为另一套件中的 lambda 参数 f，甚至是 cats 核心库中的 f(…)。像 import cats.syntax.all._ 这样的包导入不再将每个类的成员放在范围内。现在，真正在范围内的成员会解析：导入的包对象的父类型（import sttp.client4._ 给出 SttpApi 的 multipart）的成员，以及文件自己的包对象的成员。
  • 使用更新语法的 Kotlin 文件现在保持其类完整。其中涵盖 when 保护条件 (is X if cond ->)、..< 范围、多美元字符串 ($$"…") 和函数类型中的可空接收器 (T?.() -> R)。以前，围绕此类代码的类可能会表现为分散的松散函数。在 Exposed 上，存在解析错误的文件从 65 下降到 43，在 kotlinx.coroutines 上从 50 下降到 46。升级后重新索引。
  • 使用名称以 e 开头的中缀函数的 Kotlin 代码（如 Exposed 的 Users.id eq id1）现在可以清晰地解析。以前，此类行的其余部分是解析错误，并且在包含许多此类错误的文件中，其周围的整个类可能会丢失。在暴露时，有解析错误的文件从 229 下降到 71。升级后重新索引。
  • 在 Kotlin 中，现在只有当另一个类可以访问时，没有接收器的调用才会到达另一个类的方法。这意味着一个类、一个匿名 object : Base() 或围绕调用的扩展函数的接收者、它们继承的内容或 DSL lambda 的接收者（koin 的 single { get() } 在 Scope 上运行，Exposed 的 withTables { … } 在事务上运行）。文件导入的对象成员也可以访问。 Kotlin 自己的 error(…)、require(x >= 0) { … } 和 check(…) 不再落在项目类的同名方法上。顺便说一句，module { … } 在一次测试中曾在另一个测试类的私有 module 上着陆超过 260 次，并且在 lambda get() 内着陆在错误的类的 get 上。升级后重新索引。
  • 主构造函数位于类名之后、超类型列表之前的 Kotlin 类（expect open class ByteString / internal constructor(…) : Comparable<ByteString>，在 Kotlin 多平台代码中常见）不再因松散函数而丢失其成员。稍后对 Kotlin 标准库函数（apply、let、toString、map、contains…）的调用不再落在项目类型的同名方法上。在okhttp上，.apply { … }曾经登陆过ConnectionSpec.apply。升级后重新索引。
  • 在 Scala 中，仅通过名称拨打的电话现在仍可到达。封闭函数绑定为参数或本地的名称（f: A => B 为 f(true)）就是本地名称。链中稍后的调用（例如 fa.iterator.map(…)）仅到达其接收者所命名的成员。普通调用仅到达封闭类及其超类型（包括匿名子类的基类）、伴随对象或导入的对象。在猫上，像 f(a) 这样的参数调用过去常常会落在案例类的字段 f 上超过 400 次，并将 .map(…) 链接到一个操作类的 map 上。
  • 在 Kotlin 中，对顶级或扩展函数的调用现在仅解析为文件可以看到的一个：一个在其自己的包中，一个通过名称导入，或者一个来自使用 * 导入的包。在 Exposed 上，导入 kotlin.test 或 JUnit 的 assertEquals 或 JDBC 套件的帮助程序的测试曾经登陆 R2DBC 套件的帮助程序超过 3,000 次。在 okhttp 上，导入 mockwebserver3.MockResponse 的测试用于构造已弃用的同名类。具有限定接收器的函数类型（例如 (DatabaseConfig.Builder.() -> Unit)?）不再破坏其周围类的解析。升级后重新索引。
  • 像 verify(mock)、assertThat(x) 或 hashCode() 这样的纯 Java 调用现在仅链接到其所在类、该类的父类或文件静态导入的方法。它曾经链接到同名的任何类的方法：在 halo 中，Mockito 的 verify 和 eq 为一项服务的 verify 提供了超过一千个虚构的调用者，而在改造中 Truth 的 assertThat 对测试助手做了同样的事情。对项目继承方法和静态导入的调用现在链接到正确的方法，例如 jsoup 的 attr(…) 到 LeafNode 或 halo 的 and(…) / equal(…) 到 import static …Queries.*。升级后重新索引 Java 项目。

C# 和 VB.NET

  • C# 名称现在遵循语言的范围。块 namespace X { … } 仅限定其内部的类型，因此在块之后或文件的第二个命名空间中声明的类型不再归档在第一个命名空间下。写在另一个命名空间中的命名空间是 Outer.Inner。 using 链接到项目的命名空间，而不是另一个同名文件的 using。 global using 仅适用于其自己的项目。嵌套类型只能从其所有者内部或从其派生的类型（包括通过另一个部分部分）通过裸名称访问。之前，serilog的Guard归档在JetBrains.Annotations下，其测试的Some.InformationEvent()转到性能测试的Some，而AutoMapper的同文件new Source()可以到达另一个测试类的嵌套Source。
  • C# 类型名称现在遵循命名空间。类型可以从其自己的命名空间或嵌套在其中的命名空间，或通过其命名空间的 using 访问。还计算在内：项目范围的 global using、项目的 <Using> 条目、ZZPH100​​0ZZ 的隐式使用或为其命名的别名。之前，Newtonsoft 的 async Task 测试将 Task 链接到另一个命名空间中同名的测试类，而 AutoMapper 的 DTO 链接到另一个命名空间的 BaseEntity。
  • 接口的 C# 成员现在是公共的，并且不带修饰符声明的类型现在是内部的，正如语言所定义的那样。对接口类型字段的调用现在会到达接口的方法，而过去在该方法中什么也找不到。现在，根据接收者名称进行的猜测仅权衡所有者类型自己的名称，而不是其名称空间。标准 .NET 名称（例如 ToString、Add 和 Write）需要一个以所有者命名的接收器。在每种语言中，对生产代码的猜测不再落在测试套件中定义的模拟或帮助程序上。升级后重新索引。
  • 在 C# 中，诸如 TestContext、Easing 或 Helper() 之类的裸名称现在仅解析为所编写的类的成员、其外部类、其基类或使用 using static 引入的类型。其中包括 global using static 和项目文件的 <Using … Static="true"/>。在 eShop 上，测试类的 TestContext 曾经登陆过另一测试类的财产；在 Newtonsoft.ZZPH100​​1ZZ 上，TypeNameHandling.All 现在到达枚举而不是同名属性。

  • 在 C# 和 VB.NET 中，用代码编写的类型（例如 Type sourceType、List<int>、new TypeMap() 或 Dictionary<string, Type>）现在链接到该类型，而不再链接到共享其名称的属性、方法或字段。 List<…> 用于链接到某些测试类的 List 属性，Type 链接到属性的 Type 属性，TypeMap 类型的参数链接到 TypeMap 属性而不是 TypeMap 类。这些成员与数百名虚构的家属一起出现。读取属性或传递方法（例如 Builder.Services 或 MapGet("/x", GetItems)）仍然像以前一样链接。升级后重新索引 C# 和 VB.NET 项目。

Swift 和 Objective-C

  • 符合其自己名称的协议的 Objective-C 类现在链接到该协议而不是其自身。 Swift 的视图、模型和控制器的命名约定也不再适用于 Objective-C 代码。之前，SDWebImage 的每一个 @interface SDDiskCache : NSObject <SDDiskCache> 风格的类都实现了自己。
  • 在 Swift 中，对重载方法的调用现在会到达其参数标签拼写的重载，并且默认参数可选。之前，仅比较参数计数。 Alamofire 的 self.tableView(tableView, numberOfRowsInSection:) 内部的另一个 tableView 过载与其自身相连，而 cancel(optionallyProducingResumeData:) 则与 cancel(producingResumeData:) 相连。
  • 对使用某种类型声明的属性（例如 Kingfisher 的 var cache: ImageCache! 或 self.storage.write(…)）的 Swift 调用现在可以到达该类型的方法或其继承的方法。它不再落在测试中的子类重写上，或落在另一个类型的同名方法上。
  • 对现场构建的值（如 JSONDecoder().decode(…) 或 Realm().create(…)）的 Swift 调用现在解析为该类型的方法或其继承的方法。它不再落在其他类型的同名方法上：Vapor 的 JSONDecoder().decode 调用已转到请求的私有容器。
  • 在 Objective-C 中，[super init] 和其他发送到 super 的消息现在到达超类的方法，而不会到达发送类自己的覆盖。这也适用于索引失去 @implementation 范围的情况。在 SDWebImage 上，NSObject 子类的 [super init] 用于登陆 SDDiskCache 的 init，而在代理类的 class 上进行测试时则登陆 [self class]。在 AFNetworking 上，串行器的 [super encodeWithCoder:] 现在达到其超类。升级后重新索引。
  • 在 Swift 中，没有接收器或通过 self. 或 super. 编写的调用现在仅到达其周围类型的成员或该类型继承或符合的类型的成员，并且最接近的覆盖获胜。链中稍后的标准库名称（axis.entries.removeAll()、names.contains(x)）不再落在项目类型的方法上，除非接收者或调用的参数标签指向它。在图表上，min(a, b) 和 max(a, b) 曾经落在范围类型的 min 字段和 Sequence 扩展上，super.init(…) 落在 Objective-C 演示的 init 上超过 170 次。游乐场或测试目标中的全局不再与主代码链接。升级后重新索引。
  • 在 Objective-C 中，消息现在只有在真正可以发送到某个方法时才会到达该方法。发送至 self 或 super 的消息仅到达发送者的类及其超类，包括 UIKit 和 AppKit 视图上的类别。像 completionBlock() 这样的 C 风格调用永远不会被用于方法或属性。发送给局部变量的消息使用该变量的声明类型 (FMResultSet *rs)。在 SDWebImage 上，[self class]、respondsToSelector: 和 isKindOfClass: 过去常常登陆代理类的重写超过 150 次，而在 fmdb 上，[rs close] 现在达到结果集。
  • 通过嵌套类型（如 API.PackageController.GetRoute.query(on: db)）的 Swift 调用现在链接到该类型的方法。过去只保留 query，因此调用链接到首先出现的类型的 query；在 Vapor 应用程序中，每种路由类型都有一个，因此呼叫者、影响和 codegraph_explore 答案指向另一个端点的代码。这同样适用于嵌套类型的初始值设定项 (API.PackageController.Model(name:))、枚举情况 (Gitlab.Error.requestFailed(status:))、extension API.PackageController { … } 中声明的类型以及可组合架构的 Path.State.detail(…)。对项目中未命名任何类型的类型路径的调用（例如 ZZPH100​​2ZZ 的 Plot.Node.footer(…)）将保持未链接状态。升级后重新索引 Swift 项目。

  • 蒸汽路线现在链接到它指定的处理程序。 use: SearchController.show 用于链接到首先出现的控制器的 show，因此具有通用处理程序名称（如 show、index 或 get）的路由指向调用者、影响和 codegraph_explore 答案中的另一个端点的代码。现在，API.PackageController.get 等嵌套类型和控制器扩展中声明的处理程序也可以解析，而 use: self.index 则解析为集合自己的 index。升级后重新索引 Vapor 项目。
