codegraph v1.3.0

[1.3.0] - 2026-07-07

新功能

  • CodeGraph 现在索引 Nix (.nix) — flakes、NixOS 和 home-manager 模块、覆盖层和包集加入图表：let 和 attrset 绑定、函数（简单、解构 { pkgs, ... } 和柯里化）和 inherit 绑定都成为可搜索符号，绑定之间有调用边。文件级连接遵循 Nix 实际连接文件的方式：import ./relative/path.nix（import ./dir 到达目录的 default.nix）、NixOS 模块 imports = [ ./hardware.nix ../common ] 列表、片状 modules = [ ./configuration.nix ] 列表和 nixpkgs callPackage ./pkgs/foo { } 习惯用法 - 所以“这个配置实际上引入了什么”和“什么使用了这个模块”在实际设置中是可以回答的。动态引用（import <nixpkgs>、变量路径、薄片输入模块引用）故意保持未链接而不是猜测。谢谢@TyceHerrman。 （＃324，＃332，＃648）
  • NixOS 模块系统的选项接线是桥接的，因此流程问题跨越模块边界而不是陷入困境：像 launchd.user.agents.myapp = { ... } 或 home.file.".gitconfig" = { ... } 这样的配置写入链接到声明该选项的模块（options.launchd.user.agents = mkOption { ... } - 平面和嵌套声明拼写都计数，像 system.defaults.NSGlobalDomain."com.apple.dock" 这样的带引号的键与它们的确切声明匹配），这使得“启用此服务如何产生 launchd 守护进程/生成的配置文件”是可追踪的端到端和“什么设置这个选项”跨模块负责，包括测试。精度是故意保守的：内插的 ${...} 路径、在多个模块中声明的选项以及子模块内部选项命名空间保持未链接而不是猜测，并且每个桥接跃点都被标记为启发式模块系统接线，而不是显示为普通引用。
  • CodeGraph 现在索引 ArkTS (.ets) — HarmonyOS / OpenHarmony 应用程序的语言。 TypeScript 的所有内容都被提取（类、接口、枚举、类型别名、导入/导出、调用边缘），加上 ArkTS 自己的构造：@Component / @ComponentV2 结构及其装饰器（@Entry、@State、@Prop、@Link、@Local、@Param、 …）捕获和可搜索，build() 视图树链接父→子，因此“哪些页面渲染此组件”是可回答的，链接属性连接到它们调用的 @Extend/@Styles 函数，连接到调用图的 @Builder 方法和函数，以及链接到其处理程序方法的 .onClick(this.handler) 样式事件绑定。模块化 HarmonyOS 项目也跨模块边界进行解析：裸露的 import { CartRepository } from "data" 遵循 oh-package.json5 file: 对正确模块的依赖关系 - 尊重来自 .ets 和 .ts 消费者的每个模块声明的 main 条目 - 而多应用单一存储库中的模糊名称故意保持未链接而不是猜测和混合.ets/.ts 代码库可以自由交叉链接。在真正的 HarmonyOS 应用程序上进行了验证，包括官方 OpenHarmony 示例 monorepo。 （＃396，＃512，＃648，＃890）
  • ArkUI 的动态跃点是桥接的，因此流问题会穿过它们而不是变暗，每个标记为动态调度而不是显示为普通调用：分配反应性属性（@State、@Local 等）的方法链接到组件的 build()（重新渲染跃点 - 分配门控，因此仅读取状态的方法没有优势）；当双方共享静态可恢复事件密钥时，emitter.emit(eventId) 链接到匹配的 emitter.on/once 订阅者（仅一个文件内的数字 ID 对，一个模块内的命名常量，因此单一存储库中的不相关样本永远不会交叉链接）； router.pushUrl({ url: 'pages/Detail' }) 链接到目标页面的 @Entry 结构，模糊的 url 未链接而不是猜测。
  • 中断或不完整的索引现在是可见的而不是无声的：运行中止的中间索引（崩溃、内存不足、看门狗）会留下一个标记，codegraph status 报告为截断索引，删除文件的已完成运行将其自身报告为部分索引（无论是在人工输出还是在 status --json 中），并且当 codegraph index 的结果与扫描发现的结果不符时，codegraph index 会打印一条包含确切计数的警告。
  • CodeGraph 现在索引 Terraform 和 OpenTofu (.tf、.tfvars、.tofu) — 资源、数据源、模块、变量、输出、提供程序和每个 locals 属性都成为符号（例如 aws_s3_bucket.my_bucket、var.region、module.vpc、local.prefix），并使用 var.region、 module.vpc.id、data.aws_caller_identity.current 或 aws_s3_bucket.my.arn 跨文件连接，因此搜索、调用者和影响查询会在基础架构存储库上返回真实结果，而不是什么也不返回。模块调用跨模块边界桥接：module 块的输入链接到子模块的变量，module.vpc.vpc_id 到达子模块的 output "vpc_id" 定义，块的本地 source 路径链接到模块的文件 - 因此“如果我更改此模块的变量会中断”到达每个调用者，而不是在声明处死胡同（注册表和 git 源故意保留为可见边界，而不是猜到了）。通过 cloudposse/atmos remote-state 模块的跨组件接线也可以连接：当静态声明组件名称（文字或具有文字默认值的变量）并且一个目录完全匹配时，一个组件中的 module.vpc.outputs.vpc_cidr 会到达 vpc 组件自己的输出，并且一个目录完全匹配 - 任何动态或不明确的内容都保持未链接。别名提供程序是一流的：provider "aws" { alias = "east" } 获得自己的符号，资源上的 provider = aws.east（或模块的 providers 映射）链接到该配置，以 Terraform 实际继承它的方式找到模块树。 moved/import/removed 状态迁移块和 check 断言引用它们命名的资源，因此重构的书面记录是该图的一部分。 .tfvars 赋值链接到它们设置的变量，包括保存在子目录中的 var 文件。分辨率遵循 Terraform 的实际每个目录范围，因此模块之间的同名变量永远不会交叉链接，并且多模块存储库中的“依赖于 var.project_id 的内容”永远不会混合在不相关的模块中。谢谢@Javviviii2。 （#83、#310、#648）
  • CodeGraph 现在索引 CUDA (.cu、.cuh) — 内核、设备/主机函数、结构和类成为符号，并且主机→内核调用边缘在 <<<grid, block>>> 启动语法中继续存在，因此出现诸如“此调用如何到达 GPU 内核？”之类的问题。跨越 CPU/GPU 边界进行跟踪，而不是在发射地点变暗。真实世界的启动样式都是相互连接的：模板化启动（my_kernel<Traits, 256><<<grid, block>>>(args)）、通过本地函数指针启动（auto kernel = &my_kernel<...>; ... kernel<<<grid, block>>>(args) - 每个分支分配的目标链接）、大括号初始化的启动配置（<<<dim3{1,1,1}, dim3{256,1,1}>>>）以及通过 name-in-first-argument 宏（flash-attention 的 DEFINE_FLASH_FORWARD_KERNEL(kernel_name, ...) { ... } 样式）定义的内核，这些内核现在在其真实内核名称下进行索引。 CUDA 存在于普通的 .h/.hpp 标头中（其中包含许多实际设备代码，包括启动模板标头），可被内容识别并以相同的方式进行索引。已在 llm.c、flash-attention 和 NVIDIA CUTLASS 上验证。 （＃387，＃648）
  • namespace 块内定义的 C++ 符号现在在其限定名称中携带命名空间（包括 flash::compute_attn、C++17 namespace a::b {），并且命名空间限定调用 (ns::fn(...)) 解析为其定义 - 以前此类调用根本不链接，这对调用者和影响分析隐藏了命名空间密集的 C++ 代码库中的大部分调用图。
  • 拼出模板参数 (fn<T, 256>(args)) 的 C++ 调用现在链接到它们实例化的函数，与已经具有的标准化模板基类相同。
  • CodeGraph 现在索引 Solidity (.sol) — 合约、库、接口、结构、枚举、修饰符、事件、错误和状态变量成为一流符号，调用边缘遵循 emit、revert、修饰符保护（onlyOwner 样式，包括像 constructor() ERC20(...) 这样的基本构造函数链）以及库/方法调用（包括using 指令）。 import 指令解析为导入的文件，因此存在跨合约问题，例如“通过配额和余额更新跟踪 transferFrom”或“onlyRole 如何到达角色存储？”在真实的 Solidity 代码库上开箱即用（在 solmate、solady 和 OpenZeppelin 合约上验证）。谢谢@naiba。 （＃374，＃648）
  • Erlang 行为分派现在通过图表进行：通过变量模块进行框架调用 — 牛仔的 Handler:init/Middleware:execute 折叠、插件管理器的 Mod:callback(...) — 链接到声明该回调的行为的存储库实现，因此流跟踪和影响会跨越 OTP 回调边界，而不是停留在该边界。链接是精确门控的：回调数量必须匹配，恰好一个行为可能拥有该回调形状（冲突保持未链接而不是猜测），实现者必须实际导出回调，并且扇出是有界的 - 具有数百个实现者的行为保持明显的动态边界。每个桥接的跃点都被标记为其接线站点的动态调度，从不显示为普通的静态呼叫。
  • CodeGraph 现在索引 Erlang (.erl、.hrl) — 函数，其中同名的子句和参数被分组为一个跨越所有函数的符号，加上记录及其字段、-type/-opaque 别名、-define 宏和附加到每个函数的 -spec 签名。跨模块 mod:fn(...) 调用解析为目标模块的函数，fun name/arity 值被捕获为引用（因此像 lists:foreach(fun submit/1, ...) 这样的回调注册链接起来），-include/-include_lib 连接到它们拉入的头文件，-behaviour 声明将回调模块链接到其行为（并且仅链接到模块 - 存储库中其他位置的同名宏或函数是永远不要误认为是一个），-export 列表（加上 -compile(export_all)）驱动每个函数的公共/私有标志。在目标是静态的情况下，遵循 OTP 的间接惯用法：spawn/apply/proc_lib/timer/rpc 将其目标命名为 (Module, Function, Args) 参数的调用会产生调用边，并且 gen_server:call/cast 连接到目标模块的handle_call/handle_cast — 当目标为 ?MODULE 时它自己的（包括 -define(SERVER, ?MODULE) 习惯用法），以及当注册名称遵循 OTP 的名称-服务器在其模块之后的约定时的命名模块（gen_server:call(other_mod, ...)，直接或通过 -define(STORE, other_mod) 宏）；与任何模块都不匹配的注册名称将保持未链接状态。宏也参与该图：-define 主体的调用属于宏，每个 ?MACRO(...) 使用站点链接到调用链（并且裸露的 ?CONSTANT 读取被跟踪作为引用），因此隐藏在宏后面的调用路径 - set_password → ?SQL_UPSERT_T → sql_query_t - 端到端跟踪，并且“这个宏在哪里使用”是可以回答的。 escripts 索引像任何模块一样（可以理解 shebang 行），OTP 应用程序资源文件（.app.src、.app）加入图表：{mod, ...} 将应用程序链接到其回调模块，{applications, [...]} 连接伞兄弟应用程序 - 只解析模块，因此像 ssl 这样的 OTP 应用程序名称永远不会被误认为是同名函数。真正的动态调度（Mod:handle(...)、消息发送、var-module 生成）是故意保持未链接而不是猜测的。 codegraph_explore 还可以理解查询中的 Erlang 原生符号拼写——mod:fn/3 和 init/2 找到它们命名的符号。 （#635，#648）
  • CodeGraph 现在索引 Visual Basic .NET (.vb) — 类、模块、接口、结构、枚举、属性、事件、MustOverride 抽象成员和 Declare P/Invoke 签名，具有 Inherits/Implements 层次结构边缘、调用边缘（通过 VB 的不明确的调用与索引括号解决），以及New/As New 实例化链接。真实世界的 VB 样式可以清晰地解析：WinForms 设计器文件、插值和多行字符串、XML 文本（包括嵌入的 <%= %> 表达式）、单行和多行 LINQ 查询、多行 lambda、Handles/WithEvents 事件连接、自定义事件、日期文本、经典类型字符标识符（i%、 name$) 和非英语 (Unicode) 标识符。 （#648、#639、#170）
  • CodeGraph 现在索引 COBOL (.cbl、.cob、.cpy) — 具有 PERFORM/GO TO 调用边缘、CALL 跨程序调用、COPY 副本导入（包括独立副本）以及具有 88 级条件名称的 DATA DIVISION 记录的程序、部分和段落，固定和免费源格式。影响查询适用于数据项：每个 MOVE/ADD/COMPUTE/SUBTRACT 写入站点都链接回其更改的字段，因此“什么触及此抄写本字段”跨程序进行回答。 CICS 流也连接：EXEC CICS LINK/XCTL 程序目标、EXEC SQL INCLUDE 副本和伪会话 RETURN TRANSID(...) 跃点解析为拥有事务 ID 的程序。 （＃590，＃648）
  • CodeGraph 现在索引 CFML（.cfc、.cfm、.cfs）——经典的基于标记的样式 (<cfcomponent>/<cffunction>) 和现代裸脚本 component { ... } 语法，包括 extends/implements、嵌入式 <cfscript> 块（在任何嵌套深度，包括内部） <cfif>/<cfloop>/<cftry>)、调用边以及嵌入在 <cfquery> SQL 体内的 #hash# 表达式中的调用。使用 UTF-8 字节顺序标记保存的文件和带有不带引号的属性值的标签（这两种情况在长期存在的 CFML 代码库中很常见）也会被处理。谢谢@ghedwards。 (#1118)
  • 作为组件路径编写的 CFML 继承现在链接到正确的组件。 extends="coldbox.system.web.Controller" 通过点路径命名其超类型，extends="../base" 通过相对路径（FW/1 样式）命名 - 两者以前根本不产生继承边缘，这在框架式 CFML 应用程序上隐藏了大部分类型层次结构，使其免受影响和爆炸半径分析（在 ColdBox 自己的核心上，超过 90% 的继承是不可见的）。分辨率故意保守：目标的目录布局必须证实声明的路径 - 因此，存在于存储库外库（testbox、mxunit、已安装的框架）中的超类型正确地保持未链接而不是被猜测，并且不明确的路径不会产生边缘而不是产生错误的边缘。 (#1152)
  • 通过局部变量、类型化参数或组件属性进行的 CFML 方法调用现在解析为正确的方法 - 与其他面向对象语言已经具有的接收器类型推断相同。 var svc = new UserService(); svc.save()、createObject("component", "path.UserService")、类型化 <cfargument> 或 cfscript 参数以及 variables./this. 作用域字段 — 包括伪构造函数模式（init() 中的 variables.svc = new UserService()）和 WireBox 注入属性 (property name="svc" inject="UserService") — 现在都将调用链接到声明的组件的方法，通过上面的继承链接解析从超类型继承的方法。这使得调用者、影响/爆炸半径和 codegraph_explore 流跟踪遵循 CFML 服务调用，而不是丢弃它们或在同名方法中猜测。
  • Claude Code 上下文挂钩现在可以通过对照项目索引中实际的符号名称检查提示的单词，识别以任何语言的简单单词描述代码的提示。询问“the state machine des commandes”会发现 OrderStateMachine 不涉及任何关键字。信心决定注入的量：结构性问题和命名真实符号的提示仍然会预先获得完整的上下文；普通单词匹配会获得一个指向匹配符号的短指针，以便代理自行查询它们；其他一切都保持沉默，就像以前一样。
  • 匿名使用遥测现在计算上下文挂钩注入上下文、提供提示或保持沉默的频率 - 仅固定计数器名称；提示的内容永远不会被存储或发送。这使得钩子的准确性可以测量，而不是猜测。计数器记录实际发生的情况，而不是尝试的情况：错误或返回空的查找将被视为独特的静默结果，而不是被视为交付的上下文（#1143，感谢@inth3shadows）。
  • 金属着色器文件 (.metal) 现已建立索引。 Metal Shading Language 与 C++ 足够接近，顶点/片段/内核函数、结构、类型别名以及它们之间的调用都落在图中 - 因此 Apple 平台项目中的着色器管道显示在影响分析和流程跟踪中，而不是默默地跳过。 Metal 的 [[buffer(0)]] 风格的属性注释经过处理，因此它们不会破坏提取的内容。感谢@FluxKo 的报告。 (#1121)
  • CodeGraph 现在索引旧版 iBatis 2 SQL 映射 (<sqlMap>)，而不仅仅是 MyBatis 3 <mapper> 文件。 <sqlMap> 内的 <select>/<insert>/<update>/<delete>、iBatis 的 <statement>/<procedure> 和 <sql> 片段成为可搜索的语句符号 — 对于命名空间映射和无命名空间的 Map.statement id 样式 — 和 <include>引用解析为它们引入的片段，因此搜索、调用者和影响查询会在 iBatis 代码库上返回结果，而这些结果以前根本不生成任何语句符号。感谢@ESPINS 的报告和复制。 (#1182)
  • 您现在可以强制 gitignored 第一方源进入带有 codegraph.json 中的 include 列表的索引。这个解决的情况是：一个由第二个 VCS（SVN、Perforce 等）与 Git 一起跟踪的项目，其中一些真正的源代码提交给该 VCS 并故意在 .gitignore 中列出，因此它永远不会登陆 Git - git 从未列出这些文件，因此 CodeGraph 从未对它们建立索引，而且 includeIgnored（仅在 gitignored 目录中恢复嵌入的 git 存储库）和 exclude 都不是（其相反）可以提供帮助。添加根 codegraph.json（例如 { "include": ["Tools/", "Local/typescript/"] }），CodeGraph 会直接从磁盘发现这些文件（覆盖 .gitignore），并在 git 和非 git 项目上的完整索引、增量 sync 和文件监视上对它们进行索引。模式是 gitignore 样式，并与项目根相对路径（目录、递归 ** glob 或单个文件）进行匹配。显式的 exclude 仍然获胜，并且 node_modules、dist 和 .git 等内置跳过永远不会重新包含。这补充了现有的 exclude（其相反 - 保留跟踪文件 out）和 includeIgnored（选择 in 到 gitignored 嵌入式存储库）。

修复

  • 索引大型 Java 或 Kotlin Spring monorepo 的速度要快得多。参考分辨率阶段（首次 codegraph index 的大部分）可以在大型多模块项目上运行大约一个小时，现在只需几分钟即可完成，并生成相同的图表。原因：代码库中的每个 receiver.method() 调用都会重复扫描项目的整个配置键集以查找匹配项 - 该工作仅适用于 Spring @Value / @ConfigurationProperties 绑定，而永远不适用于普通方法调用。作为同一修复的一部分，名称与配置键一致的方法调用（例如 application.yml 中的 service.process 条目旁边的 service.process() 调用）不再错误链接到该配置键 - 它现在解析为实际方法。感谢@bayernjava 的报告。 (#1180)
  • 其 .gitignore 排除其子存储库的父存储库中的 codegraph init 不再默默地索引任何内容并报告成功。 “gitignored 子存储库的超级存储库”布局 — 一个顶级 Git 存储库，.gitignore 每个 service-*/ 或 packages/* 子存储库，因此 git status 保持安静 — 用于仅索引父级的几个顶级文件并用 0 个节点打印“完成”，即使在任何子存储库中运行 codegraph init 都工作正常（CodeGraph 尊重默认情况下为 .gitignore，因此跳过排除的子项）。现在，当索引为空时，CodeGraph 会检测到被跳过的 gitignored 子存储库，为它们命名，并在交互式终端中为它们建立索引（将 includeIgnored 条目写入 codegraph.json 并当场重新索引）；非交互式运行打印要添加的确切 codegraph.json 片段。合法地将 gitignored 引用克隆排除在工作索引之外的项目永远不会被困扰：只有当索引为空时才会出现报价。感谢@small-感谢您的报告。 (#1156)
  • MyBatis 映射器读取器在现实世界的 XML 上更加强大。单引号属性值（id='getById'，合法的 XML，在较旧的映射器中很常见）不再被跳过，因此这些语句将进入图中。用 <!-- ... --> 注释掉的语句和 <include> 不再产生幻象符号。写在一行上的两个供应商拆分声明（相同的 id 与 databaseId="oracle" / databaseId="mysql"）不再默默地删除其中一个。感谢@ESPINS 的报告、复制品和修复。 (#1182)
  • codegraph init 和 codegraph index 不再在大型方法名称密集代码库的“解析引用”步骤中被安全看门狗杀死（大型 Java/企业 monorepos 是主要受害者，尤其是在速度较慢的机器上）。过去，分辨率每 500 个引用才会出现一次，因此大量昂贵的引用可能会让看门狗挨饿足够长的时间，使其认为进程被卡住并杀死一个完全健康的索引。现在，解析在每次引用后都会检查点，并且其中两个昂贵的步骤变得更加便宜：现在缓存同一类型的重复方法查找，并且源文件不再为每个正在解析的调用逐行重新分割 - 因此，索引此类存储库的速度要快几倍。在接收器类型推理期间也会跳过生成或缩小的单行文件，而不是每次调用时进行扫描。感谢@UchihaYong 和@wangmeng-95 的报告。 (#1122)
  • 由于运行中断而留下的不完整索引现在可以在下次同步时自行修复，而不是永远默默地保持错误。如果索引在解析引用的过程中中途终止（崩溃、Ctrl-C 或上面修复的看门狗终止），受影响的文件看起来仍然有索引，但它们的调用者/影响边缘丢失 - 按包或模块聚类的爆炸半径太小，例如Spring @Resource 注入方法报告其 10 个真实调用者文件中的 3 个 - 并且由于增量同步仅重新解析已更改的文件，因此在完全重新索引之前，损坏是永久性的。任何同步（监视的文件更改或裸 codegraph sync）现在都会检测剩余的引用并完成解析它们，codegraph status 在索引处于该状态时发出警告，而不是将其视为健康，并且罕见的早期停止可能会放弃对第一个文件仅引用外部库的存储库的解析也得到修复。感谢@KnifeOfLife 的报告以及确定这一点的包相关性观察。 (#1187)
  • 共享后台服务器不再在一段时间内没有查询 CodeGraph 的实时编辑器/代理会话下关闭。一个安全计时器旨在收获一台“废弃”服务器（其 client 在连接未关闭的情况下就消失了）是 reaping 任何服务器，该服务器在 30 分钟内没有看到任何请求，包括一个完全实时的会话，只是没有向 CodeGraph 询问任何内容；在其余下的生命周期中，默默地将会话（以及共享同一后台服务器的所有其他会话）降低到较慢的进程内模式。在一台机器上，一天内它会在现场会话中发射 20 次，并捕获零个真实幻影。计时器现在会检查连接的 client 是否实际上仍然存在，并且只有在没有一个存在时才进行收获，因此安静但活跃的会话会保留其共享服务器，而真正废弃的会话仍会被清理。 （＃1200）
  • 当您的编辑器或代理在启动期间终止其启动器时，CodeGraph 的后台服务器不再留下延迟的 Node 进程。如果启动 CodeGraph（Codex、Claude Code 或另一个 MCP client）的应用程序在服务器的第一分之一秒内被终止（配置探测、取消的请求、启动超时），同时保持连接管道打开，则服务器可以在其孤立检测看门狗捕获参考点之前将其移交给系统，使其保持运行（空闲，约 30 MB），直到启动应用程序本身退出；经过一整天的反复发射，这些积累起来了。服务器现在尽早记录其父级，并且 npm 和独立启动器将真实主机的进程 ID 传递给它，以便它可以直接监视主机，而不仅仅是可能已经消失的启动器。作为最后的后备方案，启动后从未收到单个请求的服务器现在会自行关闭，而不是等待主机退出 - 可通过 CODEGRAPH_STARTUP_HANDSHAKE_TIMEOUT_MS 进行调整（0 禁用）。感谢@ruslan33321 的报告。 (#1185)
  • Claude Code 的自动上下文挂钩现在可以回答近三十种语言提出的结构问题——法语、西班牙语、葡萄牙语、德语、意大利语、荷兰语、波兰语、捷克语、罗马尼亚语、匈牙利语、希腊语、瑞典语、丹麦语、挪威语、芬兰语、俄语、乌克兰语、土耳其语、印度尼西亚语、越南语、泰语、印地语、阿拉伯语、波斯语、希伯来语、日语、韩语，以及简体中文和繁体中文——而不仅仅是英语和简体中文。以前是一个自然问题，例如“comment Marche la state machine des commandes？”除非它碰巧包含代码形状的符号名称，否则不会注入任何内容，这使得钩子对于非英语团队来说看起来很糟糕。用派生词形式表达的英语问题（“解释架构……”、“依赖关系是什么……”）现在也会触发，并且当他们从索引中命名符号时，任何其他语言的提示仍然会触发。感谢@anthonyle-roy-lgtm 的报告。 (#1126)
  • 使用 capitalized 名称（obj:Method() — 标准 Roblox 约定）的 Lua 和 Luau 方法调用现在链接到正确的方法。因为 Lua 的方法调用语法看起来与 Luau 类型注释相同，所以像 lg:Log() 这样的 capitalized 调用会被误读为声明变量的类型，因此每当两个或多个类共享方法名称（Init、Update、Destroy 等）时，调用就会从调用者、影响/爆炸半径和流跟踪中悄悄删除。小写方法名称不受影响。感谢@inth3shadows 进行精确的根本原因分析和重现。 (#1124)
  • 删除了已停止的管理推理功能留下的死代码。它的 codegraph login 流程在发布之前就被拔掉了，但未使用的模块仍然在平台捆绑包内发货，并且安全审查标记了其 Windows 浏览器打开步骤（它通过 cmd 路由登录 URL，如果流程重新连接起来，这将是不安全的）。剩余的模块及其测试现已完全删除。感谢@inth3shadows 的报告。 (#1114)
  • Claude Code 上下文挂钩不再将仅以“call”、“trace”、“affect”或“connect”开头的普通英语单词（callus、calligraphy、Connecticut、connective、emotionate、Tracey）视为结构问题，用于将完整的 CodeGraph 上下文注入与代码结构无关的提示中。真正的结构形式（调用、调用者、回调、调用站点、跟踪、跟踪、受影响、连接、连接性……）仍然像以前一样触发。感谢@inth3shadows 的报告。 (#1138)
  • 卡住的 git 命令不再无限期地挂起 CodeGraph。工作树检测和 git-hook 设置后面的 git 检查，以及安装程序的可选 npm install -g 步骤，现在会超时并优雅地失败，而不是永远阻塞——这对于后台 MCP 服务器来说最重要，其中无限制的 git 挂起（网络文件系统、楔形 fsmonitor）可能会事先将其冻结足够长的时间，以便安全看门狗将其杀死。感谢@inth3shadows 的报告。 (#1139)
  • 上下文挂钩的新纯字匹配可立即在由旧 CodeGraph 版本索引的项目上运行。它所依赖的单词查找是在索引时构建的，因此升级之前索引的项目是空的，钩子会默默地找不到任何东西，直到发生其他事情刷新索引；现在，钩子会在第一次使用时填充它（一次性步骤 - 通常后台 MCP 服务器的启动追赶会首先到达那里）。感谢@inth3shadows 的报告。 (#1142)
  • 对纯单词匹配的几个准确性修复：重命名的符号（例如应用模块前缀后的 NestJS 路由）在其新名称下仍然可找到（#1141）；仅作为 import 语句的包名称出现在代码中的单词不再显示为匹配符号 (#1144)；复数单词不再生成乱码的查找键（“services”不再查找“servic”）（#1145）；并且与一个单词的单数和复数相匹配的名称不再能够挤出真正的两个单词匹配（#1146）。感谢@inth3shadows 的报告。
  • 严重反映的虚幻引擎 C++ 类不再从索引中删除。装饰成员的反射标记 - UPROPERTY(...)、UFUNCTION(...)、UCLASS(...)、GENERATED_BODY()、UE_DEPRECATED_*(...)、DECLARE_DELEGATE_*(...) - 是树守护者无法识别的无分号宏调用，因此每个都会陷入错误恢复；在一个大类中，错误会堆积起来，直到整个 class_specifier 崩溃，并且该类、其基本子句及其成员消失（UCharacterMovementComponent 具有约 240 个这样的宏，完全消失，破坏了通过它的每个子类/类型层次结构和爆炸半径查询）。现在，这些行前注释宏在解析之前被清空（保留偏移量），以便类得以保留。感谢@luoyxy 的报告和根本原因分析。 （第1093章 后续）
  • 以导出/可见性宏为前缀的虚幻引擎成员和方法不再丢失。 *_API 宏不仅位于类标头中，它还为大型 UE 类（ENGINE_API virtual void Tick(...)、static ENGINE_API void AddReferencedObjects(...)）的几乎每个导出成员添加前缀；解析器将宏作为额外的类型标记读取，并且每个此类声明都会陷入错误恢复，因此在 Actor.h 和 World.h 等标头上，数百个返回类型堆积为孤立错误，并且仍然可能导致类崩溃。成员/方法级 *_API / *_EXPORT / *_ABI 宏（Unreal、Qt/Boost、LLVM）现在在解析之前被清空，镜像现有的类头恢复。 （第1093章 后续）
  • 出现在中线的虚幻引擎注释宏——枚举值的 UMETA(DisplayName=...)、参数的 UPARAM(ref) 或嵌入 using 别名的弃用标签（using FOnNetTick UE_DEPRECATED(5.5, "...") = ...;，它单独折叠了 World.h 中的 UWorld）——现在也被删除。这些位于领先的恢复在结构上无法到达的位置，并且单个恢复可以击倒周围的枚举或类。它们与仅 Unreal 的名称列表（UMETA、UPARAM、UE_DEPRECATED*）相匹配，因此标准 C++ 或其他库代码不会受到影响。这三个修复一起恢复了测试的每个大型虚幻引擎标头的主要类（Actor、ActorComponent、SkeletalMeshComponent、World、LightComponent、CharacterMovementComponent）。 （第1093章 后续）
  • 唯一的 C++ 信号是导出宏注释类的 C++ 标头不再被误检测为 C — 它已默默地删除了该类。 .h 文件默认为 C，并且仅在显示特定于 C++ 的构造时才重新分类为 C++，但该检查无法通过导出/可见性宏进行查看：class ENGINE_API UFoo : public UObject 与宏盲 class Name : 模式不匹配，因此精简的虚幻引擎样式标头仅包含 GENERATED_BODY() 而没有显式的 public: / virtual / namespace / template 被解析为 C。C 提取器不发出类节点，因此该类及其继承链接从图中消失，悄悄地撤消了 #1061 中添加的宏类恢复。 C++ 检测启发式现在可以识别带有导出宏注释的 class/struct 声明（解析前相同的形状 #1061 空白），与已检测到的 class Foo : Bar 的方式相匹配； [:{] 之前的两个令牌 <keyword> <MACRO> <Name> 永远不会出现在有效的 C 中，因此真正的 C 标头不受影响。感谢@luoyxy 的报告和根本原因分析。 (#1133)
