codegraph v1.6.0

小版本 发布时间2026年8月26日 来源colbymchenry/codegraph 英文原文

codegraph v1.6.0

这个项目是干啥的：把代码库画成一张能查询的关系图谱，让 AI 和人都快速搞清代码结构、谁调用了谁。给想理清大型项目的开发者用。

[1.6.0] - 2026-08-26

变更架构图

亮点

  • 现在支持 GitHub Copilot — codegraph install 在 VS Code、Copilot CLI 和 JetBrains IDE 中将其设置在它已经知道的代理旁边。
  • 通过一个命令进行设置 — codegraph install --yes --init 连接您的代理并在没有提示的情况下索引您的项目，非常适合新容器或 CI。
  • 为您的代理提供更好的答案 — codegraph_explore 不再重复它已经向您展示的代码，总是带回您按名称要求的文件和符号，并将其空间花在实际回答问题的代码上，而不是看起来相似的代码、生成的文件和类型填充程序上。
  • 当您继续编码时，您的图表保持正确 — 长期运行的索引不再与新索引发生偏差，并且对 codegraph.json（例如 exclude）的编辑立即应用，无需重新启动。
  • 不再出现静默崩溃或挂起 - 深度嵌套的 C/C++ 文件、Swift Vapor 项目以及用于终止或停止索引的大型同步批次现在可以干净地完成。
  • 磁盘空间泄漏已修复 - 强制终止会话可能会使数据库的预写日志无限增长（据报告为数十 GB）；剩余的日志现在会折叠回索引中，并在下次项目打开时自动修剪。索引本身没有大小限制。
  • 在工作区或 monorepo 根目录中工作 — MCP 服务器在从其上方的文件夹启动时找到您的索引项目，并在找不到项目时清楚地说明。
  • TypeScript、Rust、Erlang、C/C++ 和 Python 项目的 更准确的代码图 - 请参阅下面的完整列表。
  • 另外还有：每个项目的 Codex 设置 (codegraph install --location=local)、一个 deprioritize 设置（用于防止帮助程序文件夹的排名超过您的真实代码）、codegraph context 命令以及现在完全保留在 CodeGraph 自己的服务器上的使用统计信息。 升级后，在每个项目中运行一次 codegraph index ，以便您现有的图表可以获取这些修复 - codegraph status 会在需要时提醒您。

新功能

  • GitHub Copilot 现在是受支持的代理：codegraph install 可以在 VS Code 中配置 Copilot Chat (copilot-vscode)、GitHub Copilot CLI (copilot-cli) 以及 JetBrains IDE 中的 Copilot 插件 (copilot-jetbrains)。与所有其他代理一样，已安装的 Copilot 界面会被自动检测，其配置文件中的现有 MCP 服务器条目将被保留，并且 codegraph uninstall 会干净地反转设置。安装后重新启动 VS Code 或 JetBrains IDE，以便 Copilot 启动服务器。
  • codegraph install --init 连接您的代理并在一个命令中构建当前项目的索引，并且 codegraph init --yes 运行时没有任何提示 - 因此新的容器或 CI 作业可以使用单个非交互式行 (codegraph install --yes --init) 引导 CodeGraph。安装程序仍然不会索引任何内容，除非您使用标志请求它，并且适用于主目录或文件系统根目录的通常安全拒绝。 (#1578)
  • Codex CLI 现在可以按项目设置，而不仅仅是在用户范围内设置：codegraph install --location=local 将 ./.codex/config.toml 和 CodeGraph 块写入项目的 AGENTS.md 中，因此 CodeGraph 仅连接到该存储库，而不是连接到计算机上的每个 Codex 会话。 codegraph uninstall --location=local 颠倒了它，全局安装无论如何都保持不变。 Codex 仅在您将项目标记为 trusted 后才应用项目的配置，因此安装程序在本地安装后会如此说明。谢谢@maxmilian。 (#1531)
  • codegraph.json 中的新 deprioritize 设置可防止您命名的路径在搜索和 codegraph_explore 答案中的排名超过产品代码，而无需从索引中删除任何内容。它采用 gitignore 风格的模式，就像 exclude 一样，但仅排名：辅助脚本树、生成的输出或可选的附加目录，其通用符号名称（usage、run、status）否则会排挤实际回答查询的代码，保持完全索引和可查找 - 真正针对此类树的查询仍会返回它。谢谢@maxmilian。 (#982)
  • codegraph_explore 不再重新发送在同一对话中先前已返回的源。它已经向您显示的文件以短指针形式返回 - 路径、符号和确切的行范围，并确认该文件此后没有更改 - 并且释放的空间用于您尚未见过的代码，因此后续调用会覆盖新的领域，而不是重复上一个。如果在其间编辑了文件，则其源代码始终会再次完整显示。设置 CODEGRAPH_EXPLORE_DEDUP=0 将其关闭。
  • 当代理通过 MCP 连接时，CodeGraph 现在会预先声明它索引了 30 多种语言 - TypeScript/JavaScript、Python、Go、Rust、Java、C#、C/C++、PHP、Ruby、Swift、Kotlin 等 - 因此代理不再假设某种语言不受支持并跳过图表。 （#671）
  • 匿名使用遥测现在完全存储在 CodeGraph 自己的第一方基础设施上 - 没有第三方分析供应商接收任何数据，并且接收它的端点根本不发出出站请求。个别事件将在 90 天后删除，仅留下匿名的每日总计。所收集的内容没有任何变化，您的 IP 地址仍然不会被读取或存储，并且每个关闭开关都像以前一样工作（codegraph telemetry off、CODEGRAPH_TELEMETRY=0、DO_NOT_TRACK=1）。 TELEMETRY.md 仍然是完整的逐字段列表。

修复

codegraph_explore 的更好答案

  • 在 codegraph_explore 查询中按文件路径命名现在可以可靠地工作：根据索引解析路径，并且保证该文件位于答案的顶部。以前，路径被分成碎片 - 像 SvelteKit 的 [id] 这样的括号内的路线段使情况变得更糟 - 而像 page 或 runs 这样的片段与每个同级文件相匹配，因此您实际命名的文件可能会完全被排除在答案之外。与任何索引文件都不匹配的路径现在会被调出，而不是默默地忽略。
  • 在 codegraph_explore 查询中命名一个 kebab-case 文件不带扩展名 - background-image-table 而不是 background-image-table.tsx，导入路径和散文拼写它的方式 - 现在也返回该确切的文件。以前，名称是在连字符处分割的，并且在烤肉串前端中，这些片段（background、image、table）是代码库中最常见的单词之一，因此看起来相似的兄弟文件填充了答案，而命名文件从未出现。不命名索引文件的连字符单词（例如“交叉调用”或“非阻塞”）将被保留。
  • 措辞简单的 codegraph_explore 问题现在可以找到驼峰式代码：像“自动滚动到底部”这样的查询可以到达名为 scrollFeedToBottom 的函数，因为查询单词与标识符内的单词匹配，而不仅仅是整个名称。
  • 当 codegraph_explore 选择其起始符号时，变量和常量现在会被计数，因此普通变量中保存的状态（例如 Svelte 中的 $state 样式变量）不再被忽视。
  • codegraph_explore 现在将其答案集中在实际回答您的问题的代码上，而不是将其分散到仅与之共享单词的文件中，因此一次调用即可获得更多答案。感谢@LeDuyViet 的详细测量和复制。 (#1500)
  • 与您的问题仅弱相关的文件现在以名称、符号和行号的形式返回，而不是在其来源上花费答案 - 在后续的 codegraph_explore 中命名其中一个文件即可完整返回。 (#1500)
  • 生成的 CRUD 或 protobuf 层不再排挤旁边的手写代码：生成的文件现在可以通过文件顶部写入的 // Code generated by … DO NOT EDIT. 样式横幅来识别，而不仅仅是通过看起来生成的文件名来识别。升级后重新索引以获取新的检测。 (#1500)
  • 存储库顶级 test/ 或 spec/ 目录中的测试和规范文件现在已被识别，因此它们不再占用您询问的代码的空间。 (#1500)
  • 生成的类型声明文件使用“由……通过运行……生成”横幅（Cloudflare Wrangler 的 worker-configuration.d.ts 是常见的）来声明自己，现在被识别为已生成。以前，类似的文件可能只需要几个常见单词就可以得到 codegraph_explore 的大部分答案，从而将您询问的手写代码完全排除在响应之外。升级后重新索引以获取新的检测。
  • 手写的类型声明文件 - 全局填充程序、供应类型、模块增强的环境 .d.ts - 不再接管有关某些内容如何工作的 codegraph_explore 答案。此类文件声明通用名称（Body、Message、ImageMetadata），仅此而已，因此，一个措辞简单的问题可以与一个足够强的问题匹配，使其排名第一，并将实际处理程序排除在答案之外。现在，他们在有关行为的问题上排名较低，并且仍然按名称列出，因此后续调用即可获取它们。按名称询问类型仍然首先返回其声明，并且其余代码导入的共享类型模块不受影响。
  • 当您在 codegraph_explore 查询中命名符号时，它的定义现在实际上会返回。之前有两起案件都丢失了。如果您命名的符号不互相调用（同一工厂或模块内的兄弟函数就是日常示例），CodeGraph 就会停止将它们视为您所要求的符号，而是用文件顶部的任何内容来回答；在一个 1,400 行的文件中，这意味着第 70 行的同干 QueuedMessage 接口返回，而第 1087 行的 queueMessage 函数没有返回。当必须修剪答案以适应时，它会从文件底部向下修剪，因此长文件末尾附近的符号始终是第一个被剪切的东西。现在，修剪可以保护您命名的定义，无论它们位于文件中的哪个位置。
  • 围绕一个很长的函数构建的文件不再占用整个 codegraph_explore 答案 - 或者从其中消失。以前，这样的文件无论有多大，都会完整显示，这会耗尽每个文件所需的空间，并且当函数大于整个响应时，文件会被一言不发地删除。这些文件现在作为整行上的有界窗口返回 - 签名和正文顶部，加上调用路径穿过它时的调用站点 - 其余的后续 codegraph_explore 离开。
  • codegraph_explore 不再让答案中的第一个文件占用为其下面的文件预留的空间，因此答案的其余部分仍然会到达。以前，靠近顶部的大文件可能会悄悄地用完剩下的所有内容，而位于其下方的文件（每个文件都已被判断为足够相关，可以包含在内）会被丢弃，根本没有来源；在一个问题上，只有六分之一得到了答案。现在，每个文件都保留了它所提供的内容，并且真正与一个文件有关的问题仍然集中在该文件上。
  • 当 codegraph_explore 答案运行到其大小限制时，它现在会删除尾随注释而不是整个文件的源。以前，即使仅修剪音符就可以容纳最后一个文件，因此已经读取、排序和渲染的文件在最后一刻被丢弃。在一系列实际项目中，每次调用都会多返回一个文件和最多 20% 的源代码。
  • codegraph_explore 决定包含的每个文件现在都已实际到达。完整显示的文件仍然可能会为其下面的文件预留空间 - 上面的修复覆盖了显示为摘录的文件，但没有显示完整的文件 - 并且答案本身的大小簿记低估了每个文件的标题，因此答案超出了其限制，最终丢弃了完全准备好的文件。现在，不再适合整个文件的文件会显示为摘录而不是消失，稍微超出一点的文件会被修剪以适应而不是删除。
  • 当答案已满时，答案无法涵盖的文件列表（“探索这些名称的来源”指针）不再被丢弃。现在它已经做好了预算并进行了修剪以适应，因此完整的答案仍然会告诉您它遗漏了什么以及接下来要询问哪些名字，而不是以根本没有任何指示而结束。
  • 当 codegraph_explore 答案将文件显示为摘录时，不再适合的大摘录将被完全删除而不是被缩短。如果文件的第一个摘录碰巧是一个微不足道的摘录（一个导入块，您询问的代码旁边的一个单行帮助程序），则携带实际答案的摘录将被丢弃，并且文件返回时会保留给定空间的四分之一。在实际项目中，这意味着排名靠前的文件交付了其份额的一小部分，而相关性低得多的文件则占据了其余部分。现在，摘录会被缩短以适合整个方法，并且只有当剩下的内容太小而无法容纳任何可读内容时才会被删除。
  • 每当没有测试直接调用符号时，codegraph_explore 的爆炸半径部分就会标记为“未发现覆盖测试”——错误地将通过调用者进行测试的帮助程序标记为未经测试（测量样本中大约有 40% 的标记符号）。该检查现在跟踪调用者链最多 3 个跃点，并将间接覆盖报告为“通过调用者测试”；当没有找到任何内容时，它会准确说明所检查的内容，而不是无条件警告。感谢@inth3shadows 测量误报率。 (#1475)
  • 当文件在上次索引同步后在磁盘上发生更改时，codegraph_node 和 codegraph_explore 可以在请求的名称下返回不同的符号代码（在过时的行位置剪切当前文件字节），同时将其逐字呈现，trust 值得源。这对通过 projectPath 查询的项目（例如 monorepo 的子项目）影响最严重，这些项目没有实时文件观察器来标记待处理的编辑。现在，这两种工具都会在显示切片代码之前根据索引验证每个文件：过时的文件要么以其完整的当前源完整显示，要么以明确的“磁盘上已更改”通知保留其代码 - 永远不会用作错误的切片。全新的重新索引会自动恢复正常输出。感谢@inth3shadows 提供的详尽报告和验证通过。 (#1474)

查找您的项目、实时更新和 CLI

  • MCP 服务器现在在从其上方的工作区文件夹启动时找到您的项目：如果启动目录没有自己的索引，但其下方正好有一个索引项目（存储库容器、代理工作区、monorepo 根），则该项目将成为会话的默认项目（实时文件监视和共享守护程序），而不是每个工具调用都会失败，直到提供 projectPath 或 --path。谢谢@nakisen。 (#1606)
  • 当根本无法解决任何项目时，MCP 服务器现在会这样说，而不是默默启动：启动日志行为其搜索的目录命名，工具调用列出它可以在附近看到的索引子项目，以便您可以将一个作为 projectPath 传递。以前，服务器从外部看起来很健康，而每个工具却悄悄地没有项目可以响应。谢谢@nakisen。 (#1607)
  • 在 MCP 服务器运行时编辑 codegraph.json 的 exclude 或 include（或 .gitignore）现在会立即生效。以前，正在运行的文件观察程序会保留其启动时的范围，因此新排除的文件会被 codegraph sync 删除，然后在几秒钟后由观察程序悄悄地重新添加（看起来 exclude 根本不起作用），直到服务器重新启动。现在，范围更改会刷新观察程序并触发完全协调，并且首先根据当前范围重新检查观察程序要同步的已更改文件，因此 CLI 和实时服务器不再对索引中的内容存在分歧。谢谢@K1nG11。 (#1590)
  • codegraph status 现在可以在全新目录中看到新文件。 Git 将完全未跟踪的目录报告为单个折叠条目，因此在那里创建的源文件（例如，新搭建的 frontend/）在待更改报告中丢失，该报告可能声称所有内容都是最新的，而这些文件尚未建立索引。谢谢@maxmilian。 (#1213)
  • CLI 帮助中记录的 codegraph context <task> 命令现在实际存在 - 它为 Markdown 或 JSON 中的任务（相关符号、它们的关系和代码）构建了一个准备注入的上下文包，恢复了 Memorix 所依赖的合约外部集成（--path、--format json、--max-nodes、--no-code）。 (#1611)
  • 在 Windows 上，当钩子通过 Git Bash 运行时，由 codegraph install 编写的 Claude Code 提示钩子会失败，并显示“未找到命令”，这需要 .cmd 扩展来查找启动器。安装程序现在会编写平台正确的命令，并重新运行 codegraph install（或 codegraph upgrade）就地修复现有安装。 (#1466)
  • 按名称查找符号不再读取整个图表。每次搜索都会对您输入的每个单词的所有索引符号进行一次完整遍历，而命名多个符号的问题会对每个名称进行两次遍历 - 包括对不匹配任何内容的单词，这是常见的情况。因此，成本随着项目的规模而增长，并且当启用提示挂钩时，每条消息都会再次支付费用。这些查找现在改为通过名称索引。结果相同；只是获取它们的时间发生了变化，并且它不再随着项目而增长。谢谢@maxmilian。

索引可靠性和磁盘使用情况

  • 在具有极深嵌套的 C/C++（或任何其他）文件（例如 clang 和 gcc 测试套件或模糊器语料库中的解析器压力测试装置）上，索引不再使整个过程崩溃（没有消息且没有部分索引的分段错误）。这样的文件现在被交给后备解析器并记录解析警告，而存储库的其余部分则正常索引。感谢@apollo600 的准确诊断。 (#1581)
  • 索引不再挂在包含带有长参数列表的调用的 Swift Vapor 项目上。具有许多标记参数且没有 use: 处理程序（形状生成的请求构建器生成）的单个 .get(...) 样式调用可能会无限期地拖延 codegraph index、codegraph sync 和 MCP 服务器。路线检测现在可以在几毫秒内处理此类文件，并且每个先前识别的路线形状仍然可以像以前一样进行解析。谢谢@maxmilian。 (#1544)（斯威夫特）
  • 同步大量更改的文件不再因“超出最大调用堆栈大小”而崩溃。在文件的符号已经存储后，崩溃中止了引用解析，使得图形的连接比新索引少得多 - 并且它恰好遇到了一次重新解析许多文件的场景，包括上面的自动修复。感谢@netbrah 指出了故障。 (#1558)
  • 长期存在的索引不再偏离新 codegraph index 产生的结果。当一个文件获得或丢失一个符号时，同步从未触及的文件中对该名称的引用会一直指向更改之前正确的定义，而且——因为没有任何东西可以区分两个同名的定义——获胜者可以归结为文件的写入顺序，这在完整索引和同步之间是不同的。在这个项目自己的存储库上，通过 ZZPH100​​ZZ 重放 80 次提交导致 5.7% 的连接错误；现在是 1.3%，而仍然断言错误答案的一半下降了 99.7%。由于调用边缘是流程问题所遵循的以及 codegraph_explore 对文件进行排名的依据，因此随着索引的老化，这个答案会悄然降级，没有任何迹象表明这一点。同步速度没有变化，并且仅更改函数主体的编辑根本不做任何额外的工作。将 CODEGRAPH_NO_REBIND=1 设置为选择退出。
  • 修复了 v1.5.0 回归，其中完全有效的文件可以永久记录为具有 0 个符号，并且不会报告错误。当文件的第一次解析尝试被中断时（解析工作器崩溃或超时，很可能是在缓慢或负载过重的计算机上），自动重试会在本机提取路径上的任何语言中存储空结果，因此文件的函数和类会从搜索、调用者和影响中悄悄消失，直到下一次编辑文件。重试现在会存储文件的真实符号，并且升级后的下一次同步或重新索引会自动检测并修复已记录为无符号的文件。感谢@Baiae 的报告。 (#1541)
  • 被卡住的进程看门狗、崩溃或操作系统强制终止的 CodeGraph 进程不再让数据库的预写日志无限制地增长。以前，每个被终止的会话都会将更多数据堆积到同一个日志文件中，并且不会缩小它，在定期终止会话的计算机上，这些数据可能会悄悄地占用数十 GB 的磁盘空间。日志的静态大小现在受到限制（默认为 64 MB；CODEGRAPH_WAL_HEAL_MB 更改了它），任何过大的剩余部分都会折叠回索引中，并在下次打开项目时自动修剪。这仅限制日志 - 索引本身没有大小限制，并且大型存储库的日志在构建时仍然允许与其索引成比例增长。感谢 @tiendungdev 提供的出色的 Windows 报告证实了这一点。 (#1431)
  • 后台服务器的看门狗不再杀死正在慢速磁盘上等待的健康服务器：就像索引已经做的那样，它现在在得出进程被卡住的结论之前检查数据库文件是否仍在进展。更少的虚假杀戮也意味着更少的剩余预写日志。 (#1431)
  • codegraph status 现在在数据库大小旁边显示预写日志的大小，并在被终止的会话使其过大时发出警告，并且后台服务器日志中的每一行现在都带有时间戳，因此可以及时放置终止和重新启动。 (#1431)
  • 当操作系统重用其进程 ID 时，由内存不足终止或强制终止留下的后台守护进程不再阻止每个未来会话：守护进程管理现在会在 trusting 或向其发送信号之前验证记录的进程是否确实是 CodeGraph 守护进程，并且 codegraph unlock 会清除过时的守护进程工件以及索引锁。感谢@hcg1023 的报告和@danusha2345 的修复。 (#1553)
  • 当索引必须回退到解析一个删除了注释行的文件时（重复解析器崩溃后的最后恢复手段），该文件现在会被标记为可见警告，而不是被报告为已干净索引。恢复的结果可能不完整，并且报告成功使得新的索引悄悄地与稍后重新解析同一未更改的文件不一致。感谢 @jeremypetz 提供的精确的初始化与同步符号计算，揭示了这一点。 (#1565)
  • 接近文件大小限制的纯数据 C/C++ 标头在超时之前不再将解析器工作器占用几分钟；默认的大文件解析预算现在受到限制，同时仍遵守显式配置的较大超时。 (#1555)
  • 在批量加载期间崩溃后重新打开索引现在可以恢复每个删除的数据库索引，并且成功的恢复同步将索引标记为完整，而不是将其永久标记为已中断。 (#1556)
  • 由于太大或反复解析失败而跳过的文件现在会记录原因，因此未更改的拒绝文件不再被 redis 覆盖并在每次状态检查和同步时重试 - 并且稍后成功解析此类文件会用其真实符号替换记录。感谢@netbrah 对该批次背后的异常故障分析，以及@danusha2345 的修复。 (#1557)
  • C/C++ 函数指针分析现在限制其编译模式缓存，因此非常大的存储库在索引期间不再耗尽 JavaScript 引擎的正则表达式代码空间。 (#1559)
  • JSX 渲染分析现在仅在 JavaScript 系列文件上运行，因此 C/C++（或任何其他语言）中的 JSX 外观字符串不再创建不可能的调用边缘 - 在纯 C 项目和混合语言 monorepos 中都是如此。 (#1560)

语言和框架的准确性

  • 对导出的对象文字常量的方法的调用 - export const api = { call() { … } } 用作模块的命名空间，组织 TypeScript API 表面的常用方法 - 现在解析为该方法，无论是在定义文件中还是通过导入。以前，此类调用与任何内容（或常量本身）无关，因此 codegraph callers 和影响分析报告从任何地方调用的方法的调用者为零。升级后重新索引以拾取边缘。感谢@IAliceBobI 提供的准确报告和根本原因。 (#1573)
  • 现在可以选择共享 TypeScript 配置中定义的导入别名。 Nx 风格的 monorepos 将每个 @scope/... 别名保留在 tsconfig.base.json 中，根 tsconfig.json 仅通过 extends 继承，因此 CodeGraph 根本没有发现任何别名，并且每个跨包导入都回退到仅匹配名称 - 这会悄悄地将结果附加到碰巧共享名称的不相关符号，这正是 monorepo 需要 codegraph_impact 和 codegraph_callers 的地方对。深度链接多个配置，从 node_modules 中的包继承的配置以及在继承的配置中声明的 baseUrl 现在都遵循，并且当根 tsconfig.json 只是项目引用 shell 或根本不存在时，直接读取 tsconfig.base.json。升级后重新索引。谢谢@maxmilian。 (#1534)
  • 在通用或生命周期参数化 impl 块（impl<T> Source for BufSource<T>、impl<'a> Iterator for Parents<'a>）中实现的方法现在记录在实现类型而不是特征下。以前这样的方法无法通过其类型找到 - “谁调用 BufSource::read” 没有答案 - 并且它与特征自己的声明相冲突，这甚至可能从根本不包含调用的 impl 主体中发明一个调用图边缘。引用 (impl Trait for &Foo) 和模块限定类型 (impl Trait for m::Foo) 上的 impl 也归因于它们的类型。升级后重新索引。谢谢@Dshuishui。 (#1588) (Rust)
  • 对结构体字段（self.inner.run() 和 inner: Inner）的方法调用现在解析为字段声明类型上的方法。以前，调用被简化为裸方法名称，并匹配最接近的同名方法，这通常是调用方法本身，记录源中不存在的递归（仅在 ripgrep 中就有数百个这样的自边），或不相关类型的方法。参考文献和 Box/Rc/Arc 字段都会被查看，就像 Rust 自己的方法调用一样；类型为外部（std 或第三方类型）的字段、泛型参数或 Option/Vec 之类的容器未解析，而不是猜测。升级后重新索引。谢谢@Dshuishui。 (#1585) (Rust)
  • 共享名称但数量不同的 Erlang 函数现在是具有语言自己的 module:fun/arity 身份的单独符号，因此委托给 f/2 的日常 f/1 显示为真正的调用边缘而不是自循环，每个数量保留自己的 -spec 和源范围，-export([f/1]) 将该数量准确地标记为公共，并询问 codegraph_explore一个按照 Erlang 拼写方式的符号 — cowboy_req:header/3 — 返回该定义。升级后重新索引 Erlang 项目。谢谢@Dshuishui。 (#1610) (二郎)
  • 当参数是像 <<1,2,3>> 这样的二进制文字时，Erlang 行为分派不再错误计算调用站点的数量 - 内部的逗号被计为参数分隔符，它会默默地删除（或可能错误链接）行为回调的分派边缘。 (#1358) (二郎)
  • 唯一的 C++ 构造是普通派生类型的 C++ .h 标头（没有导出宏、class 关键字或访问部分的 struct Derived : Base）现在被识别为 C++（以前只有导出宏形式）。这样的标头被读取为 C，因此派生结构从索引中消失，并以基类型命名的幻像函数出现在其位置。现在检查还覆盖整个文件而不是前几千字节，因此长的 C 兼容前导码不再隐藏信号。升级后重新索引以获取受影响的标头。谢谢@Jaysenpeng。 (#1592)
  • C、C++、Objective-C 和 Rust 联合现在被索引为一流的 union 节点。 union 声明以前根本不产生任何符号，因此它从未出现在搜索或 codegraph_explore 中，并且附加到它的任何内容都随之消失 - 在 Rust 中，每个 impl SomeTrait for MyUnion 都失去了其边缘，该实现中的方法被留下指向图表不包含的类型，并询问哪些类型实现了特征，悄悄地跳过了联合类型。 C 中的联合形分派表现在像结构体形分派表一样解析其函数指针。 C 中的 typedef union { … } Name; 保留 typedef 的名称，并且不再被误认为是普通类型别名。谢谢@ctype-lab。升级后重新索引以获取现有项目中的联合。 (#1515)
  • 用作值的 Python 类 - 来自工厂方法的 return SomeSerializer、handler = SomeClass 别名、注册表字典和列表以及作为参数传递的类 - 现在在图中生成参考边。以前这些习惯用法是不可见的，因此在 Django 和 Django REST Framework 项目中，询问序列化程序的调用者或编辑它的影响会错过实际使用它的视图。升级后重新索引以获得新的优势。 (#1478)
  • SAP HANA .xsjs / .xsjslib 导入现在可以跨文件解析：.xsjs 文件中的无扩展名 import { x } from './helpers' 会找到 helpers.xsjslib，因此会创建跨文件调用边缘，并且 codegraph_callers / codegraph_impact 会看到它。以前，导入路径解析为空，并且调用回退到同名匹配，这可能会将边缘绑定到恰好导出相同符号的不相关文件。补充 .xsjs / .xsjslib 提取支持。谢谢@maxmilian。 (#556)
