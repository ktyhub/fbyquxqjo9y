codegraph v1.5.0

[1.5.0] - 2026-07-21

⚡ Rust 引擎发布 — 近乎即时同步

此版本将 CodeGraph 的解析引擎重建为本机 Rust 内核，彻底检查了其周围的解析管道，并使实时图有效地即时：现在即使在 27,000 个文件的存储库中，保存也能在不到一秒的时间内到达图。这是该项目历史上最大的性能升级 - 每个图形都经过逐字节验证，与之前的引擎相同。

  • 原生 Rust 解析 20 种语言 - TypeScript、JavaScript (+TSX/JSX)、Java、Python、Go、C、C++、Rust、C#、Ruby、PHP、Swift、Kotlin、Scala、Dart、R、Lua 和 Luau 现在在编译的 Rust 中进行解析内核（Metal 和 CUDA 走 C++ 道路）。没有预构建二进制文件的平台以及存在语法错误的单个文件会自动回退到以前的引擎 - 无论哪种方式都是相同的图，在从小库到 Linux 内核的存储库上得到了证明。
  • 适应您的机器 — CodeGraph 根据系统实际拥有的内容调整其解析工作器、解析器池和缓存的大小：真实核心数量（容器/cgroup 感知，而不是主机的）、macOS 和 Linux 上的诚实可用内存以及测量的每个项目解析成本。大型工作站拥有完整的并行管道； 2 核 VPS 的管道经过调整，可以可靠地完成，而不是耗尽内存——Linux 内核（70k 文件）索引在 2 核、6GB 机器上在 12 分钟内完成——比本周期开始时的 26 分钟有所下降。
  • 整体分辨率显着加快 - 自适应并行分辨率、更智能的候选方法查找以及记忆超类型/一致性行走。在此发布周期内，Swift 编译器存储库（27k 文件，Swift + C++）从 3 分钟多缩短到约 100 秒； Rust、Lua 和 Java 系列项目都实现了两位数的改进。
  • 同步现在几乎是即时的 - 即使在编译器规模下，保存也能在不到一秒的时间内到达图表。始终在线的观察程序在 300 毫秒的安静窗口后触发，用于单独保存（编辑的爆发仍然合并），并将精确更改的路径进行同步，而不是重新扫描整个树 - 在 4,400 个文件的 Java 项目上测得的保存到新鲜图工作约为 0.3 秒，在 27,000 个文件的 Swift 编译器存储库上测得约为 0.4 秒，与完全协调的字节相同。 完整详细信息请参见下面的条目。

新功能

  • 索引 TypeScript、TSX、JavaScript、JSX、Java、Python、Go、C、C++、Rust、C#、Ruby、PHP、Swift、Kotlin、Scala、Dart、R、Lua 和 Luau 项目速度更快：当预构建的二进制文件可用于您的平台时，解析和符号提取现在在本机引擎中运行（发行包包括一个），生成完全相同的图表 - 在真实存储库上针对以前的引擎进行逐字节验证，从小库到 vscode-、dubbo-、django-、git-、protobuf-、tokio-、rust-analyzer-、jellyfin-、rails-、symfony-、swift-nio-、kotlinx.coroutines-、ggplot2-、Kong-、 Scala-3 编译器和 Flutter 规模的代码库（包括 Lombok 生成的成员、C 函数指针表和 Unreal-Engine 风格的宏重标头；CUDA 和 Metal 源采用 C++ 路径）。在 CI 运行器等资源受限的机器上，加速效果最大。无需设置：没有本机二进制文件的平台以及具有语法错误的单个文件，会自动使用以前的引擎，并且 CODEGRAPH_KERNEL=0 完全关闭本机路径。
  • 参考解析现在在大型项目上并行运行。当一个项目有足够的待处理引用使其有价值时（大约 150k+，对于大型 Java/Kotlin/Spring 代码库来说是典型的），解析会在工作线程中扇出，而结果会按照单线程路径所使用的确切顺序应用 - 图表显示的字节与字节相同，大约是我们测试中包含 4,000 个文件的 Java 项目的端到端速度的两倍。小型项目会自动保留单线程路径（扇出成本高于其节省的成本）。将 CODEGRAPH_NO_PARALLEL_RESOLVE=1 设置为禁用，或将 CODEGRAPH_PARALLEL_RESOLVE_MIN=<count> 设置为在接合时进行调整。
  • 对大型项目进行索引又得到了相当大的加速——在同一个 4,000 个文件的 Java 项目上，挂钟时间减少了大约四分之一，而图表仍然逐字节相同。有两个变化：数据库不再将昂贵的检查点管理工作交错到新索引的解析中间（而是在最后折叠一次），并且在写出一批结果时，工作线程已经在解析下一批而不是闲置。
  • 在索引结束时运行的动态调度分析（回调、事件和框架连接）现在在大型项目上并行运行其传递，将该阶段大约减少了一半——并且崩溃的传递现在可以安全地重试，而不是使整个索引失败，这也使得之前在此阶段死亡的非常大的代码库更有可能索引完成。图表逐字节保持相同。
  • 在大型项目中，索引写入其关系数据的速度明显更快：辅助数据库索引在大量引用解析期间被搁置，并在最后重建一次，而不是逐行维护。图表保持逐字节相同，小型项目不受影响。
  • 非常大的代码库可靠性：在数百万个符号的项目中，现在会跳过在工作线程上失败的分析过程，并显示明确的消息，而不是以可能删除整个索引的方式重试，并且索引结束索引重建不再有在巨大的图表上触发活动监视器的风险。在 Linux 内核上进行了端到端验证（70k 文件、2M 符号、640 万关系）——现在即使在 2 核机器上也能完成索引。
  • 索引速度显着加快 - 中型 TypeScript 项目上的新 codegraph init 大约需要三分之一的挂钟时间，并且逐字节生成相同的图表。收益来自于批处理数据库写入、在专用写入器线程上存储文件、记忆重复的导入解析查找、在批量构建期间跳过每行搜索索引维护（最后重建一次），以及（仅在全新的数据库上）推迟磁盘持久性直到索引完成，因为中断的第一个索引只是重新运行。设置 CODEGRAPH_NO_FAST_INIT=1 以在初始构建期间保持完全的崩溃持久性，或设置 CODEGRAPH_NO_STORE_WORKER=1 以存储在主线程上。
  • codegraph install 和 codegraph upgrade 现在在完成后提供 CodeGraph Pro beta 访问权限 - 回答“是”，输入您的电子邮件，然后您就可以加入与 getcodegraph.com 主页表单相同的候补名单。严格选择加入并每台机器最多询问一次：除非您说“是”并输入电子邮件，否则不会发送任何内容，任一答案都会被记住，因此以后安装或升级不会重新询问，并且非交互式运行（--yes、脚本、CI）永远不会看到问题。
  • 每个版本现在都可以进行加密验证：npm 包以 npm 出处发布（npmjs.com 上的“出处”徽章，证明每个版本都是由该存储库的发布工作流程从特定提交构建的），并且 GitHub 发布包带有签名的构建证明，您可以使用 gh attestation verify <file> -R colbymchenry/codegraph 检查。
  • CPU 或内存有限的容器（Docker、CI 运行程序）内的索引现在根据容器的实际配额（而不是主机的配额）来调整其工作池的大小，并且巨大的代码库在索引期间不再膨胀临时数据库文件（以前在 Linux 内核规模项目上有数十 GB 的临时磁盘）。这些共同防止受限机器上出现内存不足和磁盘不足故障；设置 CODEGRAPH_RESOLVE_WORKERS 以显式覆盖解析工作人员计数。
  • 在多核机器上索引非常大的项目再次变得更快：并行解析工作人员现在定期刷新其只读数据库连接，这使数据库管理工作得以推进，而不是在长期读取器后面默默地建立积压——这种积压会给索引器自己的写入带来负担。图表逐字节保持相同；在多核机器上，Linux 内核规模的胜利是最大的。
  • macOS 上的索引现在在调整并行分辨率工作线程的大小时使用机器的实际内存空间。 macOS 故意让 RAM 充满可回收的缓存，因此之前的可用内存读取量很小（在空闲的机器上约为 1GB），并悄悄地将工作池减半 - 一个中等 Java 项目的新索引运行速度比硬件允许的速度慢约 15-20%。图表逐字节保持相同；同样的修复还可以让内存驱动的分析缓存在 macOS 上完全参与大型 C 代码库。
  • 新的索引获得了相当大的全面加速：在初始构建期间，数据库的辅助查找索引被搁置并在解析后重建一次，而不是逐行维护 - 后面的链接阶段已经使用了相同的经过验证的技巧，现在应用于整个解析通道 - 并且引用解析循环同样停止维护它从未读取的查找索引，在表中几乎没有留下任何东西时重建它们。中型 Java 项目的解析阶段运行速度大约快 58%，其完整的新鲜索引端到端速度大约快 19%；在 8 核机器上花费约 15 分钟的 Linux 内核规模索引现在只需大约 11 分钟即可完成，仅解决阶段就下降了三分之一。图表保持逐字节相同，增量同步不受影响。
  • 保存文件现在几乎立即更新图表：文件观察器在 300 毫秒的安静窗口后触发一个或两个更改的文件（在完全去抖下突发仍然合并，并且 CODEGRAPH_WATCH_DEBOUNCE_MS 仍然是上限），并且观察器触发的同步精确地协调更改的路径，而不是统计遍历整个存储库。目录删除和事件风暴仍然运行完整的扫描差异，因此不会错过任何无法描述的事件。测量结果：在 4,400 个文件的项目中，“保存到新鲜图形”同步工作时间降至约 0.3 秒，在 27,000 个文件的项目中降至约 0.4 秒，生成的图形逐字节与完全协调相同。
  • 索引 Swift 和其他协议/接口密集型代码库的速度显着加快：检查方法是否存在于接收器的超类型（协议、基类、扩展）上的一致性步行现在会在每个解析批次的持续时间内记住其答案，而不是重新查询每个调用站点的图表 - 在 Swift 编译器存储库（27k 个文件）上，步行运行每个索引近一百万次。该存储库的新索引从大约 185 秒下降到 100 以下，并且图表逐字节相同。候选方法查找还获得了每个名称所有者索引，因此重载名称（Swift 中的 init、Java 中的 execute）不再为每个接收器类型支付完整的候选扫描费用。
  • 通过局部变量（recv.method()、Lua 的 recv:method()、R 的 recv$method()）解析方法调用在反复调用同一接收器的存储库上要便宜得多：输入接收器的声明扫描现在会记住它已经在每个范围扫描的内容，而不是为每个调用站点重新读取相同的源代码行，并且它扫描的正则表达式模式为每个接收器而不是每次调用编译一次。 Kong 的新指数在要求解决方案修复的基础上又下降了 8%（累计 23%），图表在各处都是相同的——包括 Java 项目，在这些项目中，相同的扫描成功地输入了数万个接收器。
  • 索引 Lua 和 Luau 项目获得了相当大的加速：解析每个 require(...) 不再重新扫描项目的整个文件列表四次 - 每个项目的文件名索引立即回答相同的查找，将每个需求的分辨率从大约毫秒减少到微秒。 Kong 的新索引（1,870 个 Lua 文件）端到端运行速度提高了约 16%，并且图表逐字节相同。同样的内务处理还关闭了潜在的过时边缘，即 COBOL copybook 查找可以在文件更改后继续提供缓存的文件列表。
  • 并行参考分辨率现在自适应地参与，而不是通过固定的项目大小截止：索引器测量第一批的实际每个参考分辨率率，并在剩余工作证明合理时在运行中旋转工作池。解析引用成本高昂的语言受益最多——尤其是 Rust：tokio 的新索引运行速度快了约 23%，并且图形逐字节相同。小型项目和低核机器（2 核 CI 运行程序）与以前一样保持单线程路径。
  • 索引结束时的动态调度分析现在会跳过可能无法为手头的项目生成任何内容的传递：当没有类具有 render 方法时，React 重新渲染桥接；当所需语言不存在时，React Native 和 Expo 跨平台配对；当没有映射器 XML 时，MyBatis 映射器链接。以前，这些方法中的每一个都扫描了整个图表，然后结果为空——在一个包含 4,000 个文件的 Java 项目中，每个新索引的分析时间大约为 0.9 秒。接口实现桥接过程在实际工作中也变得更便宜：它不再为每个实现者重新获取集线器接口的方法列表一次，并且在任何每个类查找之前都会跳过扩展或实现任何内容的类。图表逐字节保持相同。
  • 索引大型 C 和 C++ 代码库在函数指针分派分析（将处理程序表（如命令表或操作结构）连接到其调用站点的过程）上花费的时间要少得多：每个源文件现在读取和准备一次而不是四次，无法贡献任何分派接线的文件在后面的链接步骤中被完全跳过，并且在具有本机引擎的平台上，每个文件扫描本身现在也本机运行。在 Linux 内核规模的树上，该过程的端到端运行速度大约快三分之一，并且图形逐字节相同；没有本机二进制文件的平台在先前的路径上保留相同的结果。

修复

  • TypeScript、TSX 和 JavaScript 文件现在使用最新的语法进行解析 - 现代语法（例如 using 声明和导入属性）不再出现可能会删除周围符号的解析错误。 （之前捆绑的语法是从 2023 年开始的。）
  • Rust 文件现在还使用最新的语法进行解析（之前捆绑的构建日期为 2023 年），这进一步增强了方法调用属性：通过结构字段的调用使用接收者上下文进行解析，而不是回退到模糊的裸名称匹配，从而删除了常见名称（如 len 和 start）上的一类错误调用边缘。
  • Ruby 文件现在还可以使用最新的语法进行解析（之前捆绑的版本是从 2024 年初开始的），它修复了记录了错误的被调用者名称的安全导航运算符方法调用 (recv&.!= x) 的错误解析。
  • PHP 文件现在还可以使用最新的语法进行解析（之前捆绑的版本可追溯到 2023 年）：使用现代 PHP 功能的文件 - 枚举常量、PHP 8.4 属性挂钩、无括号的 new X()->method() 链接 - 不再出现解析错误或错误解析，从而丢弃或弄乱其符号，因此 Symfony 和 Laravel 等代码库索引显着更准确。
  • Swift 文件现在还可以使用最新的语法进行解析（之前捆绑的版本可追溯到 2023 年）：快速测试 #expect、#Preview 样式宏、package 访问修饰符和键入的 throws 不再产生丢弃周围符号的解析错误 - 像 Vapor 这样的服务器端 Swift 项目看到了最大的恢复。
  • Dart 的语法现在与 CodeGraph 本身捆绑在一起，而不是从其 Dart 构建浮动在未固定的上游引用上的第三方包中解析 - 例程依赖项更新不再能够默默地更改 Dart 文件的解析方式。
  • 按字段名称搜索或探索现在可以找到定义它们的代码。由对象键或 API 字段名称 (profileInfo isTrialEligible quotaInfo billingMethod) 组成的查询用于返回不相关的结果，而定义文件从未出现，因为三个检索步骤每个都删除了多词驼峰命名法术语：内部大小写比较错误、仅考虑类（从不考虑函数或方法）的匹配步骤以及需要精确符号名称匹配的探索播种。所有三个都已修复 - codegraph_explore 带有一包字段名称，现在显示了组装这些字段的控制器和服务。 (#1196)
  • codegraph.json 的 includeIgnored 再次适用于“存储库文件夹”布局：当一条 .gitignore 规则覆盖包含多个嵌入式 git 存储库的父目录 (/repos/) 时，选择单个存储库（"includeIgnored": ["repos/a/"] - codegraph init 自己的提示建议的确切拼写）之前没有匹配任何内容并索引零个文件，向您循环相同的建议。两种拼写现在都可以使用 - 命名父目录以选择其下的所有内容，或命名单个存储库以仅选择这些 - 并且提示不再重新建议已配置的存储库。 (#1295)
  • 对文字（Python 中的 ", ".join(...)、JavaScript 中的 "x".split(...) 等）的方法调用不再对恰好共享内置函数名称的不相关项目函数产生调用边缘 - 具有名为 join、get 或 update 的函数的代码库可以显示来自每个字符串内置函数使用的幻像调用者。此外，嵌套在另一个函数中的函数现在只能作为来自其容器内部的调用目标进行匹配，因为从其他任何地方都无法访问它。尤其是在 Python 和 JavaScript 代码库上，爆炸半径和受影响的测试结果变得更加清晰。 (#1230)
  • 当字段类型为外部时，通过结构体字段 (target.conn.Exec(...)) 的 Go 方法调用不再绑定到不相关的同名本地方法 - conn *sql.DB 调用被归因于碰巧声明 Exec 的本地接口，从而制造内部依赖关系。现在，通过从结构定义推断字段的声明类型来解析链接字段调用：项目内类型（包括未导出的类型，例如 chi 的 tree *node）获得以前从未存在过的正确且经过验证的调用边缘，而外部类型（标准库、第三方模块）则保持未链接而不是猜测。 (#1276)
  • 通过导入的单例 (import { store } from './store'; store.notify()) 的 TypeScript/JavaScript 方法调用现在解析为类方法而不是导出的常量，因此 codegraph callers 会看到该方法的跨文件调用者 - 以前仅归因于同一文件调用，并且到处使用的方法可能看起来未使用。相同的基于声明的类型推断适用于共享它的语言（Python、Java、Kotlin、Go 等），并且失败的推断会保留旧的优势而不是猜测。 (#1292)
  • codegraph node <symbol> -f <file> 现在打印符号的源正文。将不明确的名称固定到特定文件（当许多文件定义相同函数时 -f 的全部意义）仅返回位置和调用者跟踪，没有代码。 (#1284)
  • 现在可以通过监视模式来删除整个目录：其中的文件会在下一次自动同步时从索引中删除，而不是作为陈旧记录保留下来，直到触发不相关的编辑。操作系统通常将目录删除报告为目录本身的单个事件（其内容没有每个文件的事件），观察者之前将其丢弃。 (#1285)
  • codegraph sync 现在获得了与 1.4.0 中的完整索引相同的慢速磁盘修复：数据库检查点在整个增量运行中被推迟，而不是每隔几兆字节的写入就触发一次。在机械驱动器和其他高延迟存储上，大索引上的小同步不再在 CPU 接近于零的情况下停滞几分钟 — 同步成本随更改的内容而变化，而不是随现有索引的大小而变化。相同的 CODEGRAPH_NO_WAL_DEFER=1 开关将其关闭。 (#1248)
  • 在 typedef 返回类型（SEC_ATTR UINT32 MyFunc(VOID) - 嵌入式和内核代码中常见）前面使用项目特定属性宏声明的 C 函数现在按其真实名称进行索引。以前，解析器会遇到未知的宏，并将参数列表存储为函数名称，从而在图中留下像 "(VOID)" 这样的条目，并使真正的函数无法找到。 (#1211)
  • 大量宏的 C 和 C++ 代码索引更加完整。以前使解析器陷入错误恢复的 15 个普遍存在的习惯用法——删除符号、乱序名称、创建幻像条目或丢失真实条目之间的关系——现在可以干净地解析：C 头中的 #ifdef __cplusplus / extern "C" { 兼容性保护、语句位置中的迭代器宏（list_for_each_entry(pos, head, member) { … } 和整个 Linux-kernel/git/jemalloc 系列——包括跨行调用，例如hlist_for_each_entry_rcu(…) 和 lockdep_is_held 参数）、Linux/稀疏声明注释（static int __init foo(void)、void __user *buf、container_of(p, struct T, m)）、参数化注释（__free(kfree)、__printf(4, 0)、__counted_by(count)）、每 CPU 和工作队列声明宏（static DEFINE_PER_CPU(struct T, name);，包括初始化形式）、分配器的裸类型参数和列出宏（kzalloc_obj(struct T)、list_entry(p, struct T, member)）、具有限定或指针类型的 va_arg、GNU 命名变量宏定义（#define dbg(fmt, args...)）、static notrace 样式编译器标记、C23 auto 声明、尾随参数注释（int argc UNUSED、git 的 house 风格）、单独在一行上的名称空间管理宏（FMT_BEGIN_NAMESPACE、Qt 的 Q_OBJECT）以及 C++ 返回类型前面的函数属性宏。在 Linux 内核上，这将核心目录上因解析错误而丢失的文件减少了近一半，并恢复了错误恢复默默删除的数千个调用和引用关系，git 和 redis 看到了同类的较小削减；图在本机引擎和后备引擎之间保持逐字节相同。相关修复阻止宏处理本身破坏提及相同宏名称的 #define 行，从而删除了 fmt 样式标头中的一类幻像解析错误。
  • 在命名空间 (namespace sim { Output MyClass::Apply(...) { ... } }) 内定义的 C++ 方法现在在其限定名称中携带命名空间，与其类相匹配。来自其他文件 (sim::MyClass::Apply(...)) 的完全限定调用站点再次解析为定义，因此对于此模式，codegraph callers 和文件影响不再为空。 (#1291)
  • 在模板类 (template <typename T> T Box<T>::get() { ... }) 上定义的 C++ 方法不再将模板参数列表保留在其限定名称中。它们现在索引为 Box::get — 与同一方法的内联定义相同 — 因此它们链接到它们的类并再次从调用站点解析，并且病态的多行模板参数列表不能再将限定名称超出文件系统名称限制。 (#1286)
  • Go 路由检测不再错误识别共享 HTTP 谓词名称的普通方法调用 - cache.Put("key", value)、store.Get("config", out)、bus.Handle("user.created", handler) 等被索引为 HTTP 路由，污染高速缓存代码库中的路由列表。现在的注册必须看起来像这样：它的第一个参数必须是 / 前缀路径（所有路由器）或 Handle/HandleFunc 上的 Go 1.22 "METHOD /path" 模式，现在它还提取方法，而不是将路由列为 ANY。 (#1259)
  • Windows 上的进度输出不再将 ASCII | 轨道与其周围的 Unicode │ ◆ ● 框架混合。在呈现 Unicode 的终端（Windows 终端、VS Code、ConEmu/Cmder、JetBrains、Alacritty）中，整个 codegraph init / index / sync 块现在使用匹配的方框绘制字符进行绘制；无法识别的旧版控制台会保留安全的全 ASCII 输出，以避免出现乱码。 CODEGRAPH_ASCII=1 / CODEGRAPH_UNICODE=1 仍然在任一方向上超驰。 (#398)
  • CLI 输出现在遵循 NO_COLOR 约定和新的 --color / --no-color 标志，并在管道传输时自动变为普通：当 stdout 不是终端和管道传输的 codegraph init / 时，codegraph status、query、callers 和 files 等命令不再嵌入 ANSI 颜色代码index / sync 打印简单的每阶段线，而不是进度动画控制字符。 FORCE_COLOR 或 --color 强制为渲染它的管道重新启用颜色。 (#1281)
  • 调用者和影响分析不再默默地低估多次调用同一被调用者的函数。当一个调用者包含同一被调用者的多个调用站点并且内部解析批次边界碰巧将它们分开时，第一批之后的清理会在尝试之前删除后来站点的待处理行 - 确定性地，它们的边缘从未创建，并且哪些边缘丢失会随着与项目总引用计数的不相关更改而发生变化。现在，传递后清理的目标是每个已处理引用来自的确切数据库行。在验证 nlohmann/json 上的操作员调用修复时发现，其中 write_cbor 对 to_char_type 的 11 次调用索引为 10。 (#1269)
  • C++ 显式运算符调用（a.operator+(b)、p->operator+(b)、a.operator[](3) 和其他符号形式）现在为运算符方法生成 calls 边缘，因此仅通过显式语法调用的运算符在调用者和影响分析中不再看起来未调用。 tree-sitter 使用搁置在错误节点中的操作员名称来解析这些调用站点（从不作为普通成员访问），因此调用的目标被默默地读取为接收者变量；运算符名称现在从错误节点中恢复，并像任何其他成员调用一样通过接收器类型推断进行解析 - 不相关的类上的同名运算符永远无法捕获边缘。 Infix 使用（a + b、a[i]）需要实型推断并单独跟踪。 (#1247)
  • “解析参考”达到 100% 后，codegraph init 和 codegraph index 不再看起来挂起。解析后运行的动态调度链接（回调、React 重新渲染、C 函数指针等）没有进度显示，因此在需要一段时间的存储库上（尤其是大型 C 代码库），进度条会冻结在 100% 直到完成。这项工作现在显示为它自己的“链接动态调度”进度阶段，而最重的通道（C 函数指针链接）还报告通道内的进度，因此大型 C 代码库可以平稳地推进进度条，而不是在该阶段的大部分时间将其停放在一个数字上。
  • 索引不再打印重复的“SQLite 是一项实验性功能”警告，导致进度显示混乱。该警告来自 Node 的内置 SQLite，每个解析工作程序都会触发一次；现在它在每个发射路径上都被抑制。
