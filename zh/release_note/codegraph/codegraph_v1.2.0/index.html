codegraph v1.2.0

[1.2.0] - 2026-07-02

新功能

  • 通过局部变量进行的方法调用现在解析为更多语言中的方法。当代码执行 const logger = new Logger(); logger.log(); （或等效操作）时，CodeGraph 会从其声明或初始化程序推断局部变量的类型，并将调用链接到正确的方法 - 因此这些调用现在显示在调用者、影响/爆炸半径和 codegraph_explore 流跟踪中，而不是被删除。以前只有 C++ 可以处理这个问题；现在还涵盖 TypeScript、JavaScript、Python、Java、C#、Kotlin、Swift、Go、Rust、Dart、Scala 和 PHP。 (#1108)
  • 对接收器 (logger.log) 进行的 Ruby 方法调用现在会记录该方法的边沿。以前，Ruby 索引器仅保留接收器并丢弃方法名称，因此通过变量或对象调用的方法没有记录的调用者，并且在冲击/爆炸半径和流跟踪中丢失；结合上面的局部变量类型推断，logger = Logger.new; logger.log 现在链接到 Logger#log。对类方法 (Foo.bar) 和对象构造 (Foo.new) 的调用仍然会被记录。 (#1110)
  • 相同的局部变量方法调用分辨率现在扩展到 Lua、Luau、R 和 Pascal/Delphi。通过本地调用的方法（Lua/Luau local lg = Logger.new(); lg:log()、R lg <- Logger$new(); lg$log() 或 Pascal var lg: TLogger; ... lg.Log）现在链接到正确的方法而不是被删除。 (#1112)

修复

  • 对大型项目进行索引时不再会因“主线程无响应 - 终止楔入进程”消息而被中途终止。阻止真正卡住的索引的安全看门狗将缓慢但正常的工作误认为是挂起：在大型仓库中，链接引用和跨文件关系可以合法地运行一段时间，并且该工作现在定期产生，因此看门狗可以区分真正的进度和真正的停滞。以前未能完成 codegraph init / codegraph index（并且必须回退到 CODEGRAPH_NO_WATCHDOG=1）的项目现在可以正常完成，而真正挂起的进程仍然会被捕获。感谢@zmcrazy、@YoungLiao 和@GeeLab-Mob 的报告。 (#1091)
  • 在 Windows 上，当 CodeGraph 作为后台 MCP 服务器运行时，控制台窗口不再短暂闪烁。当 npm 启动器启动捆绑运行时（每次编辑器启动服务器或在守护进程空闲后重新连接时都会发生这种情况）以及在提取丢失的平台捆绑包的自我修复步骤期间，Windows 会暂时弹出一个黑色控制台（conhost）窗口。两者现在都以隐藏方式启动，与守护进程已有的行为方式相匹配； codegraph login 的浏览器打开步骤也以同样的方式进行了强化。感谢@luoyerr 的报告和根本原因分析。 (#1092)
  • C++ 前向声明不再排挤真正的类定义。 class Foo; 前向声明（在大型 C++ 和虚幻引擎代码库中很常见，其中大量使用的类在数十个标头中前向声明）每次出现时都会被索引为其自己的类节点。因此，探索该类主要返回前向声明站点，甚至可以选择其中之一作为blast-radius的代表，埋葬实际定义及其成员和调用者。现在，C 和 C++ 会跳过无实体前向声明，就像前向声明的结构和枚举一样，因此只有真正的定义会被索引。没有主体的类是完整定义的语言（例如 Kotlin 的 class Empty 和 Scala）不受影响。感谢@luoyxy 的报告和根本原因分析。 (#1093)
  • 返回引用的 C++ 方法和用户定义的转换运算符现在以其正确的名称进行索引。像 const FGameplayTagContainer& GetActiveTags() const 这样的内联 getter（在虚幻引擎标头中随处可见）被索引为 & GetActiveTags() const 而不是 GetActiveTags，而像 operator EALSMovementState() const 这样的转换运算符则保留其尾随 () const 而不是读取 operator EALSMovementState。在这两种情况下，乱码名称意味着您无法按名称找到符号，并且其调用者未链接。现在两者都读起来很干净，与指针返回和值返回方法已经工作的方式相匹配。 (#1096)
  • 在返回类型之前使用内联说明符宏编写的 C++ 函数现在可以正确索引。在虚幻引擎中，内联助手通常写作 FORCEINLINE FString GetEnumerationToString(...)； FORCEINLINE 宏使解析器将返回类型读取为函数名称的一部分（FString GetEnumerationToString 而不是 GetEnumerationToString），并丢失真正的返回类型，因此无法通过名称找到该函数，并且其调用者未链接。 CodeGraph 现在可以识别标准的 Unreal 内联宏（FORCEINLINE、FORCENOINLINE、FORCEINLINE_DEBUGGABLE），因此名称和返回类型都会被捕获。 （＃1100）
  • 相同的函数名称恢复现在涵盖常见第三方 C++ 库（而不仅仅是虚幻引擎）中的内联宏，包括 pugixml（PUGI__FN、PUGIXML_FUNCTION）、Godot（_FORCE_INLINE_）、Boost（BOOST_FORCEINLINE）和通用 ALWAYS_INLINE / FORCE_INLINE。用这些修饰的函数现在按其真实名称进行索引。在供应这些库的大型虚幻项目中，这清除了大部分剩余的函数名称乱码。 (#1101)
  • 即使使用 CodeGraph 不具体了解的宏进行修饰，C++ 函数名称现在也可以恢复。以前编写的 SOME_LIBRARY_MACRO ReturnType doWork(...) 函数，每当 CodeGraph 无法识别宏时，都会将宏或返回类型吸收到其名称中；现在，无论宏如何，真实名称（doWork）都会被恢复，因此它是可找到的，并且它的调用者链接 - 不需要每个库的配置。公认的宏列表也得到了扩展（Qt、Folly、Abseil、LLVM、V8、Eigen、rapidjson），因此这些宏还可以捕获返回类型。这只会清理已经乱码的名称，并且仅限于 C 和 C++，因此普通名称（以及 Kotlin 和 Scala 等标识符可以合法包含空格的语言）不受影响。 (#1102)
  • 其宏被识别为完整返回类型恢复的 C++ 库集已扩展到虚幻引擎之外 - 现在涵盖 Mozilla、Protobuf、{fmt}、nlohmann/json、GLM、Bullet、Skia、OpenCV、EASTL、Cocos2d-x、GLib、SQLite 和常见的 Windows 调用约定（因此 HRESULT WINAPI CreateThing(...) 索引为 CreateThing 返回HRESULT）。不在列表中的库中的函数仍会自动恢复其名称；被列出还可以恢复返回类型。 (#1103)
  • 图遍历和爆炸半径结果不再在少数边缘情况下丢弃或错误计算关系。当一个符号可以通过多个路径到达时，冲击/爆炸半径查询可能会忽略已经以另一种方式链接的两个符号之间的直接依赖关系；单独地，API 库使用的较低级图遍历可以仅保留同​​一对符号之间的几种关系之一（例如，既调用又引用另一个符号的符号），对通过两个不同调用站点到达的调用者进行两次计数，或者返回比高度连接的符号所请求的大小限制稍多的结果。这些问题是长期存在的，并且大部分被后来的重复数据删除所掩盖，因此日常查询结果基本上不受影响，但遍历现在返回完整的、正确边界的集合。感谢@inth3shadows 提供精确的、单独追踪的报告。 （#1086、#1087、#1088、#1089、#1090）
  • 对不同文件中同名类的方法调用现在解析为正确的定义。如果两个文件各自声明一个 Logger 类及其自己的 log() 方法，则调用可能会链接到最先索引的定义 - 因此一个文件中的调用错误地指向另一个文件中的类，从而混淆了该方法的调用者和爆炸半径。这影响了许多语言中编写为 obj.log()、Logger.log() 和 Logger::log() 的调用，包括 C++、Python、TypeScript、Java、C# 和 Rust。当方法名称不明确时，CodeGraph 现在更喜欢调用文件本身中的定义（常见情况下的正确目标），而 Java/Kotlin 调用已固定到另一个文件的 import 不受影响。感谢@inth3shadows 提供的最小重现和根本原因分析。 (#1079)
