codegraph v1.6.4

[1.6.4] - 2026-11-20

亮点

  • 小问题成本更低。 询问您的代理函数或常量是什么，或者谁调用它，codegraph_explore 现在会回答定义和使用它的每一行，而不是有关相关文件的长答案。
  • Claude Code 中的答案更快。 提示挂钩现在会询问已为您的项目运行的 CodeGraph 服务器，而不是在每次提示时再次加载索引，这在大型项目中最为重要，并且 codegraph impact 的速度与 1.6.2 中的速度一样快。
  • 在共享计算机上更安全。 每个代理会话现在都会在向其发送任何内容之前检查其连接的后台服务器是否按照您的方式运行。
  • 图中的更多代码。 Elysia (Bun) 路由、PHP 包含从 Web 服务器的根目录或文件自己的文件夹构建的、Dart 3.13 主要构造函数和较新的 Kotlin 语法现在可以读取，并且 ASP.NET Core 路由以 ASP.NET 服务它们的方式命名。
  • 更准确的链接。 数十个修复可帮助调用到达其含义的代码，最重要的是在 JavaScript 和 TypeScript、Python、Rust、C#、PHP 和 Java 中，并且 codegraph affected 不再在 HTTP 调用、队列或事件的远端选择测试，除非您通过 --cross-tier。
  • 更少的卡住命令。 当 CodeGraph 同步时，git add 或提交不再因“index.lock：文件存在”而失败，解析永远不会结束的文件不再阻止 codegraph init 或同步完成，并且项目文件夹被删除的服务器现在会关闭。
  • 升级： 在此版本后使用 codegraph index 重新索引您的项目。其中许多修复是在建立索引时编写的，codegraph status 和您的代理都会告诉您旧版本何时构建索引。

安全

  • 在与其他用户共享的计算机上，每个代理会话现在会在发送任何内容之前检查其连接的 CodeGraph 后台服务器是否按照您的方式运行，并在服务器无法证明时自行提供会话服务，因此其他用户无法再代替您的服务器读取代理的查询或为其提供编造的答案。感谢@aidenpan0x 指出这一点。

新功能

  • Claude Code 提示挂钩现在从已为您的项目运行的 CodeGraph 服务器获取其上下文，而不是在每个提示上再次加载索引，因此可以更快地回答结构提示，尤其是在大型项目中；如果没有服务器正在运行，服务器很忙，或者服务器无法证明它可以像您一样运行，则钩子会像以前一样自行解决。感谢 @aidenpan0x 的报告、测量和拉取请求。 (#3284)
  • Elysia (Bun) 后端现在在图表中包含其 HTTP 路由，以请求所采用的完整路径命名，并包含另一个文件中的 new Elysia({ prefix })、.group() 和 .use() 前缀，并链接到其处理程序，因此 codegraph_explore 可以将请求从其路由跟踪到您的代码中。感谢@ChampPABA 的报告。 (#3255)
  • PHP包含从Web服务器的根构建，如require $_SERVER['DOCUMENT_ROOT'] . '/inc/header.php'，现在链接到它们的文件：CodeGraph从包含的路径名称文件中计算出服务器服务的文件夹，当它们没有解决而不是猜测时不链接任何内容，并且当你想自己命名时在codegraph.json（或项目根目录的"."）中获取"webRoot": "public"。感谢@artisanya 的报告。 (#3298)
  • Kotlin 现在使用其语法的新版本来读取，因此它过去会误读的代码，例如其方法显示为顶级函数的带注释的类、委托 by 另一个对象的类，或者像 when 保护和显式支持字段这样的更新语法，现在在它们所属的图中具有其类、函数和调用。 (#3410)
  • codegraph_explore 现在回答有关一个符号的问题，例如“谁打电话给 toValidURL？”或者“什么是 MAX_RETRIES？”，包含该符号的源代码和使用它的每一行，每行都有它所在的函数和该行的文本，而不是用仅与名称共享单词的文件填充整个答案，因此这些小问题的成本更低，并且之后无需搜索。感谢@GeorgeTaveras1231 的测量。 (#3407)

修复

设置、后台服务器和CLI

  • codegraph affected 不再选择 HTTP 调用、队列或事件另一侧的测试，例如 Angular 应用程序对其调用的 Spring 控制器进行更改的规范，因为这些测试模拟了该边界；通过 --cross-tier 来包含它们。感谢@jotder 的报告。 （＃3320）
  • CodeGraph 在检查存储库是否有更改时不再采用 git 的索引锁，因此预提交挂钩中的 git add、CodeGraph 同步时运行的提交或签出不再因“index.lock：文件存在”而失败。感谢@iamclaudia-ai 的报告。 (#3295)
  • codegraph impact 和 codegraph_impact 再次与 1.6.2 中一样快，结果相同：1.6.3 以减慢步行每一步的方式读取每个符号的从属项。感谢@inth3shadows 的报告和修复，以及@Marcos-199-GitHub 的#3285。 (#3248)
  • 当 CodeGraph 服务器在大型项目上的追赶同步因该工具调用它正在服务以防止其预写日志缩小而停止时，它现在会在重试之前等待，每次都会等待更长的时间，而不是在您继续工作时每秒重新开始。感谢@kiliman 的报告。 (#3273)
  • 在没有索引的文件夹中启动的 CodeGraph MCP 服务器不再启动其单独的挂起看门狗进程，直到会话首次调用工具或打开项目，因此仅列出工具的会话（因为许多主机打开它们）使用较少的内存。感谢@AiurArtanis 的报告和@johnhldiver-beep 的#3257。 （＃3250）
  • 项目文件夹被删除的 CodeGraph 服务器（如删除的 git 工作树）现在会在大约半分钟内退出，关闭其文件观察器并从服务器 codegraph daemon 列表中删除，而不是一直运行到最后一个会话结束并超时。在 Windows 上，它还会阻止该文件夹的索引文件被删除。感谢@deniskern 的报告和@johnhldiver-beep 的#3259。 (#3245)
  • 从主文件夹运行的 codegraph upgrade 不再将代理的用户范围设置视为项目：Cursor 的 CodeGraph 服务器持续跟踪您打开的工作区，而不是固定到主文件夹，并且不会将 CodeGraph 部分写入 ~/AGENTS.md、~/GEMINI.md 或 ~/QWEN.md。感谢@shoma-endo 的报告以及@b84330808 和@LuisAlbertoMK。 (#3234)
  • 在 OpenCode、CodeGraph 的指令中，无论是其服务器发送的指令还是 codegraph install 写入 OpenCode 的 AGENTS.md 的部分，现在都按照 OpenCode 列出工具的方式命名其工具 (codegraph_codegraph_explore)，因此代理不再调用不存在的工具名称。感谢@expiren 的报告。 (#1267)
  • codegraph init 在上次索引运行被终止或中途失败的项目中，现在表示索引不完整并运行 codegraph index，而不是“已初始化”，后者读起来像工作设置。感谢@maxmilian 的报告和@LuisAlbertoMK。 (#3228)
  • codegraph callers、callees 和 impact 现在会在上次索引后答案中的文件在磁盘上发生更改时发出警告，就像 codegraph node 和 explore 已经做的那样，因此移位的行号不再读取为当前行号。对于 --json，警告会发送到 stderr，答案会列出 changedOnDisk 下的这些文件。感谢@arifpambudi242 的报告和@mohitdixit02。 （＃3260）
  • codegraph status 现在报告 codegraph.json include 引入索引的 gitignored 源中的编辑、新文件和删除，而不是在同步获取它们之前调用最新索引。感谢 @mixxer 的报告和拉取请求。 (#3086)
  • 在 Linux 和 macOS 上，当系统使用信号杀死 CodeGraph 时，例如在 codegraph init 或 codegraph index 期间内存不足时，该命令现在会显示哪个信号并以 shell 的方式退出（对于 SIGKILL 为 137），而不是在没有消息的情况下退出 1。感谢@inth3shadows 的报告和@johnhldiver-beep。 (#3277)
  • Spring 或 Laravel 测试的请求现在仅链接到其自己的应用程序的路由，而不链接到恰好与路径匹配的 JavaScript 或 TypeScript 服务器的路由，因此 codegraph affected 不再选择 Java 或 PHP 测试来更改您的 Web 代码。感谢@jotder 的报告。 （＃3320）

索引和同步

  • codegraph sync 和文件观察器现在遵循添加、删除或重新指向导出对象的成员（如 export const api = { getUser, saveUser }）的编辑，因此文件中的 api.saveUser() 之类的调用不会像新索引那样触及指向新成员或返回到对象的链接。感谢@inth3shadows 的报告。 (#3015)
  • 解析永远不会结束的文件，例如具有半类型 JSX 属性的 .tsx 文件，不再阻止 codegraph init 退出或让 codegraph sync 和文件观察器以满 CPU 的速度旋转：它的解析现在在文件的解析时间限制处停止，并且该文件被列为超时解析。感谢@inth3shadows 的报告。 (#3274)
  • 升级后，codegraph status 和每个代理会话中的第一个 CodeGraph 答案现在会将由 1.6.3 或更早版本索引的项目标记为已过时，因为此版本读取这些索引丢失的代码，例如 Dart 主构造函数、Elysia 路由、PHP 包含从 __DIR__ 构建的以及 export default 对象的方法；在每个项目中运行 codegraph index 来重建它。 (#3411)

JavaScript 和 TypeScript

  • 使用 on() 注册的 JavaScript 和 TypeScript 事件处理程序现在仅从在同一发射器上发出的代码链接，并链接到在它们注册的位置定义的处理程序，因此每个保留自己的发射器并使用相同事件名称的两个模块不再交叉链接。感谢@inth3shadows 的报告。 (#2973)
  • 在 JavaScript 中，以经典方式编写的方法 Ctor.prototype.m = function () {…} 和静态 Ctor.m = function () {…} 现在被索引为其构造函数的方法，并且 module.exports = {…} 对象的函数作为该模块的导出，因此其中的 this.m() 到达构造函数或对象自己的 m，而不是其他地方的同名的不相关函数。感谢@inth3shadows 的报告。 (#2966)
  • 在JavaScript和TypeScript中，模块默认导出的对象的功能，例如Vuex存储分为actions.js，getters.js和mutations.js（export default { fetchUser() {…} }），现在索引为default::fetchUser，因此codegraph_explore，node，query， callers 并影响找到它们，并通过模块的默认导入、this.fetchUser() 或 Vuex dispatch('fetchUser') 链接到它们进行调用； Vuex commit 现在始终链接到突变，而 dispatch 始终链接到操作。感谢@daniel-luan-tran 的报告。 (#3393)
  • 在 JavaScript 和 TypeScript 中，包装同名导入帮助程序的类中的 this.findAll() 现在链接到类自己的方法，而不是导入的帮助程序。感谢@inth3shadows 的报告。 (#2954)
  • 在 JavaScript 和 TypeScript 中，在 this 上编写的调用（如 this.cast() 或 this.validate()）不再链接到同一文件或另一个文件中的 const、require 绑定或仅共享其名称的函数声明，因为调用到达的是对象的属性。
  • 在 TypeScript 中，对像导入一样命名的参数或局部变量（如 stream(c, async (stream) => …) 中的 stream.write()）的调用现在通过该参数或局部变量，并且在导入函数上调用的方法不再链接到函数本身； require 中的相同错误已在 1.6.3 中修复。感谢@inth3shadows 的报告。 (#2953)
  • 在 JavaScript 和 TypeScript 中，对调用者周围的函数为其自身声明的名称的调用（如内部箭头函数调用的帮助程序）现在链接到该本地声明，而不是同名文件的导入。感谢@inth3shadows 的报告。 (#2949)
  • 在 JavaScript 和 TypeScript 中，对 describe(…) 块内声明的助手或任何其他回调的调用现在链接到该块声明的助手，而不是来自恰好位于更近的另一个块的同名助手。感谢@inth3shadows 的报告。 (#2944)
  • 在 JavaScript 和 TypeScript 中，扩展内的调用（例如从 useForm() 获取的 <input {...register('email')} /> 和 register）不再链接到共享名称的不相关项目函数。感谢@inth3shadows 的报告。 (#2962)
  • 在 JavaScript 和 TypeScript 中，另一个模块通过名称传递的模块命名空间（例如 zod 的 import * as z from './external'; export { z } 的 import { z } from 'zod' 或 export * as ns from './schemas'）现在将 z.string() 引导到该模块导出的内容，就像 import * as z 所做的那样，而不是在其他地方使用同名方法。感谢@inth3shadows 的报告。 (#2951)
  • 在 JavaScript 和 TypeScript 中，通过多条 export * 行的桶的导入现在链接到导出名称本身的模块（以先出现的行为准），而不是另一个模块导出的对象的同名方法。感谢@inth3shadows 的报告。 (#3233)
  • 在 JavaScript 和 TypeScript 中，调用库调用填充的变量的方法（例如来自 React-dom、net.createServer() 或 canvas.getContext('2d') 的 const root = createRoot(el)）不再链接到碰巧共享其名称的一个项目方法。感谢@inth3shadows 的报告。 (#2947)
  • 在 TypeScript 中，调用类的静态工厂填充的变量的方法（如 const writer = DatabaseConnection.initialize(path)）现在链接到工厂表示返回的类的方法，而不是从变量名称猜测的类。感谢@inth3shadows 的报告。 (#2946)
  • 在 TypeScript 中，通过接口的函数类型属性（如 matcher.snapshot()）的调用不再链接到不相关的类的同名方法；实现该接口或构建该接口的类仍然是链接的。感谢@inth3shadows 的报告。 (#3035)
  • 在 JavaScript 和 TypeScript 中，从 this 深入的两个或多个字段（如 this.cache.list.push(1) 或 this.extractor.functionTypes.includes(type)）的调用不再链接到名为 JavaScript 自己的 push、includes、has 或 set 的不相关项目方法，也不再链接到仅共享名称的财产。感谢@inth3shadows 的报告。 (#2948)
  • 在 JavaScript 和 TypeScript 中，指向项目外部的 workspaces 条目（如 package.json 或 pnpm-workspace.yaml 中的 "../shared"）不再使该文件夹的包算作项目的一部分，因此通过导入进行的调用不再链接到具有相同名称的不相关函数。感谢@bompus 的报告和@johnhldiver-beep。 (#3093)
  • 在 JavaScript 和 TypeScript 中，对在同一语句中的另一个变量之后声明的局部变量（如 let n = 0, ob = make()）的调用，或者在解构中的默认值旁边（如 const { ob = make() } = o），当函数外部的同名变量保存库的类型时，会再次链接，就像在 1.6.3 之前一样。感谢@inth3shadows 的报告和@mohitdixit02。 (#3293)
  • 在 JavaScript 中，对项目所需模块所没有的成员的调用（例如 const utils = require('./utils') 之后的 utils.missing()）不再链接到该名称的不相关类的方法。感谢@inth3shadows 的报告和@johnhldiver-beep。 (#3272)
  • fetch 或 HTTP-client 调用另一家公司的 API，如 fetch('https://api.github.com/users/…')，不再链接到具有相同路径的您自己的服务器路由；对 localhost、代码填充的主机的调用，或通过 client 的基本 URL 仍然链接。感谢@inth3shadows 的报告和@johnhldiver-beep。 (#2974)
  • 在 JavaScript 和 TypeScript 中，不导入该名称的模块中的全局调用或 new（如 parseInt(…)、new Response(…) 或 new URL(…)）不再链接到项目中另一个文件的同名导出。感谢@inth3shadows 的报告。 (#3238)
  • 在 JavaScript 中，相对路径的文件夹 require()（如包测试中的 require('..')）现在加载文件夹 package.json 名称为 main 的文件，就像 Node 所做的那样，因此通过它调用链接到文件导出的函数。之前，没有跟踪没有 index.js 的文件夹，并且调用链接到保存 require() 结果的变量；在 fastify 上，每个测试的 Fastify() 都链接到自己的测试文件。感谢@inth3shadows 的报告。 (#2964)
  • 在 JavaScript 中，保存所需模块函数返回内容的变量（例如 const app = require('./app')()）不再算作模块本身，因此像 app.listen() 这样的调用不再链接到模块的工厂函数，而是链接到工厂返回的类的方法（当该方法已知时）。感谢@inth3shadows 的报告。 (#2964)
  • 在 JavaScript 和 TypeScript 中，从 package.json 未列出但项目已安装的包导入的名称，例如提升到 monorepo 根 node_modules 的 import { useForm } from 'react-hook-form'，不再链接到项目中其他位置的同名不相关函数 (#3271)。升级后重新索引 JavaScript 和 TypeScript 项目。

Python

  • 在 Python 中，import time 不再将导入文件链接到恰好名为 time 的项目函数，因此此类函数不再列出在其调用者及其影响中导入标准库模块的每个文件。这同样适用于 json、copy、random、logging 和任何其他模块，以及受保护的 import brotli 旁边的后备变量（如 brotli = None）。感谢@inth3shadows 的报告。 (#3239)
  • 在 Python 中，对用 typing.overload 声明的函数或方法（如 click 的 command 和 prompt）的调用现在链接到运行的 def，而不是第一个 @overload 存根，因此实现会显示其调用者，并且调用路径会通过它。下面没有实现的存根（如 Protocol 中）保留为目标，而另一个库的 overload（其主体全部运行）则保持不变。感谢@inth3shadows 的报告和@nilotpal-n7。 (#2963)
  • 在 Python 中，对包含可调用对象的属性进行像 self.create_app() 这样的调用不再链接到另一个文件中的同名函数或变量，当类本身设置该属性时，也不再链接到另一个类的该名称的方法，因此 Flask 的应用程序加载停止将示例应用程序显示为其被调用者。类拥有、继承或子类覆盖的方法仍然链接，类以该名称存储的函数也是如此。感谢@inth3shadows 的报告和@nilotpal-n7。 (#2958)
  • 在 Python 中，裸露的内置函数（如 raise TimeoutError(…)、class Bad(ValueError) 或 sorted(rows)）不再链接到代码未导入的文件中该名称的项目类或函数，因此项目自己的 TimeoutError 停止收集引发内置函数的每个文件。文件定义或导入本身的名称仍然链接。感谢@inth3shadows 的报告。 (#3232)
  • 在 Python 中，对周围代码绑定自身的名称的调用（如本地 flat = lambda …、参数、循环或理解变量、lambda 参数或封闭函数的本地或参数）不再链接到该名称的模块级函数或变量，无论它是在同一文件中还是在代码从不导入的文件中。感谢@inth3shadows 的报告和@johnhldiver-beep。 （＃3037，＃3230，＃3231）
  • 在 Python 中，通过其模块从类（如 client = httpx.AsyncClient()）构建的局部变量，或由 with 或 async with … as client 绑定的局部变量，现在具有该类，因此 client.get() 链接到 AsyncClient.get，而不是像变量一样命名的类的方法，如 Client.get。一个 with 的类从 __enter__ 中分发其他内容，以及来自项目外部模块的类，仍然给出本地 no 类型。感谢@inth3shadows 的报告和@nilotpal-n7。 (#2957)
  • 在 Python 中，从调用中在本地绑定上调用的方法（如 made = make(q) 或 s = store.stage()）现在采用被调用函数或方法声明其返回的类型：Path、str 或项目外部的另一个类不链接任何内容，其中任何碰巧共享该名称的项目方法都可以链接，并且您自己的类之一链接其自己的方法，即使其他类具有该名称之一。感谢@inth3shadows 的报告和@johnhldiver-beep。 （＃3038，＃3240）
  • 在 Python 中，函数内部编写的 from x import name 现在仅适用于该函数，因此文件其余部分中的 name 调用将到达文件自己的 def name 而不是导入的函数，作为导入其所包装的原始函数的包装器。感谢@inth3shadows 的报告。 (#3229)

Java、Kotlin、C# 和 ASP.NET

  • 在 Java 中，当两个包声明同名的类时，静态调用、对新对象的调用或通过变量的调用现在会到达调用文件可以看到的对象（包括通过通配符导入），并且使用包编写的调用（如 com.x.b.Util.log(…)）会到达该包的类。感谢@inth3shadows 的报告和@johnhldiver-beep。 （＃2976，＃3290，＃3291）
  • 在 Kotlin 中，在库类型的导入别名上声明的扩展（例如 import androidx.compose.ui.Modifier as DeclAlias 之后的 fun DeclAlias.pad()）现在链接来自对该类型的调用，无论调用文件使用什么名称导入它。感谢 @mixxer 的报告和拉取请求。 (#3084)
  • 在 C# 中，调用同一类的方法返回的方法（例如 GetMailer().Send()）现在链接到该方法声明要返回的类型的方法。感谢@Gobakabana 的报告。 (#2906)
  • 在 ASP.NET Core 中，属性路由现在以 ASP.NET 服务它们的方式命名：填充 [controller] 和 [action]，每个控制器使用自己的 [Route]（或其基本控制器），~/ 路径独立，并且标记为 [HttpHead]、[HttpOptions] 或 [AcceptVerbs] 的操作具有自己的[Route]，或者在属性列表中不再被遗漏。感谢@Gobakabana 的报告。 (#2905)
  • 在 C# 中，扩展方法现在与其 this 参数采用的类型相匹配，因此 "hi".Shout() 和 mailer.Shout() 各自到达其自己的扩展，并且对字符串自己的方法的调用不再到达同名的项目扩展。感谢@Gobakabana 的报告。 (#2906)
  • 在 C# 中，通过 ?. 或 !. 调用的方法（如 _mailer?.Send()）现在链接到接收者类型的方法。感谢@Gobakabana 的报告。 (#2906)
  • 在 C# 中，通过其对象作为值传递或存储的方法（例如 Task.Run(worker.Run) 或 Action later = worker.Run;）现在算作该方法的使用，因此 codegraph callers 和 Impact 显示它。感谢@Gobakabana 的报告。 (#2906)
  • 在 Kotlin 中，在语句开头以修饰符关键字命名的调用（例如 Gradle allOpen { } 块中的 annotation("jakarta.persistence.Entity") 或类自己的 open()）现在被读取为调用本身，因此由此类调用组成的构建脚本不再警告它对图形没有任何贡献。感谢@clayly 的报告。 (#3410)

PHP 和 Laravel

  • 在 PHP 中，调用新构建的对象（如 (new SettingClient())->getSet(1)）的方法现在链接到文件的命名空间和 use 导入名称的类，或者链接到它继承的方法，因此这些调用显示在 callers 和影响中。感谢@holysor 的报告。 (#3244)
  • 在 Laravel 中，像 [UserController::class, 'show'] 这样编写的路由现在通过普通或别名 use、组 use、导入的命名空间或完全限定名称链接到路由文件导入的控制器，而不是其他地方的同名控制器或什么都没有。感谢@inth3shadows 的报告和@johnhldiver-beep。 （＃2975，＃3292）
  • 在 PHP 中，以与其声明不同的字母大小写调用的方法（例如 calcBasePrice 和 getRate 的 PriceConverter::CalcBasePrice(1) 或 $c->GetRate()）现在链接到该方法，因为 PHP 读取方法名称时不考虑大小写，因此这些调用会显示在 callers 中并产生影响。感谢@artisanya 的报告和@johnhldiver-beep。 (#3297)
  • 在为 PHP 7 及更早版本编写的 PHP 代码中，大括号中的字符串偏移量（如 $code{0}）不再使其周围的函数或类从索引中消失，其调用记入文件；现在读起来像 $code[0]。感谢@artisanya 的报告。 (#3299)
  • 在 PHP 中，函数或方法内的文件的 require 或 include 现在根据文件计为该函数，因此 callers 和影响会遵循包含文件中的代码返回到函数及其调用者。感谢@artisanya 的报告。 （＃3296）
  • 在 PHP 中，从文件自己的目录（如 require_once __DIR__ . '/inc/a.php' 或 dirname(__FILE__) . '/inc/b.php'）构建的包含现在以普通 require_once 'lib.php' 的方式链接到该文件，并且以 ./ 或 ../ 开头的路径仅链接到确切命名的文件，因为 PHP 加载它，而从不添加添加了 .php 的文件。感谢@artisanya 的报告和@inth3shadows。 (#3298)

Rust

  • 在 Rust 中，通过 glob use 引入的模块进行的调用（例如带有 use super::* 的测试模块中的 gzip::write() 或函数名称中的 use）现在再次链接到该模块的函数。感谢@Egrn 的报告和@mohitdixit02。 (#3253)
  • 在 Rust 中，codegraph_explore 的爆炸半径现在可以识别 #[cfg(test)] 模块或 tests.rs 文件中的单元测试，而不是针对其测试的功能报告“未找到测试”。感谢@moogiemode 的报告和@maxmilian。 (#3265)
  • 在 Rust 中，通过其路径作为值传递的函数或方法（如 g.map(Graph::counts) 或 .map(Self::helper)）现在计入其调用者并影响通过名称传递的函数的方式，仅当路径确定地命名它时才链接：永远不会有另一种类型的同名方法，也永远不会是特征实现的方法，因为 Rust 在那里使用哪个方法取决于参数的类型。感谢@Egrn 的报告和@inth3shadows。 (#3254)
  • 在 Rust 中，对类型来自项目外部的值（例如外部板条箱的构建器链或 stdout.flush()）的调用不再链接到仅共享其名称的方法之一，例如您自己的 impl Write 的 write 和 flush 或关联函数（例如 Graph::build(n) 和 Rules::default()） #[derive(Default)] 类型不再链接到其他类型的 default。感谢@Egrn 的报告。 (#3252)
  • 在 Rust 中，在 format!、println!、write!、assert_eq!、vec!、matches! 或 serde_json 的 json! 的参数中编写的调用现在链接到它调用的函数或方法，就像宏外部的相同调用一样，以及宏中的变体matches! 模式现在算作对其枚举的使用。感谢@Egrn 的报告。 (#3251)

Go、Swift、Dart、C 和 C++

  • 仅声明函数和 extern 变量（不含类、命名空间或模板）的 C++ .h 标头现在在使用 CComPtr<IDiaDataSource> 等模板类型、bstr_t& path 或 const qstring &name 等引用参数或 int depth = 0 等默认参数时被读取为 C++，而不是 C，后者删除了其符号并警告“解析没有生成符号（树没有生成任何符号）”错误）”。感谢@sonyps5201314 的报告。 (#3397)
