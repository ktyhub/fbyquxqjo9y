codegraph v1.1.2

[1.1.2] - 2026-06-28

新功能

  • 现在，您可以使用 codegraph.json 中的 exclude 列表从索引中排除已提交的目录 - 即使它们是 git-tracked 的。 .gitignore 无法删除 git 已经跟踪的目录，因此签入存储库的供应商主题或 SDK（static/ 下的承诺 Metronic 主题，捆绑的供应商库）没有受支持的方法来排除 - 它只会使图表膨胀并减慢索引速度。添加根 codegraph.json ，例如 { "exclude": ["static/", "**/vendor/**"] } ，并且在 git 和非 git 项目上的索引、同步和文件监视时会跳过这些路径。模式是 gitignore 风格并与 repo-root-relative 路径匹配。这补充了现有的 includeIgnored （它的相反 - 选择加入 gitignored 嵌入式存储库）。 （#999）
  • CodeGraph 现在遵循通过宏构建的函数指针表分派的 C/C++ 命令，因此它们到达的处理函数不再是图中的死胡同。许多 C 项目通过宏和生成的表将处理程序注册到结构体的函数指针字段中 - redis 是典型的情况：每个命令（getCommand、decrbyCommand 等）都通过位于生成的 #include-d 文件中的 MAKE_CMD(…) 表连接到命令结构体的 proc 字段，然后作为 c->cmd->proc(c) 调用。 CodeGraph 现在读取那些宏构建的表 - 包括结构类型本身就是宏别名的表，其表位于 #include-d 文件中，该文件从不单独索引，或者包装在条件编译 (#ifdef) 中并与结构内联定义。它识别通过函数 typedef 声明的函数指针字段，并遵循跨字段类型的接收者 — 链式访问 (c->cmd->proc) 或通过文件范围表 ((cmdnames[i].cmd_func)(…)) 的数组下标。它还通过一个完全没有结构包装器的裸函数指针数组进行调度——解释器和模拟器中常见的操作码/处理程序表模式，其中像 opcodes[op](…) 这样的表通过索引调用许多注册的处理程序函数之一——将调度程序链接到数组中的每个处理程序。结果：询问命令处理程序的呼叫者或爆炸半径现在可以找到到达它的调度程序。对于 redis，call 显示为每个命令的调用者；对于 SQLite，通过 FUNCTION(...) 注册的内置 SQL 函数链接到调用它们的位置；对于 Vim，每个 :ex 和正常模式命令都来自调度程序。 （#991，扩展#932）
  • 当许多代理同时查询时，CodeGraph 不再超时。为所有编辑器和代理会话提供服务的共享后台服务器用于在单个线程上运行每个查询，因此大量并发请求（例如，一群子代理一起探索大型单一存储库）彼此排队，而在繁重的请求运行时，会冻结连接，因此完成的答案甚至无法发送回，直到整个批次耗尽。过去的几个同时调用者通常会因 MCP 请求超时而出现。共享服务器现在通过工作线程池应答查询，因此并发请求并行运行，并且连接始终保持响应；当它真正饱和时，呼叫会返回一个简短的“忙，请稍后重试”提示（不是错误），而不是挂起超过 client 的超时。池的大小会根据您的机器自行调整——每个核心大约有一个工作线程，剩下一个用于协调——并且单个编辑器会话不受影响（没有池，没有开销）。设置 CODEGRAPH_QUERY_POOL_SIZE 以选择特定数量的工作线程，或设置 0 以恢复为单线程进程内查询。
  • 索引现在跨多个 CPU 核心而不是一个 CPU 核心解析文件，因此在多核机器上构建项目图（codegraph index、项目的第一个索引以及更改后的后台重新索引）速度更快，尤其是在大型或解析繁重的代码库上。它生成的图与之前相同，并且重新索引保持确定性：解析并行运行，但结果仍然以固定顺序提交，因此同一项目始终生成相同的图。 CodeGraph 自动根据您的机器调整池大小（为其他所有内容留下一个空闲的核心）；设置 CODEGRAPH_PARSE_WORKERS 选择特定数量的解析工作器，或设置 CODEGRAPH_PARSE_WORKERS=1 恢复以前的单核行为。峰值内存保持不变——工作线程独立回收解析器内存，因此它不会随着核心数量的增加而增长。 （＃1015，＃320）
  • 当 CodeGraph 的 MCP 服务器在没有自己的默认项目的情况下运行时——在任何存储库外部启动（例如在 MCP 网关后面），或者在索引位于子项目中的 monorepo 根上启动——它现在将 projectPath 标记为每个工具调用的必需参数。之前，projectPath 始终是可选的，因此与此类服务器通信的代理经常会忽略它，获取通过它的指导，并且无法可靠地重试 - 每次都必须手动推动它。现在，需求是代理看到的工具定义的一部分，因此它提供了它第一次处理的项目的路径。当服务器确实有一个默认项目（正常情况下，在您的存储库中启动）时，projectPath 保持可选状态，并且没有它的调用会像以前一样退回到该项目。感谢@wauxhall 的报告。 (#993)
  • CodeGraph 的 MCP 工具现在可以在 Cursor 的 询问模式 下工作（以及任何其他仅允许只读工具的 client）。每个 CodeGraph 工具都只是读取您的索引代码 - 它永远不会更改您的工作区 - 但它不会宣传这一点，因此 Cursor 的 Ask 模式会阻止每个调用，并显示“您处于询问模式，无法运行非只读工具”，并且您必须切换到 Agent 模式才能使用 CodeGraph。 CodeGraph 现在使用标准 MCP 工具注释将其所有工具声明为只读，因此 Cursor（和类似的 clients）允许它们处于只读上下文中。工具的行为方式没有任何变化。感谢@CDsouza315 的报告。 (#1018)

修复

  • 孤立或楔入的 codegraph index 或 codegraph init 现在会自行停止，而不是永远固定 CPU 核心。如果您终止了命令（或启动它的终端/代理），底层索引器进程将继续在后台运行 - 父进程无法传递信号 - 并且真正卡住的索引也没有任何东西监视它，因为自恢复看门狗仅连接到后台 MCP 服务器。这两个差距都已解决：现在，当其父级消失时，索引会自行终止，并且停止取得进展的主线程将被终止，因此它不会无限期地挂起。使用与服务器匹配的 CODEGRAPH_NO_WATCHDOG=1（活跃度）或 CODEGRAPH_PPID_POLL_MS=0（孤立检测）选择退出。 （#999）
  • 提交大型 JavaScript/TypeScript 主题或 SDK 的存储库上的“正在解析引用”时，索引不再挂起。供应商的管理主题（Metronic 是经典案例 - 约 1,300 个提交的 .js 文件）在数百个小部件上重新声明相同的方法名称（init、update、render、destroy 等），并使用分辨率针对 每个 调用对 每个 同名定义进行评分 - 工作量随着名称重复次数的平方而增长。在这样的存储库中，它会固定 CPU 核心 15-30 分钟，但实际上从未完成。现在的分辨率是猜测一个名称何时被定义的次数比任何真实代码库重复的次数都多（截止值很大——正常项目的最高值远远低于它并且完全不受影响），因为无论如何，没有邻近启发法可以在数千个目标中选出一个真正的目标。以前楔入的索引现在可以在几秒钟内完成，并且精确的解析（导入、限定名称、类名匹配）保持不变。这与 1.1.0 导入名称修复属于同一类减速，现在因重复的方法/符号名称而关闭。如果需要，可以使用 CODEGRAPH_AMBIGUOUS_NAME_CEILING 调整截止值。感谢@DANOX2 提供的详细报告和重现。 （#999）
  • Claude Code 的前端加载提示挂钩现在会针对非英语提示触发。为结构问题注入 CodeGraph 上下文的可选钩子仅识别英语关键字，因此用中文（或任何非拉丁脚本语言）编写的结构问题不会默默地注入任何内容：尽管设置正确，但钩子看起来好像没有连接，没有错误解释原因。该门现在具有语言感知能力。它可以识别中文结构关键字（如何/流程/调用/依赖/实现/架构…），并且在任何语言中，提示都会命名项目中的真实代码符号，例如 getUserId、article_publish、user.login 或 parseToken()（名称会根据索引进行检查，因此看起来像代码的普通单词不会触发它）。非结构性提示（“修复此拼写错误”，任何语言）都像以前一样保持无操作，因此在没有给出结构性答案的情况下不会触发任何操作。感谢@whinc 的详细报告和重现。 (#994)
  • 对于保存在 ExFAT 或 FAT 外部驱动器（以及某些网络安装）上的项目，后台自动同步服务器现在启动。这些文件系统不支持服务器依赖于协调和本地侦听的操作，因此它立即失败并在每次重试时重新记录相同的错误 - 后台索引已损坏，因此您必须在更改后手动运行 codegraph sync。 （MCP 工具、提示钩子和手册 codegraph index/sync 不受影响，因为它们都不需要服务器。）服务器现在自动解决这些限制 - 回退到不同的协调方法并将其本地套接字重新定位到系统临时目录 - 因此后台索引在那里的工作方式与其他地方完全相同，无需配置。在 macOS、Linux 和 Windows 上的真实可移动驱动器文件系统上进行了端到端验证。感谢@zengwenliang416 的详细报告。 (#997)
  • 如果您使用 CodeGraph 作为库，则 QueryBuilder.deleteResolvedReferences() 帮助程序在收到非常大的 id 列表时不再抛出“太多 SQL 变量”——它发出一个无界查询，因此超过 SQLite 参数限制的列表会中止调用。现在，它像 API 中的所有其他批量查询一样将工作分成多个批次。 CodeGraph 自己的索引和引用解析从未调用此方法（它们使用不同的、已批处理的路径），因此 CLI 和 MCP 服务器不受影响。感谢@inth3shadows 的静态分析。 (#1001)
  • Swift 计算属性现在已建立索引，因此您可以搜索它们。计算属性（var isCloudProxy: Bool { … } 读取整个代码库、SwiftUI 视图的 var body: some View { … }、协议的 var title: String { get } 要求）根本不产生任何符号，因此 codegraph query 和 codegraph_explore 为其回答“未找到结果”，并且 trust 为空结果的代理会错误地得出该属性不存在的结论。计算属性（和协议属性要求）现在是您可以像其他任何东西一样查找和探索的图形符号。计算属性的 getter 也被读取为其主体，因此 SwiftUI 视图的 body 链接到它构建的子视图和帮助器 - 使视图的渲染流程可通过属性进行跟踪。存储的属性已经被索引；这缩小了计算属性的差距。感谢@monochrome3694 的精确报告和重现。 (#1020)
