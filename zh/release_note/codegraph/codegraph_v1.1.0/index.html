codegraph v1.1.0

[1.1.0] - 2026-06-23

新功能

  • Claude Code： 可选的前载钩子使您的代理自动到达 CodeGraph。当您提出结构性问题时——“X 是如何工作的”、“什么调用 Y”、“跟踪从 A 到 B 的流程”——CodeGraph 会预先将相关源和调用路径注入到提示中，因此代理可以从图表中进行回答，而不是四处寻找以重建它。在 codegraph install 期间会询问您（默认是；仅限 Claude 代码，因为它是带有提示钩子的代理），它被 codegraph uninstall 删除，而 codegraph upgrade 会为现有的 Claude 设置打开它。它是严格可添加和可降解的 - 非结构提示和未索引的项目将被保留 - 并且您可以通过设置 CODEGRAPH_NO_PROMPT_HOOK=1 随时将其关闭，而无需卸载。
  • Vue 存储操作、突变和 getter 现在被索引为您可以查找和读取的符号。无论您的商店是 Vuex （模块中的 mutations / actions 对象）还是 Pinia — 选项形式 (defineStore({ actions: { … } })) 和设置形式（defineStore('id', () => { … })，其中操作是本地函数） — 每个操作、突变和 getter 现在都是一个真实的节点。因此，codegraph search 找到 login 或 getSessionList，而 codegraph_explore / codegraph_node 显示其主体及其调用的内容，而不是“未找到”，因为该函数仅作为对象文字属性存在。
  • codegraph_explore 现在将 Vue 组件连接到它调用的 Pinia 存储操作。当代码执行 const store = useUserStore() 然后 store.fetchUser() 时，该调用现在链接到存储模块中的 fetchUser 操作 - 那么“当此视图加载其数据时会发生什么？”从组件跟踪到动作主体，而不是停在 store.fetchUser() 行。适用于 Pinia 商店样式（选项和设置），并保持精确（像 store.$patch() 这样的内置函数或不相关的同名方法不会被错误链接）。
  • codegraph_explore 现在遵循 Vuex 字符串调度。 dispatch('user/login') 或 commit('SET_TOKEN') 调用（包括命名空间的 'module/action' 键）现在链接到它所命名的操作或突变，即使多个模块共享操作名称，也会解析为正确的存储模块（并且不会被同名的 api/ 帮助器愚弄）。那么“当这个调度时，什么会运行？”跟踪从对存储处理程序的调用到它提交的突变。 Vuex 的规范 export default { namespaced, actions, mutations } 模块形状现在也已索引，因此这些处理程序是可找到的符号。
  • codegraph_explore 现在连接基于 RTK 查询 构建的 React 数据获取流程（Redux Toolkit 的 createApi）。 createApi({ endpoints }) 内部定义的端点及其生成的 useGetXQuery / useUpdateYMutation 钩子对于分析都是不可见的 - 所以“这个组件获取什么？”或“useGetThingQuery 从哪里获取数据？”死胡同，因为钩子、端点和组件没有任何东西连接它们。 CodeGraph 现在将每个端点和每个生成的钩子索引为真实符号，并连接路径 component → useGetXQuery → getX → queryFn，因此流程在一次探索调用中解析，而不是手动读取 API 切片。箭头 (endpoints: build => ({ … })) 和方法 (endpoints(builder) { return { … } }) 样式以及 useLazyGetXQuery 变体均被识别；类似名称的手写钩子保持不变。
  • codegraph_explore 现在遵循 Python 中的 Celery 任务调度。 send_email.delay(...) 或 send_email.apply_async(...) 调用现在链接到它运行的 @shared_task / @app.task 函数 - 通常在与触发它的位置（视图或服务）不同的模块 (tasks.py) 中定义 - 所以“调度此函数时实际会发生什么？”从调用站点直接跟踪到任务主体，而不是停在 .delay() 行。两种装饰器方言均被识别（裸 @shared_task 和 arg’d @app.task(bind=True, …) 形式），包括模块限定的 tasks.invalidate_cache.apply_async() 调用样式。它保持精确：非 Celery 任务上的 .delay() 永远不会被错误链接，因此不使用 Celery 的项目不会受到影响。
  • codegraph_explore 现在遵循 Java 中的 Spring 应用程序事件。现在，publishEvent(new OrderShippedEvent(...)) 调用链接到处理该事件的每个 @EventListener（通常在不同的类中），因此“发布此事件时会发生什么反应？”来自发布者的跟踪直接进入每个侦听器方法，而不是在 publishEvent(...) 处陷入死胡同。该链接是按事件类型划分的，并且可以识别所有常见侦听器样式：在其参数上键入的 @EventListener、@EventListener(SomeEvent.class) 形式、@TransactionalEventListener 和较旧的 implements ApplicationListener<SomeEvent>。一个事件分散到所有侦听器，并且没有事件总线的普通 Spring 应用程序不受影响。
  • codegraph_explore 现在遵循 C#/.NET 中的 MediatR 请求和通知调度。 _mediator.Send(command) 或 _mediator.Publish(notification) 调用现在链接到匹配的 IRequestHandler<> / INotificationHandler<> 的 Handle 方法（通常位于 Clean Architecture 布局中的不同文件中），所以“什么处理此命令？”从控制器直接跟踪到处理程序，而不是在中介调用处停止。发送的类型会被识别，无论它是内联构造的 (Send(new GetFooQuery()))、内置到本地优先 (var cmd = new …; Send(cmd)) 还是作为参数传入，并且它按类型匹配 — 因此，不是请求的 MessagingCenter.Send(...) 或同名 DTO 永远不会被错误链接，并且没有 MediatR 的项目不会受到影响。
  • codegraph_explore 现在遵循 Ruby 中的 Sidekiq 后台作业调度。 DestroyUserWorker.perform_async(id)（或 .perform_in / .perform_at）调用现在链接到该工作人员的 perform 方法 - 通常在 app/workers/ 中，远离将其排队的控制器或模型 - 所以“这里后台运行什么？”从队列中直接进入作业主体的痕迹。现代的 include Sidekiq::Job 和旧的 Sidekiq::Worker 都被识别，命名空间的工作线程解析为正确的类，即使几个共享一个名称（例如 Comments::NotifyWorker 与 Articles::NotifyWorker），并且 Rails ActiveJob 的 perform_later（一种不同的机制）被故意保留。
  • codegraph_explore 现在遵循 PHP 中的 Laravel 事件。 event(new OrderShipped($order)) 调用现在链接到处理它的每个侦听器 - 每个侦听器的 handle() 方法，通常是一个单独的 app/Listeners/ 类 - 那么“对此事件有何反应？”来自调度的痕迹直接进入听众的身体。 Laravel 注册侦听器的方式有两种：通过类型化的 handle(OrderShipped $event) （自动发现，包括侦听两个事件的 handle(A|B $event) 联合）和通过 EventServiceProvider 中的 protected $listen 映射（它还会捕获 handle() 没有类型提示的侦听器）。一个事件分散到所有侦听器，并且通过 ::dispatch() 而不是 event() 调度的排队作业被正确地排除。
  • CodeGraph 现在可以理解 Java 中 Lombok 生成的方法。 @Getter、@Setter、@Data、@Value 和 @Builder 在编译时生成 getter、setter、builder()、equals/hashCode/toString 和 @Slf4j log 字段，因此这些方法永远不会出现在源代码中 - 并且user.getName()、User.builder() 或 log.info(...) 调用用于解析为无，默默地破坏调用链分析（代理会断定该方法不存在并手动重建它）。这些成员现在通过注释和字段进行索引，因此它们出现在 codegraph search 和 ZZPH100​​ZZ/codegraph_node 中，调用者可以像任何手写方法一样跟踪它们。它们被标记为 Lombok 生成，因此它们读起来是生成的，而不是手写的；您自己编写的方法永远不会被覆盖，静态字段没有访问器，并且没有 Lombok 的类不受影响。谢谢@git87663849。 (#912)
  • codegraph_explore 现在遵循 C 和 C++ 函数指针调度。 C 使用函数指针实现多态性：结构体带有函数指针字段，具体函数通过表 (static struct cmd commands[] = {{"add", cmd_add}, …})、指定的初始值设定项 (.handler = on_open) 或赋值来注册到其中，并且代码间接分派 (p->fn(argv))。这些对分析来说都是不可见的——间接调用什么也没解析，所以 git 的命令运行程序看起来什么也没调用，而且 vtable 的实现没有调用者。 CodeGraph 现在将调度站点链接到注册的处理程序，由结构字段作为键控，因此“调度时运行什么？”从 p->fn(...) 跟踪到为该字段注册的每个函数。这涵盖了命令表习惯用法（git、redis）和 ops-struct/vtable 习惯用法（curl 的内容编码器、协议处理程序），包括从注册表重新分配通用挂钩槽的情况（h->func = found->fn）。它保持精确——不同的函数指针字段不会交叉链接，普通数据字段永远不会被视为调度，并且没有函数指针调度的项目不受影响。 (#932)
  • codegraph_explore 现在遵循 Go 中的 GoFrame 路由绑定。 GoFrame 的标准路由器以反射方式连接路由：路径和方法位于请求类型的 g.Meta 结构标记中（g.Meta `path:"/user/sign-in"方法：“发布”`), the controller method that serves it is matched by that request type, and the two are joined at runtime by group.Bind（...） — so there was no path string and no edge from a route to its handler, and “where is /用户/登录 handled?” or “where are the routes bound to controllers?” could only be answered by reading. CodeGraph now indexes each g.Meta route as a real route node and links it to the controller method whose signature takes that request type, so a route resolves to its handler structurally in one codegraph_explore call. The link is by request type, not method name — so it’s correct even when the two differ (a DeptSearchReq served by a List method); it tells apart the many identical request types a large app defines one-per-module (cash.ListReq vs order.ListReq)按包，包括克隆的插件模块；并且处理程序不存在的路由将保持未链接而不是猜测。 (#747)
  • MCP 服务器现在可以在 monorepos 和多项目设置中运行。之前，如果您在没有自己的 .codegraph/ 的地方启动 CodeGraph（通常是仅对单个服务建立索引的 monorepo 根），服务器会暴露根本没有工具，因此您的代理无法查询 CodeGraph，即使是已索引的子项目。现在，这些工具始终可用：使用 projectPath 参数（其路径或其中的任何位置）将查询指向任何索引项目，并从该项目的索引中获取 CodeGraph 答案 — 在一个会话中可以查询任意多个项目。这也意味着您在服务器启动后建立索引的项目无需重新启动即可获取，而在此之前，工具保持隐藏状态，因为服务器仅在启动时检查一次索引。真正没有索引的项目仍然清楚地告诉您的代理使用其内置工具（并且您可以运行 codegraph init 来启用它），因此单个项目的使用不会改变。谢谢@MaiLunJiye。 (#964)
  • Claude 前载钩子现在可以在 monorepo 中找到您的索引子项目。为结构问题注入 CodeGraph 上下文的可选 UserPromptSubmit 钩子以前只查找位于或高于工作目录的索引 - 因此，如果您打开 monorepo 根目录但索引了单个包（packages/api、services/auth），它什么也找不到，并且在最有用的地方保持沉默。现在，它还“查看”子项目：单个索引子项目会自动预先加载其上下文，并且有多个挂钩会预先加载您的问题名称（并列出其余内容，以便代理可以通过 projectPath 来定位它们）。单项目存储库不受影响，并且扫描受到限制并完全跳过可识别的工作区根目录之外。 (#964)
  • codegraph_explore 现在可以在大型多层项目中显示正确的代码。当您在将 API 服务器与镜像相同域单词的大前端配对的存储库中提出后端流问题时（例如位于 api/ 服务器上的 app/ 管理 UI），真正匹配多个查询术语的服务器端文件不再被更大、更互连的前端层从结果中推出。由两个或多个不同查询项证实的文件现在保留在答案中，即使更密集的不相关层会将其挤出，因此“X 如何读取项目/处理请求”返回完成工作的服务或处理程序，而不是前端视图墙。单层项目不受影响；设置CODEGRAPH_RANK_NO_MULTITERM=1恢复到之前的排名。
  • TypeScript、JavaScript、Go、Python、Rust、Ruby、C、Java、C#、PHP、Scala、Kotlin、Swift、Dart 和 Pascal/Delphi 的影响和爆炸半径分析现在可以理解常量的读者。当您更改文件范围、包级、模块级或类级常量（配置对象、查找表、共享常量）时，该文件中读取它的其他符号现在显示为受影响，而之前它们是不可见的（影响仅跟随调用、导入和继承，因此常量的使用者看起来“没有任何东西依赖于此”）。这使得codegraph impact，以及codegraph_explore/codegraph_node中的冲击轨迹，赶上“改变这个表，打破它的读者”类的变化。默认情况下它处于打开状态，并且不会向图表添加任何节点；捆绑/缩小的文件和模糊的名称将被跳过，以保持结果的精确性。设置 CODEGRAPH_VALUE_REFS=0 将其关闭。
  • C 文件范围常量和全局变量（static const 标量、指针/数组查找表和共享可变全局变量）现在被识别为本身的符号。他们之前根本没有被提取出来，因此他们从未出现在搜索中或携带任何家属；现在它们出现在 codegraph search 中并参与影响分析（见上文），因此更改 C 查找表会显示读取它的同一文件函数。
  • Java static final 常量、C# const / static readonly 常量、Scala object val 和 Kotlin 顶级 / object / companion object val 现在被分类为常量而不是通用字段，因此它们参与上面的常量读取器影响分析 - 更改 public static final表、const string、Scala object Config { val Timeout = … } 或 Kotlin companion object { const val … } 以及读取它的方法现在显示为受影响。 （每个对象 Java final / C# readonly / Scala 和 Kotlin class 实例属性保持不变。）Kotlin 常量以前根本不作为自己的符号进行索引，因此它们现在也出现在 codegraph search 中。
  • Swift 顶级 let 和 static let 常量（包括在 enum/struct 中命名的常量，常见的 Swift 模式）现在被索引为常量，并参与上面的常量读取器影响分析 - 更改 static let defaultRetryLimit 或 enum Constants { static let … } 以及读取它的同一文件代码显示为受影响。计算属性和每个实例的 let 不被视为常量。
  • Dart 顶级 const/final 和类 static const/static final 常量现在被索引为常量，并参与上面的常量读者影响分析。实例字段、var 和局部变量不被视为常量。 （已跳过生成的带有标准 .g.dart/.freezed.dart/.pb.dart 后缀的 Dart 代码。）
  • 您现在可以向 CodeGraph 教授自定义文件扩展名。将 codegraph.json 与 extensions 映射（{ "extensions": { ".dota_lua": "lua", ".tpl": "php" } }）放在您的存储库根目录中，具有这些扩展名的文件将在您命名的语言下建立索引，而不是因为扩展名不是内置默认值之一而被默默地跳过。它是选择加入并与您的代码一起提交的，因此整个团队共享它，您的映射层位于内置程序之上并在冲突中获胜（您甚至可以重新指向内置程序，例如 .h → cpp），并且会警告并跳过拼写错误的语言或格式错误的配置，而不是破坏索引。没有 codegraph.json 的项目的行为与以前完全相同。 (#906)

修复

  • codegraph index 和 codegraph init 在大型项目的“解决参考”阶段不再爬行 - 最痛苦的是混合了大型前端和后端的项目，该阶段可能会延长到很多分钟。跨数百或数千个文件导入的包或模块（react、共享 UI 包、Python logging / typing）被视为好像这些导入语句中的每一个都可能是其定义，因此解析器将每个导入与所有其他导入进行比较 - 工作随着包导入范围的平方而增长，这就是为什么它只在大型、导入繁重的存储库上爆炸的原因。导入现在直接解析为它们实际指向的定义，因此那些冗余比较消失了（在大型存储库上参考解析速度显着加快），并且图表不再累积旧后备创建的无意义的导入到导入链接。 (#915)
  • MCP 工具结果不再在 Markdown 渲染 clients 中显示为超大标题（例如 Claude Code VSCode 扩展）。结果使用 Markdown 标题 (##/###) 来表示状态摘要、每个搜索命中以及探索中的每个文件部分等内容，因此正常查询会用大字体行填充记录 — codegraph_search 和 codegraph_explore 最糟糕，其中噪音随着结果数量的增加而增加。节标题现在是粗体标签，以正常文本大小呈现，同时保持相同的结构。端子/CLI 输出不变。 （#778）
  • 指向非常大的存储库（数万个文件）的 MCP 服务器在重新启动后不再挂起第一个工具调用。启动时，CodeGraph 会根据磁盘上的当前文件来协调其索引，并且在一个巨大的存储库上，协调可以运行几分钟，同时阻止第一个请求 - 足够长的时间，以至于后台服务器有时会在扫描中强制重新启动，因此第一个查询根本不会返回。协调现在在运行时产生（保持服务器响应而不是固定它），并且第一个工具调用在应答之前仅短暂等待它并让其余部分在后台完成 - 因此您可以获得快速的第一个响应，并且索引仍然可以赶上。设置 CODEGRAPH_CATCHUP_GATE_TIMEOUT_MS 以调整第一次调用等待的时间（默认 3000 毫秒），或设置 =0 以始终等待完全协调。 （#905）
  • codegraph install 现在连接您的代理并停在那里 - 它不再索引当前目录。构建项目的图表始终是显式的 codegraph init（或 codegraph index），因此您可以决定对哪些内容以及何时进行索引，并且无论您是全局安装还是仅针对一个项目安装，步骤都是相同的。这消除了项目本地安装静默索引但全局安装没有的混乱，以及文档和工具在是否仍然需要运行 init 方面存在分歧。 （#826）
  • 使用 forwardRef、memo 或 styled-components/emotion 声明的 React 组件（const Button = forwardRef(...)、const Card = memo(...)、const Box = styled.button\…`) are now recognized as components, so finding where they're used works. Before, they were indexed as plain constants, so codegraph callersand impact analysis reported "no callers found" even when the component was rendered across dozens of files — a dangerous false "safe to change" right before refactoring a shared component. Now every
  • .tsx / .jsx 文件中定义的 React Router 和 Next.js 路由现已编入索引。以 JSX 形式编写的路由（<Route path="/users" element={<UsersPage/>}/>、createBrowserRouter([...]) 和 Next.js app//pages/ 页面文件）被完全跳过（仅选取恰好存在于普通 .ts/.js 中的路由），所以“在该路径上呈现什么？”大多数 React 应用程序都缺少路由 → 页面组件链接。现在，这些路由显示在 codegraph search/codegraph_explore 中，并连接到它们渲染的组件，就像其他框架上的后端路由 → 处理程序链接一样。
  • 当您编辑函数所在的文件时，codegraph sync（以及始终打开/MCP使用背后的文件观察器自动同步）不再删除函数的调用者。编辑后重新索引文件 - 即使仅文档字符串更改 - 会切断来自其他未更改的文件的 calls / references 边缘（例如 from pkg import mod; mod.fn() 调用者或任何跨文件引用），因此 codegraph callers / impact 会突然报告整个代码库中使用的函数“无调用者”，直到下一次完全重新索引。现在，同步会在重新索引时保留那些传入的跨文件边缘，即使编辑移动了其行号，也会将它们与符号重新匹配。在大型 Python 包树中最为明显，但它适用于每种语言。谢谢@JosefAschauer。 （#899）
  • codegraph index 现在从头开始重建完整的图表，因此它产生与新的 codegraph init 相同的结果，而不是报告“0 个节点，0 个边”并且看起来像是擦除了索引。以前，在未更改的项目上重新运行 index 会跳过每个文件（其内容未更改）并显示空的摘要；现在，它每次都会清除并重新索引，以实现诚实、完整的重建。使用 codegraph sync 在完全重建之间进行快速增量更新。谢谢@Arc-univer。 （#874）
  • 当实时观看无法再进行 trusted 时，自动同步图表的文件观察器现在会完全失败，而不是在索引悄悄变旧时看起来很健康。如果操作系统用完文件监视资源，或者另一个进程持有写入锁的时间比正常保存的时间长得多，CodeGraph 现在会禁用一次自动同步 - 并显示一条明确的消息告诉您运行 codegraph sync （或依赖 git 同步挂钩）来刷新 - 而不是永远重试或在循环中重复相同的错误。当自动同步被禁用时，CodeGraph 的工具响应（和 codegraph status）现在很清楚地说明了这一点，因此您的 AI 代理知道直接读取文件，而不是 trust 冻结索引。这对于长时间运行的 MCP/守护进程会话来说最为重要，否则这些会话可能会在看似有效的情况下继续提供过时的结果。谢谢@thismilktea。 （#876）
  • 在 Linux 上，在大型项目上达到内核的 inotify 监视限制不再默默地让一半的树不受监视。 CodeGraph 现在会告诉您一次 - 命名要引发的确切设置（fs.inotify.max_user_watches，例如 sudo sysctl fs.inotify.max_user_watches=1048576） - 并不断实时监视它可以注册的目录，而 codegraph sync （或 git 同步挂钩）涵盖其余部分。 （#876）
  • 长期运行的 MCP 服务器现在会注意到 git 工作树何时获得自己的索引。以前，如果服务器（或共享守护进程）在您运行 codegraph init 之前首先看到工作树 - 因此查找会走到主结账的索引 - 它会在整个生命周期中固定该决定：即使工作树有自己的 .codegraph/ 后，每个查询都会继续命中主结账的索引，并且每个结果都带有错误的“此索引属于不同的 git 工作树”警告，直到您重新启动服务器。 CLI 正确，但 MCP 服务器没有，重新索引也没有帮助。服务器现在会在每次调用时重新检查路径属于哪个索引，因此工作树自己的索引会被拾取，并且过时警告会消失，而无需重新启动。 (#926)
  • 当您的索引被删除并在同一路径重建时，长时间运行的 MCP 服务器现在可以恢复。如果 .codegraph/ 在服务器保持打开状态时被删除并重新创建 - 最简单的方法是在同一路径重新创建 git 工作树，或者 rm-ing .codegraph/ 并再次运行 codegraph init - 服务器会继续读取旧的、已删除的数据库文件并提供冻结快照：重命名或删除的符号仍然显示为活动状态，新符号丢失，并且 codegraph sync 无法刷新它 - 只能重新启动服务器修复了它。服务器现在检测到数据库文件已从其下方换出，并重新打开活动的文件，因此结果无需重新启动即可保持正确。 （在 Linux 和 macOS 上；Windows 不允许删除打开的文件，因此不受影响。）(#925)
  • MCP 服务器现在打开并自动同步位于封闭 git 存储库忽略的文件夹内的项目。以前，如果您索引的目录位于 gitignored 的较大存储库中，则共享 MCP 守护程序无法打开该项目 — 其日志重复为 Failed to open project … path should be a path.relative() d string, but got "./" — 因此文件监视程序从未启动，并且索引默默地变得过时，直到您手动运行 codegraph sync（设置 CODEGRAPH_NO_DAEMON=1 是唯一的解决方法）。守护进程现在打开项目并开始按预期进行监视。在 Windows 上的 Codex 中最为明显，但原因并非特定于平台。 (#936)
  • 子模块的 git 工作树不再被索引为该子模块代码的重复副本。 CodeGraph 已经跳过了普通的工作树（它索引的存储库的第二个工作视图），但是从子模块创建的工作树（在单一存储库中常见，将子模块检查到工作树中以进行并行功能工作）被误认为是真正的嵌入式存储库并被扫入，复制它与真实子模块签出共享的每个符号（一份报告约有 28% 的索引为重复项，导致查询结果和数据库都膨胀）。现在可以识别并跳过这些子模块工作树，而子模块自己的签出仍保留为不同代码的索引。谢谢@charlesxu2026-ship-it。 (#945)
  • 使用导出/可见性宏（class MYLIB_EXPORT Foo : public Bar { … }，标头中常见的 DLL 导出/可见性模式）注释的 C++ 类或结构不再被错误索引为跨越整个类主体的函数。由于不知道宏是宏，解析器将其读取为类型，并将整个声明读取为函数，因此该类以幻影 function 的形式出现，在 codegraph callers、codegraph impact 和爆炸半径分析以及倾斜的符号计数中显示为错误调用者。 CodeGraph 现在可以识别这种错误解析并删除虚假节点。谢谢@spwlyzx。 (#946)
  • codegraph status 不再报告 CodeGraph 故意保留在索引之外的文件的虚拟挂起更改 - 已提交依赖项目录内的跟踪文件（签入的 vendor/ 或 node_modules/），或 .gitignored 目录下的跟踪文件。完整索引正确地排除了这些内容，并且 codegraph sync 永远不会对它们进行索引，但 codegraph status 背后的快速更改检测器将对此类文件的每次编辑标记为“已修改”（并将新编辑标记为“添加”） - 因此，无论同步多少次，挂起的更改计数都不会清除。更改检测现在应用与完整索引相同的忽略规则，因此 status 与 sync 一致，并且基于 CodeGraph 更改检测 API 构建的工具获得相同的更正列表。 (#766)
  • 通过符号链接目录访问的文件现在指向项目之外的索引，而不是默默地跳过。当您的存储库中的文件夹是指向存储库根目录之外的位置的符号链接（Dota 2 自定义游戏和类似的 SDK 链接项目的标准布局，其中 game/ 和 content/ 链接到引擎树）时，CodeGraph 会按照符号链接发现这些文件，但随后会在读取、记录 Path traversal blocked in batch reader 并在其下不索引任何内容时阻止其中的每一个文件。读者现在同意目录扫描并索引这些文件。对 ../ 路径转义的防范措施没有改变，并且防止代理从存储库外部获取文件内容的保护措施也没有改变——只有索引器自己的读取路径遵循这些存储库内符号链接。 (#935)
