trl v1.14.0

特点

trl.losses 消失了：DPO、KTO 和 GRPO 流式传输自己的日志概率

[!警告] from trl.losses import FusedLinearDPOLoss（或 FusedLinearKTOLoss、FusedLinearGRPOLoss、FusedLinearJSDLoss）不再起作用。 v1.13 中引入的模块已被删除。 v1.13 将 Liger 的 chunked_loss 出售给 trl.losses 作为保留操作，而不是目的地 (#7063)。它面临的问题是：这些课程重新实现了每个训练师的损失数学，因此 TRL 携带每个公式的两个副本，并复制漂移。那个漂移就是错误所在。 GRPO 的 grad_norm 与默认路径不同，KTO 忽略了 PEFT 下的参考模型，KTO 类权重和 DPO label_smoothing 被默默丢弃。最糟糕的是，在普通 DDP 下，融合路径会在展开模型上产生损耗，因此 DistributedDataParallel 的减速器从未配备，梯度也从未全部缩减：每个等级都默默地保留自己的等级。 解决方法是停止重新实施。融合路径中的所有 DPO、KTO 和 GRPO 需要的是所选令牌的每个令牌对数概率，TRL 已经拥有 _ChunkedLogProbFunction 来实现这一点：它使用在线 logsumexp 流式传输词汇并在向后传递中重新计算。现在每个训练器都运行 backbone -> _ChunkedLogProbFunction -> its own existing loss code，没有变化。每次损失都执行一次，并且保留内存胜利，因为完整的 logits 仍然从未实现。 存在十三项限制只是因为损失被以无法表达这些选择的形式重写。大多数都消失了：带有 use_liger_kernel=True 的 DPO 现在接受混合损失类型、f 散度和预先计算的参考对数概率，GRPO 获得熵和离策略屏蔽。仍然拒绝：use_weighting，compute_metrics，lm_head上的PEFT适配器，即时学习PEFT，以及MoE辅助丢失。 单 H100、Qwen3-0.6B、bs=4、序列 512： |配置 |中值步长|高峰| | --- | --- | --- | | v1.13 带保险丝，内联参考 | 0.2243 | 7.05国标| | v1.14 分块，内联参考 | 0.2457 s (+9.5%) | 7.05国标| | v1.14 分块，precompute_ref_log_probs=True | 0.1971 s (-12.1%) | 4.83 GB (-31%) | 第三行是要点：该配置以前不存在，因为融合路径完全拒绝了预先计算的参考日志概率。 use_liger_kernel=True 仍然可以工作，并且仍然可以通过 Transformer 启用 Liger 的模型内核。在 DPO、GRPO 和 KTO 中，它现在选择 TRL 的分块对数概率路径，而不是 Liger 的融合损失。

融合的 Triton logprob + 熵内核现在在 TRL 中提供

损失头是 TRL 拥有的唯一热路径：变压器已经对模型内部进行了内核化，而 Hub 上的任何内容都无法涵盖解码器之后发生的情况。在一台 H100（bf16、V=151936、H=4096、8192 个代币）上，selective_log_softmax 加 entropy_from_logits 的成本为 12.8 ms，2.32 GiB 超过 [8, 1024, 151936]。融合的 Triton 内核在 0.89 毫秒内执行相同的操作，大约是 14 倍，并且比它所替换的 bf16 路径更接近 fp32 参考。 GRPO 每个步骤运行两到四次。 它现在位于 trl.kernels 的树内，并且在 CUDA、ROCm 和 XPU 上默认启用，并以 PyTorch 实现作为后备。它被短暂地从集线器加载；这是相反的，因为这个内核是纯 Triton 并在运行时编译，所以 Hub 没有购买任何东西，同时花费了与内核是否工作无关的版本门，离线下载失败，安装了 kernels 的任何人的 trust_remote_code=True，静默的 except Exception: pass 包围了所有这些，并且在 CI 中跳过了 13 项测试中的 13 项。

打破

删除了六名实验训练员

GRPOWithReplayBufferTrainer、BCOTrainer、PRMTrainer、XPOTrainer、NashMDTrainer 和 GSPO 令牌训练器已从 trl.experimental 中消失。 改变的不是保证，trl.experimental 一直没有保证，而是决定现在被写下来了。删除过去常常一次争论一个拉取请求，每个线程在获得该功能之前都会重新提出该策略。 #7182 解决了判断的权重，#7254 将其放入文档中：使用情况、外部问题和来自实际运行该功能的人员的拉取请求、稳定的培训师是否已经涵盖它、维护成本、下游消费者、所有者和年龄。故意输入判断而不是测试：没有阈值，没有通知周期，并且数字保留在删除拉取请求中，您可以在其中检查它们。纸质索引条目的寿命比它所描述的代码的寿命长。 数字说明了情况。 BCOTrainer 是 1,600 行，带有自己的参考模型处理、DeepSpeed 准备、标记化和评估循环，可在两个月内进行 11 次真正的训练；这也是 TRL 完全依赖 scikit-learn 和 joblib 的唯一原因，而这两者现在都已从 pyproject.toml 中消失了。 GRPOWithReplayBufferTrainer 从 GRPO 手工复制了 _generate_and_score_completions，并漂移到 616 个不同行中的 385 个，进行 8 次训练。

修复

  • 在普通 DDP 下，KTO 的梯度从未全部缩减。 compute_loss 仅通过分布式包装器重定向 ZeRO-3 和 FSDP，因此在普通 DDP 上，损失在未包装模型上运行，DistributedDataParallel.forward() 从未运行，其减速器从未装备，并且每个等级默默地保留自己的梯度。作者：@qgallouedec，https://github.com/huggingface/trl/pull/7247
  • 当输入表被切片时，包装重复的数据。 _pack_wrapped 调整切片视图的输出大小，但从原始子缓冲区读取，因此它从缓冲区的开头而不是从切片重新读取，并且 datasets.map(batched=True) 传递切片表。作者：@qgallouedec，https://github.com/huggingface/trl/pull/6670
  • 仅记录某些等级的奖励函数挂起或使运行崩溃。 GRPO 和 RLOO 循环每个等级所持有的键，并为每个键调用一个集体，因此等级称为不同的集体：等级 0 上的 log_metric 单独挂在 NCCL 上，而 log_extra 在分配 1EB 的 gather_object 内崩溃。作者：@behroozazarkhalili，https://github.com/huggingface/trl/pull/7382
  • 特殊令牌 ID 现在到达 Trainer 实际读取的配置，因此它不再在训练时重新对齐它们并记录用户未进行的更改（#7093 的一部分）：训练器中的 eos (#7127)、写入复合模型的文本配置 (#7315)、奖励模型 pad 令牌 (#7318) 以及应用于视觉数据集的请求的 pad 令牌 (#7316，第7352章）
  • 默认情况下，不要在蒸馏和 GOLD 入口点中量化老师，@behroozazarkhalili 在 https://github.com/huggingface/trl/pull/6769
  • 当数据集缓存是节点本地时，由 https://github.com/huggingface/trl/pull/7241 中的@qgallouedec 为每个节点准备一次数据集
  • 从https://github.com/huggingface/trl/pull/7248中@qgallouedec的模型配置中读取MoE辅助损失系数
  • 等待 @albertvillanova 在 https://github.com/huggingface/trl/pull/7213 中编写为可调用类的异步奖励函数

  • 仅在 @kashif 在 https://github.com/huggingface/trl/pull/7193 中以流模式对卸载的激活存储进行重复数据删除
