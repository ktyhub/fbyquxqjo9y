mempalace v3.3.5

这个项目是干啥的：一个给AI代理用的长期记忆系统，能存能查记忆、协调代理日志还支持团队共享，给做AI应用的开发者用。

变更架构图

亮点

  • 从损坏的 ChromaDB 宫殿中恢复 — mempalace repair --mode from-sqlite 直接从完好的 chroma.sqlite3 表重建一个新宫殿，无需针对损坏的索引打开 ChromaDB 客户端，绕过了此前使恢复不可能的 Collection.count() 失败（#1308）。已在一个 52,300 行的宫殿上验证。tool_search 也会重试挖掘后出现的瞬时 Internal error: Error finding id，并通过 index_recovered: true 报告恢复成功；这仍是部分修复，因为 tool_check_duplicate 和其他触及索引的工具尚未覆盖。
  • 破坏性变更：更严格的时间校验 — sanitize_iso_temporal() / sanitize_iso_date() 现在只接受 YYYY-MM-DD 或规范的 UTC 日期时间（YYYY-MM-DDTHH:MM:SSZ / +00:00）。"yesterday"、"2026"、"2026-05" 这类输入现在会报错，而不是静默返回空结果；请将使用部分日期的调用方迁移为完整日期。add_triple() 也会在写入时拒绝 valid_to < valid_from，把此前已存储但不可达的数据变成即时错误。
  • 更安全的持久化与跨进程隔离 — EntityRegistry.save() 现在使用同级临时文件、fsync 和 os.replace()，防止崩溃截断数月的注册表数据。ChromaBackend.close_palace() 释放 ChromaDB rust 侧的 SQLite 锁，而 MCP 知识图谱使用按路径的惰性缓存，因此轮换 MEMPALACE_PALACE_PATH 不会再读到错误租户的数据库。
  • Windows、大型宫殿与路由修复 — 在 mcp_server、hooks_cli、cli 和 fact_checker 中，Windows stdio 一致地重新配置为 UTF-8，修复了西里尔文/CJK 输出乱码。mempalace compress 现在对抽屉抓取分页，避免超过约 32k 抽屉时崩溃。miner.detect_room 使用分隔符限定的匹配，修复了单仓库误路由，例如 views/billing-page/src/Foo.test.tsx 被分配到 interviews 房间。
  • 升级建议 — 如果你遇到过 HNSW 损坏、挖掘后搜索失败、Windows 编码问题、注册表丢失担忧、租户切换或超大型宫殿，强烈建议升级。健康的单宫殿 Linux 部署通常可以跳过，除非受时间迁移影响。尽管有”没有新的面向用户功能”的说法，生成的条目还包括用于更广泛混合搜索候选的 candidate_strategy="union"、四个自动保存工具，以及考虑 gitignore 的抽屉清理；因此这不是空操作版本。

3.3.5 是一个修复版本。 没有新的面向用户功能——本周期的精力投入在数据完整性、恢复和跨进程正确性上。如果你的宫殿曾在大挖掘后遇到 Internal error: Error finding id，或者你的知识图谱三元组曾静默消失，或者你运行在 Windows / 多租户主机上——这个版本就是为你准备的。

重点修复：

  • mempalace repair --mode from-sqlite 可挽救卡在 apply_logs 上的宫殿。 当 ChromaDB 的 HNSW 段写入器卡死时（上游及 #1308 报告的损坏类型），--mode legacy 和内联修复都会把 Collection.count() 作为首次读取——而正是这个调用会抛错。旧失败模式是修复打印 Cannot recover — palace may need to be re-mined from source files，尽管 SQLite 表完全完好。新模式通过元数据段连接直接从 chroma.sqlite3 读取 (id, document, metadata)，从不对损坏宫殿打开 chromadb 客户端，并在你配置的嵌入函数下把所有内容重新 upsert 到一个新宫殿。已在一个 52,300 行的真实损坏宫殿上端到端验证。（#1308）
  • 知识图谱中的两类静默丢失现在会成为写入时错误。 valid_to < valid_from 的三元组过去会被持久存储但不可达（时间过滤器匹配不到任何 as_of）；add_triple() 现在在写入时拒绝倒置区间。转发给 SQLite 的日期字符串通过 sanitize_iso_temporal()（别名 sanitize_iso_date()）预先校验，它接受 YYYY-MM-DD 和规范 UTC 日期时间（YYYY-MM-DDTHH:MM:SSZ / +00:00），并拒绝其他一切——像 "yesterday" 这样的自然语言输入不再静默产生空结果集。行为变更：在 3.3.4 中可用的部分日期输入（"2026"、"2026-05"）现在会报错；请改用完整日期或规范 UTC 日期时间。（#1214、#1164、#1167、#1374、#1417）
  • EntityRegistry.save() 现在具备崩溃安全性。 人物/项目映射是数月的挖掘数据，旧代码使用非原子的 Path.write_text()——在截断与完整刷新之间发生断电、OOM 或 kill -9，会静默清空它（注册表的 load() 会吞掉 JSONDecodeError）。保存现在写入同级临时文件、fsync，然后 os.replace() 到位。在重命名返回之前的任何崩溃中，旧注册表保持完好。（#1215）
  • MCP tool_search 能挺过批量挖掘后的 HNSW 刷新窗口。 CLI 挖掘之后，ChromaDB 的 HNSW 段元数据可能有约 30-60 秒未刷新；wing 范围的 MCP 搜索在整个窗口内都会撞上 Internal error: Error finding id。tool_search 现在检测这一特定瞬态，清除该宫殿的 MCP 本地和共享后端缓存，休眠 2 秒并重试一次。成功的重试会打上 index_recovered: true 标记，方便调用方观察。这是对更广泛的 #1315 集群的部分修复——tool_check_duplicate 和其他触及索引的工具仍需同样的包装。（#1396）
  • Windows 和多租户主机上的跨进程正确性。 ChromaBackend.close_palace() 现在会正确释放 ChromaDB 的 rust 侧 SQLite 文件锁——在 shutil.rmtree 之后重新打开同一宫殿路径不再因 SQLITE_READONLY_DBMOVED 失败。MCP 服务器的 _kg 不再是模块级单例：在工具调用之间轮换 MEMPALACE_PALACE_PATH 的多租户主机现在会通过按路径的惰性缓存命中正确的 SQLite 文件。（#1067、#1105、#1136、#1160）
  • Windows stdio 全面改为 UTF-8。 mempalace search > out.txt 和管道式 fact_checker 调用不再在进程边界处把西里尔文/CJK 抽屉文本变成乱码。mcp_server、hooks_cli 以及 cli/fact_checker 都以相同方式重新配置。（#1282）
  • miner.detect_room 针对单仓库的路由修复。 子串检查是双向的，因此任何互为子串的标记都会匹配——views/billing-page/src/Foo.test.tsx 被路由到 interviews 房间，因为 "views" in "interviews" 先匹配上了。现在使用分隔符限定的标记匹配（-、_、.、/）。（#1004，关闭 #1002）
  • mempalace compress 在超过约 32k 抽屉的宫殿上不再崩溃。 抽屉抓取现在分页，与 miner.py 中的 #851 修复一致。（#1073、#1107）

内部方面：测试可靠性也得到改进——tests/test_palace_locks.py 和 tests/test_chroma_collection_lock.py 把子进程生成从 fork 改为 spawn（Python 3.13 + 多线程父进程在 fork 下会死锁，且 macOS 通过 CoreFoundation 禁止 fork-without-exec），多个测试文件现在把 sqlite3.connect(...) 包在 contextlib.closing() 中，让连接在失败路径上也能释放。（#1430、#1431）

承诺不变。每个词都精确存储。一切都留在你的机器上。没有遥测。不会悄悄回退到我们未告知的云 API。每个版本都在打磨已有的能力。
