mempalace v3.3.6

修订 发布时间2026年6月6日 来源MemPalace/mempalace 英文原文

3.3.6 是一个功能发布。 该周期的头条工作：默认多语言回忆（embeddinggemma 取代 MiniLM，从 0.35 → 0.88 跨语言余弦跳跃），生活记忆图的第一次切割（机翼内的走廊，机翼之间的隧道，Hebbian 增强 + Ebbinghaus 衰减，因此连接随着使用而增强，不使用则消失），办公文档挖掘（PDF， DOCX、PPTX、XLSX、RTF、EPUB（通过新的 --mode extract）、虚拟行号 + 手术室指针（在确切日期引用确切的行范围）以及实体检测清理通道，使“代码”远离您的走廊，并使“克劳德代码”原子化。 承诺没有动摇。每个词都准确存储。一切都保留在您的机器上。没有遥测。每个版本都会增强已有的内容。

特点

  • 通过 --mode extract 进行 Office 文档挖掘。 除了现有的源代码/文本路径之外，新的 mempalace mine <dir> --mode extract 还可提取 PDF、Word (.docx)、PowerPoint (.pptx)、Excel (.xlsx)、RTF 和 EPUB 书籍。使用 pip install mempalace[extract] 安装 — 为 RTF 拉出 striprtf，为二进制格式拉出 MarkItDown（带有 [docx,pdf,pptx,xlsx] 子附加功能）。 Python 3.9 用户获得 RTF 覆盖只是因为 MarkItDown 需要 3.10+。提取路径中的抽屉携带 extract_mode 元数据，因此 convo 矿工“已经开采了？”检查和抽屉 ID 生成在每种模式下保持隔离（#1528）。 (#1555)
  • 虚拟行号 + 手术室指针。 存储的抽屉现在带有虚拟行号，因此读取的 CLI 动词和手术室指针可以引用确切的行范围。 Closet 指针（第 6a 层）包括从文件名和内容正文日期解析派生的日期+行范围信息（python-dateutil 现在是核心 dep），因此 MemPalace 可以为您指出确切日期的确切行，而不仅仅是“这个抽屉中的某个位置”。 （＃1555，＃1584）
  • 翼内走廊。 当两个实体（人、项目、主题）同时出现在同一个抽屉中时，矿工现在会记录一条“走廊”——在该翼内连接它们的图形边缘。作为 compute_hallways_for_wing 中挖掘后步骤的一部分自动计算，因此图表随着新内容而增量增长，无需单独的命令。一个宫殿内跨房间实体导航的基础。 （＃1558，＃1560）
  • 从走廊提升跨翼隧道。 当同一个实体出现在多个翼楼的走廊中时，MemPalace 现在会自动将其提升到隧道中 - 让查询从一个人的翼楼跳到他们出现的项目翼楼，无需任何人手动调用 create_tunnel。现有 compute_topic_tunnels 路径的主题隧道保持不变。 (#1565)
  • **生活记忆动态（赫布增强+艾宾浩斯衰变）。**每当新内容（“将电线连接在一起的东西”）强化相同的连接时，走廊和隧道就会变得更强，如果连接停止出现在传入的抽屉中，走廊和隧道就会逐渐消失。导航权重跟踪真实的宫殿使用情况，而不是静态的，因此随着宫殿的实际使用，检索排名会随着时间的推移而提高。 (#1578)
  • API 工具记录自动路由到 wing_api。 来自 API 式 AI 工具（Claude Code、Claude.ai、ChatGPT、Slack-bot 导出、通用 OpenAI 形状 JSON 等）的对话记录现在路由到专用的 wing_api，而不是混合到人类对话翼中。当您寻找“我说了什么”与“代理说了什么”时，可以防止工具调用流量污染个人/项目部门，并提高搜索精度。 (#1236)
  • 新安装默认多语言嵌入：embeddinggemma-300m ONNX（q8，MRL→384-dim）。 MemPalace 之前的嵌入器 (all-MiniLM-L6-v2) 仅接受英语训练 — 德国/法国/HI/IT/KO/RU 上平行翻译文本平均值 0.35 的跨语言余弦相似度（RU 为 0.17，近正交）。俄语用户实际上无法找到自己的记忆，这违背了 CLAUDE.md 的“100% 召回”设计承诺。 mempalace/embedding.py 中的新 EmbeddinggemmaONNX 类使其达到 0.88 平均值（通过直接 ONNX 运行时测试与 Ollama gguf 进行无损验证）。首次使用时通过 huggingface_hub 延迟下载 onnx-community/embeddinggemma-300m-ONNX (~300 MB)。通过 Matryoshka 表示学习将输出截断为 384 维，因此该模型是 ChromaDB 384 维集合的替代品 - 没有架构更改。 Sim 前缀 ("task: sentence similarity | query: ") 会自动应用。 Onboarding (python -m mempalace.onboarding) 现在提供多语言模型作为默认设置 - 选择它将 embedding_model: embeddinggemma 写入 config.json，因此后续运行会选择它而无需重新提示。从未设置环境变量或运行载入的现有安装保留在 minilm（向后兼容）上。 MEMPALACE_EMBEDDING_MODEL=minilm|embeddinggemma 覆盖两者。在现有宫殿上切换模型需要重新嵌入 - 更改后运行 mempalace repair rebuild-index。 (#1483)
  • 多语言 deps 移至核心。 huggingface_hub、tokenizers 和 numpy 现在是必需的 deps，因此多语言路径在 pip install mempalace 之后开箱即用。 [multilingual] extra 保留为无操作别名，以便与安装脚本向后兼容。 300 MB ONNX 模型本身仍然在首次使用时延迟下载，而不是在安装时延迟下载。
  • 更友好的 ChromaDB EF 名称不匹配错误。 在不运行 rebuild-index 的情况下在现有宫殿上切换 MEMPALACE_EMBEDDING_MODEL 之前曾出现 ChromaDB 的裸 Embedding function conflict: new: X vs persisted: Y ValueError — 准确，但没有告诉用户如何恢复。 ChromaBackend.get_collection() 现在包装该错误并指向两个选项：恢复环境变量，或运行 mempalace repair rebuild-index --palace <path>。 (#1483)
  • hooks.auto_save 用于静音模式会话切换。 新的配置旋钮（以及通过保存挂钩连接的 --silent CLI 标志）允许用户选择退出 Stop / PreCompact 上的自动日记保存。对于您不希望捕获每个对话的“静默模式”会话很有用。默认行为不变 - 除非明确禁用，否则自动保存仍会运行。 (#711)
  • 从实体检测中过滤常见的英语内容词。 高频英语内容词（“系统”、“用户”、“内存”、“项目”、“上下文”等）被每个抽屉检测器标记为实体，并污染实体注册表作为“人”。现在，在实体分类期间会查阅已提供的 COCA 单词列表（前 N 个内容单词），以便在到达注册表之前对其进行过滤。针对捆绑单词列表中格式错误的 JSON 进行了强化。 (#1605)
  • **挖掘时不区分大小写的实体匹配。**初始宫殿构建（mempalace init）不区分大小写地匹配实体名称，但增量挖掘过程中使用的每个抽屉标记器却没有 - 因此同一个人在 init 和 ingest 之间被标记不同（“Aya”与“aya”成为不同的实体）。增量标记器现在镜像不区分大小写的匹配器，恢复整个宫殿生命周期中实体标记的一致性。 (#1557)

错误修复

  • 三个 upsert 路径中的静默数据丢失。 三个 upsert 站点（文件摄取、对话摄取和一个修复分支）正在对未分块的内容调用嵌入器，在嵌入器的最大令牌限制下静默截断。长抽屉落地时仅索引了其主要部分，这违反了长格式内容的“100% 召回”承诺。现在，所有三个都首先通过分块器进行路由，以便嵌入和存储完整的文档。 （#1540，#1539 的后续）
  • 段落分块器为长段落发出过大的块。 段落拆分器假定段落总是短于 CHUNK_SIZE 并将它们整个发出；长段落（法律文本、密集的技术文章）悄然超出了嵌入器的上下文窗口。分离器现在对每个发出的块进行硬上限以纪念 CHUNK_SIZE。 （#1538，修复#1534）
  • 每个文件的块上限是硬编码的，对于大型转录本而言太低。 每个文件的块上限为针对源代码调整的值的安全限制；挖掘非常大的对话记录会悄悄地将尾部丢弃到超过该上限的位置。现在可配置，默认值提高到覆盖实际的转录本大小。 （#1554，修复#1455）
  • Windows 上的挂钩子进程/ChromaDB 死锁。 Stop/PreCompact 挂钩可能会对 Windows 上已打开的 ChromaDB client 造成死锁，从而使主机 (Claude Code) 陷入等待挂钩状态。修复分为三个部分：矿锁回收时的陈旧 PID 超时、MCP 服务器中的空闲退出路径以及检测到死锁模式时的结构化错误，以便主机可以恢复。 （#1562，修复#1552）
  • create_tunnel 损坏的连字符翼名称。 端点解析器在 - 上分裂，因此名称包含连字符（mem-palace、my-app）的翼在名称中间被截断，并且隧道指向不存在的端点。端点解析现在保留完整的段。 （＃1529，修复＃1504）
  • MCP 知识图缓存为符号链接/大小写不同的宫殿路径生成了重复的图。 缓存键是原始路径字符串，因此 /Users/me/.mempalace/palace 和 /Users/me/.mempalace/Palace（在 macOS 上大小写折叠）或符号链接别名生成两个单独的缓存 KnowledgeGraph 实例，指向同一个 SQLite 文件，存在陈旧读取风险。缓存现在通过 realpath + normcase 进行规范化，因此它们会折叠到单个规范密钥上。 （#1383，修复#1372）
  • 保存挂钩截断连字符的项目文件夹名称。 Wing-name 解析器在 - 上进行拆分并仅保留第一段，因此 mem-palace 变成了 mem。修复保留了完整的项目文件夹 slug，因此连字符的宫殿在钩子调用中保持一致。 （#1424，修复#1410）
  • 矿工默默地跳过符号链接。 用户对挖掘后丢失的数据感到困惑；矿工跳过符号链接而不显示它。现在记录每个跳过的符号链接及其原因，以便间隙可见。 （#1466，修复#1462）
  • 主机泄漏的 PYTHONPATH 可能会在导入时影响 MemPalace 自己的模块。 软件包 __init__ 现在会在导入时删除泄漏的条目，因此导入的 MemPalace 始终是已安装的条目。 （＃1439，修复＃1423）
  • macOS stock-bash hook 脚本。 Hook 脚本使用了 mapfile (bash 4+)，破坏了 macOS stock /bin/bash 3.2。切换到 sed 管道，以便钩子在每台 Mac 上都能开箱即用。 （#1441，修复#1440）
  • 插件 Stop/PreCompact 挂钩可能会无限期地挂在卡住的子进程上。 有界超时可确保主机始终能够取得进展，即使 MemPalace 的子进程不健康也是如此。 （＃1470，修复＃1465）
  • MCP 处理程序现在针对格式错误的输入返回结构化 JSON-RPC 错误。 未知参数名称返回 -32602 Invalid params，而不是非结构化 Python TypeError；错误形状的参数返回结构化错误而不是原始回溯。 （＃1500，＃1513）
  • CLI 将“宫殿不存在”与“宫殿存在但空”区分开来。 对于新用户来说看起来相同的两个状态现在分别报告，并为每个状态提供可操作的下一步消息。 （#1532，修复#1498）
  • mempalace repair 后通：VACUUM + FTS5 重建。 宫殿修复后，SQLite 知识图文件保留了碎片页面和过时的 FTS5 索引；运行 VACUUM 并在最后重建 FTS5 可回收磁盘并恢复搜索性能。 (#1523)
  • Convo 矿工模式隔离。 “已经开采？”检查和抽屉 ID 生成忽略了 extract_mode，因此切换模式要么重新挖掘相同的内容（数据重复），要么在模式之间发生冲突的抽屉 ID。按模式确定范围可以使每个模式的抽屉保持隔离并正确进行重复数据删除。 （#1528，修复#1505）
  • 在挖掘结束时进行 FTS5 验证。 挖掘现在将验证 FTS5 索引完整性作为后续步骤，以便在写入时而非读取时捕获损坏。 （#1548，修复#1537）
  • hooks_cli 在浅安装路径上崩溃。 假设深度安装树，索引为 Path.parents[3] 的代码会在 MemPalace 从浅路径（例如 /opt/mp）运行时引发 IndexError。添加了一个防护，因此浅安装不再因钩子命令而崩溃。 (#1585)
  • HNSW 段隔离：零字节与缺失暗淡。 早期隔离启发式标记任何缺少 dim 元数据字段的 HNSW 段已损坏，但大多数都是可恢复的；该检查现在可以区分可恢复的缺失暗淡和实际损坏，从而保留工作索引段。零字节链接列表文件（部分写入的段）现在被彻底拒绝。 （#1452、#1461、修复#1457）
  • 以 UTF-8 而不是 cp1252 编写的矿井锁持有者文件。 非 ASCII Windows 用户名和路径不再损坏锁文件并破坏过时锁检测。 (#1438)
  • 矿工槽声明现在立即写入占位符 PID。 声明和 PID 写入之间的崩溃不再留下幻像锁。 （＃1543，修复＃1443）
  • mine_convos 现在在 mine_palace_lock 内部运行。 两个并发的 convos mine 调用不再会损坏索引。 (#1477)
  • 迁移工具清理。 ChromaDB 版本迁移工具现在会在迁移过程中触发异常时关闭其 SQLite 连接并删除临时宫殿目录；失败的迁移将停止泄漏文件句柄和磁盘。如果写入或重命名失败，实体注册表原子写入现在会删除其 .tmp sidecar。 （#1216、#1408、修复#1373）
  • 修复工具允许空/无元数据单元。 ChromaDB 在重建过程中偶尔会返回带有空元数据字典或 None 的单元；现在，两者都被迫进行合理的默认设置，以便重建工作完成，否则陷入困境的宫殿也将得到恢复。 （#1459、#1445、修复#1426）
  • create_tunnel MCP 处理程序现在传播错误。 错误的端点或方向被吞并并作为误导性成功返回；现在作为结构化 MCP 错误传播。 （＃1546，修复＃1473）
  • 显式隧道存储在硬编码中~/.mempalace/tunnels.json path that ignored MempalaceConfig.palace_path. Drawers, KG triples, the people map, and every other piece of palace state honour the configured palace_path (and the MEMPALACE_PALACE_PATH env var), but palace_graph._TUNNEL_FILE was a module-level constant initialised once from os.path.expanduser("~") + "/.mempalace/tunnels.json". Under any setup where $HOME is isolated from the configured palace — subagent profiles with their own $HOME, sandboxes, multi-tenant hosts, container mounts that move the palace to /srv/ — drawers landed in the configured palace while tunnels silently landed in a different file that no other process touching the same palace could see. Worst case is the agentic one: an isolated worker calls create_tunnel then list_tunnels`ZZPH10 0ZZ`palace_graph._TUNNEL_FILE is replaced by _get_tunnel_file() which derives the path from a new MempalaceConfig.tunnel_file property (sibling of palace_path). The default single-user install is unchanged because the default palace_path is still ~/.mempalace/palace and its sibling tunnels.json is the legacy path. Backwards-compatibility: if the configured tunnel file does not exist but a file is present at the pre-3.3.6 hardcoded ~/.mempalace/tunnels.json path AND the two paths differ, _load_tunnels logs a one-line WARNING命名两条路径并返回一个空列表 - 我们故意不自动迁移，因为默默地合并两个位置的隧道状态可能会破坏新数据；用户自己移动或复制文件。 (#1467)
  • create_tunnel did not validate that the source and target rooms actually exist in the chroma index. _require_name only checked that wing/room names were non-empty strings; nothing queried the collection to confirm at least one drawer carried matching {wing, room} metadata. Pointing an explicit tunnel at a phantom room — common when an agent fabricates a room name it expects to exist, or types a slug wrong — silently succeeded. Combined with the read-bubble described in the previous fix, an agent could create_tunnel`ZZPH1 27ZZ`list_tunnels and have both calls return its own bogus write. create_tunnel now calls _check_room_exists(wing, room, col) for both endpoints before persisting an explicit tunnel; if either endpoint has zero matching drawers the call raises ValueError naming the offending wing/room pair. Three deliberate carve-outs: (1) kind != "explicit" skips validation because topic tunnels generated by compute_topic_tunnels use synthetic topic:<name> room identifiers that don’t correspond to real chroma rooms; (2) _get_collection returning None (palace not yet created, transient backend failure, tests without a real chroma backend) skips validation rather than fail-closed — matches the tolerance pattern used everywhere else in palace_graph; (3) exceptions raised by the underlying col.get(where=..., limit=1, include=[]) query are logged and treated as “can’t verify, allow” so a temporary index fault never blocks legitimate writes. Behaviour change: existing callers that previously created tunnels pointing at empty rooms (e.g. as scaffolding before mining them) will now raise ValueError。首先归档抽屉，然后创建隧道 - 这是文档始终推荐的顺序。 (#1468)

性能

  • Convo 矿工预取挖掘集一次。 每个文件发出一个 WHERE 查询来检查“已经挖掘？”；现在一次预取完整的挖掘集，从而减少大型转录语料库的占用时间。 (#1474)
  • rebuild_index 进度回调。 多小时重建现在使用默认 ETA 打印机报告进度；用户不再需要猜测该过程是否取得进展。 (#1487)
  • MCP 冷启动诊断 + 选择加入预热。 添加对正在加载的嵌入器及其所需时间的可见性，以及选择加入预热路径，以便用户可以查看并解决缓慢的首次查询延迟。 （#1530，修复#1495）

内部

  • palace_graph._TUNNEL_FILE (module-level constant) replaced by _get_tunnel_file(config=None) and _legacy_tunnel_file(). Tests previously monkeypatching the constant must now monkeypatch the resolver functions. The tests/test_palace_graph_tunnels.py::_use_tmp_tunnel_file helper, tests/test_closets.py::TestTunnels setup/teardown, and three tests in tests/test_miner.py were updated accordingly. Topic-tunnel tests in test_miner continue to work without stubbing _get_collection because kind="topic"短路新的验证路径。
