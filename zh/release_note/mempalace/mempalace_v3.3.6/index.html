mempalace v3.3.6

修订 发布时间2026年6月6日 来源MemPalace/mempalace 英文原文

变更流程图

亮点

  • 多语言召回是头条——但切换模型需要重建索引 — 新安装和引导流程（python -m mempalace.onboarding）现在默认使用 embeddinggemma-300m ONNX（q8，经 MRL 截断到 384 维，因此无需改动 ChromaDB schema），把 DE/FR/HI/IT/KO/RU 的跨语言余弦相似度从约 0.35 提升到约 0.88（俄语此前接近正交，仅 0.17）。如果你存储非英语内容，这是升级的主要理由。关键在于，从未设置 MEMPALACE_EMBEDDING_MODEL、也没运行过 onboarding 的现有安装仍停留在 minilm，因此不会自动发生任何变化；如果你通过该环境变量或 config.json 中的 embedding_model: embeddinggemma 切换模型，必须运行 mempalace repair rebuild-index，否则会遇到 ChromaDB 嵌入函数冲突——现在 ChromaBackend.get_collection() 会包装该错误，并指出两条恢复路径（回退环境变量，或重建索引）。huggingface_hub、tokenizers 和 numpy 现已成为核心依赖，[multilingual] 保留为无操作别名，约 300 MB 的模型会在首次使用时惰性下载。
  • 记忆图变得”活”起来——属于增量改动，但是一次真正的能力跃迁 — 同一 wing 内共现的实体现在会在挖掘后步骤中通过 compute_hallways_for_wing 自动生成”走廊”（hallways），跨 wing 出现的实体会自动提升为隧道（无需手动 create_tunnel）；compute_topic_tunnels 保持不变。Hebbian 增强 + Ebbinghaus 衰减让权重跟随实际使用变化，而不是保持静态，因此检索排序会随时间改善。如果你依赖实体导航，就值得升级；否则风险很低，因为它是增量的且不需要迁移。
  • 办公文档挖掘与精确引用 — mempalace mine <dir> --mode extract（安装 mempalace[extract]）在源码/文本之外新增 PDF/DOCX/PPTX/XLSX/RTF/EPUB；抽屉带有 extract_mode 元数据，使去重和抽屉 ID 按模式隔离，修复了跨模式重复/冲突的 bug（#1528，修复 #1505）。虚拟行号和 Tier 6a closet 指针现在能引用确切日期上的确切行范围，python-dateutil 提升为核心依赖（#1555、#1584）。注意：Python 3.9 用户只能得到 RTF，因为 MarkItDown 需要 3.10+。
  • 恢复”100% 召回”承诺的正确性修复——仅凭这些就值得升级 — 三条 upsert 路径此前对未分块的内容做嵌入，并静默把长抽屉截断到开头部分（#1540，#1539 的后续）；段落切分器会产生超过 CHUNK_SIZE 的块（#1538，修复 #1534）；硬编码的单文件块上限会丢掉大型转录的尾部（#1554，修复 #1455）。挖掘现在会在后处理步骤校验 FTS5 完整性（#1548），repair 以 VACUUM + FTS5 重建结束（#1523）。如果你的宫殿包含长文内容或大型转录，旧数据可能索引不全——重新挖掘或修复以恢复。
  • 谁可以跳过，以及细则 — 如果你只用英语、没有长文/办公文档、不使用实体导航，并且在 Linux 上使用短 ASCII 路径，那么这些改动基本无感——embedder 默认值的变更不影响现有安装，其余都是增量加固；除非截断修复与你相关，否则可以合理跳过。另附带的还有：用 COCA 词表过滤实体注册表中的通用英语内容词（#1605）、增量挖掘时的大小写不敏感实体匹配，让 “Aya” 和 “aya” 不再分裂（#1557）、用于静默会话的 hooks.auto_save 退出开关（#711）、API 工具转录路由到 wing_api（#1236）、Windows 死锁/锁修复（#1562、#1438）、macOS bash 3.2 钩子兼容性（#1441）、符号链接/路径缓存规范化（#1383），以及带连字符的 wing 名称保留（#1529、#1424）。诚实的提醒：这是一个功能版本，不是空操作或重新打标签，但提供的 CHANGELOG 在一个条目中间被截断（“…ignored MempalaceConf”），因此最后一项修复的完整范围无法确认。

3.3.6 是一个功能版本。 本周期的头条工作：默认多语言召回（embeddinggemma 取代 MiniLM，跨语言余弦从 0.35 → 0.88）、活性记忆图的第一版（wing 内的走廊、跨 wing 的隧道、Hebbian 增强 + Ebbinghaus 衰减，让连接随使用增强、随闲置淡去）、办公文档挖掘（PDF、DOCX、PPTX、XLSX、RTF、EPUB，通过新的 --mode extract）、虚拟行号 + 精确指向确切日期上确切行范围的 closet 指针，以及实体检测清理，让 “Code” 不再进入你的走廊、让 “Claude Code” 保持整体。

承诺不变。每个词都精确存储。一切留在你的机器上。没有遥测。每个版本都在打磨已有的能力。

功能

  • 通过 --mode extract 挖掘办公文档。 新的 mempalace mine <dir> --mode extract 在现有源码/文本路径之外，还能摄入 PDF、Word（.docx）、PowerPoint（.pptx）、Excel（.xlsx）、RTF 和 EPUB 电子书。用 pip install mempalace[extract] 安装——会拉取用于 RTF 的 striprtf，以及用于二进制格式的 MarkItDown（含 [docx,pdf,pptx,xlsx] 子扩展）。Python 3.9 用户只能获得 RTF 支持，因为 MarkItDown 需要 3.10+。extract 路径产生的抽屉带有 extract_mode 元数据，使 convo 挖掘器的”是否已挖掘？“检查和抽屉 ID 生成按模式隔离（#1528）。（#1555）

  • 虚拟行号 + 精确 closet 指针。 存储的抽屉现在带有虚拟行号，因此 read CLI 动词和 closet 指针可以引用确切的行范围。Closet 指针（Tier 6a）包含从文件名和正文日期解析（现已是核心依赖 python-dateutil）得出的日期 + 行范围信息，因此 MemPalace 能指给你确切日期上的确切行，而不只是”这个抽屉里的某处”。（#1555、#1584）

  • wing 内走廊。 当两个实体（人物、项目、主题）出现在同一个抽屉中，挖掘器现在会记录一条”走廊”——一条在该 wing 内连接它们的图边。它作为挖掘后步骤中 compute_hallways_for_wing 的一部分自动计算，因此图会随着新内容增量增长，无需单独命令。这是单个宫殿内跨房间实体导航的基础。（#1558、#1560）

  • 跨 wing 隧道由走廊提升而来。 当同一实体出现在多个 wing 的走廊中时，MemPalace 现在会自动把它提升为隧道——让查询可以从某人的 wing 跳到他出现过的项目 wing，无需任何人手动调用 create_tunnel。现有的 compute_topic_tunnels 路径产生的主题隧道保持不变。（#1565）

  • 活性记忆动力学（Hebbian 增强 + Ebbinghaus 衰减）。 走廊和隧道在每次被新内容强化时变强（“一起放电的就连在一起”），如果某条连接不再出现在新抽屉中则逐渐淡去。导航权重跟随宫殿的实际使用，而不是静态的，因此随着宫殿被真正使用，检索排序会随时间改善。（#1578）

  • API 工具转录自动路由到 wing_api。 来自 API 式 AI 工具（Claude Code、Claude.ai、ChatGPT、Slack-bot 导出、通用 OpenAI 格式 JSON 等）的对话转录现在会进入专门的 wing_api，而不再混入人类对话 wing。这样工具调用流量就不会污染个人/项目 wing，并在你想找”我自己说了什么”而不是”智能体说了什么”时提高搜索精度。（#1236）

  • 新安装默认使用多语言嵌入：embeddinggemma-300m ONNX（q8，MRL→384 维）。 MemPalace 此前的 embedder（all-MiniLM-L6-v2）只训练了英语——在平行翻译文本上的跨语言余弦相似度在 DE/FR/HI/IT/KO/RU 平均只有 0.35（俄语 0.17，接近正交）。俄语用户实际上找不到自己的记忆，这打破了 CLAUDE.md 中”100% 召回”的设计承诺。新的 EmbeddinggemmaONNX 类把这个平均值提升到 0.88（通过直接 ONNX-runtime 测试验证与 Ollama gguf 无损一致）。首次使用时通过 huggingface_hub 惰性下载 onnx-community/embeddinggemma-300m-ONNX（约 300 MB）。输出通过 Matryoshka 表示学习截断到 384 维，因此该模型可直接替换 ChromaDB 的 384 维集合——无需 schema 变更。Sim 前缀（"task: sentence similarity | query: "）会自动应用。

    引导流程（python -m mempalace.onboarding）现在把多语言模型作为默认提供——选择它会把 embedding_model: embeddinggemma 写入 config.json，后续运行无需再次询问就会采用。从未设置环境变量或运行过 onboarding 的现有安装仍停留在 minilm（向后兼容）。MEMPALACE_EMBEDDING_MODEL=minilm|embeddinggemma 会覆盖两者。在已有宫殿上切换模型需要重新嵌入——更改后运行 mempalace repair rebuild-index。（#1483）

  • 多语言依赖移入核心。 huggingface_hub、tokenizers 和 numpy 现在都是必需依赖，因此 pip install mempalace 之后多语言路径开箱即用。[multilingual] 扩展保留为无操作别名，以兼容安装脚本。约 300 MB 的 ONNX 模型本身仍是首次使用时惰性下载，而非安装时下载。

  • 更友好的 ChromaDB 嵌入函数名不匹配错误。 在已有宫殿上切换 MEMPALACE_EMBEDDING_MODEL 而不运行 rebuild-index，此前会抛出 ChromaDB 裸的 Embedding function conflict: new: X vs persisted: Y ValueError——准确但没有告诉用户如何恢复。ChromaBackend.get_collection() 现在会包装该错误，并同时指出两个选项：回退环境变量，或运行 mempalace repair rebuild-index --palace <path>。（#1483）

  • 用于静默会话的 hooks.auto_save 开关。 新增配置开关（以及贯穿保存钩子的 --silent CLI 标志接线），让用户可以选择不在 Stop / PreCompact 时自动保存日记。适用于你不想记录每次对话的”静默模式”会话。默认行为不变——除非显式禁用，自动保存仍会运行。（#711）

  • 从实体检测中过滤常见英语内容词。 高频英语内容词（“system”、“user”、“memory”、“project”、“context” 等）此前会被逐抽屉检测器标记为实体，并以”人物”身份污染实体注册表。现在在实体分类时会参考随包提供的 COCA 词表（top-N 内容词），让这些词在进入注册表前被过滤。同时加固了对词表中畸形 JSON 的处理。（#1605）

  • 挖掘时大小写不敏感的实体匹配。 初次构建宫殿（mempalace init）时实体名是大小写不敏感匹配的，但增量挖掘中使用的逐抽屉标注器不是——因此同一个人在 init 和 ingest 之间被标注得不同（“Aya” 与 “aya” 变成两个不同实体）。增量标注器现在采用同样的大小写不敏感匹配，恢复宫殿整个生命周期中实体标签的一致性。（#1557）

错误修复

  • 三条 upsert 路径中的静默数据丢失。 三处 upsert 点位（文件摄取、对话摄取，以及一个 repair 分支）此前对未分块内容调用 embedder，在 embedder 的最大 token 限制处静默截断。长抽屉只有开头部分被索引，破坏了对长文内容的”100% 召回”承诺。现在三处都先经过切分器，确保全文都被嵌入和存储。（#1540，#1539 的后续）
  • 段落切分器对长段落产生过大的块。 段落切分器假定段落总比 CHUNK_SIZE 短，于是整段输出；长段落（法律文本、密集技术文章）会静默超出 embedder 的上下文窗口。现在切分器硬性限制每个输出块以遵守 CHUNK_SIZE。（#1538，修复 #1534）
  • 单文件块上限被硬编码，对大型转录太低。 一处安全限制把每个文件的块数上限设为针对源码调优的值；挖掘超大会话转录会静默丢弃超过该上限的尾部。现在该值可配置，默认值已提高以覆盖真实转录规模。（#1554，修复 #1455）
  • Windows 上钩子子进程 / ChromaDB 死锁。 Stop/PreCompact 钩子在 Windows 上可能与已打开的 ChromaDB 客户端死锁，让宿主（Claude Code）卡在等待钩子。三部分修复：挖掘锁回收的陈旧 PID 超时、MCP 服务器中的空闲退出路径，以及检测到死锁模式时返回结构化错误，让宿主可以恢复。（#1562，修复 #1552）
  • create_tunnel 破坏带连字符的 wing 名称。 端点解析器按 - 分割，因此名称中含连字符的 wing（mem-palace、my-app）会在名称中间被截断，隧道指向不存在的端点。现在端点解析保留完整 slug。（#1529，修复 #1504）
  • MCP 知识图谱缓存对符号链接/大小写不同的宫殿路径产生重复图。 缓存键是原始路径字符串，因此 /Users/me/.mempalace/palace 与 /Users/me/.mempalace/Palace（macOS 上大小写折叠）或符号链接别名会产生两个指向同一 SQLite 文件的缓存 KnowledgeGraph 实例，有陈旧读取风险。现在缓存通过 realpath + normcase 规范化，使它们收敛到同一个规范键。（#1383，修复 #1372）
  • 保存钩子截断了带连字符的项目文件夹名。 wing 名称解析器按 - 分割且只保留第一段，因此 mem-palace 变成 mem。修复保留完整的项目文件夹 slug，让带连字符的宫殿在钩子调用之间保持一致。（#1424，修复 #1410）
  • 挖掘器静默跳过符号链接。 用户会对挖掘后数据缺失感到困惑；挖掘器此前跳过了符号链接却没有提示。现在会记录每个被跳过的符号链接及原因，让缺口可见。（#1466，修复 #1462）
  • 宿主泄漏的 PYTHONPATH 可能在导入时遮蔽 MemPalace 自身模块。 包的 __init__ 现在在导入时清除泄漏的条目，确保导入的始终是已安装的 MemPalace。（#1439，修复 #1423）
  • macOS 自带 bash 的钩子脚本。 钩子脚本使用了 mapfile（bash 4+），破坏了 macOS 自带的 /bin/bash 3.2。改用 sed 管道，让钩子在所有 Mac 上开箱即用。（#1441，修复 #1440）
  • 插件的 Stop/PreCompact 钩子可能在卡住的子进程上无限挂起。 有界超时确保即使 MemPalace 的子进程不健康，宿主也总能继续推进。（#1470，修复 #1465）
  • MCP 处理器现在对畸形输入返回结构化 JSON-RPC 错误。 未知参数名此前返回 -32602 Invalid params 而不是非结构化的 Python TypeError；形状错误的参数现在返回结构化错误，而不是原始 traceback。（#1500、#1513）
  • CLI 区分”宫殿不存在”与”宫殿存在但为空”。 对新用户看起来相同的两种状态现在分别报告，并各自给出可操作的下一步提示。（#1532，修复 #1498）
  • mempalace repair 后置处理：VACUUM + FTS5 重建。 宫殿修复后，SQLite 知识图谱文件会留下碎片页和陈旧的 FTS5 索引；在结束时运行 VACUUM 并重建 FTS5 可回收磁盘空间并恢复搜索性能。（#1523）
  • Convo 挖掘器模式隔离。 “是否已挖掘？“检查和抽屉 ID 生成此前忽略 extract_mode，因此切换模式要么重复挖掘相同内容（数据重复），要么跨模式发生抽屉 ID 冲突。按模式限定作用域使各模式的抽屉相互隔离且去重正确。（#1528，修复 #1505）
  • 挖掘结束时校验 FTS5。 挖掘现在会在后处理步骤校验 FTS5 索引完整性，从而在写入时而非读取时发现损坏。（#1548，修复 #1537）
  • hooks_cli 在安装路径较浅时崩溃。 代码用 Path.parents[3] 索引，假定安装目录树很深，当 MemPalace 从较浅路径（如 /opt/mp）运行时会抛出 IndexError。新增保护，使浅层安装不再在钩子命令上崩溃。（#1585）
  • HNSW 段隔离：零字节 vs 缺失维度。 早期的隔离启发式把任何缺失 dim 元数据字段的 HNSW 段都标记为损坏，但其中大多数其实可恢复；现在检查会区分”可恢复的缺失维度”和”真正损坏”，保留可用的索引段。零字节的链表文件（部分写入的段）现在会被直接拒绝。（#1452、#1461，修复 #1457）
  • 挖掘锁持有者文件以 UTF-8 而非 cp1252 写入。 非 ASCII 的 Windows 用户名和路径不再破坏锁文件、不再导致陈旧锁检测失效。（#1438）
  • 挖掘器槽位认领现在立即写入占位 PID。 认领与 PID 写入之间崩溃不再留下幽灵锁。（#1543，修复 #1443）
  • mine_convos 现在在 mine_palace_lock 内运行。 两个并发的 convos mine 调用不再可能破坏索引。（#1477）
  • 迁移工具清理。 ChromaDB 版本迁移工具现在会在迁移中途发生异常时关闭其 SQLite 连接并移除临时宫殿目录；失败的迁移不再泄漏文件句柄和磁盘。实体注册表原子写入现在会在写入或重命名失败时删除其 .tmp 旁路文件。（#1216、#1408，修复 #1373）
  • 修复工具容忍空/None 元数据单元格。 ChromaDB 在重建期间偶尔返回空元数据字典或 None 的单元格；现在两者都会被强制转为合理默认值，使重建完成、原本卡住的宫殿得以恢复。（#1459、#1445，修复 #1426）
  • create_tunnel MCP 处理器现在会传播错误。 错误的端点或方向此前会被吞掉并返回误导性的成功；现在会作为结构化 MCP 错误向上传播。（#1546，修复 #1473）
  • 显式隧道此前存储在一个硬编码的 ~/.mempalace/tunnels.json 路径，忽略了 MempalaceConfig.palace_path。 抽屉、KG 三元组、人物地图以及宫殿的其他所有状态都会遵循配置的 palace_path（以及 MEMPALACE_PALACE_PATH 环境变量），但 palace_graph._TUNNEL_FILE 是一个模块级常量，只在初始化时从 os.path.expanduser("~") + "/.mempalace/tunnels.json" 求值一次。在 $HOME 与配置宫殿隔离的任何设置下——拥有自己 $HOME 的子代理配置、沙箱、多租户主机、把宫殿挂载到 /srv/ 的容器——抽屉落在配置的宫殿里，隧道却悄悄落进另一个其他进程碰不到同一宫殿时就看不到的文件。最糟的是代理场景：一个隔离的 worker 调用 create_tunnel 再 list_tunnels，得到的是自己写在泡泡里的那条，于是 worker 自我确认了一条共享宫殿里根本不存在的隧道，并向编排器报告完成。现在 palace_graph._TUNNEL_FILE 被 _get_tunnel_file() 取代，后者从新的 MempalaceConfig.tunnel_file 属性（palace_path 的同级）派生路径。默认单用户安装不变，因为默认 palace_path 仍是 ~/.mempalace/palace，其同级 tunnels.json 就是旧路径。向后兼容：如果配置的隧道文件不存在，而 3.3.6 之前硬编码的 ~/.mempalace/tunnels.json 处存在文件且两者路径不同，_load_tunnels 会记录一行 WARNING 指出两个路径并返回空列表——我们有意不做自动迁移，因为跨两个位置静默合并隧道状态有覆写较新数据的风险；由用户自己移动或复制该文件。（#1467）
  • create_tunnel 此前不校验源和目标房间是否真的存在于 chroma 索引中。 _require_name 只检查 wing/room 名是非空字符串；没有任何查询去确认至少有一个抽屉带有匹配的 {wing, room} 元数据。把显式隧道指向一个幽灵房间——常见于智能体凭空编造一个它期望存在的房间名，或把 slug 拼错——此前会静默成功。结合上一项修复中描述的读取泡泡，智能体可以 create_tunnel → list_tunnels，两次调用都返回自己那次伪造的写入。现在 create_tunnel 在持久化显式隧道前会对两个端点都调用 _check_room_exists(wing, room, col)；如果任一端点匹配抽屉数为零，调用会抛出 ValueError 并指出有问题的 wing/room 对。三处有意例外：(1) kind != "explicit" 跳过校验，因为 compute_topic_tunnels 生成的主题隧道使用合成的 topic:<name> 房间标识符，并不对应真实的 chroma 房间；(2) _get_collection 返回 None（宫殿尚未创建、后端瞬时故障、没有真实 chroma 后端的测试）时跳过校验而非直接失败——与 palace_graph 其他地方的容错模式一致；(3) 底层 col.get(where=..., limit=1, include=[]) 查询抛出的异常会被记录并当作”无法验证，放行”，这样临时索引故障绝不会阻塞合法写入。行为变更：此前创建指向空房间的隧道的调用方（例如在挖掘之前作为脚手架）现在会抛出 ValueError。请先归档抽屉，再创建隧道——文档一直是这么建议的顺序。（#1468）

性能

  • Convo 挖掘器一次性预取已挖掘集合。 此前对每个文件发一次 WHERE 查询来检查”是否已挖掘？“；现在一次性预取完整的已挖掘集合，大幅缩短大型转录语料的耗时。（#1474）
  • rebuild_index 进度回调。 长达数小时的重建现在会用默认的 ETA 打印器报告进度；用户不再需要猜进程是否还在推进。（#1487）
  • MCP 冷启动诊断 + 可选预热。 增加了对正在加载哪个 embedder、耗时多久的可见性，以及一条可选的预热路径，让用户能够看到并解决首次查询延迟高的问题。（#1530，修复 #1495）

内部

  • palace_graph._TUNNEL_FILE（模块级常量）被 _get_tunnel_file(config=None) 和 _legacy_tunnel_file() 取代。此前对该常量做 monkeypatch 的测试现在必须改为对解析函数做 monkeypatch。tests/test_palace_graph_tunnels.py::_use_tmp_tunnel_file 辅助函数、tests/test_closets.py::TestTunnels 的 setup/teardown，以及 tests/test_miner.py 中的三个测试都已相应更新。test_miner 中的主题隧道测试无需 stub _get_collection 即可继续工作，因为 kind="topic" 会短路新的校验路径。

3.3.6 是一个功能发布。 该周期的头条工作：默认多语言回忆（embeddinggemma 取代 MiniLM，从 0.35 → 0.88 跨语言余弦跳跃），生活记忆图的第一次切割（机翼内的走廊，机翼之间的隧道，Hebbian 增强 + Ebbinghaus 衰减，因此连接随着使用而增强，不使用则消失），办公文档挖掘（PDF， DOCX、PPTX、XLSX、RTF、EPUB（通过新的 --mode extract）、虚拟行号 + 手术室指针（在确切日期引用确切的行范围）以及实体检测清理通道，使“代码”远离您的走廊，并使“克劳德代码”原子化。 承诺没有动摇。每个词都准确存储。一切都保留在您的机器上。没有遥测。每个版本都会增强已有的内容。

特点

  • 通过 --mode extract 进行 Office 文档挖掘。 除了现有的源代码/文本路径之外，新的 mempalace mine <dir> --mode extract 还可提取 PDF、Word (.docx)、PowerPoint (.pptx)、Excel (.xlsx)、RTF 和 EPUB 书籍。使用 pip install mempalace[extract] 安装 — 为 RTF 拉出 striprtf，为二进制格式拉出 MarkItDown（带有 [docx,pdf,pptx,xlsx] 子附加功能）。 Python 3.9 用户获得 RTF 覆盖只是因为 MarkItDown 需要 3.10+。提取路径中的抽屉携带 extract_mode 元数据，因此 convo 矿工“已经开采了？”检查和抽屉 ID 生成在每种模式下保持隔离（#1528）。 (#1555)
  • 虚拟行号 + 手术室指针。 存储的抽屉现在带有虚拟行号，因此读取的 CLI 动词和手术室指针可以引用确切的行范围。 Closet 指针（第 6a 层）包括从文件名和内容正文日期解析派生的日期+行范围信息（python-dateutil 现在是核心 dep），因此 MemPalace 可以为您指出确切日期的确切行，而不仅仅是“这个抽屉中的某个位置”。 （＃1555，＃1584）
  • 翼内走廊。 当两个实体（人、项目、主题）同时出现在同一个抽屉中时，矿工现在会记录一条“走廊”——在该翼内连接它们的图形边缘。作为 compute_hallways_for_wing 中挖掘后步骤的一部分自动计算，因此图表随着新内容而增量增长，无需单独的命令。一个宫殿内跨房间实体导航的基础。 （＃1558，＃1560）
  • 从走廊提升跨翼隧道。 当同一个实体出现在多个翼楼的走廊中时，MemPalace 现在会自动将其提升到隧道中 - 让查询从一个人的翼楼跳到他们出现的项目翼楼，无需任何人手动调用 create_tunnel。现有 compute_topic_tunnels 路径的主题隧道保持不变。 (#1565)
  • **生活记忆动态（赫布增强+艾宾浩斯衰变）。**每当新内容（“将电线连接在一起的东西”）强化相同的连接时，走廊和隧道就会变得更强，如果连接停止出现在传入的抽屉中，走廊和隧道就会逐渐消失。导航权重跟踪真实的宫殿使用情况，而不是静态的，因此随着宫殿的实际使用，检索排名会随着时间的推移而提高。 (#1578)
  • API 工具记录自动路由到 wing_api。 来自 API 式 AI 工具（Claude Code、Claude.ai、ChatGPT、Slack-bot 导出、通用 OpenAI 形状 JSON 等）的对话记录现在路由到专用的 wing_api，而不是混合到人类对话翼中。当您寻找“我说了什么”与“代理说了什么”时，可以防止工具调用流量污染个人/项目部门，并提高搜索精度。 (#1236)
  • 新安装默认多语言嵌入：embeddinggemma-300m ONNX（q8，MRL→384-dim）。 MemPalace 之前的嵌入器 (all-MiniLM-L6-v2) 仅接受英语训练 — 德国/法国/HI/IT/KO/RU 上平行翻译文本平均值 0.35 的跨语言余弦相似度（RU 为 0.17，近正交）。俄语用户实际上无法找到自己的记忆，这违背了 CLAUDE.md 的“100% 召回”设计承诺。 mempalace/embedding.py 中的新 EmbeddinggemmaONNX 类使其达到 0.88 平均值（通过直接 ONNX 运行时测试与 Ollama gguf 进行无损验证）。首次使用时通过 huggingface_hub 延迟下载 onnx-community/embeddinggemma-300m-ONNX (~300 MB)。通过 Matryoshka 表示学习将输出截断为 384 维，因此该模型是 ChromaDB 384 维集合的替代品 - 没有架构更改。 Sim 前缀 ("task: sentence similarity | query: ") 会自动应用。 Onboarding (python -m mempalace.onboarding) 现在提供多语言模型作为默认设置 - 选择它将 embedding_model: embeddinggemma 写入 config.json，因此后续运行会选择它而无需重新提示。从未设置环境变量或运行载入的现有安装保留在 minilm（向后兼容）上。 MEMPALACE_EMBEDDING_MODEL=minilm|embeddinggemma 覆盖两者。在现有宫殿上切换模型需要重新嵌入 - 更改后运行 mempalace repair rebuild-index。 (#1483)
  • 多语言 deps 移至核心。 huggingface_hub、tokenizers 和 numpy 现在是必需的 deps，因此多语言路径在 pip install mempalace 之后开箱即用。 [multilingual] extra 保留为无操作别名，以便与安装脚本向后兼容。 300 MB ONNX 模型本身仍然在首次使用时延迟下载，而不是在安装时延迟下载。
  • 更友好的 ChromaDB EF 名称不匹配错误。 在不运行 rebuild-index 的情况下在现有宫殿上切换 MEMPALACE_EMBEDDING_MODEL 之前曾出现 ChromaDB 的裸 Embedding function conflict: new: X vs persisted: Y ValueError — 准确，但没有告诉用户如何恢复。 ChromaBackend.get_collection() 现在包装该错误并指向两个选项：恢复环境变量，或运行 mempalace repair rebuild-index --palace <path>。 (#1483)
  • hooks.auto_save 用于静音模式会话切换。 新的配置旋钮（以及通过保存挂钩连接的 --silent CLI 标志）允许用户选择退出 Stop / PreCompact 上的自动日记保存。对于您不希望捕获每个对话的“静默模式”会话很有用。默认行为不变 - 除非明确禁用，否则自动保存仍会运行。 (#711)
  • 从实体检测中过滤常见的英语内容词。 高频英语内容词（“系统”、“用户”、“内存”、“项目”、“上下文”等）被每个抽屉检测器标记为实体，并污染实体注册表作为“人”。现在，在实体分类期间会查阅已提供的 COCA 单词列表（前 N 个内容单词），以便在到达注册表之前对其进行过滤。针对捆绑单词列表中格式错误的 JSON 进行了强化。 (#1605)
  • **挖掘时不区分大小写的实体匹配。**初始宫殿构建（mempalace init）不区分大小写地匹配实体名称，但增量挖掘过程中使用的每个抽屉标记器却没有 - 因此同一个人在 init 和 ingest 之间被标记不同（“Aya”与“aya”成为不同的实体）。增量标记器现在镜像不区分大小写的匹配器，恢复整个宫殿生命周期中实体标记的一致性。 (#1557)

错误修复

  • 三个 upsert 路径中的静默数据丢失。 三个 upsert 站点（文件摄取、对话摄取和一个修复分支）正在对未分块的内容调用嵌入器，在嵌入器的最大令牌限制下静默截断。长抽屉落地时仅索引了其主要部分，这违反了长格式内容的“100% 召回”承诺。现在，所有三个都首先通过分块器进行路由，以便嵌入和存储完整的文档。 （#1540，#1539 的后续）
  • 段落分块器为长段落发出过大的块。 段落拆分器假定段落总是短于 CHUNK_SIZE 并将它们整个发出；长段落（法律文本、密集的技术文章）悄然超出了嵌入器的上下文窗口。分离器现在对每个发出的块进行硬上限以纪念 CHUNK_SIZE。 （#1538，修复#1534）
  • 每个文件的块上限是硬编码的，对于大型转录本而言太低。 每个文件的块上限为针对源代码调整的值的安全限制；挖掘非常大的对话记录会悄悄地将尾部丢弃到超过该上限的位置。现在可配置，默认值提高到覆盖实际的转录本大小。 （#1554，修复#1455）
  • Windows 上的挂钩子进程/ChromaDB 死锁。 Stop/PreCompact 挂钩可能会对 Windows 上已打开的 ChromaDB client 造成死锁，从而使主机 (Claude Code) 陷入等待挂钩状态。修复分为三个部分：矿锁回收时的陈旧 PID 超时、MCP 服务器中的空闲退出路径以及检测到死锁模式时的结构化错误，以便主机可以恢复。 （#1562，修复#1552）
  • create_tunnel 损坏的连字符翼名称。 端点解析器在 - 上分裂，因此名称包含连字符（mem-palace、my-app）的翼在名称中间被截断，并且隧道指向不存在的端点。端点解析现在保留完整的段。 （＃1529，修复＃1504）
  • MCP 知识图缓存为符号链接/大小写不同的宫殿路径生成了重复的图。 缓存键是原始路径字符串，因此 /Users/me/.mempalace/palace 和 /Users/me/.mempalace/Palace（在 macOS 上大小写折叠）或符号链接别名生成两个单独的缓存 KnowledgeGraph 实例，指向同一个 SQLite 文件，存在陈旧读取风险。缓存现在通过 realpath + normcase 进行规范化，因此它们会折叠到单个规范密钥上。 （#1383，修复#1372）
  • 保存挂钩截断连字符的项目文件夹名称。 Wing-name 解析器在 - 上进行拆分并仅保留第一段，因此 mem-palace 变成了 mem。修复保留了完整的项目文件夹 slug，因此连字符的宫殿在钩子调用中保持一致。 （#1424，修复#1410）
  • 矿工默默地跳过符号链接。 用户对挖掘后丢失的数据感到困惑；矿工跳过符号链接而不显示它。现在记录每个跳过的符号链接及其原因，以便间隙可见。 （#1466，修复#1462）
  • 主机泄漏的 PYTHONPATH 可能会在导入时影响 MemPalace 自己的模块。 软件包 __init__ 现在会在导入时删除泄漏的条目，因此导入的 MemPalace 始终是已安装的条目。 （＃1439，修复＃1423）
  • macOS stock-bash hook 脚本。 Hook 脚本使用了 mapfile (bash 4+)，破坏了 macOS stock /bin/bash 3.2。切换到 sed 管道，以便钩子在每台 Mac 上都能开箱即用。 （#1441，修复#1440）
  • 插件 Stop/PreCompact 挂钩可能会无限期地挂在卡住的子进程上。 有界超时可确保主机始终能够取得进展，即使 MemPalace 的子进程不健康也是如此。 （＃1470，修复＃1465）
  • MCP 处理程序现在针对格式错误的输入返回结构化 JSON-RPC 错误。 未知参数名称返回 -32602 Invalid params，而不是非结构化 Python TypeError；错误形状的参数返回结构化错误而不是原始回溯。 （＃1500，＃1513）
  • CLI 将“宫殿不存在”与“宫殿存在但空”区分开来。 对于新用户来说看起来相同的两个状态现在分别报告，并为每个状态提供可操作的下一步消息。 （#1532，修复#1498）
  • mempalace repair 后通：VACUUM + FTS5 重建。 宫殿修复后，SQLite 知识图文件保留了碎片页面和过时的 FTS5 索引；运行 VACUUM 并在最后重建 FTS5 可回收磁盘并恢复搜索性能。 (#1523)
  • Convo 矿工模式隔离。 “已经开采？”检查和抽屉 ID 生成忽略了 extract_mode，因此切换模式要么重新挖掘相同的内容（数据重复），要么在模式之间发生冲突的抽屉 ID。按模式确定范围可以使每个模式的抽屉保持隔离并正确进行重复数据删除。 （#1528，修复#1505）
  • 在挖掘结束时进行 FTS5 验证。 挖掘现在将验证 FTS5 索引完整性作为后续步骤，以便在写入时而非读取时捕获损坏。 （#1548，修复#1537）
  • hooks_cli 在浅安装路径上崩溃。 假设深度安装树，索引为 Path.parents[3] 的代码会在 MemPalace 从浅路径（例如 /opt/mp）运行时引发 IndexError。添加了一个防护，因此浅安装不再因钩子命令而崩溃。 (#1585)
  • HNSW 段隔离：零字节与缺失暗淡。 早期隔离启发式标记任何缺少 dim 元数据字段的 HNSW 段已损坏，但大多数都是可恢复的；该检查现在可以区分可恢复的缺失暗淡和实际损坏，从而保留工作索引段。零字节链接列表文件（部分写入的段）现在被彻底拒绝。 （#1452、#1461、修复#1457）
  • 以 UTF-8 而不是 cp1252 编写的矿井锁持有者文件。 非 ASCII Windows 用户名和路径不再损坏锁文件并破坏过时锁检测。 (#1438)
  • 矿工槽声明现在立即写入占位符 PID。 声明和 PID 写入之间的崩溃不再留下幻像锁。 （＃1543，修复＃1443）
  • mine_convos 现在在 mine_palace_lock 内部运行。 两个并发的 convos mine 调用不再会损坏索引。 (#1477)
  • 迁移工具清理。 ChromaDB 版本迁移工具现在会在迁移过程中触发异常时关闭其 SQLite 连接并删除临时宫殿目录；失败的迁移将停止泄漏文件句柄和磁盘。如果写入或重命名失败，实体注册表原子写入现在会删除其 .tmp sidecar。 （#1216、#1408、修复#1373）
  • 修复工具允许空/无元数据单元。 ChromaDB 在重建过程中偶尔会返回带有空元数据字典或 None 的单元；现在，两者都被迫进行合理的默认设置，以便重建工作完成，否则陷入困境的宫殿也将得到恢复。 （#1459、#1445、修复#1426）
  • create_tunnel MCP 处理程序现在传播错误。 错误的端点或方向被吞并并作为误导性成功返回；现在作为结构化 MCP 错误传播。 （＃1546，修复＃1473）
  • 显式隧道存储在硬编码中~/.mempalace/tunnels.json path that ignored MempalaceConfig.palace_path. Drawers, KG triples, the people map, and every other piece of palace state honour the configured palace_path (and the MEMPALACE_PALACE_PATH env var), but palace_graph._TUNNEL_FILE was a module-level constant initialised once from os.path.expanduser("~") + "/.mempalace/tunnels.json". Under any setup where $HOME is isolated from the configured palace — subagent profiles with their own $HOME, sandboxes, multi-tenant hosts, container mounts that move the palace to /srv/ — drawers landed in the configured palace while tunnels silently landed in a different file that no other process touching the same palace could see. Worst case is the agentic one: an isolated worker calls create_tunnel then list_tunnels`ZZPH10 0ZZ`palace_graph._TUNNEL_FILE is replaced by _get_tunnel_file() which derives the path from a new MempalaceConfig.tunnel_file property (sibling of palace_path). The default single-user install is unchanged because the default palace_path is still ~/.mempalace/palace and its sibling tunnels.json is the legacy path. Backwards-compatibility: if the configured tunnel file does not exist but a file is present at the pre-3.3.6 hardcoded ~/.mempalace/tunnels.json path AND the two paths differ, _load_tunnels logs a one-line WARNING命名两条路径并返回一个空列表 - 我们故意不自动迁移，因为默默地合并两个位置的隧道状态可能会破坏新数据；用户自己移动或复制文件。 (#1467)
  • create_tunnel did not validate that the source and target rooms actually exist in the chroma index. _require_name only checked that wing/room names were non-empty strings; nothing queried the collection to confirm at least one drawer carried matching {wing, room} metadata. Pointing an explicit tunnel at a phantom room — common when an agent fabricates a room name it expects to exist, or types a slug wrong — silently succeeded. Combined with the read-bubble described in the previous fix, an agent could create_tunnel`ZZPH1 27ZZ`list_tunnels and have both calls return its own bogus write. create_tunnel now calls _check_room_exists(wing, room, col) for both endpoints before persisting an explicit tunnel; if either endpoint has zero matching drawers the call raises ValueError naming the offending wing/room pair. Three deliberate carve-outs: (1) kind != "explicit" skips validation because topic tunnels generated by compute_topic_tunnels use synthetic topic:<name> room identifiers that don’t correspond to real chroma rooms; (2) _get_collection returning None (palace not yet created, transient backend failure, tests without a real chroma backend) skips validation rather than fail-closed — matches the tolerance pattern used everywhere else in palace_graph; (3) exceptions raised by the underlying col.get(where=..., limit=1, include=[]) query are logged and treated as “can’t verify, allow” so a temporary index fault never blocks legitimate writes. Behaviour change: existing callers that previously created tunnels pointing at empty rooms (e.g. as scaffolding before mining them) will now raise ValueError。首先归档抽屉，然后创建隧道 - 这是文档始终推荐的顺序。 (#1468)

性能

  • Convo 矿工预取挖掘集一次。 每个文件发出一个 WHERE 查询来检查“已经挖掘？”；现在一次预取完整的挖掘集，从而减少大型转录语料库的占用时间。 (#1474)
  • rebuild_index 进度回调。 多小时重建现在使用默认 ETA 打印机报告进度；用户不再需要猜测该过程是否取得进展。 (#1487)
  • MCP 冷启动诊断 + 选择加入预热。 添加对正在加载的嵌入器及其所需时间的可见性，以及选择加入预热路径，以便用户可以查看并解决缓慢的首次查询延迟。 （#1530，修复#1495）

内部

  • palace_graph._TUNNEL_FILE (module-level constant) replaced by _get_tunnel_file(config=None) and _legacy_tunnel_file(). Tests previously monkeypatching the constant must now monkeypatch the resolver functions. The tests/test_palace_graph_tunnels.py::_use_tmp_tunnel_file helper, tests/test_closets.py::TestTunnels setup/teardown, and three tests in tests/test_miner.py were updated accordingly. Topic-tunnel tests in test_miner continue to work without stubbing _get_collection because kind="topic"短路新的验证路径。
