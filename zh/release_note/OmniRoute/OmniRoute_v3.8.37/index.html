OmniRoute v3.8.37

[3.8.37] — 2026-06-26

✨ 新功能

  • feat（提供商）： 添加 DGrid AI 网关提供商 — api.dgrid.ai/v1 处的 OpenAI 兼容网关（别名 dgrid、API 密钥身份验证、直通模型）。免费路由器层（10 RPM / 100 RPD）；终身充值 5 美元可将限制提高至 20 RPM / 1,000 RPD。 （#4931 — 感谢@dgridOP）
  • 壮举（提供商）： 添加 Pioneer AI (Fastino Labs) 提供商 — api.pioneer.ai/v1 上与 OpenAI 兼容的聊天完成功能。使用别名 pn、X-API-Key auth 和 10 个开放层无服务器模型的目录（Qwen3、Llama 3.1/3.2、Gemma 3、SmolLM3）进行注册。免费 75 美元积分，无需信用卡。门控企业模型（Claude/GPT/Gemini）需要事先在 Pioneer 平台上进行微调，并有意从目录中排除。 （#4909 — 感谢@HikiNarou）
  • 壮举（提供者）： 添加 xAI Grok 入站翻译器和思考修补程序 — Grok 请求现在在入站路径上进行翻译，并且推理已标准化，因此 Grok 模式在 clients 上表现一致。 （#4910 — 感谢@mugnimaestra）
  • feat(oauth): Codex 批量导入端点 — POST /api/oauth/codex/import 在一次调用中接受多个 Codex OAuth 凭据，以实现快速多帐户登录。 （#4914 — 感谢@beaaan）
  • 功能（嵌入）： 将 dimensions 覆盖字段添加到嵌入组合，以便嵌入组合可以固定每个目标的输出向量大小。 （#4913 — 感谢@wenzetan）
  • feat(sse)： 自动升级成功的组合模型 - 新的选择加入 comboAutoPromoteEnabled 设置会重新排序组合的持久模型列表，以便当组合模型成功响应时，它会移动到位置 #1 以供将来的请求。 （#4852 — 感谢@arssnndr）
  • feat(sse)： 添加可切换的工具源诊断 - 调试工具路由问题时每个工具定义源自的选择加入开关表面。 （#4856 — 感谢@DuyPrX）
  • feat(headroom)： 代理生命周期管理 + 仪表板 UI — 从仪表板启动/停止/监控 Headroom 压缩代理，并支持 Docker sidecar。 (#4649 — 感谢@diegosouzapw / @carmelogunsroses)
  • feat(sse): x-omniroute-strip-reasoning 请求标头从上游响应中删除 reasoning_content（选择加入，保留推理感知的 clients）。 (#4678 — 感谢@anuragg-saxenaa / @diegosouzapw)
  • **壮举(cli)：**对 Factory Droid CLI 集成的多模型支持。 (#4682 — 感谢@anuragg-saxenaa / @diegosouzapw)
  • feat(sse): 从结构化 RetryInfo 有效负载中解析 Gemini CLI 429 retryDelay，以便冷却时间遵循上游提供的退避。 （#4738 — 感谢@NoxzRCW）
  • feat(sse)： 将 GPT-4 和 GPT-4o mini 添加到 GitHub Copilot 提供商目录。 （#4798、#4797 — 感谢@decolua）
  • feat(api)： 添加 MiniMax-M3 定价行（规范 + 小写别名），以便新的 MiniMax 默认模型获得准确的每个请求成本核算，而不是回落到零/默认费率。 （#4814 — 感谢@octo-patch）

🔧 错误修复

  • 修复（sse）： response.completed 中的密集、确定性 response.output 排序 - 项目现在按其实际的 output_index 排序（通过记录为发射的累加器 + 稳定排序），而不是从无序状态字典重建； normalizeOutputIndex 取代了脆弱的 parseInt 调用，需要强大的索引强制；被取代的工具调用（在中流的同一索引处替换）将从最终输出数组中排除。 （#4906 — 感谢@Marco9113）
  • **修复(sse)：**将 Codex 自定义/自由格式工具（apply_patch、type:"custom"，没有 parameters）标准化为 { input: string } 函数模式而不是空模式 - 空模式使模型使用 {} 调用 apply_patch，从而破坏了需要 { input: string } 的 Codex 运行时。还映射 custom_tool_call / custom_tool_call_output 输入项并通过 custom_tool_call_input.delta/.done 事件流传输 apply_patch 工具调用。 （#4862 — 感谢@nstung463）
  • **修复（sse）：**在翻译草案 2020-12 反重力工具模式（例如来自 OpenCode）时保留 required 数组，剥离不受支持的 JSON 模式元关键字，同时保留所需的强制参数，以便模型不再调用没有它们的工具。 （#4843 — 感谢@anuragg-saxenaa）
  • 修复（sse）： Kiro工具架构清理程序 - 剥离不支持的JSON-Schema关键字（anyOf/$ref/if-then等）和散列截断工具名称> 64个字符在调度之前，将流式工具调用名称映射回client，因此Kiro不再拒绝工具与 400 "Improperly formed request" 通话。 （#4847 — 感谢@smarthomeblack）
  • **修复（sse）：**使anthropic-compatible-*提供者的anthropic-version默认保护不区分大小写，因此调用者/操作员提供的Anthropic-Version（任何大小写）不再被第二个小写anthropic-version: 2023-06-01标头破坏。 （#4823 — 感谢@zakirkun）
  • **修复（db）：**通过 whoami-v2 端点验证 HuggingFace API 令牌作为纯身份验证探针，因此细粒度推理提供者令牌（即使模型/任务端点拒绝它们也有效）不再被错误地标记为无效；仅 401/403 表示密钥无效，其他非正常状态表现为暂时性上游错误。 （#4819 — 感谢@Delcado19）
  • **修复(sse)：**在 buildKiroPayload 到达 AWS Bedrock 之前拒绝 buildKiroPayload 中仅 Anthropic 的 [1m] context-1m 后缀 — Kiro 由 Bedrock 支持，无法兑现 Beta 版，因此转发的 kr/*[1m] 模型 ID 在上游格式错误；调用者现在会收到一个明显的错误，将他们指向 1M 上下文路由的直接人类提供者。 （#4816 — 感谢@Delcado19）
  • **修复（仪表板）：**将引擎组合编辑器引擎与 API 模式对齐 - 命名组合管道下拉列表提供了 PUT /api/context/combos/[id] 拒绝的四个引擎（headroom、session-dedup、ccr、llmlingua），因此选择其中一个会使保存返回 400，而 UI 吞掉了错误。下拉列表现在源自与 stackedPipelineStepSchema 共享的单个规范引擎映射（由单元测试保护的奇偶校验），并且编辑器表面保存错误以及空名称/空管道验证，而不是静静地失败。 （#5062 — 关闭#4955）
  • **修复（sse）：**表面格式错误的 HTTP-200 上游响应，而不是将它们视为成功，因此可以触发组合回退。 （#4942 — 感谢@haipham22）
