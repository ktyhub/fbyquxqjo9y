OmniRoute v3.8.39

OmniRoute v3.8.39

✨ 新功能

  • feat(oauth)：通过本地帮助程序 + 粘贴凭据进行远程 Antigravity 登录 — Antigravity（以及其他 Google“本机/桌面”OAuth 提供商）使用 Google 的 firstparty/nativeapp 同意，仅当可以从批准的浏览器访问环回重定向 (127.0.0.1:<port>) 时才释放身份验证代码。在远程 VPS 安装上，该环回位于服务器上，因此同意永远挂起并且永远不会发出代码 - “粘贴回调 URL”后备没有任何可粘贴的内容（Google 端约束，与上游 9router 中相同）。新的 omniroute login antigravity CLI 帮助程序在用户的自己的机器（127.0.0.1 工作的地方）上运行 OAuth，交换代码，并打印单行 omniroute-cred-v1.… 凭据 blob；仪表板的 Antigravity Connect → 步骤 2 字段现在接受该 blob（以及回调 URL），并通过新的 paste-credentials 操作保持连接（服务器端加入、提供商允许列表，需要 blob 的嵌入式提供商来匹配路由）。 SSH 本地转发隧道被记录为零工具替代方案。请参阅 docs/guides/REMOTE-MODE.md。 (#5203)
  • feat(agent-bridge)：容器/无头的优雅证书安装后备 — 当 MITM 根 CA 无法自动安装到系统 trust 存储中（Docker / 无头 / 无 sudo / 只读 trust 存储）时，代理桥在启动时不再出现通用“证书安装失败”的硬故障。现在，它以跳过模式启动，仪表板会显示特定于平台的手动安装指南（以及 CA 下载链接），以便操作员可以手动 trust 证书。 trust-cert 端点针对环境故障返回结构化的 { skippable, manualGuide } 响应 (HTTP 200)，而不是 500；仍会明确报告显式用户取消。 （#4546 — 感谢@phuchptty）
  • feat(压缩)：CCR ranged/grep/stats 检索（ReDoS 安全、向后兼容） — 使用可选的 range（字节/行切片）、grep（ReDoS 安全文字或与存储行的有界模式匹配）和 stats（字节/行/字计数）参数扩展了 omniroute_ccr_retrieve MCP 工具和 /api/compression/retrieve 端点，以便代理准确提取他们需要切片或摘要，而不是重新扩展整个存储块。所有参数都是可选的——没有参数返回与现有行为相同的完整块字节； ionizer/fuzzy/headroom 编写的 CCR 存储完全兼容。压缩路线图的第六项。 (#5187)
  • 壮举（压缩）：TOON best-of-N 候选编码器 + 编码器 A/B 表 - 通过 best-of-N 方案在余量压缩引擎中添加 @toon-format/toon 作为候选编码器：GCF 和 TOON 按提示运行，并保留较短的结果，而不是硬交换编码器（GCF 已经对余量块进行了编码，而 TOON 不是无损通用胜利）。编码器 A/B 比较表（GCF、TOON、JSON — 字节和 cl100k 令牌）现已在压缩工作室中显示。压缩特征提取路线图的第五项（工作台：#5080，门：#5127，模糊/门：#5143，离子发生器：#5148)。 (#5163)

🔧 错误修复

  • 修复（oauth）：反重力刷新不再使空上游响应上存储的refresh_token为空 - Google的OAuth令牌端点使用非旋转刷新令牌：刷新响应通常省略refresh_token，偶尔将其作为空字符串返回。反重力执行器的 refreshCredentials 使用了 typeof tokens.refresh_token === "string" ? tokens.refresh_token : credentials.refreshToken，并且因为 typeof "" === "string" 为 true，所以空字符串响应用 "" 覆盖了好的令牌 - 在第一次刷新时将其清空。现在，该检查将非字符串 或空 值视为不存在，并保留存储的标记，与规范的 refreshGoogleToken (tokens.refresh_token || refreshToken) 语义相匹配。 （#3850 — 感谢@3xa228148）
  • 修复（api）：LAN/Tailscale 仪表板访问 — ws: CSP 方案、GET 豁免版本路由、表面组合字段错误 — 从非环回主机打开仪表板时出现三个故障：(1) CSP connect-src 仅允许 ws: 方案用于环回源，阻止来自 LAN/Tailscale 的仪表板 ws://<lan-host>:* Live WebSocket clients；现在允许裸 ws: 方案（与已经允许的裸 wss: 对称），在 next.config.mjs 中保持声明性，没有全局中间件（该项目在设计上没有）； (2) 尽管只有 POST 生成子进程 (git/npm/pm2)，但 GET /api/system/version 的所有方法都被 LOCAL_ONLY_API_PREFIXES 阻止 - 新的 LOCAL_ONLY_API_GET_EXEMPTIONS 集免除了此路径的安全读取方法，同时保持 POST/PUT/PATCH/DELETE 严格仅环回； (3) COMBO_002 验证错误仅出现通用消息 — firstField/firstMessage 现在从第一个 Zod 问题中提取并包含在响应正文中。 （#5083 — 感谢@KooshaPari 的诊断和原始 PR #5084）
  • 修复（sse）：推迟</think>关闭，这样它就不会在Claude→OpenAI流中的tool_calls之前泄漏 - 当Claude思考块后面跟着tool_use块时，翻译器无条件地在content_block_stop处发出content: "</think>"块，在tool_calls增量之前注入虚假的辅助文本块并破坏与OpenAI兼容的clients （例如基米编码）。关闭标记现在被推迟：它在思维块后面的第一个 text_delta 处刷新（保留 Claude 代码/光标的 #4633 / decolua/9router#454 行为），或者在没有收集到 tool_calls 时在流完成时刷新。工具使用流在思考块之后永远不会得到 text_delta，因此 </think> 永远不会在 tool_calls 之前发送到内容中。 (#5123)
  • 修复（sse）：规范命令代码执行器中的数组用户消息内容以防止上游 400 - 当 client 发送 content 是内容部分数组（例如 [{type:"text",text:"…"}, …]）的用户轮流时，原始数组被逐字转发到命令代码上游，这要求 user 角色的 messages[N].content 是纯字符串 -导致 DeepSeek V4-Pro 和其他命令代码模型上出现 expected string, received array / HTTP 400。 convertMessages 的用户分支现在调用 normalizeContentText()（已被系统、助手和工具分支使用），因此多部分用户内容在分派之前会连接到一个字符串。部分地址（#5166）；仅推理模型上的 0 输出标记症状是单独跟踪的。
  • 修复（mcp）：对于未知/过期的 Streamable HTTP 会话 ID 返回 HTTP 404（不是 400） — 当 MCP 会话终止或闲置并且 client 重用过时的 Mcp-Session-Id 标头时，Streamable HTTP 传输会回复 HTTP 400。 MCP 规范（2025-03-26 和 2025-11-25，会话） Management) 在这种情况下强制要求 HTTP 404 Not Found，并且符合规范的 clients 仅重新初始化 404 上的会话，因此 400 是不可恢复的。现在，处理程序对于当前但未知的会话 ID 返回 404，而非初始化请求上的_missing_会话 ID 正确地保持为 400。（#5169 — 感谢 @czer323）
  • 修复（api）：在安全设置中阻止“自动（零配置）”现在会从 /v1/models 中删除 auto/* - 模型目录顶部的内置 auto/* 组合广告商（#4164 / #4235）忽略了 settings.blockedProviders，因此在“安全”→“阻止的提供商”下检查 自动（零配置） 没有效果，并且模型选择器没有效果不断列出每个 auto/* 条目。现在，当系统提供程序 auto（其 ID 和别名均为 auto）被阻止时，注入循环会跳过整个 auto/* 块，这与从目录中过滤其他提供程序的方式一致。 （#5192 — 感谢@WslzGmzs）
  • 修复（cli）：从物理RAM自动校准服务器V8堆，而不是固定的512MB默认值 - 服务器是用硬编码的--max-old-space-size=512（omniroute serve）生成的，或者根本没有堆标志（Electron桌面，然后继承了运行时的低约512MB默认值），因此RAM丰富的机器在负载下仍然会OOM崩溃（FATAL ERROR: Ineffective mark-compacts near heap limit … ~500MB） at code=134），具有许多提供商/帐户和大型模型目录（一份报告：16GB RAM、65 个提供商、~100 个帐户、~2600 个模型）。新的 calibrateHeapFallbackMb(os.totalmem()) 帮助程序将默认堆导出为约 35% 的物理 RAM，固定到 [512, 4096]，并连接到 bin/cli/commands/serve.mjs 和 electron/main.js。显式的 OMNIROUTE_MEMORY_MB（或预设的 --max-old-space-size）仍然获胜，因此 #2939 覆盖合约不变。 （#5172、#5160、#5152 — 感谢@manchairwang、@Xyzjesus）
  • 修复（oauth）：反重力登录不再挂起 - 即发即忘登录 + 有界后交换 - 仪表板的反重力 OAuth 登录无限期旋转，因为 postExchange 等待 onboardUser 内联重试循环（每次尝试最多 10 × 5 秒，每次获取没有超时），永远阻止 /exchange 响应。匹配上游 9router Web 流：onboardUser 现在在后台任务中运行“即发即弃”； /exchange 端点受 10 秒硬超时限制，因此它始终返回；进度端点允许仪表板轮询入职完成状态。 (#5193)
  • 修复（反重力）：在升级组合之前按配额系列重试反重力帐户 - 当一个反重力帐户返回 Gemini 模型的配额或速率限制 429（例如 gemini-3.5-flash-medium）时，组合编排可能会过早地前进到下一个组合模型，而不是为同一配额系列尝试其他符合条件的反重力帐户。反重力配额系列意识现已添加到后备路径中，因此一个帐户上的 429 会在组合降级为较低层模型之前触发共享该配额桶的其他反重力帐户之间的有界同模型重试。 （#5180 — 感谢@Ardem2025）
  • 修复（翻译器）：在非流 malformed-200 防护中接受 Claude 消息形状 — 当 Claude client（例如 Claude 代码）路由到非 Claude 提供者时，翻译后的非流响应正文采用由 convertOpenAINonStreamingToClaude 生成的 Claude 消息形状 (type: "message", content[])。 detectMalformedNonStream 只识别 OpenAI choices[].message 和响应 API output[]，因此该形状下降到 empty_choices → 502。守卫现在识别 Claude Messages 形状：携带 signature 的文本、工具_使用和思维块计数为有效输出，而真正空的 content: [] 仍被标记。 （#5156 — 感谢@NomenAK）
  • 修复（sse）：通过参数模式匹配解析无名的 deepseek-web <tool> 块 - 当 chat.deepseek.com 发出没有 <name> 子项、没有 JSON 主体 name/type 密钥且没有标签后缀的 <tool> 块时，返回 extractCall 中的每个名称解析路径null 和原始 XML 以纯文本形式泄露给 client。现在，基于模式的保守回退会将块提取的参数名称与每个声明的工具的模式键进行比较；如果恰好有一个工具匹配，则使用其名称。零或不明确 (>1) 匹配仍会返回 null，因此不会出现呼叫错误归属的情况。 （[#5154]（https://github.com/diegosouzapw/OmniRoute/issues/5154），[#5173]（https://github.com/diegosouzapw/OmniRoute/pull/5173））
  • 修复（流）：将提供商安全完成原因标准化为 content_filter — Gemini 和 Antigravity 可以返回与 OpenAI 兼容的下游 clients 无法识别的安全/禁止终端原因（SAFETY、RECITATION、BLOCKLIST、PROHIBITED_CONTENT）。共享的完成原因标准化帮助器现在将这些映射到标准 content_filter 值，应用于两个提供程序的流和 JSON 收集路径。 （#5197 — 感谢@rdself）
  • **修复（响应）：在路由之前标准化非数组响应 API input ** — OpenAI 响应 API 接受 input 作为字符串、对象或列表，但 OmniRoute 仅处理列表形有效负载；字符串或对象 input 被默默地放置在“响应”→“聊天完成”路径上。翻译器现在在发送之前将 input 标准化为列表； Codex 原生响应路径也在转发前进行标准化（防止上游 400 Input must be a list）；并且提示注入和 PII 消毒剂提取路径受到对象值 input 的保护，因此安全检查不会抛出。 （#5204 — 感谢@wilsonicdev）
  • 修复（zenmux）：规范 Z.AI 模型的供应商前缀 GLM 系统角色 — ZenMux 通过供应商前缀 OpenAI 兼容 ID（例如 z-ai/glm-5.2）公开 Z.AI GLM。现有的 GLM 检测仅匹配裸露的 glm-*/glm id，因此 zenmux/z-ai/glm-5.2 保留系统消息； Z.AI 拒绝以 assistant(tool_calls) → tool 序列之前的系统转动结束的压缩历史。该修复扩展了 GLM 检测以覆盖 z-ai/glm-* 前缀，并通过现有的 normalizeSystemRole 路径路由它们。 （#5158 — 感谢@Thinkscape）
  • 修复（xai）：添加 OAuth 连接测试探针 + 标准化 xAI 推理工作别名 — xAI 在提供程序更新后使用 HTTP 400 拒绝不支持的推理工作值（max、xhigh）； xAI 转换器现在在转发之前将 max 和 xhigh 映射到 high。此外，xAI OAuth 连接没有仪表板测试配置，因此提供商测试返回 "Provider test not supported"；现在，专用的 OAuth 测试探针已连接到 xAI 帐户，并具有回归覆盖范围以实现工作量标准化。 （#5157 — 感谢@nguyenxvotanminh3）
  • 修复（服务）：从.env尊重HOSTNAME而不是硬编码0.0.0.0 - bin/cli/commands/serve.mjs将process.env传播到子进程环境中，但立即用文字"0.0.0.0"覆盖HOSTNAME，默默地丢弃任何用户配置的绑定地址，即使HOSTNAME记录在.env.example 和 docs/reference/ENVIRONMENT.md。 dist/server.js 已正确读取 process.env.HOSTNAME；只有 CLI 包装器覆盖了它。该修复应用 process.env.HOSTNAME || "0.0.0.0"，以便 env 值生效。 （[#5134]（https://github.com/diegosouzapw/OmniRoute/issues/5134），[#5170]（https://github.com/diegosouzapw/OmniRoute/pull/5170）-感谢@anki1kr / @Angelo90810）
  • 修复（cli）：强制NODE_ENV匹配自定义Next服务器中的开发/启动运行模式 - 当.env.example运送NODE_ENV=production时，通过scripts/dev/run-next.mjs启动npm run dev将该值转发到编程next()条目，这与next CLI不同 - 不会对其进行标准化以匹配运行模式。由此产生的生产标志导致 PostCSS 跳过 Tailwind 的 CSS 转换，在 globals.css 上显示为 Module parse failed: Unexpected character '@'。自定义服务器现在显式强制 dev 路径使用 NODE_ENV=development，对于 start 路径强制使用 NODE_ENV=production，无论 .env 是什么。 （#5189 — 感谢@backryun）
  • 修复（cli）：将开发服务器节点堆限制提高到 8 GB 以防止 OOM - 在编译繁重的仪表板路由时，npm run dev 与 FATAL ERROR: Ineffective mark-compacts near heap limit — Allocation failed - JavaScript heap out of memory 一起崩溃，因为 node scripts/dev/run-next.mjs 在 V8 的 ~4 GB 默认值上运行，没有 --max-old-space-size 标志。 dev npm 脚本现在在调用时传递 --max-old-space-size=8192（这是可以为该进程设置此标志的唯一点）。 （#5198 — 感谢@backryun）
  • 修复（cli）：重新启用 Turbopack 作为默认的 npm run dev 捆绑程序 — PR #4092 强制使用 webpack，因为早期的 Turbopack 16.2.x 恐慌（turbopack-core/module_graph 中的 internal error: entered unreachable code: there must be a path to a root）阻止了 OmniRoute 模块图。这种恐慌不再在固定的 Next 16.2.9 上重现，因此 OMNIROUTE_USE_TURBOPACK 在 .env.example 中从 0 翻转为 1，将其与已将默认值记录为 1 的 docs/reference/ENVIRONMENT.md 对齐。 （#5206 — 感谢@backryun）
  • 修复（身份验证）：允许 mimocode 的合成无身份验证回退 — 没有显式凭据的 mimocode 连接在到达执行程序之前被阻止。身份验证层现在允许 mimocode 提供程序进行合成的无身份验证回退，因此无凭据访问模式可以按预期工作。 （#5205 — 感谢@KooshaPari）
  • 修复（组合）：拒绝空响应 API output: [] 作为故障转移触发器 - 带有 object: "response" 和 output: [] 的非流响应 API 主体被组合响应质量验证器接受为有效的 HTTP 200，允许组合目标停止而不是故障转移到下一个分支。非流验证器现在在通用 output 快捷方式之前检查 Responses-API 形状的主体，并将空的 output: [] 拒绝为 empty_choices；结构非空输出（例如 function_call）仍然有效。 （#5207 — 感谢@KooshaPari）
  • 修复（代理）：清除代理缓存时关闭缓存调度程序 - 缓存代理和直接重试调度程序在缓存清除时未关闭，泄漏打开的连接句柄。缓存清除路径现在在所有被逐出的调度程序上调用 close()；调度程序缓存和生命周期助手已从超大的代理调度程序模块中提取到专用助手中以供重用。 （#5202 — 感谢@KooshaPari）
  • 修复（代理）：合并每个代理 URL 的并发快速失败运行状况探测 — 在高并发情况下，每个并发请求都会为同一代理 URL 打开自己的 TCP 运行状况探测，从而产生雷鸣般的爆发。并发代理快速失败检查现在已合并，因此每个代理 URL 一次仅运行一个 TCP 探测；已完成的结果运行状况缓存将被保留，以便后续的相同 URL 检查立即返回。 （#5109、#5208 — 感谢@KooshaPari）
  • 修复（pwa）：在显示离线页面之前更喜欢缓存导航 - 服务工作人员太渴望在短暂的导航失败时显示 /offline。现在，它会缓存成功的导航响应，并在回退到 /offline 之前查询缓存的路线或应用程序 shell；当不存在缓存的导航或应用程序 shell 时，/offline 仍然是最终的后备方案。 （#5165、#5209 — 感谢@KooshaPari）
  • 修复（请求记录器）：永远不会在压缩徽章中呈现负百分比 — 当压缩每个提示令牌 (totalIn = 0, compressed > 0) 时，压缩药丸显示 (-100%)，因为徽章格式在百分比值之前硬编码了一个前导 -。在这种情况下，徽章现在省略了负号，正确地将节省表示为正比率。 （#5201 — 感谢@KooshaPari）
  • 修复（仪表板）：使用琥珀色作为主更新步骤警告图标 - 主更新步骤 (HomePageClient.tsx) 中的警告状态图标使用 text-yellow-500 (Tailwind #eab308)，它在浅色背景（~1.9:1，低于 WCAG AA）上对比度较差，并且与同一组件中每个同级元素使用的 amber 警告约定不一致。切换到 text-amber-500 — 一行 className 更改，没有行为变化。 (#5176)
