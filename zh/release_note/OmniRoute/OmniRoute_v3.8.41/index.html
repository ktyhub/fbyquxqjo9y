OmniRoute v3.8.41

[3.8.41] — 2026-06-29

✨ 新功能

  • feat(relay)：可选择的中继后端 (TS / Bifrost / auto) — OpenAI 兼容的中继端点现在可以通过本机 Bifrost sidecar 路由其热路径，而无需 clients 更改 URL。 OMNIROUTE_RELAY_BACKEND / RELAY_ROUTING_BACKEND = ts | bifrost | auto：默认为现有TypeScript继电器；当 BIFROST_BASE_URL 设置时（且 BIFROST_ENABLED ≠ 0），auto 选择 Bifrost，如果 sidecar 无法到达，则自动回退到 TS； bifrost 保持严格的故障行为。身份验证、每个 IP/令牌速率限制、提示注入检查和模型允许列表在调度之前仍在下一个中继路由中运行（控制平面保留在应用程序中）；响应携带 X-Routing-Backend / X-Routing-Fallback。回归防护：tests/unit/api/v1/relay-routing-backend.test.ts、tests/unit/api/v1/bifrost-sidecar.test.ts。 （[#5315]（https://github.com/diegosouzapw/OmniRoute/pull/5315），#5316 — 感谢@KooshaPari）

🔧 错误修复

  • 翻译器（克劳德）：当 OpenAI→Claude 请求仅 system/developer 消息时，合成最小的 user 回合，因此请求不会因 [400]: messages: at least one message is required 而失败。 openaiToClaudeRequest将每个系统/开发人员转入Claude的顶级system领域，并将其过滤出messages；全系统输入（OpenCode 压缩/标题生成请求）离开了 messages: []，而消息 API 拒绝了该输入 — 在 OpenCode 中作为中间任务 stream error 出现，从而放弃了对话。仅当 messages 为空时（系统指令仍驱动响应），防护才会触发，因此非空请求不受影响。 (#5342 — 感谢@wild-feather)
  • 提供商（双子座）： 删除已停用的 Google AI Studio 模型 ID，并将目录与实时 GenAI API 实际服务的内容保持一致（已于 2026 年 6 月 29 日根据官方弃用页面进行验证）。删除了长期退役的 gemini-1.5-pro/gemini-1.5-flash、已关闭的 gemini-2.0-flash/gemini-2.0-flash-lite 和已失效的实验；重命名 gemini-3.1-flash-lite-preview → GA gemini-3.1-flash-lite；将退役的 text-embedding-004 替换为现役的 gemini-embedding-001/gemini-embedding-2；并添加优雅的 modelDeprecation 转发，以便旧版/重命名的 ids 重定向到 GA 模型而不是 404ing。本机 AI-Studio 直接图像/视频/音乐注册故意超出范围（需要真正的执行器工作；这些模型仍然可以通过反重力/顶点/聚合器访问）。 （#5337 — 感谢@backryun）
  • **服务（仪表板）：**修复嵌入式服务仪表板故障（＃5298） - 服务主管现在从 /api/services/[name]/logs 延迟初始化，因此在引导程序注册主管之前，cliproxy/9router 日志不再是 404；生命周期按钮发送 JSON（空安装主体默认为 version: "latest"，格式错误的 JSON 仍返回 400 Invalid JSON body）；生命周期和日志流故障显示为可操作的 UI 错误，而不是默默地不显示任何日志； Tailscale CGNAT 100.64.0.0/10 对等点算作私有 LAN 本地，仅用于本地服务访问；父 /dashboard/context → /dashboard/context/settings 重定向会停止 RSC 预取 404；和 /api/v1/providers/{cliproxyapi,9router}/models 返回同步的嵌入式服务模型而不是 invalid_provider。 （[#5299]（https://github.com/diegosouzapw/OmniRoute/pull/5299），#5298 — 感谢@KooshaPari）
  • **思考（克劳德）：**修复 OpenAI 兼容路径上的克劳德自适应思维中的三个独立缺陷（光标 → 克劳德 OAuth）。 (A) 仪表板 Thinking-Budget 设置在每次重新启动时都会被删除 - setThinkingBudgetConfig 在启动时从未被调用，因此保存的 {mode:"adaptive"…} 会默默地恢复为直通；现在它已经从 server-init 的设置中水化了。 (B) Claude 执行器在翻译后强制注入自适应思维，忽略操作员的预算 - 它现在尊重 mode:"auto"（条带），同时保持默认（直通）行为字节相同，因此本机 Claude 代码不受影响，并将操作员 thinking.type:"enabled" 重新映射到 adaptive 形状 Opus 4.7/4.8 需要 (enabled → 400)。 (D) 在重放时，无签名的 reasoning_content 被重建为带有伪造签名的 thinking 块 → Anthropic 400 "Invalid signature in thinking block"；它现在发出一个无签名的 redacted_thinking 块（真实签名仍然逐字保留）。回归守卫：tests/unit/thinking-budget-hydration-5312.test.ts、base-thinking-budget-config-5312.test.ts、openai-to-claude-redacted-replay-5312.test.ts（现有的#5123/#4479/#2454套件保持绿色）。 </think> 内容标记通道不匹配（RC-C，与 #5245 共享）被跟踪为后续活动，等待实时人类验证。 （#5312 — 感谢@vitalNohj）
  • opencode（代理池）： OpenCode 免费每帐户代理模式现在提供全局 代理池下拉列表（按 ID 引用），而不是在每个帐户上强制手动主机/端口/凭据 - #5217 的间隙 1。 已保存/自定义切换：“已保存”从 GET /api/settings/proxies 中选择预先保存的代理并存储 {fingerprint, proxyId}，因此更新该池代理适用于使用它的每个帐户； “自定义”将手动输入（内联存储）保留为逃生舱口。解析发生在服务器端（resolveAccountProxiesFromRegistry），因此执行器仍然会收到未更改的已解析代理；现有的内联条目继续工作，并且未知/删除的 proxyId 可以安全地降级为直接。回归防护：tests/unit/noauth-proxy-resolution.test.ts、tests/unit/ui/noauth-account-card.test.tsx。 (#5217 差距 1 — 感谢 @daniij)
  • **思考（克劳德）：**让reasoning_content-native clients（例如光标）选择退出</think>关闭标记，这样它就不再将孤儿</think>泄漏到可见的content中（#5312的RC-C，与#5245共享）。标记抑制机制已经存在（UA 允许列表，#5348），但 Cursor 的 UA 被故意排除；这会添加一个显式请求标头 x-omniroute-thinking-marker: off（也可以使用 on/keep 强制保留）来覆盖 UA 策略。如果没有标头，行为是字节相同的 - 扫描 content 中标记的 Claude 代码/光标编写器 client (#4633) 仍然会收到它。回归守卫：tests/unit/think-close-marker-suppress-5245.test.ts（#5123 case-b + #4479 保持绿色）。 （[#5312]（https://github.com/diegosouzapw/OmniRoute/issues/5312），[#5245]（https://github.com/diegosouzapw/OmniRoute/issues/5245）-感谢@vitalNohj，@wild-feather）
  • cors: 浏览器/Electron clients（例如 Wayland AI）现在可以使用 OmniRoute 作为开箱即用的 OpenAI 兼容提供程序。经过令牌验证的 API 表面（/v1/*、/v1beta/*）现在默认返回一个宽松的 Access-Control-Allow-Origin（在不存在时回显请求 Origin、*）——匹配 9router 和 OpenAI 兼容的生态系统——因此渲染器 fetch 可以读取响应，而不是因“找不到站点”而被 CORS 阻止失败 /空目录（而 curl 不发送预检，可以工作）。这是安全：那些通过 Authorization/x-api-key 标头进行身份验证的路由浏览器永远不会自动附加（没有凭证会话/CSRF 暴露），并且 Access-Control-Allow-Credentials 永远不会与 echo/通配符配对。经过 Cookie 验证的 管理/仪表板路线保持完全失败关闭； CORS_ALLOW_ALL/CORS_ALLOWED_ORIGINS 仍优先。回归防护：tests/unit/cors/origins.test.ts、tests/unit/authz/pipeline.test.ts。 （#5242 的错误 2 — 感谢 @jonlwheat2-gif）
  • grok-web: 转发 Cloudflare 清除 cookie 并停止将 IP 信誉块错误标记为坏 cookie。即使有一个有效、完整的浏览器会话，“检查 cookie”也会返回 Invalid SSO cookie — 但 cookie 解析器从来都不是问题（它从完整的 DevTools 标头中可靠地提取 sso/sso-rw）。修复了两个实际间隙：(1) buildGrokCookieHeader 现在在粘贴时转发 cf_clearance 和 __cf_bm（之前已删除它们；AIClient2API 也转发它们）——严格来说，一个裸露的 sso 斑点仍然会准确生成 sso=…； (2) 当用户提供 cf_clearance 时，来自 grok.com 的 401 / invalid-credentials-403 现在显示为 IP 信誉/反机器人块（cf_clearance 是 IP+TLS+UA 固定的，无法从其他计算机重播），而不是误导性的“无效 SSO cookie — 重新粘贴”。没有间隙的裸 cookie 仍然会收到重新粘贴提示。 web-cookie-auth.test.ts + provider-validation-specialty.test.ts 中的回归防护。 （#5350 — 感谢@SeaXen）
  • **cli（服务）：**为 omniroute serve 选择本机 HTTPS/TLS - 因此严格的 CSP Electron 应用程序和浏览器可以通过 https:// 而不是普通的 http://localhost 访问 OmniRoute。提供 ZZPH100​​ZZ（或 OMNIROUTE_TLS_CERT/OMNIROUTE_TLS_KEY），独立服务器在同一侦听器上终止 TLS（无额外端口/代理）； WebSocket 升级（实时仪表板 + /v1 流）在 wss:// 上工作，自 https.Server extends http.Server 以来没有变化。如果没有 TLS 标志，HTTP 路径的字节与之前相同；只有证书/密钥之一或不可读的路径会记录警告并保持 HTTP（永远不会半启用，永远不会崩溃）。为本地主机自动生成的自签名证书是后续措施；现在提供显式的证书/密钥（或带有 TLS 终止符的前端 OmniRoute）。回归防护：tests/unit/tls-options.test.ts。 （#5242 的 Bug 1C — 感谢 @jonlwheat2-gif）
  • opencode/可观察性： 使 OpenCode 免费帐户/代理轮换可见，并修复随之而来的两个实际缺陷。 (1) 每个请求轮换选择日志 (dispatch via account … through proxy …) 为 debug（默认为 APP_LOG_LEVEL=info 隐藏） — 提升为 info，因此洗牌/冷却生命周期是可审核的（令牌保持屏蔽状态）。 (2) 即使应用帐户代理，[ProxyEgress] 也会报告 proxy=direct，因为出口记录器在执行程序的嵌套代理上下文之外运行 - 现在捕获有效的应用代理（通过通过代理 AsyncLocalStorage 线程化的应用代理接收器）并反映在出口日志中。 (3) [callLogs] too many SQL variables — deleteCallLogRowsByIds 在一个 IN (…) 中删除了多达 5000 个 id，超过了 SQLite 的 ~999 绑定参数上限并中止日志修剪/保留； id 现在已分块（每个语句≤500）。回归防护：tests/unit/call-log-trim-sql-vars-5217.test.ts、apply-executor-proxy-info-5217.test.ts、扩展opencode-proxy-rotation-4954.test.ts。代理池下拉菜单（按 ID）UI（间隙 1）是需要浏览器验证的后续操作。 （#5217 — 感谢@daniij）
  • chatgpt-web： 将工具/函数调用连接到 chatgpt-web 提供程序。它是唯一一个从未读取过 body.tools 的网络会话执行器——两个响应构建器都硬编码了 finish_reason:"stop" 并仅发出内容，因此工具调用被默默地丢弃（模型以散文形式回答）。现在，它使用共享的 webTools 提示仿真垫片（<tool>-合约系统消息 + <tool>{…}</tool> 响应解析），与其 9 个兄弟执行器（qwen-web、perplexity-web 等）完全一样 - 它只是在 #3259 推出中被省略。工具模式缓冲并发出 tool_calls + finish_reason:"tool_calls"（关闭图像生成路径）；普通聊天没有改变。回归防护：tests/unit/chatgpt-web-tools-5240.test.ts。 （#5240 — 感谢@Rougler）
  • oauth/dashboard：修复持久/错误的反重力“令牌过期”徽章（#3679/#3850 的延续）。有两个原因：(1) 新的 OAuth 连接从未设置 tokenExpiresAt（仅 expiresAt），因此仪表板徽章（更喜欢 tokenExpiresAt || expiresAt）回落到原始授权时钟，并且可能会闪烁错误的“令牌已过期”，直到第一次后台刷新。创建现在将 expiresAt 镜像到所有 5 个 OAuth 创建路径（共享 buildOAuthConnectionCreatePayload）中的 tokenExpiresAt，与已写入两者的每个刷新路径一致。 (2) 当支持刷新的连接没有可用的刷新令牌时，运行状况检查扫描会默默地跳过它，永远留下 testStatus="active"，而装饰徽章显示已过期；它现在显示一个终端 testStatus="expired"（“需要重新验证”），严格控制，因此它永远不会破坏非刷新提供程序或已经终端/冷却状态。回归防护：tests/unit/oauth-connection-tokenexpiresat-5326.test.ts、tests/unit/token-health-no-refresh-token-expired-5326.test.ts。 (#5326)
  • **路由：**对于 API 密钥循环连接（一个连接的 extraApiKeys 中有多个密钥），自动禁用上游 402 "Insufficient account balance" 上耗尽的 API 密钥。每个连接路径已终止 402（→ credits_exhausted），但每个密钥运行状况跟踪器 (recordKeyHealthStatus) 仅记录 401 的故障，因此 402 耗尽的密钥保持轮换并不断重试。现在，402 通过新的 recordKeyTerminal 立即将当前密钥标记为无效（终端 - 平衡不会在会话中恢复），因此旋转器会跳过它并转到下一个健康密钥；该状态在重新启动后仍然存在。还将 insufficient balance/insufficient_balance/insufficient account balance 添加到积分耗尽的身体信号中，因此非 402 积分外响应也会终止。回归防护：tests/unit/key-health-402-disable-5239.test.ts。 (#5239 — 感谢@muflifadla38)
  • cli： omniroute serve 不再丢弃用户设置的 NODE_OPTIONS=--max-old-space-size=…。它曾经使用校准的默认值无条件覆盖 NODE_OPTIONS（并传递显式的 --max-old-space-size CLI arg），因此导出 --max-old-space-size=8192 的用户仍然以旧上限运行并 OOM’d（#5238 记者集 8192，在〜505MB 时崩溃）。现在它镜像了 Electron 和独立启动器：如果 NODE_OPTIONS 已经固定堆，则该值获胜（并且重复的 CLI arg 被抑制）；否则会附加校准后的 --max-old-space-size，保留不相关的标志。回归防护：tests/unit/serve-node-options-preserve-5238.test.ts。 （#5238 的缺陷 C；b.mask/OOM 根部分单独跟踪。）
  • 仪表板：在提供商的可用型号工具栏（提供商详细信息页面）中恢复 {active}/{total} active 型号计数徽章。它在 v3.8.13 god-file 分解过程中被丢弃（#3327）——ModelVisibilityToolbar 仍然收到 activeCount/totalCount，但它们作为未使用的 _ 前缀参数而被孤立，并且渲染 <span> 从未被继承（modelsActiveCount i18n 密钥保留）。将现有道具重新连接到现有钥匙；零数据层或 i18n 更改。回归防护：modelVisibilityToolbarActiveCount.test.tsx。 (#5264)
  • rerank： /v1/rerank 不再拒绝带有 400 "Invalid rerank model" 的 SiliconFlow 和 DeepInfra Qwen3-Reranker 模型，即使 /v1/models 列出了它们。模型 ID 解析器从来都不是问题（它已经在第一个斜杠处拆分，因此 siliconflow/Qwen/Qwen3-Reranker-8B 可以正确解析）——siliconflow 和 deepinfra 只是重新排序提供程序注册表中缺失。添加了两者：SiliconFlow 与 Cohere 兼容，DeepInfra 通过新的 deepinfra 适配器（URL 路径 POST /v1/inference/<model> 中的模型、{queries,documents} 请求、映射到 Cohere results[] 的位置 {scores} 响应）。回归防护：tests/unit/rerank-providers-5332.test.ts。 （#5332 — 感谢@maikokan）
  • authz/dashboard： 当通过 LAN IP/非 localhost 主机访问仪表板时，停止拒绝使用 403 INVALID_ORIGIN 的每个仪表板突变。原点固定检查 (#5278) 仅接受配置的 *_PUBLIC_BASE_URL（通常是 http://localhost:20128）加上内部 request.url 原点 - Next.js 独立报告为绑定主机，而不是真正的 Host。因此，打开仪表板，例如http://192.168.0.15:20128 使浏览器的同源 Origin 无法匹配任何候选者，并且每个 POST/PUT/DELETE（保存 API 密钥、保存提供程序、测试连接）失败，而 GET 仍然有效。两个修复： (a) 请求 Host（或 trusted X-Forwarded-Host）现在被接受为有效的突变源，由两个独立的检查控制 - 标记标记的套接字对等体必须是环回/私有 LAN 并且 主机本身必须是环回/私有 LAN IP 文字，因此 DNS 重新绑定域（分类为 remote）永远不会成为trusted 起源和协议固定到实际连接； (b) INVALID_ORIGIN 响应现在携带可操作消息（设置 OMNIROUTE_PUBLIC_BASE_URL），并且仪表板通过共享 extractApiErrorMessage 帮助程序显示 API 错误 .message，而不是渲染原始错误对象。回归防护：tests/unit/authz/public-origin.test.ts（直接 LAN/环回 + DNS 重新绑定防御）、tests/unit/api-error-message-5340.test.ts。 (#5340)
