airflow 2.11.0

小版本 发布时间2025年5月20日 来源apache/airflow 英文原文

airflow 2.11.0

这个项目是干啥的：一个用代码编排定时任务的调度平台，把数据处理流程串成流水线，按时运行、失败可重试，适合要管理大量周期性作业的工程师。

变更架构图

亮点

  • 移除对 Python 3.8 的支持 — Airflow 2.11 要求 Python 3.9–3.12。请在升级 Airflow 前先升级运行时；仍停留在 Python 3.8 的环境将不再受支持（#49980、#50015）。
  • 预览 Airflow 3 的 delta 调度 — 2.11 中 schedule=timedelta(...) 默认仍使用 DeltaDataIntervalTimetable。设置 [scheduler] create_delta_data_intervals=False 可选择新的 DeltaTriggerTimetable，它在调度时不使用数据区间；Airflow 3 将把此行为设为默认（#47074）。
  • 升级前统一计时指标单位 — 启用 [metrics] timer_unit_consistency=True，让所有计时指标以毫秒上报。这解决了此前 StatsD 用毫秒、而 OpenTelemetry 和 Datadog 用秒的分裂问题；请检查仪表盘阈值和告警中的单位假设（#39908、#43966）。
  • 从 execution_date 迁移到 logical_date — 暴露 execution_date 的模型现在也包含 logical_date。请在 Airflow 3 彻底移除 execution_date 之前，把插件、模板和自定义代码更新为使用 logical_date（#44283）。
  • 用新 CLI 命令审查配置 — 使用 airflow config lint 识别需关注的配置，airflow config update 辅助迁移。应用配置变更请先审查，以免生产出现意外行为（#45736、#50353、#46757）。

重大变化

DeltaTriggerTimetable 用于基于触发器的调度 (#47074)

此更改引入了 DeltaTriggerTimetable，这是一种新的内置时间表，可补充现有的套件 通过支持基于增量的触发计划来制定气流时间表，而不依赖于数据间隔。 Airflow 目前有两种主要类型的时间表：

  • 基于数据间隔（例如“CronDataIntervalTimetable``, ``DeltaDataIntervalTimetable”）
  • 基于触发器（例如“CronTriggerTimetable”） 但是，对于增量间隔，没有类似的基于触发器的选项，如“timedelta(days=1)”。 因此，即使是像“schedule=timedelta(days=1)”这样简单的时间表也是通过数据间隔来解释的 镜头——为不关心上游/下游数据依赖性的用户增加了不必要的复杂性。 此功能向后移植到 Airflow 2.11.0，以帮助用户在升级到 Airflow 3.0 之前开始过渡。
  • 在气流 2.11、“schedule=timedelta(...)`` still defaults to ``DeltaDataIntervalTimetable”中。
  • 新的配置选项“[scheduler] create_delta_data_intervals`` (default: ``True``) allows opting in to ``DeltaTriggerTimetable”。
  • 在 Airflow 3.0 中，此配置默认为“False``, meaning ``DeltaTriggerTimetable”成为 timedelta 计划的默认值。 通过在 2.11 中翻转此配置，用户可以提前预览并采用新的调度行为 - 最大限度地减少升级过程中的意外情况。

所有后端的一致计时指标（#39908、#43966）

此前，Airflow 报告“StatsD”的计时指标以毫秒为单位，但其他后端的计时指标以秒为单位 例如“OpenTelemetry`` and ``Datadog”。这种不一致使得解释或比较变得困难 跨系统的计时指标。 Airflow 2.11 引入了一个新的配置选项：

  • [metrics] timer_unit_consistency (default: False in 2.11, True 并放入气流 3.0 中）。 启用后，无论后端如何，所有计时指标都会以毫秒为单位一致报告。 此设置已成为强制性的，并且在 Airflow 3.0 中始终为“True”（该配置将被删除），因此 在 2.11 中启用它可以让用户尽早迁移并避免升级过程中出现意外。

轻松迁移到 Airflow 3

此版本引入了几项更改，以帮助用户为升级到 Airflow 3 做好准备：

  • 所有使用 execution_date now also include a logical_date field. Airflow 3 drops execution_date entirely in favor of logical_date 的型号 (#44283)
  • 在 2.11 中添加了“airflow config lint`` and ``airflow config update”命令，以帮助审核和迁移 Airflow 3.0 的配置。 （#45736、#50353、#46757）

Python 3.8 支持已删除

对 Python 3.8 的支持已被删除，因为它已达到使用寿命。 气流 2.11 需要 Python、3.9、3.10、3.11 或 3.12。

新功能

  • 引入 DeltaTriggerTimetable (#47074)
  • 向后移植“airflow config update`` and ``airflow config lint”更改以方便迁移到 Airflow 3（#45736、#50353）
  • 添加链接以在 DAG 依赖关系视图中显示 DAG 中的任务 (#47721)
  • 跨所有指标记录器对齐计时器和计时指标（毫秒）（#39908、#43966）

  • 修复 ti.log_url timestamp format from "%Y-%m-%dT%H:%M:%S%z" to "%Y-%m-%dT%H:%M:%S.%f%z" (#50306)
  • 确保生成的 airflow.cfg contains a random fernet_key and secret_key (#47755)
  • 通过内部 api 修复了设置 rendered_map_index (#49057)
  • 存储来自 TaskInstancePydantic into TaskInstance 的 render_map_index (#48571)
  • 允许使用log_url property on TaskInstancePydantic（内部API）（＃50560）
  • 修复默认为空对象的触发器表单 (#46872)
  • 修复 TypeError when deserializing task with execution_timeout set to None (#46822)
  • 始终填充映射任务 (#46790)
  • 确保 check_query_exists 返回布尔值 (#46707)
  • 用户界面：“/xcom/list`` got exception when applying filter on the ``value”列（#46053）
  • 允许通过实验性内部 api 设置注释字段 (#47769)

杂项

  • 添加 logical_date to models using execution_date (#44283)
  • 放弃对 Python 3.8 的支持（#49980、#50015）
