airflow 3.4.0

📦PyPI：https://pypi.org/project/apache-airflow/3.4.0/ 📚 文档：https://airflow.apache.org/docs/apache-airflow/3.4.0/ 🛠 Release Note：https://airflow.apache.org/docs/apache-airflow/3.4.0/release_notes.html 🐳 Docker 图片：“docker 拉 apache/airflow:3.4.0” 🚏 约束：https://github.com/apache/airflow/tree/constraints-3.4.0

重大变化

任务循环（#73005、#74222、#74275、#74345）

Airflow 3.4.0 引入了任务循环 (AIP-111)：一个装饰任务组可以重复多次 使用“.loop()``. A conditional loop works like a ``do ... while”循环在运行时决定的时间 - 主体至少运行一次，并且“until”条件决定何时停止，边界为 max_iterations。每次迭代都可以使用前一次迭代的结果，并且迭代运行一次 一个又一个（迭代中的任务仍然可以并行运行）。保留重试尝试 在每次尝试的 UUID 下，因此每次迭代的数据都会被保留并可以有选择地清除。 详细使用说明请参见：doc:/authoring-and-scheduling/loops。 ..注意:: 降级到任何早于 3.4.0 的版本可能会很慢，具体取决于 3.4.0 的数量 升级后已写入的 XCom 行。升级已在 300m排XCom桌子，所以请不要担心升级时间（我们确保 XCom 数据在迁移过程中没有被触及或读取以保留它 快）。 这是因为此版本包含开始存储新 XCom 的迁移 xcom_v2 表中的行，为了降级，我们必须将这些行移过来 到旧表，如果不复制就无法做到这一点 写入xcom值。 当发现无法映射回的数据时，降级将拒绝继续 安全。每个迁移单独提交，因此后面的 3.4.0 迁移 此时已被逆转：修复数据并重新运行 降级，或运行“airflow db migrate”返回到3.4。 在 MySQL 上，这些检查后的失败会使架构部分降级， 因为MySQL无法回滚DDL。在尝试之前进行备份 建议降级MySQL，这样在这种情况下可以恢复。

非 Python Dags 的 Dag 导入器 (#72369、#73728、#73853、#74020、#74084、#74333、#74586)

Airflow 3.4.0 可以用其他语言编写整个 Dag - 计划、任务和依赖项 比Python。 AIP-85 在任务 SDK 中添加了一个可插入 Dag 导入器，教导 Dag 处理器 识别“.py”之外的源格式：每种格式注册一个导入器，处理器运行 匹配语言运行时，生成的 Dags 在 Airflow 中显示，如 Python Dags。格式 其上包含 TypeScript、Go 和 Java 语言 SDK 以及本机 YAML Dag 格式（a .yaml file with a $schema 标记，根据模式进行验证并内置到实际运算符中， 具有显式模板）。 Dag Importer 框架和语言 SDKs 在 3.4 中是实验性的 他们的 API 可能会改变。 详细使用说明请参见：doc:/administration-and-deployment/dag-importers。

在 BaseExecutor.executor_queues 下统一执行器工作负载队列 (#63491)

执行器工作负载状态现在存储在统一的“BaseExecutor.executor_queues”映射键上 通过“WorkloadType`` and scheduled through ``trigger_workloads”。之前的每类型属性 和入口点（queued_tasks, queued_callbacks, supports_callbacks, trigger_tasks， order_queued_tasks_by_priority) 和 Airflow 3.3 连接测试表面折叠成 此映射并保留为向后兼容的垫片，发出“RemovedInAirflow4Warning”（将 在 Airflow 4.0 中删除）。树外执行器应声明“supported_workload_types”并且 实施“trigger_workloads”。连接测试现在可以在相同的心跳下进行 预算作为任务并优先考虑。参见 #63491 <https://github.com/apache/airflow/pull/63491>_ 获取完整的迁移指南。

psycopg3 现在是默认的 Postgres 驱动程序 (#68496)

psycopg3 (psycopg) 现在是元数据数据库的默认驱动程序，用于同步和 异步引擎，取代 psycopg2 和 asyncpg。裸露的“postgresql://”（或遗留的 postgres:// / postgres+psycopg2://) sql_alchemy_conn 被重写为 postgresql+psycopg://, and the derived async URL uses postgresql+psycopg_async://时 psycopg3 已安装（否则回退到 asyncpg）。 Airflow 也会禁用 psycopg3 服务器端语句准备（prepare_threshold = None），以便元数据数据库正常工作 交易模式 PgBouncer 后面的框，推荐的生产设置。保留 psycopg2 或 asyncpg，安装额外的apache-airflow-providers-postgres[psycopg2] / [asyncpg] 显式配置连接；有关详细信息，请参阅#68496 和#69469，包括如何重新启用 声明准备。

资产触发的 Dags 默认为每个事件创建一次运行 (#68517)

单资产计划和资产 OR 表达式现在为每个事件创建一次 Dag 运行，而不是 在一次运行中消耗所有排队的事件。这也适用于“AssetOrTimeSchedule”和 PartitionedAssetTimetable。 要保留批处理，请设置“batch_asset_events=True`` on the timetable or enable ”[调度程序] batch_asset_events“ 并重新解析受影响的 Dags。已经序列化的时间表没有这个 选项保留其之前的批处理行为，直到重新解析。 需要多个事件的时间表，包括“schedule=[a, b]”、资产 AND 表达式和 使用“RollupMapper”分区时间表，默认继续批处理。显式设置 这些时间表的“batch_asset_events=False”会引发时间表验证错误。

自定义图形颜色通过 ui_color and ui_fgcolor 返回 (#68760)

操作员和任务组上的“ui_color`` and ``ui_fgcolor”属性为图形视图着色 再次——节点从“ui_color`` and the operator label from ``ui_fgcolor”填充，就像他们在 Airflow 2。自从 Airflow 3.0 以来，它们就被默默地忽略了。 该值可以是原始颜色（十六进制代码，如“#e8b7e4”或 CSS 名称）或 Chakra 主题标记 — 调色板标记，例如“blue.500`` or a semantic token such as ``brand.solid”，适应 浅色和深色模式（包括通过自定义 UI 主题添加的令牌）；令牌通过a解析 主题控制的 CSS 变量。节点边界持续反映任务实例运行状态；的 自定义颜色仅应用于填充和标签。

validate_key now raises ValueError instead of AirflowException (#68890)

airflow.utils.helpers.validate_key utility now raises ValueError 而不是 AirflowException 当提供无效密钥时（例如无效格式或无效密钥） 违反长度限制）。

已弃用的 Dataset alias has been removed from the airflow 模块 (#70154)

请改用“Asset`` from ``airflow.sdk”。

未绑定到 Dag 的审核日志行现在需要 AUDIT_LOGS_ALL 视图 (#70759)

审计日志中“dag_id`` is ``NULL”记录不与 Dag 绑定的操作的行， 例如连接、变量和池的更改。它们被返回给任何可以阅读的调用者 根本没有事件日志，因为没有每个 Dag 密钥来授权它们，并且两个读取路径都失败了 回到 Dag 级别的审计日志检查。 他们现在以同样的方式在专用的“AccessView.AUDIT_LOGS_ALL”上进行门控 对于没有注册 Dag 的文件，“AccessView.IMPORT_ERRORS_ALL”会出现导入错误。行绑定 Dag 保留其现有的每 Dag 检查。

  • “GET /eventLogs`` no longer returns rows with a ``NULL`` ``dag_id”给没有新版本的呼叫者 视图，并将它们从“total_entries`` and pagination. ``GET /eventLogs/{event_log_id}”中排除 返回“403`` for such a row. An id matching no row still returns ``404”。
  • 使用简单的身份验证管理器，视图仅授予“ADMIN”角色。具有 FAB 授权 manager 它映射到一个新的“All Audit Logs`` resource, which ships in the ``Admin”角色；定制 需要读取这些行的角色必须显式授予“All Audit Logs.can_read”。
  • 无法映射请求的“AccessView”的身份验证管理器现在拒绝该视图并发出 UserWarning instead of raising KeyError。这会影响比核心更老的授权管理器 他们运行的对象是先前因服务器错误而导致请求失败的对象。

团队名称现在必须小写，并且不能包含两个连续的下划线 (#70886)

airflow teams create and airflow teams sync 现在仅接受匹配的名称 (?!.*__)[a-z0-9_-]{3,50} — 小写字母、数字、连字符和单下划线。上层 之前接受了大小写字母和“__”。 团队名称嵌入在“AIRFLOW_CONN__<TEAM>___<ID>”环境变量命名空间中， 保存团队范围内的秘密，后端在构建该变量时将名称大写。 因此，data_eng and Data_Eng 解析了它们之间的单个命名空间，以及一个名称 包含“___”的内容无法与分隔符分开。 airflow db migrate 小写每个存储的团队名称，移动该团队的 Dag 包， 连接、变量、池和触发器。两个仅大小写不同的存储名称 折叠成一排并默默地合并两个团队，因此在任何此类情况下迁移都会拒绝开始 对存在——首先重命名除一个之外的所有对象。由于其他原因而保持无效的名称，例如 包含“__``, are migrated as they are; they keep working, but ``airflow teams sync”退出 非零，直到它们被重命名。

更改待处理资产事件触发 Dag 运行的方式 (#70972)

现在，使用“airflow db clean”删除资产事件记录也会删除任何资产事件 仍在等待下游 Dag。这主要影响等待多资产条件的 Dags， 在满足条件之前可以清除待处理事件。立即删除资产事件 一致意味着不会触发运行；以前这样的待处理触发器仍然可以触发 事件被清除后。 相关地，在该资产上安排时排队等待 Dag 的资产事件仍然 用于触发运行，并出现在运行的触发事件中，即使资产较晚 从 Dag 的日程中删除。此前，它们都被默默地丢弃了。

回调现在在运行之前兑换一次性令牌 (#71192)

工作人员现在使用 API 服务器兑换回调的一次性令牌（“PATCH /execution/callbacks/{callback_id}/run“) 在导入并运行回调之前。兑换 token 将回调从排队状态移至运行状态，并将其交换为短期执行范围 令牌。在此更改之前，回调运行时没有工作人员进行任何经过身份验证的调用，因此 为其铸造的令牌从未被检查过。 由于令牌是一次性的，因此重新传递或重放的消息会到达回调，即 已经运行或完成的被拒绝而不是再次运行。 3.4 上的工作人员需要 API 服务器 服务于该端点；与较旧的 API 服务器通信的工作人员协商 API 版本并 表现得好像端点不存在一样。

清除任务现在默认会丢弃其任务状态存储条目 (#72100)

现在清除任务实例会丢弃其“task_state_store”条目，因此下一次尝试将开始 从头开始，而不是从检查点恢复或重新连接到外部作业 由已清除的尝试记录。重试不受影响并保持任务状态与以前一样。这适用 清除单个任务实例（清除端点/对话框和“airflowctl tasks``/”dags 清晰）；清除整个 Dag 运行仍然保持任务状态（在 `#72929 <https://github.com/apache/airflow/issues/72929>`_）。为了保留旧的行为，通过 keep_task_state=True“（或在清晰的对话框中勾选“保持任务状态”；每个浏览器的默认值是 可在“设置”>“清除”下找到）。请注意，任务实例清除现在也会删除 该任务实例的“task_state_store”行。

[core] execute_tasks_new_python_interpreter 现在适用于 Airflow 3 任务进程 (#72164)

在 Airflow 3 上，该选项对任务执行没有影响（只有 Edge 工作线程读取它）。当设置为 True, the task supervisor now exec 是分叉任务后的一个新解释器 进程，这可以防止分叉继承由主管线程（永久的）持有的锁 挂在任务的第一个 TLS 调用处）。保留 Airflow 2 中“True”选项的部署 这种行为及其每任务口译员的启动成本，在升级时无需采取进一步行动；设置 将其设置为“False”以保持裸叉。任务流程读取全局值，因此是团队范围的 Edge 单独设置不会将其打开。具有选项“True”的边缘工作人员已经开始了新的工作 主管的口译员，现在将开始另一名口译员来完成该任务。 Dag 处理器 触发器和任务回调（回调管理程序从一个不能被执行的闭包中运行） 以执行子命名）不受影响并保持裸叉。

通过耗尽活动运行来优雅地暂停 Dags (#72407、#73225、#73055、#73763)

Airflow 现在支持 Dags 的“draining”调度状态。排空会阻止调度程序 创建新的计划或资产触发的 Dag 运行，同时允许已排队并运行的 Dag 运行继续。仍允许显式触发的运行。 在出色的 Dag 运行完成后，Dag 自动转换为“paused”。用户可以 取消排空以将 Dag 返回到“active”。 暂停 Dag 上的手动运行、回填和资产实现可能会耗尽 Dag，而不是 取消暂停：在 UI 中选择 Drain，或在 REST API 请求中设置 drain_dag。排水 让 Dag 的未完成运行开始或恢复（除了那些由暂停回填保持的运行），不会创建 计划的运行，并在所有未完成的运行完成后再次暂停 Dag。暂停的回填仍然存在 暂停，必须恢复运行才能完成并完成排水。 UI、REST API 和 airflowctl expose the active, draining, and paused 调度 状态，并且 Dags 列表可以同时暂停、耗尽或取消暂停多个选定的 Dags。现有 is_paused API usage remains supported; use scheduling_state时必须处于排水状态 明确选择或报告。

重新解析没有注册 Dag 的文件现在需要 REPARSE_ALL 视图 (#72896)

在定义任何 Dag 之前导入失败的文件没有用于授权重新解析的每个 Dag 密钥 反对，所以“PUT /parseDagFile/{file_token}`` previously returned ``404”。重新解析这样一个 文件现在被控制在专用的“AccessView.REPARSE_ALL”上——一个它自己的、独特的写入操作 从查看导入错误的权限 - Dag 导入错误模式获得重新分析操作 对于这些文件。

  • “PUT /parseDagFile/{file_token}”适用于没有注册 Dag 授权的文件 REPARSE_ALL and returns 403 when the caller lacks it, instead of 404。一个文件有 已注册的 Dag 保留其现有的每 Dag“can_edit”检查。
  • 使用简单的身份验证管理器，视图仅授予“ADMIN”角色。具有 FAB 授权 它映射到新的“All Reparses`` resource, which ships in the ``Admin”角色；定制 需要重新解析此类文件的角色必须显式授予“All Reparses.can_read”。

删除了 --file-io option from the airflow info 命令 (#73054)

“--file-io”将报告上传到 file.io 并打印了可共享的链接。 file.io 不再 接受匿名上传，因此该选项无法成功；它也以未处理的回溯结束 而不是报告失败。 重定向输出： 气流信息—anonymize > airflow-info.txt 请注意，当 共享报告：简单的“airflow info”打印连接字符串，包括密码， 明文。

[workers] execution_api_retries 不再重试任务心跳 (#73244)

心跳有两个重叠的重试机制：任务 SDK API client 重试每个请求， 包括心跳，supervisor单独统计连续心跳失败的次数 [workers] max_failed_heartbeats。 client 重试还产生了不需要的副作用： 在后退时阻塞管理程序的监控循环，因此在 API 服务器中断期间 主管将延迟转发任务日志和/或注意到任务子流程已 退出。 心跳重试现在仅由“max_failed_heartbeats”控制，其默认值已 从“3`` to ``30”进行调整，以保持对无法访问的 API 服务器大致相同的容忍度 两种机制结合起来就给出了之前的结果。 如果您已明确设置“[workers] max_failed_heartbeats”，您可能希望重新考虑您的值 已经选择了。现在是整个重试预算：使用默认的[workers] min_heartbeat_interval of 5 seconds, the worker tolerates roughly 5 * max_failed_heartbeats 终止正在运行的任务之前 API 不可用的秒数。您可能应该保留 结果值低于任何配置的“[scheduler] task_instance_heartbeat_timeout”（默认 300 秒）。

在解析时验证截止日期警报回调；已弃用数字间隔 (#73294)

DeadlineAlert now refuses a callback that is not exactly AsyncCallback 或 SyncCallback，因此子类在解析 Dag 时失败，而不是在调度程序读取时失败 它回来了。 调度程序通过确切的类名解码存储的回调，因此没有由 Dag 命名的类 作者在那里被导入或实例化，这意味着可以编写一个子类，然后永远不会 阅读。 传递一个数字“interval`` is deprecated and now emits ``RemovedInAirflow4Warning”。它 仍然被接受并被视为秒数，但支持的类型是“timedelta”和 VariableInterval. A timedelta subclass such as pendulum.duration(...) 被接受并且 标准化为普通的“timedelta”，之前它通过了验证，然后在验证过程中失败了 序列化。 interval=True is refused, because bool is an int 子类并且将 否则视为一秒。

POST /assets/{asset_id}/materialize 端点现在需要 JSON 请求正文 (#73328)

以前，没有正文的请求会被接受，并且资产会使用默认值具体化。 该端点现在需要一个显式的 JSON 主体，与其他变异端点一致： 没有正文的请求会被“422”拒绝，空的 HTML 表单不是有效的输入 不再了。所有主体字段都是可选的，因此空对象（“{}”）是有效的主体。

TaskInstance 尝试次数现在会在下一次尝试开始之前增加 (#73554)

..注意:: 如果您有任何外部系统查看任务日志或 TI 状态以获取重试 TI，则您 将需要了解此更改并更新您的代码。 例如，如果您发出请求“GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id} 期望获取有关的信息 失败的尝试，你现在需要查看GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id}/tries/{try_number - 1}“ 当任务处于 up_for_retry 状态时，try_number 现在标识即将进行的尝试。要检索尝试 失败，请求“/tries/{try_number - 1}”。 UI 显示待处理的尝试并提供链接 前一次尝试的日志。 Airflow 现在分配任务实例的 UUID 并尝试编号一起不变，以便它们保持一致 确定相同的尝试。 之前当任务进入重试冷却期时，它会被赋予一个新的UUID，但继续 尝试编号 N 并具有 UP_FOR_RETRY 状态，直到该时间段结束（此时尝试 将被标记为“失败”并且尝试次数会增加）。相反，失败的尝试立即 标记为 FAILED 状态，并在 UP_FOR_RETRY 状态下创建新的尝试。

弃用 cyclic 任务组依赖项 (#73746)

当每个任务组被视为单个任务组时，其任务组在一个循环中相互依赖的 Dag 单元，现在在解析时发出“TaskGroupCycleDeprecationWarning”，并在中显示 Dag 警告 命名所涉及的任务组和任务的 UI。这些 Dags 仍然解析并运行，因为它们 任务依赖项是 acyclic，但 Airflow 3.5 计划在解析时拒绝它们。 TaskGroup 中任何任务的依赖关系都算作整个组的依赖关系，因此 离开任务组并返回任务组的路径是一个循环。例如，“a >> bridge >> b”， 在其外部加上a and b in the same TaskGroup and bridge，使组依赖于 还设置了“bridge`` and ``bridge`` depend on the group, even if ``a >> b”。

  • 在任务组之间或任务组之外移动任务，以便每个组都依赖于同一组中的其他组 仅方向。在上面的示例中，将“bridge`` into the group, or move ``b”移出其中。
  • 要在 CI 中捕获这些 Dags，请使用“-W”运行 Dag 测试 错误::airflow.sdk.exceptions.TaskGroupCycleDeprecationWarning。该检查在 Dag 出现时运行 添加到“`DagBag, so only tests that load your Dags into a “DagBag`”并断言有 没有导入错误捕获它们；仅导入 Dag 文件的测试则不会。 请参阅 Dags 文档中的“Cyclic 任务组依赖项”。

任务 SDK API cli trust 系统证书存储而不是 certifi (#73116)

启用“[api] client_use_public_certs”（默认）后，任务 SDK client 会与 执行 API 现在通过 truststore trusts 操作系统的证书存储，而不是 certifi CA bundle. CAs from [api] ssl_ca_file and [api] ssl_cert 仍然是 trusted 除了系统存储之外，“certifi”不再是任务 SDK 依赖项。 Workers 必须在系统存储中安装他们所依赖的公共 CA（例如， 基于 Debian 的映像上的“ca-certificates”包）。在 macOS 和 Windows 上，证书验证 委托给操作系统，操作系统可以拒绝 OpenSSL 接受的服务器证书， 例如没有“serverAuth”扩展密钥使用的私有 CA 证书。

年长的工作人员无法再恢复“next_kwargs”持有自定义类的延迟任务 (#73577)

当延迟任务在具有旧任务 SDK 的工作线程上恢复时，API 服务器不再从存储的“next_kwargs`` to convert them to the legacy format. Built-in value types, assets and asset aliases (including asset access control) are still converted, without constructing them. A deferred task whose ``next_kwargs”中重建任意类，任何其他类现在在此类工作线程上失败，并出现命名类型错误并要求升级任务 SDK，而不是在无法解码的有效负载上崩溃。 **该怎么做：**如果您运行具有“apache-airflow-task-sdk`` 1.1.x or older and your deferrable operators or triggers pass instances of custom classes in ``next_kwargs`` (for example via ``self.defer(..., kwargs=...)`` or in the trigger event payload), upgrade the Task SDK on those workers to 1.2.0 or later. Newer workers receive ``next_kwargs`` unchanged and are not affected. Until all workers are upgraded, pass only built-in values, assets and asset aliases in ``next_kwargs”任务的工作人员，这些任务可能会在较旧的工作人员上恢复。

Deadline Alert 回调 kwargs 在回调运行时解码 (#74830)

调度程序不再解码截止日期警报回调的关键字参数。他们 保持其序列化形式并在回调运行时进行解码：由触发器触发 AsyncCallback, and by the callback runner on the worker for a SyncCallback。 运行“SyncCallback”截止日期警报的工作人员需要包含此更改的任务 SDK，因此 一起升级“apache-airflow`` and ``apache-airflow-task-sdk”工人。一名工人与 升级后的“apache-airflow”和较旧的任务 SDK 会导致此类回调失败并出现错误 运行它们。升级之前创建的回调将像以前一样运行。

自定义 XCom 后端重写 serialize_value must implement store_value 以支持任务循环 (#74858)

循环内任务的每次迭代都是其自己的任务实例，但是“serialize_value” 对于所有 它们，因此根据这些构建其存储位置的后端使得每次迭代都是 XCom 读回最后一次迭代的值。后端应覆盖“store_value”并且 load_value instead, and build the storage location with XComCoordinate.build_path, 这是每个任务实例唯一的，或者当写入无法知道任务实例时每次写入都是唯一的。 当配置的 XCom 后端仍然存储值时，使用循环的 Dag 在启动时失败 通过“serialize_value”，即使它已经写入了唯一的位置。这包括 XComObjectStorageBackend from apache-airflow-providers-common-io 1.10.1 及更早版本； 在使用任务循环之前升级提供程序。 自定义任务状态存储后端同样需要包括 存储键中的“scope.region_id”支持循环内的映射任务 并通过清除重新生成循环迭代。
