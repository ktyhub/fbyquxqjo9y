airflow 3.2.0

小版本 发布时间2026年4月7日 来源apache/airflow 英文原文

airflow 3.2.0

这个项目是干啥的：一个用代码编排定时任务的调度平台，把数据处理流程串成流水线，按时运行、失败可重试，适合要管理大量周期性作业的工程师。

变更架构图

亮点

  • 按分区感知的资产调度 — Airflow 现在可以基于特定资产分区触发下游 DAG，而不必在资产整体发生任意更新时触发。对于按日期分区的 S3 路径、Hive 表或 BigQuery 表，这能避免不必要的下游运行，只处理发生变化的切片。对数据感知型流水线而言，这是最值得升级的理由。
  • 实验性的隔离与回调特性 — Multi-Team Deployments 在单个 Airflow 实例内提供相互隔离的 DAG、连接、变量、资源池和 executor。Deadline Alerts 新增 executor 运行时的 SyncCallback、可选的 executor 定向，以及每个 DAG 支持多条告警。两项特性均为实验性，可能发生变化；尤其注意 SyncCallback 目前无法使用存储在 Airflow 元数据数据库中的 Connection。
  • UI 扩展性提升，但移除一个端点 — 网格虚拟化（#60241）降低了 DOM 和内存开销，所有任务视图现在统一使用流式端点 GET /ui/grid/ti_summaries/{dag_id}?run_ids=...，而不再每次运行发一次请求。破坏性变更： GET /ui/grid/ti_summaries/{dag_id}/{run_id} 已被移除；自定义调用方必须适配 application/x-ndjson 响应，每行一个 GridTISummaries 对象。UI 中的 XCom 编辑、HITL 审批历史和更完善的甘特图视图也减轻了运维负担。
  • Task SDK 迁移 — 面向任务的异常现在来自 airflow.sdk.exceptions，序列化相关代码已迁至 airflow.sdk.serde 和 airflow.sdk.serde.serializers.*。旧的 airflow.exceptions 和 airflow.serialization.serde 导入仍可用，但会触发 DeprecatedImportWarning；serde 兼容路径将在 Airflow 4 中移除。请尽快更新自定义 operator、sensor、扩展和序列化器；同时调整校验代码，因为无效的 sensor 参数现在抛出 ValueError 而非 AirflowException。
  • 其他兼容性破坏与升级结论 — REST API 现在要求 retry_exponential_backoff 为数值并拒绝布尔值，不过 Python DAG 仍保留自动布尔转换；建议改用 2.0 和 0。TaskInstance.run()、render_templates()、get_template_context() 以及 PriorityWeightStrategy.serialize()/deserialize() 已被移除。DagBag/FileLoadStat 路径不再使用以斜杠开头的相对路径——请改用 pathlib.Path；airflow connections list --conn-id 由 airflow connections get 取代。这是一个值得升级的大版本：分区感知调度、大型 DAG 或多团队试验都受益明显；不受影响的用户可以暂缓，但应在 Airflow 4 之前规划好 SDK 与 API 的迁移。

重大变化

资产分割

Airflow 3.2.0 的主要功能是资产分区——数据感知的重大演变 调度。您现在可以安排下游，而不是根据整个资产触发 Dags 基于特定数据分区的处理。仅相关数据切片触发下游 工作，使管道编排更加高效和精确。 这在使用分区数据湖时很重要 - 日期分区的 S3 路径、Hive 表 分区、BigQuery 表分区或任何其他分区数据存储。以前，任何更新 无论哪个分区发生变化，资产都会触发所有下游 Dags。现在只剩下权利了 工作会在正确的时间触发。 详细使用说明请参见:doc:/authoring-and-scheduling/assets。

多团队部署

Airflow 3.2 引入了多团队支持，允许组织在单个 Airflow 部署中运行多个独立的团队。 每个团队都可以拥有自己的 Dags、连接、变量、池和执行器，从而实现真正的资源和权限隔离，而无需每个团队使用单独的 Airflow 实例。 这对于通过共享基础设施为多个数据工程或数据科学团队提供服务，同时在团队的资源和访问之间保持严格界限的平台团队来说尤其有价值。 详细使用说明请参见:doc:/core-concepts/multi-team。 ..警告:: 多团队部署在 3.2.0 中处于实验阶段，并且可能会在未来版本中发生变化 用户反馈。

对截止日期警报的同步回调支持

除了现有的之外，截止日期警报现在还支持通过“SyncCallback”进行同步回调 异步“AsyncCallback”。同步回调由执行器执行（而不是 触发器），并且可以选择通过“executor”参数定位特定的执行器。 Dag 还可以通过将列表传递给“deadline”参数来定义多个截止日期警报， 每个警报都可以使用任一回调类型。 ..警告:: 截止日期警报在 3.2.0 中处于实验阶段，并且可能在未来版本中发生变化 用户反馈。同步截止日期回调（SyncCallback）目前不支持 支持存储在 Airflow 元数据数据库中的连接。 详细使用说明请参见：doc:/howto/deadline-alerts。

UI 增强和性能

  • 网格视图虚拟化： 网格视图现在使用虚拟化——仅将可见行渲染到 DOM。这极大地提高了查看具有大量任务运行的 Dags 时的性能，减少了复杂 Dags 的渲染时间和内存使用量。 (#60241)
  • 用户界面中的 XCom 管理： 您现在可以直接从 Airflow UI 添加、编辑和删除 XCom 值。这使得在开发和日常操作过程中调试和管理 XCom 状态变得更加容易，而无需 CLI 命令。 (#58921)
  • HITL 详细历史记录： 人在环审批界面现在包括完整的历史记录视图，让操作员和审阅者可以查看任何任务的批准和拒绝的完整审计跟踪。 （＃56760，＃55952）
  • 甘特图改进：
    • 显示所有任务尝试：甘特图现在显示每次尝试，而不仅仅是最新的尝试
  • 甘特图中的任务显示名称：显示 task_display_name 以提高可读性 (#61438)
    • 甘特图中的 ISO 日期：跨浏览器一致的日期格式 (#61250)
    • 修复了空日期时间崩溃：甘特图不再在具有空日期时间字段的任务上崩溃

调度程序 CLI 的新“--only-idle”标志

“airflow scheduler`` command has a new ``--only-idle”标志仅在 调度程序空闲。这有助于用户运行调度程序一次并处理所有触发的 Dags 和 排队的任务。它需要并补充“--num-runs”标志，以便可以设置一个小值 而不是猜测调度程序需要多少次迭代。

将每次运行的 TI 摘要请求替换为单个 NDJSON 流

网格、图表、甘特图和任务详细信息视图现在获取任务实例 通过单个流式 HTTP 请求进行摘要 (GET /ui/grid/ti_summaries/{dag_id}?run_ids=...) 而不是一个请求 每次运行。 每次运行任务完成后，服务器会发出一条 JSON 行 实例已准备就绪，因此列会逐渐出现，而不是一次性全部出现。 改变了什么：

  • GET /ui/grid/ti_summaries/{dag_id}?run_ids=... 现在是唯一的端点 对于 TI 摘要，返回一个“application/x-ndjson”流，其中每个 line 是一次运行的序列化“GridTISummaries”对象。
  • 旧的单次运行端点“GET /ui/grid/ti_summaries/{dag_id}/{run_id}” 已被删除。
  • 序列化的 Dag 结构加载一次并在所有运行中共享 共享相同的“dag_version_id”，避免多余的反序列化。
  • 所有 UI 视图（网格、图表、甘特图、任务实例、映射任务实例、组 任务实例）使用流端点，传递一个或多个“run_ids”。

所有 API 服务器输出的结构化 JSON 日志记录

新的“json_logs`` option under the ``[logging]”部分使Airflow 将其所有输出生成为换行符分隔的 JSON （结构化日志）而不是 人类可读的格式化日志。这涵盖了 API 服务器（gunicorn/uvicorn）， 包括访问日志、警告和未处理的异常。 并非所有组件都支持这一点 - 特别是“airflow celery worker”，但是 启用“json_logs”时任何非 JSON 输出都将被视为错误。 (#63365)

删除旧版 OTel Trace 元类和共享跟踪器包装器

位于airflow.traces中的接口和函数是 内部代码提供了管理跨度的标准方法 内部气流代码。它们并不是面向用户的代码 并且从未被记录下来。不再需要它们，所以我们 在 3.2 中删除它们。 (#63452)

将任务级异常导入移动到任务 SDK 中

Airflow 现在从以下来源获取面向任务的异常（“AirflowSkipException``, ``TaskDeferred”等） airflow.sdk.exceptions. airflow.exceptions 仍然暴露相同的异常，但它们是 发出“DeprecatedImportWarning”的代理，以便 Dag 作者可以在删除垫片之前进行迁移。 改变了什么：

  • 运行时代码现在一致引发任务级异常的 SDK 版本。
  • 任务 SDK 重新定义了这些类，因此工作人员在运行时不再依赖“airflow-core”。
  • airflow.providers.common.compat.sdk 集中提供程序的兼容性导入。 行为改变：
  • 验证用户输入的传感器和其他助手现在会引发“ValueError”（而不是 AirflowException) when poke_interval/ timeout 参数无效。
  • 从“airflow.exceptions”导入已弃用的异常名称会记录一条警告，引导用户 SDK 导入路径。 “airflow.sdk.exceptions”现在提供的例外：
  • AirflowException and AirflowNotFoundException
  • AirflowRescheduleException and AirflowSensorTimeout
  • AirflowSkipException, AirflowFailException, AirflowTaskTimeout, AirflowTaskTerminated
  • TaskDeferred, TaskDeferralTimeout, TaskDeferralError
  • DagRunTriggerException and DownstreamTasksSkipped
  • AirflowDagCycleException and AirflowInactiveAssetInInletOrOutletException
  • ParamValidationError, DuplicateTaskIdFound, TaskAlreadyInTaskGroup, TaskNotFound, XComNotFound
  • AirflowOptionalProviderFeatureException 向后兼容性：
  • 不过，仍然从“airflow.exceptions”导入的现有 Dags/操作符继续工作 他们记录警告。
  • 提供商可以依靠“airflow.providers.common.compat.sdk”来保持一个有效的导入路径 跨受支持的 Airflow 版本。 迁移：
  • 更新自定义运算符、传感器和扩展以从中导入异常类 airflow.sdk.exceptions（或来自提供商兼容垫片）。
  • 调整自定义验证代码以期望“ValueError”对于无效的传感器参数（如果它） 之前捕获过“AirflowException”。

支持 retry_exponential_backoff 参数的数字乘数值

retry_exponential_backoff parameter now accepts numeric values to specify custom exponential backoff multipliers for task retries. Previously, this parameter only accepted boolean values (True or False), with True using a hardcoded multiplier of 2.0。 新行为：

  • 数值（例如“2.0``, ``3.5”）直接指定指数退避乘数
  • retry_exponential_backoff=2.0 将每次重试尝试之间的延迟加倍
  • retry_exponential_backoff=0 or False disables exponential backoff (uses fixed retry_delay) 向后兼容性： 使用布尔值的现有 Dags 继续工作：
  • retry_exponential_backoff=True → converted to 2.0（保持原始行为）
  • retry_exponential_backoff=False → converted to 0.0（无指数退避） API 变化： “retry_exponential_backoff`` has changed from ``type: boolean`` to ``type: number”的 REST API 架构。 API clients 必须使用数值（布尔值将被拒绝）。 迁移： 虽然 Python Dags 中的布尔值会自动转换以实现向后兼容性，但为了清晰起见，我们建议更新为显式数值：
  • 更改“retry_exponential_backoff=True`` → ``retry_exponential_backoff=2.0”
  • 更改“retry_exponential_backoff=False`` → ``retry_exponential_backoff=0”

将序列化/反序列化 (serde) 逻辑移至任务 SDK 中

Airflow 现在从“airflow.sdk.serde”获取 serde 逻辑，而不是 airflow.serialization.serde. Serializer modules have moved from airflow.serialization.serializers.* 至“airflow.sdk.serde.serializers.*``. The old import paths still work but emit ``DeprecatedImportWarning” 来引导迁移。 Airflow 4 中将删除向后兼容层。 改变了什么：

  • 序列化/反序列化代码从“airflow-core`` to ``task-sdk”包中移出
  • 串行器模块从“airflow.serialization.serializers.*`` to ``airflow.sdk.serde.serializers.*”移出
  • 新的序列化器应添加到“airflow.sdk.serde.serializers.*”命名空间 代码接口变化：
  • 从“airflow.sdk.serde.serializers.*`` instead of ``airflow.serialization.serializers.*”导入序列化器
  • 从“airflow.sdk.serde`` instead of ``airflow.serialization.serde”导入序列化函数 向后兼容性：
  • 从“airflow.serialization.serializers.*”导入的现有序列化程序继续使用弃用警告
  • 所有现有序列化器（内置、日期时间、pandas、numpy 等）均可在新位置使用 迁移：
  • 对于现有的自定义序列化程序：更新导入以使用“airflow.sdk.serde.serializers.*”
  • 对于新的序列化器：将它们添加到airflow.sdk.serde.serializers.* namespace (e.g., create task-sdk/src/airflow/sdk/serde/serializers/your_serializer.py）

从 PriorityWeightStrategy 中删除的方法

在（实验）类“PriorityWeightStrategy``, functions ``serialize()”上 和“deserialize()”从未在任何地方使用过，并且已被删除。他们 不应在用户代码中依赖。 (#59780)

从 TaskInstance 中删除的方法

在类“TaskInstance``, functions ``run()``, ``render_templates()”上， get_template_context()，以及与其相关的私人成员已被 已删除。自 3.0 起，该类已被视为内部类，并且不应被视为内部类 在用户代码中依赖。 （＃59780，＃59835）

修改DagBag返回的信息

新行为：

  • DagBag now uses Path.relative_to 实现一致的跨平台行为。
  • FileLoadStat now has two additional nullable fields: bundle_path and bundle_name。 向后兼容性： FileLoadStat will no longer produce paths beginning with / 的意思是“相对于 dags 文件夹”。 对于依赖此行为执行基于字符串的路径操作的任何自定义代码来说，这是一个重大更改。 建议用户更新此类代码以使用“pathlib.Path”。 (#59785)

删除--conn-id option from airflow connections list

多余的“--conn-id`` option has been removed from the ``airflow connections list”CLI 命令。 请改用“airflow connections get”。 (#59855)

添加操作员级别 render_template_as_native_obj 覆盖

操作员现在可以覆盖 Dag 级别“render_template_as_native_obj”设置， 启用对模板是否呈现为本机 Python 的细粒度控制 基于每个任务的类型或字符串。设置“render_template_as_native_obj=True”或 False on any operator to override the Dag setting, or leave as None（默认） 从达格继承。

添加对 API 服务器的 Gunicorn 支持，具有零停机工作线程 recycling

API 服务器现在支持 Gunicorn 作为滚动工作重新启动的替代服务器 以防止长时间运行的进程中的内存积累。 主要优点：

  • 滚动工作人员重新启动：新工作人员在老工作人员之前产生并通过健康检查 被杀死，确保工人 recycling 期间零停机。
  • 内存共享：Gunicorn 使用预加载 + fork，因此工作人员通过以下方式共享内存 写时复制。与 uvicorn 相比，这显着减少了总内存使用量 多进程模式，每个工作人员独立加载所有内容。
  • 正确的 FIFO 信号处理：Gunicorn 的 SIGTTOU 杀死最旧的工作进程 (FIFO)， 不是最新的 (LIFO)，这对于滚动重新启动是正确的。 配置： .. 代码块:: ini [api]

    使用gunicorn代替uvicorn

    服务器类型=gunicorn

    启用滚动工作线程每 12 小时重新启动一次

    工人刷新间隔= 43200

    一次重启一个worker

    工人刷新批量大小 = 1 或者通过环境变量： .. 代码块:: bash 导出 AIRFLOW__API__SERVER_TYPE=gunicorn 导出 AIRFLOW__API__WORKER_REFRESH_INTERVAL=43200 要求： 安装gunicorn额外：pip install 'apache-airflow-core[gunicorn]' 关于 uvicorn 的注意事项（默认）： 默认的 uvicorn 模式不支持滚动工作重启，因为： 1.当workers=1时，没有master进程可以发送信号
  1. uvicorn 的 SIGTTOU 杀死了最新的工作进程（LIFO），破坏了滚动重启的目的
  2. 每个uvicorn工人独立加载所有内容，不共享内存 如果您需要worker recycling 或内存高效的多worker 部署，请使用gunicorn。 (#60921)

改进了具有许多映射任务的 Dags 的渲染任务实例字段清理性能（大约快 42 倍）

配置“max_num_rendered_ti_fields_per_task`` is renamed to ``num_dag_runs_to_retain_rendered_fields” （旧名称仍然适用于弃用警告）。 保留现在基于 N 个最近的 dag 运行，而不是 N 个最近的任务执行， 这可能会导致为条件/稀疏任务保留的记录较少。 (#60951)

AuthManager 回填权限现在由“requires_access_dag`` on the ``DagAccessEntity.Run”处理

is_authorized_backfill of the BaseAuthManager 接口已被删除。 Core 将不再调用此方法及其 提供者对应的实现将被标记为已弃用。 现在使用现有的“DagAccessEntity.Run”权限检查回填操作的权限 requires_access_dag 装饰器。换句话说，如果用户有运行 Dag 的权限，他们就可以对其执行回填操作。 请更新您的安全策略，以确保需要执行回填操作的用户拥有适当的“DagAccessEntity.Run”权限。 （用户 拥有 Backfill 权限但没有 DagRun 权限的用户将无法在没有任何更新的情况下执行回填操作）

添加了 Python 3.14 支持

Airflow 3.2.0 增加了对 Python 3.14 的支持。 (#63787)

通过消除任务启动时的“SerializedDAG”负载来减少 API 服务器内存

API 服务器在启动任务时不再加载完整的“SerializedDAG”， 显着减少内存使用。 (#60803)

从容器镜像中删除 MySQL client

MySQL client 支持已从官方 Airflow 容器映像中删除。 MySQL用户 基于官方映像构建必须自行安装 client。 (#57146)

在 PythonOperator 中添加对异步可调用对象的支持

PythonOperator parameter python_callable 现在也支持 Airflow 3.2 中的异步可调用， 允许用户运行 async def 函数，而无需手动管理事件循环。 (#60268)

使 @continuous 时间表的 start_date 为可选

“schedule="@continuous"`` parameter now works without requiring a ``start_date”以及具有此计划的任何 Dags 将在未暂停时立即开始运行。 (#61405)

新功能

  • 通过“PYTHON_LTO”构建参数使 Python LTO 可配置来添加 FIPS 支持 (#58337)
  • 通过新的“--queues`` CLI option for the ``trigger”命令添加对基于任务队列的触发器分配到特定触发器主机的支持 (#59239)
  • 添加 --show-values and --hide-sensitive flags to CLI connections list and variables list 以默认隐藏敏感值 (#62344)
  • 添加对通过“AIRFLOW__SECRETS__BACKEND_KWARG__<KEY>”环境变量设置个人秘密后端 kwargs 的支持 (#63312)
  • 将 only_new 参数添加到 Dag clear 以仅清除新添加的任务实例 (#59764)
  • 添加 log_timestamp_format 配置选项用于自定义组件日志时间戳 (#63321)
  • 添加 --action-on-existing-key option to pools import and connections import CLI 命令 (#62702)
  • 添加回 --use-migration-files flag for airflow db init (#62234)
  • 添加 AllowedKeyMapper 用于资产分区中的分区键验证 (#61931)
  • 添加 ChainMapper 用于链接多个分区映射器 (#64094)
  • 在 Docker 构建中添加 Python 源包的加密签名验证 (#63345)
