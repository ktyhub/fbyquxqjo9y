airflow 3.3.2

修订 发布时间2026年9月17日 来源apache/airflow 英文原文

airflow 3.3.2

这个项目是干啥的：一个用代码编排定时任务的调度平台，把数据处理流程串成流水线，按时运行、失败可重试，适合要管理大量周期性作业的工程师。

变更架构图

亮点

  • 回填授权封堵 ID 枚举泄露（#71113） — 四条回填路由（ GET 以及 pause/unpause/cancel）现在只针对路径中指定的回填做授权，绝不再依据请求体或查询串里的 dag_id。隐藏的 DAG 和未知 ID 都返回相同的 404 "Backfill not found"（此前是可区分的 403），因此跨 DAG 枚举回填 ID 不再可行。按旧详情字符串 Could not find backfill with id {backfill_id} 做匹配的客户端必须更新；GET/POST /backfills 和 dry_run 不变。
  • 显式凭据现在优先于会话 cookie（#72225） — get_user() 文档所述的 bearer → OAuth2 → cookie 优先级此前无法生效，因为 JWTRefreshMiddleware 先缓存了 cookie 主体，导致混合请求以 cookie 用户的身份运行并记录审计。现在同时带 _token 和 Bearer/OAuth2 token 的请求会解析为显式主体，且无效或过期的显式凭据会被拒绝（401/403），而非静默回退到 cookie。纯 cookie 的浏览器会话的令牌刷新保持不变。如果某工具依赖 cookie 胜出，请去掉 header 或 cookie 以明确选择身份。
  • API 全面的更广泛认证加固 — 分区 dag-run 列表不再泄露 DAG 是否存在（#72660），/assets/events 限定为调用方可读的 DAG（#71785），测试已有连接需要读权限（#71428），删除排队的资产事件需要 DAG 编辑权限（#71828），登出会吊销所有提交的凭据而非仅会话 cookie（#72933）。插件作者应注意新文档声明插件的 FastAPI 应用不由 Airflow 认证（#72932），并新增了授权示例（#72942），同时澄清了 is_authorized_hitl_task 钩子的时机（#72807）。
  • 升级时需验证的迁移与元数据修复 — bytea→JSONB 的 XCom 迁移不再破坏本就已解析为 JSON 的值（#72886），PyMySQL 下的 db migrate 能处理删除唯一约束的 schema 迁移（#72613），db clean 现在真正清理 callback 表（#72899）。Variable 处理有多处修正：非字符串 JSON 值（#71526、#72878）、写冲突校验错了团队（#72125）、Variable.set 重写 team_name（#71904），以及导出/导入静默破坏值（#71791）。如果有大量 XCom 历史或自定义 Variable，请在迁移后核验数据。
  • 更清晰的 API 错误语义与 Task SDK 稳定性 — 端点现在返回有意义的 4xx 而非 500：针对缺失 Dag run 的任务启动（#72900）、状态存储路由中的未知任务实例（#71860），以及无效的 clearTaskInstances 请求体（422，#71559）；移除了不可达的创建 Variable 时的 404（#72190）。Execution API 路由保持与旧版 Task SDK 客户端兼容（#71438），partition_key 受 2026-06-30 的 Execution API 版本门槛控制（#72827），Task SDK IPC 短读取不再使子进程崩溃或让 supervisor 挂起（#71609）。
  • 性能收益与新的 SDK 接口 — 数据库/内存压力通过以下改动下降：批量 Variable/Pool 更新中的 N+1 修复（#72160）、上一个任务实例查找（#72944）、单行查找的 LIMIT 1 限制（#72842、#72702），以及有界的调度器反序列化 DAG 缓存（#71821）。新能力包括面向异步任务和 watcher 的异步资产存储访问器（#72851）、通过 SDK 公共接口暴露的 deadline 引用（#71208、#72244、#72738），以及 create_async_metadata_engine 文档（#72804）。

重大变化

回填端点不再透露 Dags 中存在哪些回填 ID

在其路径中命名回填的四个路由 - GET /backfills/{backfill_id} 和 pause, unpause and cancel 路线 - 解决了他们授权的 Dag 每当路径的 id 与任何行都不匹配时，就会从请求中提供的“dag_id”中反对。 调用者无法看到未知的 id 和 Dag 上的回填，因此得到不同的答复， 它枚举 Dags 中的回填 ID。 现在，路径中指定的回填是这些路由唯一授权的内容。 行为改变：

  • 请求对调用者现在无法读取的 Dag 进行回填会返回“404” (Backfill not found) — 未知 id 得到的相同响应 — 而不是 403 returned before. A caller who can read the Dag still gets 403 用于写入 他们不被允许制造。
  • 请求正文中的“backfill_id`` in the path is never authorized against a ``dag_id” 或查询字符串。 GET /backfills, POST /backfills and POST /backfills/dry_run 在他们的路径中指定没有回填并继续授权请求。
  • 现在，所有四个路由都以相同的详细信息“Backfill not found”回答未知 ID。 之前回答的“pause``, ``unpause`` and ``cancel”路线 Could not find backfill with id {backfill_id}. Clients matching on detail 必须更新。 (#71113)

显式凭证现在优先于会话 cookie

get_user() 被写入为首选显式不记名令牌，然后是 OAuth2，然后是 会话 cookie，但只要存在 cookie，就无法达到该优先级。 JWTRefreshMiddleware 运行 首先，单独从“_token”cookie 解析用户并将其标记在 request.state, and get_user() 在查看之前返回该缓存用户 明确的凭证。每个核心-API 路由上的有效订单都是 cookie over bearer。 因此执行的请求携带会话 cookie 和显式凭证， 并被记录在审计日志中，作为 cookie 的主体而不是身份 client 推出。现在，仅当请求不包含任何内容时，才会尊重缓存的用户 明确的凭证。 行为改变：

请求携带 both _token cookie and an Authorization: Bearer 标头

现在被解析为不记名代币的主体，之前它被解析为
饼干的。这同样适用于与 OAuth2 令牌组合的 cookie。

当有效的“`_token`” cookie 伴随它时。之前cookie默默地接管了
并且作为 cookie 的主体，请求成功；失败现在已经很响亮了。

``JWTRefreshMiddleware`` 的令牌刷新行为不变。
