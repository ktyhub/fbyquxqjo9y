compose v5.6.0

小版本 发布时间2026年10月2日 来源docker/compose 英文原文

compose v5.6.0

变更流程图

亮点

  • 部分支持 jobs（仅手动触发） — v5.6.0 引入了 compose-go jobs 和 container-spec 分层（#14093），但只支持手动触发的 jobs；定时 jobs 明确推迟到对应的 Docker Engine 支持合并之后。把它当预览功能：如果你的工作流依赖定时 jobs，暂时不要迁移过去——但现有负载升级不会出问题。

  • Provider services 获得网络继电器并加入镜像阶段 — 新增 get-service-config 请求（#14175），publish-endpoint 现在会部署一个网络继电器（#14193），get-relay-info 告诉 provider 在哪里绑定（#14258），并有专门的 relay 网络（#14275），provider services 现在参与镜像阶段并按需分发镜像（#14252）。这是给 provider 集成用的基础设施；如果你不构建或使用它们，无需配置。相关加固（#14236、#14238、#14264）修复了陈旧继电器和副本迁移的 bug。

  • Service config-hash 被固定，减少无谓重建 — hash 的字节布局现在固定下来，并与 compose-go 的结构体重构解耦（#14215，在合并顺序问题后由 #14253 修复），Compose 也适配了 compose-go v2.16.1 静默提升 x-initialSync 的行为（#14281）。如果你见过 Compose 升级后容器被无谓重建，这点值得升级——这是本版本的稳定性收益。

  • 上线前需在 CI 中验证的行为变化 — dry run 现在改为声明式，commit 不再创建真实镜像（#14150）；down 现在会清理悬空镜像（#14266）；不支持的 compose-file 属性会发出警告（#14196）；watch 在密集编辑时会合并重建（#14202）；双栈端口绑定顺序被保留（#14213），--parallel 现在适用于所有批量引擎调用 fan-out（#14177），并且从 OCI 1.1 回退到 OCI 1.0 的 push 会发出警告（#14146）。没有声明破坏性 API 变更或明确的迁移步骤，但 dry-run 和 down rmi 的改动会改变可观察的副作用。

  • 升级建议 — 如果你依赖 watch、端口发布、--parallel、dry-run 准确性，或 up-monitor 对外部停止/移除容器的检测（#13990），以及需要 config-hash 和日志/重连修复（#14140、#14227），应升级。如果你只用基本的 up/down，没有 provider 或 job 需求，并希望在测试前避免新警告/悬空镜像清理，可以放心跳过——但没有强烈的理由留在 v5.5.1，这是一次真实的功能+修复发布，不是重打标签或纯元数据变更。

发生了什么变化

ℹ️ 此版本增加了对作业的部分支持：目前仅支持手动触发的作业，计划作业尚不可用。一旦相应的Docker引擎支持合并，完整的工作支持将落地。
