compose v5.4.0

变更流程图

亮点

  • Reconciliation 现在把卷和网络纳入计划 — 重头戏：reconcile 引擎在计划中建模了卷重建（#13962）和网络生命周期（#13966），因此 docker compose up 可以收敛这些资源，而不是临时处理。如果你在 reconcile 下跑有状态或多网络栈，这就是升级理由——但要预期资源会按计划创建/重建，所以先在预发环境验证卷/网络配置。

  • 无破坏性变更或迁移步骤 — 本版本没有任何需要重写配置或手动迁移的内容。唯一值得当作变更看待的是上面的 reconcile 计划，它会改变何时重建卷/网络；其他人无需准备即可升级。

  • 消除隐性意外的配置与扩缩容修复 — 零副本服务在 hash 时被保留（#13931），因此缩容到零的服务不再反复变动；配置标志现在真正应用到 --services/--volumes/--networks/--models/--hash（#13979）；被静默忽略的服务选择现在会发出警告（#13950）。如果你用脚本化 Compose 命令或依赖 profiles/scale，值得升级。

  • 构建与仓库正确性 — 构建使用平台 image-manifest digest 而非 attested index（#13949），type:image 卷源和 pre_start hook 镜像与服务镜像一起被固定/解析（#13956、#13937），up 在重新加载模型时遵循 --insecure-registry（#13894），cp dry-run 不再返回 nil Content（#13982）。对多平台构建和私有/不安全仓库很重要。

  • 工具链刷新；多数用户可以跳过 — Go 1.26.5、buildkit v0.32.1、buildx v0.36.0、github.com/docker/cli 29.6.2+incompatible、compose-go v2.14.0、gRPC 1.82.1，加上通过 OIDC 的 CI 发布以及文档迁移到 AGENTS.md/AI_AGENT_DISCLOSURE.md。这些对最终用户是透明的——如果 reconcile、复杂构建/仓库或修复的配置命令不影响你，这是一次安全但紧迫性低的升级。
