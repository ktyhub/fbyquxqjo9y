mflux v.0.19.0

mflux v.0.19.0

这个项目是干啥的：一个在Mac本地跑的AI绘画和修图工具，支持Qwen-Image和FIBO图像编辑，给想在电脑上手动画图的创作者用。

变更架构图

亮点

  • LoRA 语义变更——需要迁移 — 使用 --config-from-metadata 时，--lora/--lora-paths 现在会替换 sidecar 中的适配器，而不是叠加；--lora-paths 不跟任何值会禁用 sidecar LoRA，而单独使用 --lora-scales 则保留它们并修改其强度。依赖叠加的脚本必须显式列出每一个适配器。含有过时绝对路径的 sidecar 不再阻挡有效的替换，缺失、不可读、不兼容或无法烘焙的适配器现在会让运行失败，而不是静默地用错误权重生成或写出一个假的合并检查点。mflux-generate-boogu、mflux-generate-fibo 和 mflux-generate-fibo-edit 中也移除了不支持的 LoRA flag 和 Python API 参数。
  • CLI 兼容性与模型选择 — 所有 mflux CLI 现在要求完整的长选项名：使用 --prom 之类缩写的脚本必须改为 --prompt。内置 --model 名称改为从注册表派生，修复了此前被拒绝的有效名称，如 lens-turbo、krea-2-raw 和 qwen-image；不过 mflux-generate-krea2、mflux-generate-z-image-turbo、mflux-generate-ernie-image 和 mflux-generate-ernie-image-turbo 现在会明确拒绝不兼容的内置模型。本地检查点路径和 HuggingFace repo ID 仍然支持，mflux-save 现在通过注册表选择检查点架构，不再把未知名称静默当作 Flux1。
  • 检查点与配置正确性 — model_path 下保存的 ControlNet 权重现在会被加载，而不再被 hub 权重静默替换，从而保留量化和微调成果，也避免不必要的网络访问。基础模型与 ControlNet 注册表条目共用的 repo ID 现在优先按基础模型处理，推断出的配置保留原有设置，而不是回退到通用默认值。这修复了 Turbo/ControlNet 选择错误、Qwen 编辑 sigma 调度、ERNIE 训练 guidance 以及 supports_kv_cache；不支持的选项现在也会给出警告，mflux-capabilities 可以 JSON、YAML 或 Markdown 形式展示其状态。
  • 生成行为与内存控制 — 十个 CLI 现在根据所选模型推导默认 --steps，大幅减少蒸馏模型的计算量，也避免基础模型步数过少；显式指定的 --steps 不受影响。mflux-upscale-controlnet 终于会透传 --guidance 和 --scheduler，因此设置了这两者的命令会产出不同图像，而未指定 --guidance 时仍沿用原来的 4.0 默认值。Qwen Image Edit 在所有量化级别上的输出都有变化，以消除分块拼接痕迹；现在默认保留输入尺寸，并遵循 --scheduler。恢复的 --vae-tiling 和 --vae-tile-size 提供了独立于 --low-ram 的显式解码内存控制。
  • 依赖与升级结论 — twine 及约 24 个传递依赖不再随 mflux 一起安装；发布上传改用 uv publish，贡献者/CI 的类型检查迁移到 ty==0.0.72。值得升级的人群包括 LoRA 用户、自定义或 ControlNet 检查点用户、Qwen Image Edit 用户，以及碰到被修复的 CLI/模型解析 bug 的人——但请先更新脚本以使用完整 flag 名，并适配 LoRA 破坏性变更。运行未受影响的默认 FLUX.1 工作流、且上述行为都与你无关的用户可以跳过此版本，尽管现在安装更轻量了。

⚠️ 行为改变

  • 元数据 sidecar 不再将其 LoRA 堆叠在命令行的顶部：--config-from-metadata 通过串联恢复 lora_paths/lora_scales，而它恢复的每个其他密钥都遵循显式给定的参数。因此，sidecar 的适配器始终适用，并且没有任何拼写可以替代它们 - --config-from-metadata prior.metadata.json --lora mine.safetensors 0.9 两者都运行。由于两个列表中只有一个通常来自命令行，因此计数不一致，resolve_scales 填充或截断了警告后面的差异：--lora-paths cli.safetensors 使新适配器没有自己的比例，因此 sidecar 转到 sidecar 的适配器，新适配器填充到 1.0，而 --lora-scales 0.8 位于在 sidecar 的比例生成的单适配器 sidecar 上0.8 废弃。 --lora/--lora-paths 现在取代了 sidecar 的适配器，而不是添加它们，没有值的 --lora-paths 没有任何值重新运行，而 --lora-scales 本身保留了 sidecar 的适配器并应用了新的优势。围绕堆叠行为编写的任何脚本都必须命名它想要的每个适配器。 Sidecar 还记录每个适配器的解析绝对路径，因此在机器之间传输的适配器在命令行上不存在的路径上失败 - 即使用户命名自己的副本也会失败，因为死路径无论如何都会被合并并解析；现在可以使用了，当没有替换时，错误会命名它来自的 sidecar 并从两个方向退出。 （＃577，＃618）
  • --guidance 和 --scheduler 现在对 mflux-upscale-controlnet 生效：两者均由解析器注册，然后从未传递给 generate_image，因此您输入的任何内容都会被 Flux1Controlnet 自己的默认值替换。它们现在被转发，这意味着传递任一标志的调用会产生与以前不同的图像。省略 --guidance 仍然会给出升频器始终运行的 4.0，而不是 ui_defaults.GUIDANCE_SCALE (3.5)，因此对于从未设置它的命令没有任何变化。 (#577)
  • 缩写的长选项被拒绝：每个 mflux CLI 现在都需要完整写入标志，因此 --prom 不再代表 --prompt。选项规定是通过扫描 argv 来检测的，它看不到缩写，并且今天明确的缩写在添加新标志时开始在其他地方解析。任何使用缩短标志编写的脚本都需要完整的拼写。 （#499）

✨ 改进

  • 从 mflux 的依赖项中删除了 twine：它的存在只是为了支持发布脚本，但是每个 pip install mflux 都引入了 twine 以及大约 24 个传递包（cryptography、keyring、rich、readme-renderer，…）。发布脚本的令牌模式上传现在外壳为 uv publish - --check-url 复制了 twine 的 skip_existing，令牌通过 UV_PUBLISH_TOKEN 传输，因此它永远不会出现在记录的命令中，并且瞬态重试语义保持不变 - 而 twine check dist/* 在短暂环境中通过 uv tool run twine 生存。 CI 的 trusted 发布路径未受影响（pypa/gh-action-pypi-publish 仍在上传）。还修复了调用uv为python -m uv的脚本，该脚本需要发布环境未安装的uv PyPI包；它现在从 PATH 调用 uv 二进制文件。添加通过 gh 触发发布工作流程的 just release 配方。 （#644）
  • 类型检查从 mypy 迁移到 astral 的 ty（在开发部门、预提交和 CI 中固定 ty==0.0.72）：完整项目检查约为 0.4 秒，而 mypy 则为 2-9 秒。预先存在的违规行为在 [tool.ty.rules] 中被视为忽略规则（带有计数），以便重新启用并逐步修复；新代码必须通过所有非基线规则。添加 just typecheck。 (#597)
  • 更安静的 LoRA 加载：堆叠第二个适配器，为其融合的每一层打印一条 🔀 行 - 文件自己的 🔧 行与其 ✅ Applied to N layers 摘要之间有数百行，其中已经说明了有多少行已落地。这三个每层消息现在是 logger.debug，就像解析规则的跟踪一样。 (#577)
  • 现在默默地删除 CLI 选项发出警告：接受无法接受的选项的命令在解析时会这样说，而不是忽略它，例如引导蒸馏模型上的 --guidance。添加 mflux-capabilities，这是每个图像生成命令的机器可读转储，包含其选项、默认值、类型和每个选项的状态（已执行、忽略、有条件或拒绝），格式为 JSON、YAML 或 Markdown。 （#499）

✨ 改进

  • --vae-tiling 和 --vae-tile-size 标志：恢复对平铺 VAE 解码的面向用户的控制，与 --low-ram 解耦（以前是启用它的唯一方法）。 --vae-tiling 使用默认的 512px 平铺启用平铺解码； --vae-tile-size 256 缩小了图块以进一步减少峰值解码内存，并暗示了 --vae-tiling。两者均由 --low-ram 组成，它们覆盖其隐式平铺默认值。原始的 --vae-tiling/--vae-tiling-split 标志在 Z-Image 重构中被删除（#284）；这恢复了通用 VAETiler 之上的功能。 （＃311，＃407）

🐛 错误修复

  • 加载时忽略保存的 FLUX ControlNet 权重：FluxInitializer.init_controlnet 始终从远程存储库获取 ControlNet 组件，从不咨询它所支持的所有其他组件的 model_path。重新加载由 mflux-save 编写的检查点会默默地将其 ControlNet 权重交换为集线器的权重 - -q 保存返回时该组件未量化，微调被丢弃，而其他完整的本地检查点仍然需要网络。自从 #607 使 mflux-save 真正编写 ControlNet 组件后才可访问。持有 transformer_controlnet/*.safetensors 的 model_path 现在从磁盘加载它，分支 ZImageInitializer 已经有了；内置名称或没有该组件的目录保留集线器路径。 （#610，#642）
  • 由解析为 ControlNet 变体的两个注册表项共享的存储库 ID：多个根与 ControlNet 衍生品共享 model_name，解析器按 priority 顺序返回第一个匹配项 — 这将 Z-Image ControlNet 置于普通 Turbo 之前，因此 --model Tongyi-MAI/Z-Image-Turbo 在每个解析器调用程序中构建了 ControlNet 配置（生成 CLI 和 mflux-save 调度类似）。现在，裸存储库 id 上的关系更喜欢基本条目，其规则是派生变体始终由其自己的密钥或别名来寻址；键和别名的解析与以前完全一样。 （#609，#641）
  • 失败的 LoRA 被报告为已应用：解析适配器和将其折叠到重物之间的每一步都有一条打印警告并继续进行的路径，然后运行宣布 ✅ All LoRA weights applied successfully。无法解析的适配器从列表中删除 - 从未触及的基本模型生成，并且使用多个适配器，将比例转移到错误的适配器上，因为 resolve_scales 将缩短的列表填充回长度。加载时丢失或无法读取的文件打印 ❌ 并返回。模型没有的目标层，或者结果不是线性的目标层，每层打印 ❌ 并将适配器仅应用于模型的一部分。烘焙捕获了所有异常 - 包括基础权重/三角形形状不匹配 - 打印 ⚠️ 并返回未烘焙的层，因此 mflux-save 编写了一个广告为合并的检查点来保存原始基础权重，并且普通生成（默认情况下烘焙）在没有适配器的情况下安静地运行。所有这些现在都在提高。烘焙错误将失败的层命名为 (blocks.0.attn.wq)，而 mflux-save 在写入单个文件之前烘焙每个组件，因此不匹配会中止，而不是在磁盘上留下半个检查点。现在，围绕输入错误或丢失的适配器路径编写的任何脚本都会退出，而不是生成没有它的图像。 (#577)
  • boogu 和 FIBO 接受了 --lora，然后丢弃了它：mflux-generate-boogu、mflux-generate-fibo 和 mflux-generate-fibo-edit 都声明了 LoRA 标志，因此解析器解析了每个适配器 - 当名称是 repo id 时从 HuggingFace 下载它 - 然后初始化器将其扔在地板上，而 mflux-capabilities 报告 "lora": true 并且在任何时候都没有任何警告。 mflux 没有为任一架构实现 LoRA 映射，因此标志消失而不是被忽略：三个 CLI 不再采用它们，匹配 mflux-generate-lens 和 --help，并且功能转储现在与代码一致。 BooguInitializer/FIBOInitializer 和 BooguImage/FIBO/FIBOEdit 构造函数丢失了未使用的 lora_paths/lora_scales/bake_lora 参数，因此 Python API 停止接受它忽略的适配器，以及 mflux-save --model boogu --lora ...，它通过签名过滤掉相同的 kwargs 并写入未修改的检查点，现在退出并显示一条消息。 （＃577，＃615）
  • --model 在 4 个 CLI 上默默地忽略：mflux-generate-krea2、mflux-generate-z-image-turbo、mflux-generate-ernie-image 和 mflux-generate-ernie-image-turbo 接受了 --model，然后构建了硬编码配置，因此 --model dev 默默地运行 Krea-2-Turbo（等），而 mflux-capabilities 报告该选项已被尊重。现在，每个设备都通过共享的 ConfigResolution.resolve_restricted（镜头图案）验证 --model：内置注册表名称必须是 CLI 自己型号的别名，否则会出现错误。本地检查点路径和 HuggingFace 存储库 ID（parse_args 通过 model_path 路由）保持不变：它们保留 CLI 自己的配置和路径中的负载权重，一如既往。验证通过身份而不是 model_name 来比较注册表项，因此 --model z-image-controlnet（其条目共享 Tongyi-MAI/Z-Image-Turbo 存储库 ID）被普通的 Turbo CLI 正确拒绝； lens_generate 的内联检查与 model_name 进行比较，现在使用相同的帮助程序。 （＃577，＃614）
  • mflux-completions 在每次调用时崩溃：mflux-upscale-controlnet 解析器添加了其 LoRA 参数两次，因此每个构建路径在写入单个完成之前都会因 argparse.ArgumentError: conflicting option string: --lora-style（退出 1）而终止。现在，回归测试会为 mflux-completions 知道的每个命令构建解析器。 （＃577，＃613）
  • Qwen 图像编辑调节分辨率：以编辑目标分辨率而非视觉语言调节分辨率（按区域计算约 384 像素）对转换器的图像调节潜伏进行编码，从而防止编辑输出中出现斑驳/平铺的伪影。这会改变每个量化级别的编辑输出，而不仅仅是 -q 4。 (#420)
  • Qwen Image Edit默认尺寸：默认保留第一个输入图像尺寸；显式的 --width/--height 值或比例因子（例如 2x）仍然选择调整大小。 (#420)
  • Qwen 图像编辑 CLI 调度程序：将 --scheduler 转发到 Qwen 编辑管道（之前被忽略）。 (#420)
  • 推断的模型配置丢失了设置：ConfigResolution 逐个字段地重建推断的配置，因此从本地路径或变体名称 (/models/qwen-image-edit-q4) 解析的任何内容都会默默地回退到通用默认值。它现在承载所有字段并仅重写身份。这将恢复 Qwen 编辑 sigma 时间表（0.9/8192/0.02 而不是 1.15/4096/None）、ERNIE 的 LoRA 训练指南以及 flux2-klein-9b-kv 上的 supports_kv_cache。 (#420)
  • 默认 --steps 忽略了 10 个 CLI 上的模型：每个图像 CLI 在 main() 中而不是在解析时选择其模型 - boogu、krea2、lens、z-image、z-image-turbo、flux2、flux2-edit、qwen、qwen-edit、ideogram4 - 针对 --steps 解析None 模型并默默继承了 FLUX.1-dev 的 25。这是 4 步蒸馏（boogu、lens、klein）工作的 6 倍，是 50 步基本模型（z 图像）工作的一半。步骤表现在由规范模型而不是别名作为键控，并通过 AVAILABLE_MODELS 解析，因此 --model klein-4b 和 --model flux2-klein-4b 不再不一致，并且 CLI 通过 add_model_arguments(default_model=...) 向解析器声明自己的模型。 Krea 2 的 DEFAULT_STEPS = 8 后备机制由于解析器始终提供 25 而无法访问，因此消失了。显式 --steps 不受影响。 (#580)
  • --model <name> 对于大多数内置模型都失败：CLI 接受的名称是从 AVAILABLE_MODELS 漂移而来的手动维护列表 (ui_defaults.MODEL_CHOICES)，其中缺少的任何内容都被视为本地检查点目录 — mflux-generate-lens --model lens-turbo 与 Model not found: 'lens-turbo' 一起死在 CLI 运行的唯一模型的规范名称上。 16 个注册表项和大约 40 个别名受到影响，其中包括 krea-2-raw、qwen-image 以及每个 klein-*、boogu-*、zimage* 和 fiboedit* 拼写。接受的名称现在源自注册表，因此新模型或别名不需要第二次编辑。 --base-model 同样放弃了过时的 argparse choices= 列表，该列表拒绝了 qwen-image 等有效名称；现在，它已针对 ConfigResolution 自己的根模型列表进行了验证，并且检查还涵盖了从元数据 sidecar 恢复的 base_model。 (#577)
  • mflux-save 在错误的架构下编写检查点：模型类是由子字符串链选择的，而不是以 else: Flux1 结尾的原始 --model 字符串，因此每个未教授的名称都保存为 FLUX.1 模型 - lens、lens-turbo、klein-4b/9b/9b-kv 和seedvr2* 全部都是 — 而 fibo-edit* 由 txt2img FIBO 类保存，而 z-image-controlnet* 由普通 ZImage 保存。没有提出任何问题；这种不匹配后来作为一个可卸载的检查点出现了。 Dispatch 现在会通过注册表 (ConfigResolution.resolve_key)，因此规范键、别名、HuggingFace 存储库 id 和 --base-model 拼写都会落在拥有这些权重的类上，无法识别的名称会显示一条消息而不是默认为 Flux1，并且两个没有保存路径的模型（Lens、SeedVR2）都会这么说。每次拒绝还列出了 mflux-save 可以写入的模型，而 --help 不显示 - 它列出了无法保存的模型。如果在没有保存类的情况下将模型添加到 AVAILABLE_MODELS，则漂移测试会失败。两个值得注意的结果：--model dev-controlnet-canny/dev-controlnet-upscaler/schnell-controlnet-canny 现在通过 Flux1Controlnet（包括 ControlNet 权重）保存，而不是作为裸 Flux.1，并且 mflux-save --model boogu 不再与 bake_lora 上的 TypeError 一起死亡，这是 BooguImage 不接受的。 （#607）
  • ERNIE 多帧潜伏：pack_latents 将 VAE 的时间轴索引远离，因此除了单帧之外的任何内容都被默默丢弃；现在它失败了。 (#577)
  • ernie-image-turbo 指导合同：模型声明为 supports_guidance: true，而其 CLI 存在于除 1.0 之外的任何指导上，这在 mflux-capabilities 转储中自相矛盾。 (#578)
  • 部分 Krea 2 Turbo 下载已完成：仅当模型不需要子目录时，才根据其下载模式检查缓存的快照。 Krea 2 Turbo 将其变压器保留在存储库根目录中，名称为 turbo.safetensors，因此获取 vae/ 和 text_encoder/ 然后停止的下载报告已完成。 Hugging Face 的修复下载从未运行，并且负载后来在 Missing specified weight files in <snapshot>: ['turbo.safetensors'] 中终止，它读起来像是损坏的缓存而不是中断的传输。现在也在子目录分支中检查根级 *.safetensors 模式。 （＃577，＃593）
  • 保存的检查点加载了目录中的任何内容：mflux-save 写入一个 model.safetensors.index.json 命名每个分片，并且重新加载会遍历目录而不是读取它。将 -q 4 保存到同一文件夹中的现有 -q 8 检查点上会留下 q8 尾部，这些过时的张量会覆盖刚刚写入的张量，而元数据仍然报告 4。检查点缺少一个分片，索引名称会加载其余部分并出现不足。现在，索引决定读取哪些分片，并且不在磁盘上的命名分片会随文件名一起引发。没有索引或索引损坏的检查点将继续从目录加载。 (#577)
  • 元数据 sidecar 没有恢复尺寸、负面提示或初始化图像：每次运行都会嵌入 height、width、negative_prompt 和 image_paths，但 --config-from-metadata 不会读回其中任何一个，因此仅在 1536x768 生成的 sidecar 重新运行会以 1024x1024 默认值显示负面提示掉落 — 任何 CFG 模型上都会出现不同的图像，而不仅仅是尺寸不同的模型。编辑 CLIs 根本无法重新运行 sidecar：--image-paths 是 required=True，argparse 在恢复块运行之前强制执行，因此 mflux-generate-qwen-edit --config-from-metadata prior.metadata.json 退出了 sidecar 携带的 2 个要求较高的图像。现在，所有四个密钥均已恢复，每个密钥都遵循命令行选项，并且恢复后而不是解析期间需要 --image-paths。本机上不存在的 sidecar 初始化映像现在在解析时命名 sidecar 时出错，而不是首先加载整个模型并在裸露的 FileNotFoundError 上死亡。 （＃577，＃634）
  • mflux-capabilities 中缺少高档命令：COMMAND_PREFIXES 仅覆盖了 mflux-generate* 和 mflux-concept*，因此 mflux-upscale-controlnet 和 mflux-upscale-seedvr2 都没有出现在转储中 - 这就是上面的 --metadata 错误被存在的合同检查所忽视的原因。两者现在都已完全覆盖发布，这意味着采用 build_parser() 约定并声明其硬编码配置不能遵循的内容：两者都忽略 --base-model，在 mflux-upscale-controlnet 上，--negative-prompt 被忽略，而 --model 是有条件的（路径或存储库 id 加载权重，内置模型名称不执行任何操作，因为配置始终是dev-controlnet-upscaler）。现在，当传递被忽略的选项时，这两个命令都会在解析时发出警告。 (#577)
  • mflux-upscale-seedvr2 --metadata 从未写过 sidecar：CLI 接受了该标志，然后保存而不转发它，因此高档运行完成并且没有 JSON 出现。它的同级产品 mflux-upscale-controlnet 在同等线路上超过了 export_json_metadata。 (#577)
  • 表意文字 4 量化：mflux-save -q 现在实际上量化了表意文字 4。模型中的每个承重线性都是 Fp8Linear，它没有定义 to_quantized，其组件被标记为 skip_quantization，因此 -q 4 编写了一个标记为 quantization_level: 4 的 FP8 检查点，并且仅触及了 VAE。添加 Fp8Linear.to_quantized，删除跳过标志，在重建保存的检查点而不是假设 q8/group-64 时从存储的形状中导出位和组大小，并将量化嵌入重建为嵌入而不是线性。 -q 8 为 26 GB，-q 4 为 14 GB，两者在视觉上与 FP8 没有区别。 （#559）

📝 文档

  • 表意文字 4 门控权重：记录 HF_TOKEN / hf auth login 步骤以及现有注释，即访问必须在模型卡上获得批准 - 身份验证是一半的人错过的，没有它，批准的帐户仍然会失败，并带有裸露的 401/403。添加覆盖 mflux-save -q 的量化部分并使用 --model-path 加载已保存的检查点。 （#559）

🧰 DX 和维护

  • 开发工作流程：Makefile 替换为 justfile：make <target> 消失了；使用 just <target> 代替（just install、just lint、just format、just check、just test-fast，…）。裸机运行 just（或 just --list）会显示所有配方及其说明。语义遵循 #576 后的 Makefile：uv sync 安装，并且 ruff 从 pyproject.toml 开发依赖项固定。 CI lint 作业还使用固定的 just-setup 复合操作通过 just --fmt --check 对 justfile 本身进行 lint。本地需要 just ≥ 1.50。 (#590)
