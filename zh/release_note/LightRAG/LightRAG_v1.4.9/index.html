LightRAG v1.4.9

这个项目是干啥的：是一个轻量级的检索增强框架，让开发者用更低成本把文档变成能问答的知识库，并借助图结构提升回答质量。

变更架构图

亮点

  • 所有查询端点都返回 references — 所有查询 API 现在都会返回一个 references 字段，包含被引用的文档及其标识符（PR #2147）。这是本版本的中心特性：前端终于能把答案映射回确切的来源分块，而不用从正文里扒文本——这是在 LightRAG 之上构建可审计、以引用为先的 UI 的基石。
  • 上下文格式变了——请审查你的集成 — 传给 LLM 的上下文经过重构，流式响应现在也带上 references 字段（前端默认忽略）（PR #2140）。任何解析查询 API 返回上下文数据的下游代码都需要重新检查；即使方法签名没变，也请把它当作一次”软破坏性变更”。
  • 脚注引用由你掌控 — user_prompt 现在可以充当输出指令：要求用 [^1] 这样的 Markdown 脚注，这些编号就能与 references 中的文档 ID 一一对应。WebUI 在聊天中渲染脚注块（PR #2145），并在查询设置中加入已保存提示词下拉框（PR #2146），让你能在自己的业务系统里把答案直接连回原始资料。官方提供了面向 GPT‑4.1‑mini/Qwen3 和 DeepSeek 的提示词示例。
  • 文件删除的路径穿越漏洞已修复 — 删除操作现在会校验路径穿越（PR #2113）。如果你把文件管理端点暴露给不可信输入或多租户用户，这条安全修复就足以构成升级理由。
  • 搜索与去重行为变化 — WebUI 的实体搜索从客户端改为服务端驱动（PR #2124），并落地了一套完整的文档去重机制（PR #2135）。搜索延迟会有所不同，重复上传的处理也更严格；请重新测试那些反复索引同一文档的自动化流程。
  • 重复查询问题消除 — 新增独立的 aquery_llm 路径，去掉了重复查询并统一了响应处理（PR #2152）。冗余 LLM 调用变少，意味着异步/流式查询在按量计费的 API 上成本和延迟都会下降。

重要提示

v1.4.9 引入了关键增强功能，重点是改进参考输出格式并将结构化参考合并到查询结果中。所有查询 API 端点现在都包含 references 字段，使前端应用程序能够检索引用的文档及其与 LightRAG 查询结果关联的相应标识符。 发送到 LLM 的上下文格式已更新。来自 LLM 的流响应现在包含 references 字段（默认情况下前端会忽略）。 如果您的应用程序依赖于 LightRAG 查询 API 返回的上下文数据，您可能需要相应地更新您的代码。 通过利用 user_prompt 参数，用户可以指示 LLM 生成带有脚注注释的响应。 LLM 输出中的脚注编号可以无缝映射到 references 字段中返回的文档 ID。这种集成使 LightRAG 与您的业务系统之间更加紧密地结合，使用户能够直接访问原始源材料。 user_prompt作为LLM的附加输出指令。这里提供两个例子：

  1. user_prompt 适用于 gpt-4.1-mini 或 Qwen3
For inline citations, employ the footnote reference format `[^1]`, where the `^` following the opening square bracket denotes a superscript link. When multiple citations are required at a single location, enclose each reference ID within separate footnote markers (e.g., `[^1][^2][^3]`).
  1. user_prompt 用于 DeepSeek：
内嵌引文标注使用Markdown脚注格式`[^1]`, 当某处有多个引文标注时,应将每个引用ID分别置于独立的中括号内（例如：`[^1][^2][^3]`）。仅需对回答的关键事实和依据信息给出标注。出现在引文标中的引文ID都应该列在最后生成的参考文献中段落中。不要在参考文献段落之后生成脚注段落。
