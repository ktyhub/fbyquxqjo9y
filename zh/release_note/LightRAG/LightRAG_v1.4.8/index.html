LightRAG v1.4.8

这个项目是干啥的：是一个轻量级的检索增强框架，让开发者用更低成本把文档变成能问答的知识库，并借助图结构提升回答质量。

变更架构图

亮点

  • 原始数据检索 API — 新增 query_data() 与 /query/data，以结构化响应返回完整召回的原始数据，让你可以做自定义重排、引用处理和后处理，而不必只依赖生成的答案（PR #2036、#2100）。
  • 小模型抽取能力增强 — 重写了提示词、增强解析器鲁棒性、加入提示缓存与容错，改善了小型本地模型的实体/关系抽取效果。升级后请在有代表性的语料上验证抽取结果——图谱内容变了，查询结果自然也会变（PR #2051、#2072、#2076、#2093）。
  • 抽取输出设有上限 — 按所用提供方配置合适的 token 上限：o1-mini 及更新模型用 OPENAI_LLM_MAX_TOKENS、OPENAI_LLM_MAX_COMPLETION_TOKENS，Ollama 用 OLLAMA_LLM_NUM_PREDICT。这样能在请求超时前截断失控的表格/引用抽取；上限可按 LLM_TIMEOUT × output tokens/sec 估算（例如 9000 = 180s × 50）。对 Qwen3-30B 这类容易循环的模型，调高 OPENAI_LLM_TEMPERATURE（如 0.9）可能有帮助。
  • 实体名称过滤更严格 — 抽取时会丢弃两位数字名称、短于 6 个字符的名称，以及 1.1、1.2.3 这类点分数字标签。噪声和图谱规模都会下降，但也可能误删有意义的标识符；请核查受影响的标签，重新抽取后图谱会更精简。
  • 批量规模与运行稳定性 — 处理流程针对数百篇文档、数十万条实体关系做了优化。向量库重试、Gunicorn 超时从 210s 提高到 300s、更清晰的错误上下文，都减少了部分失败。流水线状态历史只保留最近 1,000 条，如需完整审计轨迹请另行持久化（PR #2055、#2064、#2078）。
  • 破坏性变更 — 暂无。

导入注释

  1. 引入了原始数据查询API /query/data，使开发人员能够检索LightRAG调用的完整原始数据以进行细粒度处理。 2.优化系统，批量高效处理数百个文档和数十万个十种关系，解决UI延迟问题，增强系统整体稳定性。
  2. Drop entities with short numeric names that negatively impact performance and query results;删除仅包含两位数字的名称、少于六个字符的名称以及混合数字和点的名称，例如 1.1、12.3、1.2.3 等。
  3. 显着提高较小参数模型的实体和关系提取的数量和质量，从而导致查询性能大幅提升 5.优化了Qwen3-30B-A3B-Instruct和gpt-oss-120b模型的提示工程，为模型输出添加了针对性的容错功能。
  4. 实施了 max tokens 和 tempreture 配置，以防止在大型语言模型 (LLM) 响应的实体关系提取阶段过长或无限的输出循环。
# Increased temperature values may mitigate infinite inference loops in certain LLM, such as Qwen3-30B.
OPENAI_LLM_TEMPERATURE=0.9

# For vLLM/SGLang doployed models, or most of OpenAI compatible API provider
OPENAI_LLM_MAX_TOKENS=9000

# For Ollama Deployed Modeles
OLLAMA_LLM_NUM_PREDICT=9000

# For OpenAI o1-mini or newer modles
OPENAI_LLM_MAX_COMPLETION_TOKENS=9000

The purpose of setting max tokens parameter is to truncate LLM output before timeouts occur, thereby preventing document extraction failures.这解决了包含大量实体和关系的某些文本块（例如表格或引文）可能导致法学硕士输出过长甚至无限循环的问题。此设置对于本地部署的较小参数模型尤其重要。最大代币价值可以通过以下公式计算： LLM_TIMEOUT * llm_output_tokens/second（即9000 = 180s * 50 tokens/s）
