druid 0.10.0

小版本 发布时间2017年4月18日 来源apache/druid 英文原文

druid druid-0.10.0

这个项目是干啥的：一个能对海量数据做实时分析的数据库，查询快、几秒就能出结果，给需要做数据看板和实时报表的分析师用。

Druid 0.10.0 包含来自 40 多个贡献者的数百项性能改进、稳定性改进和错误修复。主要的新功能包括内置 SQL 层、数字维度、Kerberos 身份验证支持、“索引”任务的改进、新的“喜欢”过滤器、大列、将协调器和霸主作为单个服务运行的能力、更好的默认性能以及八个新扩展。 如果您要从 Druid 的早期版本升级，请参阅下面的“从 0.9.2 及更早版本更新”以获取升级说明，包括一些向后不兼容的更改。 完整的更改列表在这里：https://github.com/druid-io/druid/pulls?utf8=%E2%9C%93&q=is%3Apr%20is%3Aclosed%20milestone%3A0.10.0 此版本的文档位于：http://druid.io/docs/0.10.0/

变更架构图

亮点

内置 SQL

Druid 现在包含一个由 Apache Calcite 提供支持的内置 SQL 服务器。 Druid 提供了两种 SQL API：HTTP POST 和 JDBC。这为新开发人员更熟悉的 Druid 原生 JSON API 提供了替代方案，并且可以更轻松地集成原生 SQL 的现有应用程序。在此初始版本中，SQL 层并非支持所有 Druid 和 SQL 功能，但我们打算在未来版本中扩展这两个功能。 可以通过在配置中设置 druid.sql.enable=true 来启用 SQL 支持。有关详细信息和文档，请参阅 http://druid.io/docs/0.10.0/querying/sql.html。 由 @gianm 在 #3682 中添加。

数字维度

Druid 现在支持摄取和查询时的数字维度。用户可以将长列和浮动列作为维度进行摄取（即，如果启用了汇总，则将数字列视为摄取时间分组键的一部分，而不是聚合器）。此外，Druid 查询现在可以接受任何长列或浮点列作为分组或过滤的维度。 字符串列和数字列之间存在性能权衡。数字列的分组通常比字符串列更快。数字列没有索引，因此它们的过滤速度通常比字符串列慢。 有关摄取文档，请参阅 http://druid.io/docs/0.10.0/ingestion/schema-design.html#numeric-dimensions；有关查询文档，请参阅 http://druid.io/docs/0.10.0/querying/dimensionspecs.html。 由 @jon-wei 添加到 #3838、#3966 和其他补丁中。

Kerberos 身份验证支持

添加了一个名为“druid-kerberos”的新扩展，它添加了对使用 Kerberos 对 Druid 节点进行用户身份验证的支持。它使用简单且受保护的 GSSAPI 协商机制 SPNEGO(https://en.wikipedia.org/wiki/SPNEGO) 通过 HTTP 进行身份验证。 有关如何配置 kerberos 身份验证的文档，请参阅 http://druid.io/docs/0.10.0/development/extensions-core/druid-kerberos.html。 由@nishantmonu51 在#3853 中添加。

索引任务改造

重新编写了索引任务以提高性能，特别是对于跨越多个间隔并生成许多分片的作业。现在可以自动确定分段粒度 intervals，并且不再需要指定，但如果同时提供 intervals 和 numShards，则可以减少摄取时间。 此外，索引任务现在支持 appendToExisting 标志，这会导致数据被索引为当前版本的附加分片，而不是作为覆盖先前版本的新版本。 请参阅 http://druid.io/docs/0.10.0/ingestion/tasks.html#index-task 文档。 由@dclim 在#3611 中添加。

喜欢过滤器

Druid 现在包含一个“like”过滤器，可以启用 SQL LIKE 样式的过滤，例如 foo LIKE 'bar%'。该实现通常比正则表达式过滤器更快，并且在可能的情况下鼓励优于正则表达式过滤器。特别是，bar% 等前缀上的同类过滤器比 ^bar.* 等等效正则表达式过滤器要快得多。 请参阅 http://druid.io/docs/0.10.0/querying/filters.html#like-filter 文档。 由 @gianm 在 #3642 中添加。

大列

Druid 现在支持大于 2GB 的单个列。通常不需要此功能，因为一般指导意见是段的大小通常应为 500MB–1GB，但在其中一列比所有其他列大得多的情况下非常有用（例如，大型草图）。 所有 Druid 用户都可以使用此功能，并且在使用内置列类型时无需特殊配置。如果您开发了自定义指标列类型作为 Druid 扩展，则可以通过覆盖 ComplexMetricsSerde 中的 getSerializer 来启用大列支持。 由 @akashdw 在 #3743 中添加。

协调员/霸主组合选项

现在可以通过将 Coordinator 和 Overlord 功能合并到 Coordinator 进程中来简化 Druid 部署。为此，请在协调器上适当设置 druid.coordinator.asOverlord.enabled 和 druid.coordinator.asOverlord.overlordService，然后停止您的霸主。 http://coordinator-host:port/console.html 上将提供 Overlord 控制台。 目前，这是一项实验性功能，默认情况下处于关闭状态。我们打算考虑在 Druid 的未来版本中将其设置为默认值。 有关此功能和配置选项的文档，请参阅 http://druid.io/docs/0.10.0/configuration/coordinator.html。 由@himanshug 添加到#3711。

性能更好的默认值

此版本更改了两个默认设置以提高开箱即用的性能：

  • Druid 0.9.0 中引入的 buildV9Directly 选项现在默认启用。此选项通过直接创建 v9 数据格式而不是先创建 v8 然后转换为 v9 来提高索引性能。如有必要，您可以通过在索引任务中将“buildV9Directly”设置为 false 来回滚到旧代码。
  • Druid 0.9.2 中引入的 v2 groupBy 引擎现在默认启用。这个新的 groupBy 引擎从头开始重写，以获得更好的性能和内存管理。如有必要，您可以通过将runtime.properties中的“druid.groupBy.query.defaultStrategy”或查询上下文中的“groupByStrategy”设置为“v1”来回滚到旧引擎。有关 groupBy v1 和 v2 之间差异的详细信息，请参阅 http://druid.io/docs/0.10.0/querying/groupbyquery.html。

从 0.9.2 及更早版本更新

请参阅下文，了解升级前您应注意的 0.9.2 和 0.10.0 之间的变化。如果您从 0.9.2 之前的版本进行更新，请参阅相关中间版本的 release note 以获取更多说明。

滚动更新

滚动更新应遵循 http://druid.io/docs/0.10.0/operations/rolling-updates.html 描述的标准 Druid 更新流程。 ###查询API变化 请注意更新时以下向后不兼容的查询 API 发生变化。某些查询可能需要调整才能继续按预期运行。 -出于安全原因，JavaScript 查询功能现在默认处于禁用状态 (#3818)。如果您使用这些功能，您可以通过在运行时属性中设置 druid.javascript.enabled=true 来重新启用它们。有关详细信息（包括安全注意事项），请参阅 http://druid.io/docs/0.10.0/development/javascript.html。

  • GroupBy 查询不再允许 __time 作为维度、聚合器或后聚合器的输出名称 (#3967)。
  • 当未指定 fromNext 时，选择查询分页规范现在默认为 fromNext: true 行为 (#3986)。对于指定了 fromNext 的 Select 查询，行为没有变化。如果您更喜欢旧的默认值，则可以通过 druid.query.select.enableFromNextDefault 运行时属性更改此设置。 详细信息请参见 http://druid.io/docs/0.10.0/querying/select-query.html。
  • SegmentMetadata 查询默认不再包含“大小”分析 (#3773)。您仍然可以通过在查询时将“size”添加到“analysisTypes”来请求“size”分析。

部署和配置更改

更新时请注意以下与部署相关的更改。

  • Druid 现在需要 Java 8 才能运行 (#3914)。如果您当前运行的是 Java 7，我们建议先升级 Java，然后再升级 Druid。
  • Druid 现在默认使用 groupBy 的“v2”引擎，而不是传统的“v1”引擎。 **作为此过程的一部分，内存使用限制已从基于行的限制更改为基于字节的限制，因此以前满足资源限制的某些查询现在可能会超出它们并失败。**您可以通过适当调整新的 groupBy 引擎来避免这种情况。如有必要，您可以通过将runtime.properties中的“druid.groupBy.query.defaultStrategy”或查询上下文中的“groupByStrategy”设置为“v1”来回滚到旧引擎。有关 groupBy v1 和 v2 之间差异的更多详细信息，请参阅 http://druid.io/docs/0.10.0/querying/groupbyquery.html。

    这个新的 groupBy 引擎从头开始重写，以实现更好的性能和内存管理。查询 API 和结果在两个引擎之间是兼容的；但是，从集群配置的角度来看，存在一些差异：（1）groupBy v2 主要使用堆外内存而不是堆内内存； (2) 每个并发查询需要一个合并缓冲区； (3) 如果你为groupBy配置了缓存，它必须是历史记录； (4)不支持chunkPeriod。

  • Druid 现在 druid.processing.numMergeBuffers 有一个非零的默认值（#3953）。这将增加其默认配置中使用的直接内存量。此更改是与更改默认 groupBy 引擎相关的，因为新的“v2”引擎需要合并缓冲区。如果您以前使用 groupBy v1，您应该能够通过减少 JVM 堆来弥补这一点，因为 groupBy v2 使用堆外内存而不是堆内内存。
  • Druid 查询相关进程（代理、历史、索引任务）现在急切地分配 druid.processing.numThreads 数量的大小为 druid.processing.buffer.sizeBytes 的 DirectByteBuffer 实例，用于启动时的查询处理（#3628）。在 Druid 的早期版本中，这种分配是惰性的。此更改不会影响长时间运行的 Druid 集群的内存使用，但这意味着 Druid 启动时用于处理缓冲区的内存必须可用。
  • 在非 UTC 时区运行时，预定义的分段粒度常量（例如“天”）的行为将在升级时发生变化。以前，这将使用当地时间生成分段。在 Druid 0.10.0 中，这将使用 UTC 天生成段。如果您在 UTC 时区运行 Druid，则此更改无效。请注意，官方不支持在非 UTC 时区运行 Druid（请参阅 http://druid.io/docs/0.10.0/configuration/index.html），我们建议始终在 UTC 时区运行所有进程。要使用 Druid 0.10.0 创建本地时间段，您可以使用本地时间段粒度，例如：
"segmentGranularity" : {
     "type" : "period",
     "period" : "P1D",
     "timeZone" : "America/Los_Angeles"
}

扩展更改

  • AggregatorFactory、BufferAggregator 和 PostAggregator 接口已更改（#3894、#3899、#3957、#4071）。如果您部署了包含 AggregatorFactory 或 PostAggregator 的自定义扩展，则需要重新编译它。 Druid 的内置扩展都已针对此更改进行了更新。
  • 针对 Druid 0.10.x 的扩展必须使用 JDK 8 进行编译。
