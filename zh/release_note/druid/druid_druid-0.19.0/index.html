druid 0.19.0

小版本 发布时间2020年7月21日 来源apache/druid 英文原文

Apache Druid 0.19.0 包含约 200 个新功能、错误修复、性能增强、文档改进以及来自 51 个贡献者的额外测试覆盖范围。请参阅完整的更改列表 和标记到里程碑的所有内容 了解更多详细信息。

# 新功能

# 默认启用 GroupBy 和 Timeseries 矢量化查询引擎

Druid 0.16 中引入了用于 GroupBy 和 Timeseries 查询的矢量化查询引擎，作为一项可选功能。从那时起，我们对这些引擎进行了广泛的测试，并认为现在是时候让这些改进吸引更广泛的受众了。请注意，目前并非所有查询引擎都已矢量化，但此更改使得任何符合矢量化条件的查询都将这样做。如果您在将 druid.query.vectorize 设置为 false 时遇到任何问题，此功能可能仍会被禁用。 https://github.com/apache/druid/pull/10065

# Druid 对 Apache Avro 对象容器文件的本机批处理支持

Druid 0.19.0 中的新增功能，本机批量索引现在支持 Apache Avro 对象容器格式 编码文件，允许批量摄取 Avro 数据，而无需外部 Hadoop 集群。查看文档 了解更多详细信息 https://github.com/apache/druid/pull/9671

# 更新了 Druid 对 SQL 数据库的原生批处理支持

Druid 0.19.0 中添加了“SqlInputSource”，以与 Druid 0.17 中首次引入的新本机批量摄取规范配合使用，弃用了 SqlFirehose。与“SqlFirehose”一样，它目前支持 MySQL 和 PostgreSQL，使用这些扩展中的驱动程序。这是一个相对较低级别的摄取任务，操作员必须注意手动确保摄取正确的数据，或者通过专门设计查询以确保不会摄取重复数据进行追加，或者确保在覆盖时查询整个数据集以进行替换。有关更多操作详细信息，请参阅文档。 https://github.com/apache/druid/pull/9449

# 基于 Apache Ranger 的授权

Druid 0.19.0 中的新扩展添加了一个 Authorizer，它为 Druid 实现访问控制，由 Apache Ranger 支持。请参阅[扩展文档]((https://druid.apache.org/docs/0.19.0/development/extensions-core/druid-ranger-security.html)和[身份验证和授权](https://druid.apache.org/docs/0.19.0/design/auth.html)，了解有关此扩展提供的基本功能的更多信息。 https://github.com/apache/druid/pull/9579

# 阿里巴巴对象存储服务支持

为[阿里巴巴云对象存储服务（OSS）]（https://www.alibabacloud.com/product/oss）添加了新的“contrib”扩展，以提供深度存储和用作批量摄取输入源。由于这是一个“contrib”扩展，因此默认情况下不会将其打包在二进制发行版中，有关如何在集群中使用的更多详细信息，请参阅[社区扩展](https://druid.apache.org/docs/0.19.0/development/extensions.html#community-extensions)。 https://github.com/apache/druid/pull/9898

# Google Compute Engine 的摄取工作线程自动缩放

0.19.0 中添加了另一个新的“contrib”扩展，以支持摄取工作人员自动缩放，这允许 Druid Overlord 在 Google Compute Engine 存在待处理任务或空闲工作人员时提供或终止工作人员实例（MiddleManager 或索引器）。与 Amazon Web Services 摄取自动扩展扩展（不使用 Auto Scaling 组而直接配置和终止实例）不同，GCE 自动扩展程序使用 托管实例组 来更紧密地符合运营商在 GCE 中配置集群的方式。与其他“contrib”扩展一样，它不会默认打包在二进制发行版中，有关如何在集群中使用的更多详细信息，请参阅社区扩展。 https://github.com/apache/druid/pull/8987

# REGEXP_LIKE

Druid SQL 和本机表达式中添加了新的 REGEXP_LIKE 函数，其行为与 LIKE 类似，只是使用正则表达式作为模式。 https://github.com/apache/druid/pull/9893

# Web 控制台查找管理改进

Druid 0.19 的 Web 控制台还包括对查找表管理界面的一些有用的改进。创建和编辑查找现在是通过接受用户输入的表单来完成的，而不是使用原始文本编辑器来输入 JSON 规范。 此外，clicking 查找旁边的放大镜图标现在将允许显示该查找的前 5000 个值。 https://github.com/apache/druid/pull/9549 https://github.com/apache/druid/pull/9587

# 每个数据源“loadstatus”API 的新协调器

协调器 API 可以更轻松地确定最新发布的段是否可用于查询。这类似于现有协调器“loadstatus”API，但特定于数据源，可以指定间隔，并且可以选择实时刷新元数据存储快照以获取最新信息。请注意，在使用此 API 查询大量段时，操作员仍应谨慎行事，特别是在强制元数据刷新时，因为这可能是大型集群上的“繁重”调用。 https://github.com/apache/druid/pull/9965

# 对范围和散列分区的本机批量追加支持

部分错误修复，部分新功能，Druid 原生批处理（再次）支持在使用“散列”或“范围”分区算法对现有时间块进行分区时将新数据附加到现有时间块。请注意，目前附加的段仅支持“动态”分区，当回滚到旧版本时，降级后 Druid 将无法识别这些附加的段。为了回滚到以前的版本，这些附加的段应该与其余的时间块一起压缩，以获得同质的分区方案。 https://github.com/apache/druid/pull/10033

# 错误修复

Druid 0.19.0 包含 65 个错误修复，您可以在此处查看完整列表。

# 修复批量摄取的“动态”分区段无法原子查询的问题

Druid 0.19.0 修复了一个重要的查询正确性问题，其中批量摄取任务生成的“动态”分区段不跟踪分区的总数。这意味着当这些段上线时，它们并不是作为一个完整的集合，而是作为单独的段，这意味着会有一段交换时间，可以在一个时间块内从不完整的分区集中查询结果。 https://github.com/apache/druid/pull/10025

# 修复以允许带有空存储桶的“hash”和“range”分区段现在可查询

在 0.19.0 之前，Druid 在使用哈希或范围分区时存在一个错误，如果数据倾斜导致任何存储桶在摄取后为“空”，则分区永远不会被识别为“完整”，因此永远无法查询。 Druid 0.19.0 通过调整分区规范的架构解决了这个问题。对 json 格式的这些更改应该向后兼容，但是回滚到以前的版本将再次使这些段不再可查询。 https://github.com/apache/druid/pull/10012

# 不正确的平衡器行为

0.19.0 之前的 Druid 版本中存在一个错误，允许在未设置 druid.server.maxSize 的情况下进行（错误的）协调器操作。如果所有历史记录都没有设置此值，则此错误将允许段加载，并在集群中有效地随机平衡它们（无论实际配置了什么平衡器策略）。此错误已修复，但因此必须将 druid.server.maxSize 设置为历史数据段缓存位置大小的总和，否则它们将无法加载段。 https://github.com/apache/druid/pull/10070

# 升级到 Druid 0.19.0

从0.18.1升级到0.19.0时，请注意以下问题。如果您从 0.18.1 之前的版本进行更新，请参阅相关中间版本的 release note。

# 现在必须为历史服务器设置“druid.server.maxSize”

协调器错误修复 作为副作用，现在需要为要加载的段设置 druid.server.maxSize。虽然对于以前的版本应该正确设置此值，但请确保在升级集群之前正确配置此值，否则将无法加载段。 https://github.com/apache/druid/pull/10070

# 系统表“sys.segments”列“payload”已被删除并替换为“dimensions”、“metrics”和“shardSpec”

从 sys.segments 表中删除“payload”列应该会使对该表的查询更加高效，并且其中最有用的字段“dimensions”、“metrics”和“shardSpec”列表已被拆分出来，因此仍然可用于处理查询。 https://github.com/apache/druid/pull/9883

# 更改了段加载线程的默认数量

druid.segmentCache.numLoadingThreads 配置的默认值已从“核心数”更改为“核心数除以 6”。这应该会使历史记录在加载大量段时表现得更好，从而限制对查询性能的影响。 https://github.com/apache/druid/pull/9856

# 广播加载规则不再具有“并置数据源”

0.19.0 中添加了许多不完整的更改，以促进更有效的连接查询，这些更改基于利用广播负载规则在集群中传播较小数据源的思想，以便连接操作可以下推到单独的段处理。虽然尚未完成的功能，但作为实现这一目标的更改的一部分，“广播”加载规则不再具有“共置数据源”的概念，该概念将尝试仅将段广播到具有已配置数据源段的服务器。这在实践中效果不佳，因为它是非原子的，这意味着广播段将落后于并置数据源的负载和丢弃，因此我们决定删除它。 https://github.com/apache/druid/pull/9971

# 代理和实时任务现在可以配置为从“广播”数据源加载段

上述准备工作的另一个效果是引入高效的“广播连接”，如果配置了段缓存，代理和实时索引任务现在将加载由“广播”规则加载的段。由于该功能并不完整，因此没有理由在 0.19.0 中执行此操作，并且除非明确配置，否则不会发生这种情况。 https://github.com/apache/druid/pull/9971

# lpad 和 rpad 功能行为更改

lpad 和 rpad 函数在 Druids 默认非 SQL 兼容模式下进行了轻微的行为更改，以使它们的行为与 PostgreSQL 一致。在新行为中，如果 pad 表达式是空字符串，则结果将是（可能已修剪的）原始字符，而不是将空字符串视为 null 并将结果强制为 null。 https://github.com/apache/druid/pull/10006

# 提供自定义 Druid 表达式的扩展现在预计将实现 equals 和 hashCode 方法

Druid 0.19.0 中对 Expr 接口的更改要求任何通过 ExprMacroTable 提供自定义表达式的扩展也必须实现 equals 和 hashCode 方法才能正常运行，尤其是 JOIN 查询，它依赖于过滤器和表达式分析来确定如何以最佳方式处理查询。 https://github.com/apache/druid/pull/9830
