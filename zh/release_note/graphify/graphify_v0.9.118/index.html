graphify v0.9.118

跨 14 个社区拉取请求的一批提取器、解析、服务、导出、集群和报告修复。 Objective-C、C 和 C# 更改会改变节点/边缘输出，因此 AST 缓存架构会发生变化（51 到 53），并且升级后的第一个构建会重新提取受影响的语言；其他修复不需要重建。

  • 修复：csharp 名为 partial、required、async、nint、nuint 或 with（上下文关键字）的本地参数或字段，当以它开头的语句不再使文件脱轨时，tree-sitter-c-sharp 会错误解析；它在解析之前被重写为其逐字 @name 形式（保留字节长度），因此封闭类型及其后面的成员被保留，而不是被默默删除（#5043，感谢@ThatAblaze）。
  • 修复：c 通过结构函数指针字段（ops->run()、ops.run()）的调用不再为同名自由函数制造 calls 边缘；字段名称不是指针运行时目标的证据，因此放弃猜测。简单的直接调用仍然可以解决（#5410，感谢@sdivyanshu90）。
  • 修复：objc 一个 Objective-C 方法，其名称折叠到 @interface/@implementation/@protocol 中的同级 ID 上（-setup/-_setup 中的前导/尾随 _，或仅区分大小写）获取其自己的加盐节点 ID，而不是覆盖它；一个方法的声明和定义仍然共享一个节点（#5390，感谢@ayushcodes10）。
  • 修复：go 结构体字段的所有者类型的作用域为它自己的包，因此在两个包中声明名称的类型的字段绑定到正确的包，并且其成员调用解析而不是因为不明确而被删除（#5408，感谢 @azizur100389）。
  • 修复：提取通过 export * 桶的 Svelte 导入现在解析为真正的定义模块，与普通的 .ts 匹配。跨文件解析器屏蔽了 .vue，但没有屏蔽 .svelte，因此 Svelte <script> 导入因模板解析错误而丢失；连锁桶解决和模糊的再出口失败。运行 graphify extract . --force 一次来修复已经缓存的图表（#5403，感谢@Max17190）。
  • 修复：提取检测到但未提取的音频和视频文件（无头提取没有转录步骤）现在会在摘要中报告，而不是默默消失，与其他跳过通知相匹配；没有为它们制造节点（#5076，感谢@ayushcodes10）。
  • 修复：sections get_section 的重试不再重用完整图的三元组搜索索引。重试针对 networkx 子图视图运行，其 .graph 字典与服务缓存索引的对象相同，因此重试搜索过时的、超出部分的 id 并引发了 KeyError；重试视图现在拥有自己的图形元数据，这也消除了并发服务调用者的共享图形索引损坏危险（#5385，感谢@Deepjyoti-Sarmah）。
  • 修复：服务 MCP 服务器从事件循环中加载 graph.json，因此大型图重新加载不再阻塞并发请求；重新加载期间的请求将服务于当前图表，而损坏的重新加载会使旧图表完好无损（#5371，感谢@Deepjyoti-Sarmah）。
  • 修复：更新在图形未更改的情况下删除的集群 GRAPH_REPORT.md 会重新生成，而不是被不变门跳过；图本身是字节相同的（从分区缓存恢复），因此没有不必要的重建（#5402，感谢@Max17190）。
  • 修复：查询图像节点在种子评分中与文档和论文一起降级，因此富含标题的图像不再超出其术语恰好重复的查询的真实代码（#445，感谢@ayushcodes10）。
  • 修复： export 导出文件名遵循目标文件系统的 NAME_MAX（通过 pathconf 探测，不假定为 255），因此 graphify export obsidian/wiki/canvas 不再在报告较低限制的文件系统（例如 eCryptfs (143)）上中止与 ENAMETOOLONG；长名称会用哈希后缀截断，内部链接使用缩短的名称（#2109，感谢@Synvoya）。
  • 修复：wiki 有向图导出现在包括传入边，因此社区审核不再低估置信度（当页面显示“EXTRACTED 100%”时，传入的模糊边可能是不可见的）。在上帝节点页面上，传入的边被标记为 (incoming)，因此像 calls 这样的关系不会向后读取（#5369，感谢 @sdivyanshu90）。
  • 修复：config .graphifyrc 现在解析 demote_docs / query_demote_docs，因此项目可以在 rcfile 中设置文档降级，而不是仅通过 CLI 标志；显式标志仍然会覆盖它（#5290，感谢@debojyoti10CC）。
  • Perf：重建期间的集群社区重叠计数是从一次传递中的共享节点计算出来的，而不是与每对社区相交，将 O（社区平方）步骤转变为具有字节相同结果的线性步骤（#5382，感谢 @Max17190）。
