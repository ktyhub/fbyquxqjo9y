RuView v3809

RuView v3809

变更流程图

亮点

  • 跨进程刷新加锁（#2599） — 刷新现在在所有平台上使用一个永久的 credentials.lock 文件和 File::lock：Unix 上用 flock，Windows 上用 LockFileEx。这消除了易竞态的目录删除式锁和陈旧锁启发式判断；进程死亡时操作系统会自动释放锁。
  • 失败即关闭的 token 处理 — 凭证在锁内重新读取，存储的 refresh token 会在请求发出前被移除。如果请求可能已到达 Identity 但失败、超时、返回无效响应，或无法保存新的凭证对，则同时清除存储中和内存中的凭证。这防止了已使用 token 的复用以及随之而来的整个会话族被吊销。
  • 明确的争用与超时行为 — 等待者最多轮询 30 秒（长于 20 秒的刷新超时），随后返回 StoreError::RefreshBusy，既不发请求也不改状态。应把它当作跨进程争用处理，而不是认证失败。请求发出后超时现在需要重新认证，而不是静默复用旧 token。
  • 更安全的持久化语义 — 临时凭证文件在原子重命名之前会先同步，且该失败仍是致命的。父目录 fsync 现在改为尽力而为，防止 FUSE 或网络挂载上不支持的目录同步丢弃已成功轮换的凭证对并把用户登出。
  • 回归覆盖与测试隔离 — 子进程测试验证单次刷新行为、进程死亡后锁释放、超时清理，以及未建立连接时凭证得以保留。测试也不再启动真实浏览器，使认证测试套件可安全地在日常本地和 CI 中运行。

无破坏性变更。

由 CI 管道验证的源快照。此条目不包含固件包。 变化： [安全敏感]修复（ruview-auth）：跨进程一次刷新；锁定超时后不继续；发送的令牌永远不会被保留（#2599）

  • 修复（ruview-auth）：跨进程一次刷新，锁定超时后不继续，发送的令牌永远不会保留 当身份（cognitum-one/console#857）撤销整个会话系列时 再次呈现使用过的刷新令牌。 Ensure_fresh 可以做到这一点 普通使用：
  • 等待另一个进程的锁 3 秒后，它仍然继续进行；
  • 它提供了之前加载的令牌，而不是重新读取文件 锁下；
  • 在请求失败或超时后保留旧令牌；
  • 当答案没有携带新令牌时，它会重用旧令牌；
  • 在非 Unix 上它根本没有锁。 现在：
  • login/lock.rs：Unix 上的集群。在其他地方，原子 credentials.lock.d 目录（120 秒后失效），如果无法读取锁定状态，则会失败 关闭。等待者轮询最多 LOCK_WAIT（30 秒，比请求的时间长） 超时）。如果仍然没有锁，则返回新的锁 StoreError::RefreshBusy，没有发送任何内容，也没有更改任何内容。
  • 在锁定下文件被重新读取，并且记录已经另一个进程 使用刷新。
  • 在发送之前，存储的记录会丢失其刷新令牌（无令牌 标记）。在请求中途终止的进程会留下一条应答记录 NoRefreshToken，绝不是可重复使用的已用令牌。
  • 一旦请求到达身份，任何失败都会清除存储的 凭证，内存中的会话也变得无令牌。这涵盖了 超时、重置、错误答案、错误正文以及新内容保存失败 对。只有从未建立过的连接才能恢复旧令牌。
  • 没有新刷新令牌的答案不存储任何内容；用过的不保留。
  • client::refresh 受 REFRESH_TIMEOUT（20 秒）限制。 测试（store_refresh_tests.rs）。每个场景都在一个子进程中运行，该子进程 该测试二进制文件是否被重新调用。身份是 127.0.0.1 夹具和所有 代币是固定装置。
  • 两个进程有一个过期文件：1 次刷新，并且都获得新的一对。
  • 发送后超时会清除文件，下次运行不会发送任何内容。
  • 永远不会发送剩余的无令牌记录。
  • 持有的锁给出 RefreshBusy 并且不发送任何内容。
  • 被拒绝的连接保留令牌。
  • 没有刷新令牌的答案不会保留任何内容。 变异检查：将锁下的重读删除会产生2次刷新； 错误后保留令牌未通过超时测试。 cargo test -p ruview-auth --all-features：70 + 25 + 2 通过。
  • 修复（ruview-auth）：File::lock 处处永不删除的锁定文件；持久写入（评论 393） 来自 review-393 对 #2599 的修复：
  • 锁。删除接管锁（如以下目录中的非 Unix 锁目录） previous commit) 可以让两个 taker 都持有它； review-393 转载了这个 CLI 同等游戏机上的百分之一。锁现在是File::lock （自 1.89（存储库的固定工具链）以来稳定）在每个平台上：
    • 它锁定credentials.lock，永远不会被删除；
    • 它在Unix上使用flock，在Windows上使用LockFileEx；
    • 当持有者退出或死亡时操作系统释放它，所以没有 陈旧启发式；
    • 根本无法打开的锁无法关闭；
    • RefreshBusy 之后的 30 秒等待时间不变。 该板条箱不再调用 libc。可选的 libc 依赖项保留在 Cargo.toml 因此 Cargo.lock 在此 PR 中不会更改。
  • 耐用性。在 Unix 上，父目录在重命名后进行 fsync。开 其他平台 write_private 现在sync_all 是重命名之前的tmp 文件。
  • 刷新测试中的子进程已删除仅测试挂钩 他们的环境。 新测试：
  • 由活动子进程持有的锁；一旦孩子被杀 （永不释放），锁释放；
  • 8 线 x 25 发子弹永远不会有超过 1 个支架；
  • 锁定文件永远不会取消链接。 压力：完整的 lib 测试二进制文件运行了 90 次，其中 6 次并行，共 90 次通过。
  • 修复（ruview-auth）：使凭证目录 fsync 尽最大努力（L8） 父目录 fsync 在重命名后运行，已经放置了新的目录 配对到位，其错误是致命的。在 FUSE 或网络安装上 拒绝目录 fsync (EINVAL/ENOTSUP)，每次刷新都会清除 新配对并注销用户。现在使用跟踪::警告进行记录并且 被忽视；重命名之前的 tmp 文件的sync_all仍然是致命的。 更正了标记保存注释，添加了注入目录 fsync 的测试 通过 RUVIEW_TEST_FAIL_DIR_FSYNC 失败（保存成功；刷新轮转 并保留新的对），并删除现在未使用的可选 libc 依赖项。
  • 修复（ruview-auth）：永远不要从测试中启动浏览器 open_browser 的单元测试称为真正的启动器，因此每个 cargo test -p ruview-auth 在 http://127.0.0.1:1/nope 中打开了一个选项卡 开发者的浏览器。在 cfg(test) 下，open_browser 现在记录命令 它将运行而不是生成它，并且测试断言该命令。 来源提交： f7de049ebd637aae7f5d20d51cc23162938cbad9 容器镜像通过传感服务器发布工作流程单独发布。 固件下载附在专用的 vX.Y.Z-esp32 版本中。
