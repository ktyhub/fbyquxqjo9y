codebase-memory-mcp v0.10.4

修订 发布时间2026年8月14日 来源DeusData/codebase-memory-mcp 英文原文

codebase-memory-mcp v0.10.4

变更流程图

亮点

  • Windows 提权账户可以安装并启动了 — v0.10.3 把文件属主与令牌的 user SID 比较，但 Windows 给新对象打的是 owner SID（对任何管理员组成员都是 BUILTIN\Administrators），于是 install 创建了自己的暂存文件后又以 activation transaction I/O failed: owner-not-current-user 拒绝它，服务启动时直接因传输通道关闭而退出。现在 cbm 接受它实际写入的 SID（仍拒绝真正的外来属主），很可能就此关闭了悬置已久的 #1416。Windows 管理员应升级——除此别无解法。

  • 安装不再破坏不属于自己的东西 — 通过 mise、Homebrew、nix、asdf 或 cargo 安装的二进制不再被动：不再往 ~/.local/bin 放影子副本、不再追加 shell-rc、除非是 cbm 自己放的二进制，否则不改 PATH；update 现在会诚实拒绝并指出可用的命令（mise upgrade、brew upgrade）。新增 --clients=claude,codex 限制哪些检测到的客户端会写入 MCP 配置/agents/skills/hooks（此前每次重装都会配置所有客户端再回滚）；单独运行 --clients 会列出支持的取值。包管理器用户单为这一点就该升级。

  • 诊断信息直指真正原因 — 激活拒绝现在会指出拒绝它的目录和规则，而不是指向未打印的错误；客户端路径启动失败会以带原因的 JSON-RPC 错误返回，而不再是“transport closed unexpectedly”（stderr 对 MCP 客户端不可见）；ui_enabled / ui_port 现在是一等配置键，可通过 config set 关闭回环监听器，无需手改 config.json（它们此前在 config list 中不可见）。如果你一直在排查无声的安装/启动失败，这个版本值得升级。

  • 查询正确性与配置修复，但有一个现实注意事项 — 跳数缓冲区饱和后，OPTIONAL MATCH 不再静默丢弃无匹配行（正是 WHERE x IS NULL 要暴露的行）——这是个会悄悄返回错误答案的 bug，对正确性敏感的用户应升级。Codex 安装现在会把自有的内联 hook 归并到规范块中、保留外来 hook，并在 TOML 有歧义时直接失败；旧版本遗留的 # <<< 标记现在会在移除时自愈。重要：OpenCode 的修复只是部分的——cbm 现在会指向 opencode.json / opencode.jsonc 中实际存在的那个，但写入在 v0.10.4 上仍会失败，报 error: agent_config agent=OpenCode op=mcp_install（#1630）。别指望升级后 OpenCode 安装就能用。

  • 升级结论与迁移 — 无需索引、缓存或配置迁移；重新运行 install.sh / install.ps1、通过包管理器更新，或照常使用 npm/PyPI。必须升级：Windows 提权账户、包管理器安装用户，以及依赖 OPTIONAL MATCH 正确性的人。可以跳过：其他所有人，除非你想要改进的诊断或顺带的加固（发布流水线按 #1245 固定并校验下载的工具、子进程启动失败现在回退重试至约 500ms，以及注册表条目不再在版本公开前发布）。这是实打实的修复版本，不是重新打标签或仅改元数据的空操作。

代码库-内存-mcp v0.10.4

安装和诊断版本。如果 v0.10.3 拒绝为您安装或启动 — 特别是在 Windows 上，或者在通过包管理器安装了 cbm 的计算机上 — 这就是您要采取的方法。

接下来的大部分内容都来自提交精确报告的人，并且在某些情况下，他们在我们之前找到了错误的根源。

Windows：提升的帐户根本无法安装或启动

作为管理员组帐户运行意味着 install 失败并显示 activation transaction I/O failed: owner-not-current-user，或者 MCP 服务器在启动期间退出，日志中除了关闭的传输外没有任何内容。

原因是我们自己的，而且是具体的：我们将文件的所有者与令牌的 user SID 进行比较，但 Windows 使用令牌的 owner SID 标记新创建的对象 - 对于管理员组的任何成员来说，该 SID 默认为 BUILTIN\Administrators。因此，安装程序创建了自己的临时文件，然后在几秒钟后拒绝它，因为它属于其他人。再多的重新启动或关闭进程也无济于事，因为没有任何东西在运行。

我们现在还接受 SID Windows 实际上标记在我们创建的内容上。这比“trust 任何管理员”要窄：真正不同的帐户拥有的文件仍然会被拒绝。由 @spam0115 和 @gotspatel 报告，这也很可能是长期运行的 #1416 的原因。

安装不再触及它不拥有的东西

对于那些被我们践踏的人来说，有两个变化：

由mise、Homebrew、nix、asdf 或cargo 安装的二进制文件将被保留。 之前，install 将第二个副本放入~/.local/bin 中——根据PATH 顺序隐藏托管副本——并附加到您的shell rc 文件中。现在它配置代理并保持二进制文件和您的 PATH 不变，update 诚实地拒绝并命名将起作用的命令（mise upgrade，brew upgrade），而 PATH 仅在我们实际放置二进制文件时进行修改。由 @SC-CTS 报道。

您可以选择配置哪些 client。 install 为每个检测到的 client 编写了 MCP 配置、代理、技能和挂钩，并且恢复您不想要的那些是毫无意义的，因为下一次安装会重新创建它们。 --clients=claude,codex 现在对其进行限制，而 --clients 自己列出了每个支持的令牌。由 @PsyTech-Rob 报道。

错误告诉您实际发生了什么

这里连续三个修复，都来自同一个抱怨：我们的消息肯定是错误的。

  • 激活拒绝不再指向它未显示的证据。 v0.10.3 正确地停止将非会话引起的故障归咎于“活动 CBM 会话”，但随后告诉您检查从未打印的错误。它现在命名目录和拒绝的规则。
  • 无法启动的服务器会说明原因。 Client 路径启动失败仅写入 stderr，没有 MCP client 表面 - 因此，您会收到一个特定的、可命名的拒绝，因为“传输意外关闭”。这些失败现在以 JSON-RPC 错误的形式到达，并带有原因。
  • 无需编辑 JSON 即可关闭 UI 侦听器。 ui_enabled 控制环回 HTTP 端口，禁用它的唯一方法是手动编辑 config.json；它对 config list 不可见，并被 config set 拒绝。它和 ui_port 现在都是一流的配置键。由 @PsyTech-Rob 报道，他花了两次调试会话才找到了开关。

Codex、OpenCode 和配置文件修复

  • 重复安装不再永久破坏 Codex (@astandrik)。拥有的内联钩子分配被协调到规范块中，而不是被忽略并重新添加；外部钩子条目保持不变，真正不明确的 TOML 会被拒绝，而无需修改文件。
  • OpenCode 在 OpenCode 实际读取的文件中安装土地 (@iandol)。 更正 (2026-08-14)： 这只是一半正确，我们不应该直接声明它。 目标 是固定的 - 我们现在写入 opencode.json / opencode.jsonc 中已经存在的那个，而不是总是创建 OpenCode 忽略的 .json 文件。但在 Linux 和 Windows 上报告，v0.10.4 和 error: agent_config agent=OpenCode op=mcp_install 上的写入本身仍然失败。追踪于#1630。这是第二个正在运行的版本，我们在该版本中描述了此修复已完成；抱歉，也感谢那些一直说不是的记者。
  • 我们编写的孤立标记可以自行修复。 较早的安装可能会留下没有开启器的结束 # <<< 标记，此后每次安装都会导致 client 彻底失败。现在去除会去除杂散线。 “写入”仍然会拒绝不平衡——只有一个标记就没有可防御的区域可以替换。

查询正确性和平台支持

  • OPTIONAL MATCH 停止默默地删除行 (@SEPURI-SAI-KRISHNA)。一旦跃点缓冲区饱和，不匹配的行（正是 WHERE x IS NULL 存在的内容）就会被丢弃。不是崩溃，不是内存错误：结果悄然减少，没有任何迹象表明答案不完整。
  • FreeBSD 解析其自己的可执行路径 (@PR9000)，安装和所有权检查依赖于该路径，以及针对主要三个平台之外的平台的构建修复。

安全

发布管道现在在执行任何外部工具之前固定并验证其下载的外部工具，而不是在构建时对上游项目发布的任何内容进行trusting。验证涵盖作业可能运行的每个平台，来自单个固定参考。

由 Andrew Hundt 报道 (#1245)。

可靠性

子进程在繁忙的机器上幸存下来。 v0.10.3 开始重试生成，内核拒绝“再试一次”，但只持续了大约 30 毫秒——足以短暂下降，而不适合连续数百毫秒保持进程匮乏的机器，而这正是它发生的时间。现在，重试会呈指数级下降，大约半秒后就会放弃。一台真正耗尽的机器仍然会快速失败而不是挂起，而真正的错误——丢失二进制文件、拒绝权限——会像以前一样立即失败。

并且发布管道在发布公开之前不再发布其注册表项 - 该错误导致 v0.10.3 自己的注册表步骤失败，并针对其自己的资产出现 404 错误。

升级

  • 二进制安装： 从下面下载，或重新运行 install.sh / install.ps1。
  • **包管理器：**像往常一样通过它们进行更新 - cbm 现在将保留该二进制文件。
  • npm / PyPI： 像往常一样。
  • 无索引、缓存或配置迁移。
