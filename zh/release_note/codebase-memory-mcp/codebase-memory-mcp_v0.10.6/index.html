codebase-memory-mcp v0.10.6

这个项目是干啥的：给 AI 编程助手装的代码库记忆，一次调用就摸清整个项目的架构和调用关系并用图谱记牢。给想让 AI 快速看懂大项目的人用。

亮点

  • 索引性能回退已修复（#1669、#1654） — 0.10.x 的变慢问题消失了：跨文件注册表现在每个语料库构建一次而非每个文件一次（Java 在 elasticsearch 上 477 秒 → 86 秒），移除了三次与语料库规模成正比的扫描，另修复了悄悄丢边的 C# usage-edge bug（dotnet/runtime 上 1211 秒 → 450 秒，边数比 0.9.0 多 48%），并用按节点记忆化消除 2^n 的表达式类型重复求值（TypeScript 37 秒 → 约 24 秒）。还回退了 mimalloc arena-commit 默认值导致的 Linux OOM 回退；新增基于比值的 CI 复杂度防护套件（不看墙钟时间）和 CBM_PROFILE=1 逐阶段计时，防止任何阶段再次变成超线性。

  • 真实配置导致的安装失败已解决 — Hermes（#1631）：空流集合、第 0 列块序列、续行的双引号字符串，以及 LET'S GO 这类词中撇号，现在都能逐字节保留地安装。goose（#1673、#1675）：现在会输出必需的 name 字段，条目不再被静默丢弃，envs: {} 同级项也不再中断写入。OpenCode/带注解条目（#1630、#1582）：修复只替换 command 值，保留注释和客户端键，且属主判断对分隔符不敏感（C:\\... == C:/...）。Windows UTF-8 BOM（#1656）作为保留的前导处理，Codex 托管的 hook 对（#1633）就地调和并给出拒绝原因。

  • 自写入条目与 Windows DACL 就地修复 — cbm 自己写入的条目不再被卡成“外来”：任何旧版本的格式、或二进制被移到新路径的情况，都会就地修复，而真正外来的条目保持逐字节不变。Windows 上运行时目录的仅属主 DACL 现在只在状态确实错误时才重新打标（终结 #1601 中每天 11 条空操作“Security change”USN 记录，以及 #1620 中的原子发布重写窗口），并检测修复 v0.10.3 之前因不可读的 0 字节 worker 日志而留下的空 DACL 目录。（#1416、#1601、#1620）

  • 破坏性变更/迁移 — 无。未移除任何 API 名、flag 或配置格式，改动都是向后兼容的修复，升级时会自愈（goose 块、Codex v0.10.2 hooks）——无需手动迁移。小改动：CBM_RUNTIME_DIR 会在生成的 Codex 配置中传递（#1664），缺失末尾换行不再导致部分解析，update 不再指称不存在的安装器（#1653）。

  • 值得升级 — 对 0.9.x–0.10.5 的用户答案是肯定的：如果大型仓库索引变慢，或 install 拒绝过 Hermes、goose、OpenCode、Codex 或带 BOM 的配置，此版本正对症下药。没有索引负载、也没有受影响客户端配置的用户可以跳过。所有发布的二进制均通过 VirusTotal 清理并公布逐二进制 SHA-256 判定；这是实质修复版本，不是重新打标签或仅改元数据的改动。

代码库-内存-mcp v0.10.6

一个版本中有两个故事：0.10.x 索引速度减慢消失了，以及安装 v0.10.5 中幸存的故障已修复 - 包括您配置中的每个构造 发送给我们。如果从0.9.0开始cbm对你来说变慢了，或者install仍然拒绝你的爱马仕， goose、OpenCode 或 Codex 配置，这是要采用的版本。

索引回归程序 (#1669)

自 0.10.0 以来，索引大型存储库已从较慢变为无法使用 — java 更糟 6 倍， C# 2.6×、TypeScript 2×。原因不是一个错误而是一系列错误：每个文件的工作量都在扩展 与整个语料库。所有这些都是固定的，在同一主机上针对同一主机进行测量 语料库如报告：

  • Java 477 s → 86 s (elasticsearch)：跨文件解析重建了每个的注册表 语料库中的定义每个文件。现在它是一次性构建并共享的，每个文件都有一个 覆盖本地符号。
  • C# 1211 秒 → 450 秒（dotnet/运行时），现在比 0.9.0 多 48% 的边：三个 消除了语料库比例扫描，加上一个已悄然存在的导入上下文错误 抑制 C# 使用边缘 - 生成的一个 147 KB 的文件从 490 秒缩短到 6.8 秒。
  • TypeScript 37 s → ~24 s (microsoft/TypeScript)：表达式类型求值器 每个封闭替代项重新评估共享子表达式一次 — tsc 编译时为 2^n 传播链条。每个节点的备忘录使其对每个节点进行一次评估；病理档案 TS 一致性套件的时间从 20 秒下降到实际上为零。
  • Linux 内存爆炸已修复 (#1654)：v0.10.4 可能会 OOM 36 GB 机器索引树 v0.9.0 13 分钟内处理完毕。 mimalloc 的 Linux arena-commit 默认值已恢复。
  • 它保持固定：一个新的复杂性防护套件在每个平台和行程上在 CI 中运行 如果任何管道通道再次变为超线性，则在计数器ratios（从不挂起时间）上，并且 CBM_PROFILE=1 现在可以打印任何生产二进制文件的每遍计时。

安装：根据您的真实配置构建

Hermes（#1631，由 @iandol 和 Galaxy-VN 报道，根本原因是由 @rg6304）：四块普通YAML使install永久失效——空流 集合（plugins: []、tool_choice: {}），第 0 列的块序列，双引号 字符串以 \ 和词中撇号（角色中的 LET'S GO）继续 字符串打开了一个从未关闭的“引用”）。所有四个现已被接受；报价和 锚点仅是值开始处的指示器，与 * 修复中使用的规则相同 v0.10.4。两位记者的完整配置 — 每个 15 KB — 端到端安装 保留原始字节。

我们自己编写的条目再次被识别。 较旧的 cbm 版本编写了 command: 未引用；鹅块获得了所需的字段；然后您的条目被宣布为“外国” 永远。我们的密钥下的条目与任何先前版本所写的形状相匹配 - 或 它的命令是我们在移动路径上的二进制文件 - 已就地修复。真正的外国条目 仍然被拒绝字节未触及。

goose (#1673 + #1675)：扩展块现在带有 name field goose 的解析器 需要 — 在此之前，goose 默默地删除了该条目，并且“成功”安装 看不见的。同级中的 envs: {} 不再中止写入（社区修复 @pcristin — 模型贡献，按原样合并）。升级时修复旧块。 OpenCode / 带注释的 MCP 条目 (#1630、#1582)：当 client 将密钥添加到我们的条目时 （“启用”：true 和朋友），修复现在仅替换命令值 - 注释和 client 密钥逐字保存。并且所有权比较是分隔符不敏感的：一个条目 存储 C:\...\codebase-memory-mcp.exe 与安装程序的二进制文件相同 C:/.../codebase-memory-mcp.exe。 @gotspatel 发布的配置是破解的文件 这是经过四个版本的坚持之后的一个。

Windows 编写的带有 UTF-8 BOM 的配置 (#1656)：PowerShell 的 Set-Content 编写了一个 字节顺序标记，并且无论内容如何，对此类文件的每次 YAML 编辑都会失败 - 记者用一个26字节的文件证明了内容独立性，而这26字节就是他们的 23 字节控制加上 BOM。现在被视为序言：跳过 结构，写入时保留。

Codex（#1633，关闭来自#1580的@spam0115的残差）：钩子协调器接受 托管钩子对 v0.10.2 编写（包括 Windows CRLF+BOM 变体）并重写 就位；拒绝现在会说出他们的原因，而不是笼统地失败。

Windows：DACL 不再与你对抗

运行时目录的安全描述符在每个进程启动时重新标记， 是否有什么问题。第1601章 统计十一次无操作“安全改变”USN 一天内对单个文件进行记录； #1620 丢失的原子发布到重写窗口。 现在，仅当目录尚未位于确切的所有者专用目录中时，才会触发重新标记 状态 — 以及被 v0.10.3 之前的 DACL 机制损坏的目录（空 DACL 日志 @patxisan 发现的文件夹，这解释了一个月内无法读取的 0 字节工作日志 六份报告）均已检测并修复到位。 （＃1416，＃1601，＃1620）

还附带：CBM_RUNTIME_DIR 在生成的 Codex 配置中转发（#1664 — 重新定位的守护进程对于 Codex 生成的服务器是不可见的），缺少最后的换行符是没有 不再报告为部分解析，并且 update 不再命名不属于的安装程序 那里（#1653）。
