codebase-memory-mcp 0.7.0

小版本 发布时间2026年6月12日 来源DeusData/codebase-memory-mcp 英文原文

codebase-memory-mcp 0.7.0

变更流程图

亮点

  • 混合 LSP 现已默认开启 — 按文件、类型感知的解析会重写 CALLS 目标，覆盖六大语言族：Python、PHP、TypeScript/JavaScript/JSX/TSX、C#/.NET、C/C++/CUDA 和 Go。调用图准确性因此显著提升，据报告约 4% 的 TypeScript 调用和 14% 的 Go 调用被重新归属。

  • 大型代码库的严重性能回退已修复 — LSP 与提取遍历中的 O(n²) tree-sitter 子节点迭代被替换。试运行显示 microsoft/TypeScript 全量提取从 5,100 秒降到 50 秒，dotnet/roslyn 从崩溃变为 46 秒，Linux 全量提取 188 秒完成。大型仓库应强烈考虑升级。

  • 需要注意的行为变更 — CBM_MODE_ADVANCED 被移除，但 "mode":"advanced" 请求会静默回退到 full；这是保持兼容性的做法，因为 LSP 现在运行于 full、moderate 和 fast 三种模式。另外，search_graph 的默认最大返回数从 500,000 改为 200——依赖无上限结果集的调用方可能需要显式分页或调高上限。

  • 安全性与可靠性加固 — 修复包括 search_code 多词正则处理、sqlite_writer 索引单元格页面保护、GitHub Actions shell 注入、缓冲区溢出/OOM/NULL 语句处理、日志互斥锁/watcher/indexer 中的竞态，以及 ws 漏洞 GHSA-58qx-3vcg-4xpx。并发使用 SQLite 的用户还获得 CBM_SQLITE_MMAP_SIZE 和 PASSIVE 检查点。

  • 谁该升级 — 推荐给索引大型或类型丰富代码库的用户、把 MCP 服务暴露给不可信查询的人，以及 Windows/BSD 或 Pine Script 用户。升级二进制后重启 Claude Code，让 MCP 服务重新加载。小型、单用户、非上述目标的项目可以跳过，除非你需要这些安全修复。

📦 已存档的发布页面 — 该版本的二进制文件不再发布。获取最新版本。

v0.7.0 — 跨六种语言的混合 LSP、社区贡献、全平台验证

🧠 标题：混合 LSP

此版本是调用图不再是猜测的版本。

对于每种受支持的语言，我们现在提供混合 Light-Semantic-Pass LSP - 一个运行“内部”提取的每个文件、类型感知解析器。它跟踪作用域、推断表达式类型、跟踪导入、遍历继承，并在每个 CALLS 边缘上重写已解析的被调用者。简单的树木保护者通行证为您提供了结构图； LSP 通行证为您提供正确的被叫方。 六种语言现在受益 - 其中四种在此版本中首次获得了 LSP。

语言 LSP 的作用 标题
Python 范围绑定、表达式类型、方法分派、super()、装饰器、多重继承、TypedDict、匹配/大小写缩小、海象、理解元素类型、泛型和跨文件解析 100%在替补席上； 95% 真实实例属性解析

锐化 LSP（存在于 v0.6.1；此处大幅升级）

语言 锐化了什么
C / C++ / CUDA 第 2 层预构建的每种语言跨 LSP 注册表；模板返回类型替换；命名空间 + 类体步行者的复杂度为 O(n)
去 第 2 层 + 第 3 层元数据驱动的跨 LSP（完全跳过 AST 重新行走）；每个文件的步行者 O(n)；池化线程本地解析器

第 1/2/3 层架构（这是使其易于处理的部分）

LSP 工作确实非常昂贵——每个解析工作人员都会天真地为每个文件重新构建一个打字上下文。相反，它分三层运行：

  • 第 1 层 — cbm_extract_file 内的每个文件 LSP：范围、表达式类型、本地解析。
  • 第 2 层 - 预构建的每语言跨 LSP 注册表：从每个项目定义构建 一次 的共享只读基础，然后通过后备指针从每个文件覆盖链接起来。解决工人分享；整个注册表中没有每个文件的重新遍历。 （现已连接所有六种语言。）
  • 第 3 层 — 元数据驱动的跨 LSP (Go)：使用每个文件传递发出的 lsp_unresolved 元数据，并完全跳过跨文件 AST 重新遍历。

在宽文件上使用 O(n)

每个文件 LSP 步行器 - process_node、ast_sweep_shapes、apply_jsdoc_signatures、infer_implicit_returns、*_resolve_calls_in_node 以及七个提取端 DFS 步行器 - 使用 for (i=0; i<count; i++) ts_node_child(node, i) 习惯用法。树保姆中每次调用的时间复杂度为 O(i)，因此在宽根上的时间复杂度为 O(n²)。像 TypeScript 的 reallyLargeFile.ts（583k 行，几乎所有评论）这样的装置造成了灾难性的后果。 新的 cbm_lsp_collect_children O(n) 游标助手 + 用于提取 DFS 的共享 ts_nstack_push_children 现在适用于所有六个 LSP 和提取器。 来自试运行验证的数字：

回购 文件 LSP 覆盖 之前 → 之后

lsp_overrides 是“其被叫方 LSP 重新归因于比文本解析器推断的更精确目标的调用”。对于类型丰富的语言（C#、Go、TS、PHP），这需要数以万计的更正。

一路上修复了两个真正的错误

  • process_node 通过调用的参数计数对以 NULL 结尾的 param_types[] 进行索引；调用的参数多于函数声明的参数，读取超过终止符的参数 → 垃圾 CBMType* 的 deref → 崩溃。现在以 param_count 扫描为边界。
  • return_type_of 通过 cbm_type_tuple(NULL, …) 构建元组返回类型。多重返回签名现在通过 ctx->arena。

始终开启

CBM_MODE_ADVANCED 被删除。 LSP 分辨率在每种索引模式下运行（full、moderate、fast）——此时步行者的时间复杂度为 O(n)，质量（约 4% 的呼叫在 TS 上重新归因，约 14% 在 Go 上）值得每种模式中的延迟。 "mode":"advanced" 请求回退到 full（与旧的高级模式相同的行为，因此没有重大变化）。附带的好处是，由于 LSP 门控关闭的增量运行而默默引起的 104 个 test_incremental.c 故障现在已经消失了。

🔍 披露（发布准备透明度）

CI 绿化清理中的一些变化是判断性的，而不是纯粹的修复。对它们进行标记，以便审阅者可以进行事后猜测：

  1. LSP 基准（pylsp_bench_resolution_ratio、cslsp_bench_resolution_ratio） — 在 CBM_SKIP_PERF 后面进行模拟运行；在发布的 CI (skip_perf=false) 中，它们使用 ASan 感知的时间预算（在消毒剂下×10）运行，并在断言之前释放结果，这样任何未来的预算失误都不会泄漏。 调用分辨率比质量也由始终在 CI 中运行的非基准 test_py_lsp 和 test_cs_lsp 套件保证。
  2. 安全审核允许列表扩展（每项均已审核；内联记录）：
    • URL 允许列表：https://www.sqlite.org/c3ref/c_checkpoint_full.html — store.c 注释中的文档引用，而不是网络调用。
    • mcp.c 文件读取阈值提高了 12 → 13。第 13 次读取是更新检查 HTTP 响应 + HTTP 请求正文 — 两者都有界；预先存在于搜索/ADR/Windows 支持提交中。
    • fopen("w") 允许列表扩展为包括 src/foundation/diagnostics.c（原子 .tmp + 重命名指标转储）。
  3. CBM_MODE_ADVANCED 已删除。 "mode":"advanced" 请求现在回退到 full（始终运行 LSP）——行为相同，因此现有调用者不受影响。

⬆️ 升级

通过 "mode":"advanced" 的现有呼叫者继续工作（静默回退到 full）。升级 ~/.local/bin/codebase-memory-mcp 中的二进制文件后，重新启动 Claude Code，以便 MCP 服务器获取新的二进制文件。
