变更流程图

亮点

  • 值得升级吗？ — 这是安装与升级修复版本，不是能力变更：没有新功能，并明确“无索引、缓存或配置迁移”。已经装好并能在 v0.10.0/v0.10.1 上正常运行的客户端可以跳过。如果你被安装器/更新器拒绝，或看到 MCP 服务假死，就升级——这里每个修复都来自版本发布 24 小时内提交的用户报告。
  • 恢复 npx / 临时安装 — npx codebase-memory-mcp 会稳定地产生一个什么都不回答的服务（客户端等 30 秒、stdout 零字节，表现为 -32000: Connection closed）。守护进程的二进制镜像检查把真正的指纹不匹配（篡改场景）和“镜像根本无法检查”（对临时 npx 缓存路径总是如此）混为一谈。现在无法检查的情况被放行，因为前面的握手已经证明 semver、构建指纹以及协议/存储/特性 ABI；真正的不匹配仍被硬性拒绝，且放行会记日志，让这道较弱的检查可见。此外，连不上守护进程的客户端现在一律返回点明原因的 JSON-RPC 错误，而不再静默退出——如果你通过任何临时或基于缓存的 runner 启动 cbm，这点都很重要，不只是 npx。修复归功于 @wassolles。
  • 恢复普通 Linux 家目录 / WSL2 安装 — 当 ~ 和 ~/.local 组可写时（WSL2 上是 0775、常见发行版骨架、共享主组），install.sh 会失败并报 error: failed to stage install candidate: activation transaction I/O failed。原来要求安装目录及其所有上级目录都没有组写位的规则，现在改为对组可写的上级目录警告并接受；全局可写的上级目录仍被拒绝（防止安装途中路径被换），安装目录本身保持仅属主私有，使二进制在校验与启动之间无法被替换。拒绝信息现在会指出目录、其模式和拒绝规则——对共享组或 WSL2 用户相关，其他环境无影响。由 @AmirF194 定位根因，@shochdoerfer 和 @iandol 确认。
  • 0.9.x 更新恢复；变体选择器移除 — v0.10.0 合并为每平台一个归档、始终内嵌图 UI，但 update 仍提示选择 “ui”/“standard”，其中 “ui” 只会 404，而 “standard” 其实是 UI 版本。选择器及其 flag 被移除（对传这些 flag 的脚本是破坏性的接口变更）。由于已发布的二进制无法回溯打补丁，现在每个归档还会发布 ui-* 副本，让旧的 0.9.x 更新器请求旧名字、拿到完全相同的字节并顺利完成，无需用户操作。如果你的 0.9.x 更新已经失败，重新运行 install.sh / install.ps1 是最快路径。由 @iandol 报告。
  • macOS 诊断清理；安全部分仅供取证 — install.sh 不再打印误导性的 No such xattr: com.apple.quarantine 行，真正被拦的安装现在会指向 codebase-memory-mcp daemon status 以列出占用它的进程。附加的 Security Verification 块不改变任何运行时行为：它公布 8 个归档的 VirusTotal 关联和 SHA-256 来源信息（13/14 个提取对象干净，唯一一个 Microsoft !ml 检出被声明为误报并附验证步骤）。对供应链审计有用，对升级决策可忽略。由 @listepo 报告。

代码库内存-mcp v0.10.2

安装和升级版本。如果 v0.10.0 或 v0.10.1 拒绝安装、拒绝更新，或者您的 MCP client 显示服务器未连接任何内容 — 这就是修复方法，所有这些故障都来自过去 24 小时内提交的用户报告。

所有这些背后的模式是：原则上正确的门拒绝普通的、合法的设置，然后没有说明原因。下面的每一项都保留了重要的保护，删除了拒绝真实用户的部分，现在准确地指出了它拒绝的内容以及如何继续。

npx（以及每个临时安装路径）再次工作

通过 npx codebase-memory-mcp 运行 cbm 产生的服务器没有任何响应：client 等待 30 秒并退出，并在标准输出上显示零字节，该代理显示为 -32000: Connection closed。每个 npx 调用都确定性地达到了这一点。

该守护进程验证连接的 client 的二进制映像，并将两种截然不同的结果视为一次失败：“此映像的哈希值与我的不同”（存在检查的篡改情况）和 “根本无法检查此映像” — 这是临时 npx 缓存路径始终产生的结果。现在承认第二个：在已经证明语义版本、构建指纹和协议/存储/功能 ABI 之前的握手，因此拒绝除此之外的交易是用真正的兼容性证明换取不可用的证明。真正的指纹不匹配仍然会被拒绝，很难，并且承认会被大声记录下来，因此较弱的检查永远不会被发现。

单独且无条件地：现在无法到达守护进程的 client 在 JSON-RPC 中如此说，指出原因，而不是默默退出。感谢**@wassolles**，他带来了复制品、已读过的入场路径以及三个候选修复——我们发送的那个是他们的。

安装到普通的 Linux 家庭中又可以工作了

install.sh 失败并出现 error: failed to stage install candidate: activation transaction I/O failed — 这条消息让人们寻找磁盘错误和文件系统类型，以获取实际上的权限策略：安装程序不需要在安装目录 * 及其上方的每个父目录 * 上设置组写入位。 WSL2 在 0775 发布 ~ 和 ~/.local，几个发行版骨架和任何使用共享主要组的站点也是如此。

世界可写的父级仍然被拒绝——任何本地用户都可以在安装过程中交换路径组件。现在，可组写的父级会受到警告并被接受，而安装目录本身严格保持所有者私有：这是二进制文件所在的位置，并且组写在那里将让另一个帐户在验证和启动之间替换可执行文件。拒绝现在指定目录、其模式以及拒绝的规则。

由 @AmirF194 在干净的容器中引起的根源，直至精确的谓词和行；由 @shochdoerfer 和 @iandol 独立确认。

从 0.9.x 更新再次有效

v0.10.0 将每个平台整合为一个存档，始终嵌入图形 UI，但 update 仍然询问您想要哪种变体 - 其中“ui”只能 404，而“标准”悄悄地“是”UI 构建。选择器及其标志消失了。 已在现场安装的二进制文件无法追溯修复，因此版本现在还发布每个存档的以 ui-* 命名的副本。每个要求旧名称的 0.9.x 更新程序都会获得相同的字节并正常完成，无需您执行任何操作。由 @iandol 报道。

macOS 安装诊断

install.sh 不再打印 No such xattr: com.apple.quarantine — 一条无害的行（curl 下载的存档只是不带有隔离属性），它被误认为是不相关故障的原因，甚至成为错误报告的标题。当安装确实被正在运行的会话阻止时，错误现在指向 codebase-memory-mcp daemon status 以列出实际持有它的进程，而不是断言会话存在并让您找到它们。由 @listepo 报道。

升级

  • 二进制安装： 从下面下载，或重新运行 install.sh / install.ps1 — 重新运行安装程序就是更新。
  • npm / PyPI： 像往常一样通过包管理器更新。
  • 来自 0.9.x： 从此版本开始，旧更新程序再次运行；如果您已经失败，重新运行安装程序是最快的路径。
  • 无索引、缓存或配置迁移。
