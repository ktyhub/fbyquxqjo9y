不稳定（API-不稳定） 更新了第三方 C++/CUDA 扩展的稳定 libtorch ABI 对称内存可轻松编程多 GPU 内核 能够在 torch.compile 中任意切换错误或在图形中断时恢复 扩展了轮子变体支持，包括 ROCm、XPU 和 CUDA 13 Intel GPU 上的 FlexAttention 支持 X86 CPU上基于FlexAttention的Flash解码优化 ARM 平台改进和优化 在所有支持的 CUDA 版本上启用 Linux aarch64 二进制轮构建 有关这些突出功能的更多详细信息，您可以查看[发布博文](https://pytorch.org/blog/pytorch-2-9/)。以下是此版本的完整 release note。 # 向后不兼容的更改 ## 最低支持的 Python 版本现在是 3.10 (#162310) PyTorch 2.9.0 所需的 Python 最低版本是 3.10。我们还提供 3.14 和 3.14t 作为此版本的预览版。 ## 当自定义运算符的输出与输入共享存储时未定义的行为 这是一个提醒，PyTorch 自定义运算符的输出（使用 `torch.library` 或 `TORCH_LIBRARY` API 注册）不允许返回与输入张量共享存储的张量。违反此条件会导致未定义的行为：有时结果是正确的，有时结果是垃圾。 在 [#163227](https://github.com/pytorch/pytorch/pull/163227) 之后，违反此条件且之前在 `torch.compile` 下返回正确结果的自定义运算符现在可能会在 `torch.compile` 下默默返回错误结果。因为这正在改变未定义行为的行为，所以我们不认为这是一个错误，但我们仍然在本节中将其记录为“潜在的意外行为更改”。 这是[`torch.library.opcheck`](https://docs.pytorch.org/docs/stable/library.html#testing-custom-ops)检查的条件之一，并在[自定义操作员手册](https://docs.google.com/document/d/1_W62p8WJOQQUzPsJYa7s701JXt0qf2OfLub2sbkHOaU/edit?tab=t.0#bookmark=id.4c0um7xkba6e)中提到 ### 更多细节 PyTorch 自定义运算符的输出不允许返回与输入张量共享存储的张量 例如，以下两个自定义运算符不是有效的自定义运算符： ```py @torch.library.custom_op("mylib::foo", mutates_args=()) def foo(x: torch.Tensor) -> torch.Tensor: # the result of `foo` must not directly be an input to foo. return x

@torch.library.custom_op(“mylib::bar”, mutates_args=()) def bar(x: torch.Tensor) -> torch.Tensor: # the result of bar must not be a view of an input of bar return x.view(-1)

最简单的解决方法是在输出中添加一个额外的 `.clone()`：
```py
@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

遇到这种情况的常见方法是用户想要创建一个自定义运算符，该运算符有时会就地改变输入，有时会返回一个新的张量，如下例所示。

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

这种动态不受支持并导致未定义的行为。解决方法是将自定义运算符拆分为两个自定义运算符，一个始终就地改变输入，另一个始终返回新的张量。

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

构建 MacOS-14+ 的金属内核并删除所有 MacOS-14 之前的特定逻辑，需要 MacOS-14+ 继续前进（#159733，#159912）

PyTorch MPS 仅在 MacOS-14 或更高版本上受支持。如果您需要在 MacOS Ventura 上使用 MPS，请避免更新到 Python-3.9 或更高版本

升级到 DLPack 1.0 (#145000)

此升级与 DLPack 版本进行了相同的 BC 破坏性更改。 torch.utils.dlpack 中的对象已更新以反映这些更改，例如 DLDeviceType。 有关具体更改以及如何更新代码的详细信息，请参阅 PR。

在 torch.cat 中引发适当的错误 (#158249)

torch.cat 现在在适当的情况下提高 ValueError、IndexError 或 TypeError，而不是通用的 RuntimeError。如果您的代码捕获了这些错误，您可以进行更新以捕获新的错误类型。

ONNX 导出器默认为 dynamo=True (#159646、#162726)

以前，如果未提供参数，torch.onnx.export(...) 使用旧版 TorchScript 导出器。 ONNX 导出器现在默认使用较新的 torch.export.export 管道 (dynamo=True)。此更改提高了图形保真度和面向未来的导出，但可能会暴露以前被掩盖或以不同方式处理的图形捕获错误。 以前在火炬 2.8.0 中：

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

现在在火炬 2.9.0 中：

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

建议：首先尝试新的默认值；仅当遇到阻塞问题并向上游报告时才回退。 长期解决方案：修复根本原因，而不是依赖后备或 TorchScript 导出器。

默认情况下，在导出中关闭运行时断言，以支持形状保护功能（#160111、#161178、#161794）

要启用运行时断言，请使用 export(..., prefer_deferred_runtime_asserts_over_guards=True)。还杀死 allow_complex_guards_as_runtime_asserts 标志，将其合并到前一个选项中。 此外，exported_program.module() 将生成对 _guards_fn 子模块的调用，该子模块将对输入运行额外的检查。不希望出现此行为的用户可以在图中删除此调用，或者执行 exported_program.module(check_guards=False) 以避免生成。

在 ONNX 中将默认 opset 设置为 20 (#158802)

Opset 20 支持更新的运算符定义。如果您的工具或下游运行时仅支持 opset 18，请明确固定它。对于最新的 ONNX 运算符，您可以尝试使用 opset 23。 以前在火炬 2.8.0 中：

# opset_version=18
torch.onnx.export(...)

现在在火炬 2.9.0 中：

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

将 draft_export 放入导出器 API (#161454, #162225)

从默认导出器路径中删除隐式草稿跟踪，实现更清晰的行为和更快的故障。 昂贵的 torch.export.draft_export 诊断路径不再自动调用（在大型型号上可能需要几个小时）。您仍然可以选择进行深度诊断： 以前在火炬 2.8.0 中：

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#
# Inside export_to_onnx.py:
#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

现在在火炬 2.9.0 中：

# To trigger torch.export.draft_export once
# torch.export.export strict=False/True both
# fail:

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

删除 torch.onnx.dynamo_export 和 onnxrt torch 编译后端 (#158130, #158258)

torch.onnx.dynamo_export 已删除。请改用torch.onnx.export。 不再支持实验性 ONNX 运行时编译后端 (torch.compile(backend="onnxrt"))。

删除 torch.onnx.enable_fake_mode (#161222)

dynamo=True 模式默认使用 FakeTensor，这样可以节省内存。

基于 TorchScript 的导出器的一些面向公众的 ONNX 实用程序 API 现在是私有的 (#161323)

torch.onnx.verification 中已弃用的成员已被删除。以前的私有 torch.onnx.symbolic_opsets* 功能将不再可用。如果您需要访问任何私有函数以与基于 TorchScript 的导出器兼容，请考虑复制源代码。

删除 torch.onnx.symbolic_caffe2 (#157102)

ONNX 导出器对 caffe2 的支持已结束并被删除。

删除会减慢构建速度的 /d2implyavx512upperregs 标志 (#159431)

针对 Windows VS2022 版本重新引入 AVX512 优化，可能会导致特定版本的 VS2022 出现问题，请参阅#145702

将 ScalarType 添加到垫片转换和 stable::Tensor.scalar_type (#160557)

以前，用户扩展只能抽象地传递显示为 int32_ts 的混淆数据类型。现在，用户可以放心地在主要标量类型的扩展中使用 torch::headeronly::ScalarType。此 PR 通过 shim 添加翻译层来实现 ABI 稳定性，这样即使 ScalarType 枚举值将来发生变化，用户扩展也不必担心。 此更改增加了对用户扩展的 ScalarType 支持，并且仅在扩展检索上述 Tensor dtype 并将其传递到的用例中对不受欢迎的 dtypes 进行了狭小的 BC 破坏：quint*s、qint*s、Bits*、dummy_uint*s、dummy_int*s、Float8_e8m0fnu 和 Float4_e2m1fn_x2 aoti_torch_call_dispatcher。

弃用

弃用 torch.utils.data.DataLoader 中的 pin_memory_device 参数 (#158323)

我们将启用 pin_memory 的功能移回 BaseDataLoaderIter 内部。这是 StatefulDataloader 所必需的，它直接利用 BaseDataLoaderIter 而不是 Dataloader 类 init

弃用 torch.export.export_for_training API，转而使用等效的 torch.export.export API (#158203)

torch.export.export_for_training 存在是因为我们无法将导出的内部用法迁移到最终的 IR。现在我们已经完成了迁移，我们弃用并删除了这个 API。
