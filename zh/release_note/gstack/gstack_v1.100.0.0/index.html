gstack v1.100.0.0

gstack v1.100.0.0

这个项目是干啥的：把 Claude Code 变成一支虚拟开发团队的配置集，内置 CEO、设计、审查、测试、发版等角色，给想单枪匹马做大项目的开发者和小团队用。

变更架构图

亮点

  • 安全：仅涉及依赖的安全公告 — hono 被固定到 4.13.16，修复了 4.13.13 中的五条安全公告（GHSA-3gg2-335m-rxc6、GHSA-46wx-v44x-9hh2、GHSA-4h7h-rv7c-7m2v、GHSA-4m76-xfj5-7975、GHSA-h7mg-cq63-vhpq）。它只通过开发和测试工具进入 gstack，gstack 自身代码从不使用它，因此这些公告在正常运行中并不可达。贡献者应运行 bun install；这属于纵深防御，而非应急的运行时安全升级。

  • 并发与 CI 闸门 — 在 Ubuntu 26.04 和当前 ubuntu-latest 上，shell 锁现在只允许一个持有者，防止并发更新挪动同一份 checkout，或并发的 gstack-config set 调用丢失键。gstack-pr-wait、gstack-ci-gate 和稳定版发布现在把任务重跑缺失、工作流启动前就失败、提交状态失败都判为红灯。Ubuntu 26.04 以及 CI/发布用户应升级。Ubicloud 用户还获得 vCPU 上限强制、ubi-runner.sh room，以及带前缀安全的过期 VM 清理。

  • /ship：破坏性的 PR/合并行为改变及可靠性 — PR 正文在折叠区之前最多显示三行纯文本，且每次 gstack-ship-queue land 合并都变成一条以 PR 标题命名的提交。需要旧呈现方式的仓库可配置 .gstack/plain-titles.json：body_since 让较旧的 PR 只作为警告，该文件也可扩展或替换默认的内部词表。评审轮次现在按 PR 计数——最多两轮——合并版本总会得到完整评审，被作废的评审不计入，每次 /ship 运行都保留在 PR 历史中。Linux 测试扇出修复了 E2BIG，同时仍算作一次运行；--step-timeout <seconds> 控制默认的一小时预算，耗尽时打印 PREGATE: time limit hit。

  • /autoplan：评审人的质疑变成所有者决策 — 对范围、顺序、方向、成本或打包方式的质疑，现在呈现为推荐评审人改法的选项，而不再默认”保持你的方向”。冲突的范围/顺序质疑会把计划送回评审。计划可选择在 ### Owner's words 下引用所有者原话，应用计划可用 ### Day one 表格开头；引用只针对本仓库的审批记录做校验。修正了审批语义，/autoplan 用户应升级。

  • 移除：可选的编辑后测试检查 — Stop hook 不再检查 check_after_last_edit；/verify 改用通俗语言询问是否运行该测试。上游测得该 hook 对评分的影响仅 -0.5 到 +2 分，处于噪声范围内。自定义 skill 契约保留其他检查，但该项会被跳过并打印 SKILL_CONTRACT_SKIPPED，直到被移除。如果你此前依赖该 hook 而非 /verify，请更新工作流。只消费文档、不跑 /ship、/autoplan、Ubuntu/CI 自动化或 Ubicloud 的用户可以延后；这些工作流的活跃用户应升级。

gstack v1.100.0.0

此版本修复了依赖中的五条安全公告，让 gstack 的 shell 锁在 Ubuntu 26.04 上安全可用，并改变了 /ship 撰写和评审 pull request 的方式。还移除了一项可选的 hook 检查。

gstack v1.100.0.0

此版本修复了依赖项中的五个安全建议，使 gstack 的 shell 锁在 Ubuntu 26.04 上安全，并更改了 /ship 写入和审查拉取请求的方式。删除了一项可选的挂钩检查。

修复

  • 安全性：hono 固定到 4.13.16，它修复了 5 个建议（GHSA-3gg2-335m-rxc6、GHSA-46wx-v44x-9hh2、GHSA-4h7h-rv7c-7m2v、GHSA-4m76-xfj5-7975、GHSA-h7mg-cq63-vhpq） 4.13.13。 hono仅通过其开发和测试工具才能到达gstack，而gstack自己的代码从不使用它，因此这五个工具都无法到达；贡献者在他们的下一个 bun install 上得到修复。 (#4408)
  • gstack 的 shell 锁在 Ubuntu 26.04 和 GitHub 的当前 ubuntu-latest 上再次允许一个持有者，其 Rust mkdir 报告成功，即使另一个进程首先创建了该目录。在此之前，两个更新可能会同时移动一个结账，或者两个 gstack-config set 调用可能会丢失彼此的密钥。 (#4262)
  • 当检查模型在其结果行后写入文本时，/ship 的文档检查不再浪费其两次尝试之一；它被要求一次，免费，单独重新发送结果。 (#4285)
  • 一旦该文档检查中的任何结果行显示“已阻止”，则后面的行和重新发送的答案都不能将其变为通过。仍然存在一个差距：在通过结果行之后仅以纯文本编写的阻止程序仍然取决于报告它的重新发送的答案。 (#4434)
  • 您编写的技能，其合同中仍列出 check_after_last_edit ，保留其其他检查。可选的 Stop 挂钩仅跳过该项目并打印 SKILL_CONTRACT_SKIPPED 行命名该文件，直到您将其删除；未列出任何其他内容的合同将被视为无效。 (#4439)
  • 当先前的检查尝试失败并且重新运行未创建任何作业时，或者当工作流在开始任何作业之前失败时，gstack-pr-wait、gstack-ci-gate 和稳定版本不再调用绿色提交。失败的提交状态也算为红色。 (#4257)
  • /ship 提供合并完整评论的拉取请求版本。一旦分支删除的行随其基础发生变化，早期的审查就不再有效，并且 PR 机构的审查历史记录会保留每个 /ship 运行而不是仅保留最后一个。 (#4365)
  • 在具有数千个单元测试文件的项目中在 Linux 上运行任何测试之前，/ship 的测试步骤不再因 E2BIG: argument list too long 失败；这些文件被分割到多个运行程序进程中并计为一次运行。 (#4426)
  • /ship 的远程测试命令不再将每个选定的测试文件放在一个命令行上，Linux 拒绝超过 128 KiB。 (#4429)
  • /autoplan 的批准页面在两个审阅者对其提出质疑并且不同意其是范围还是订单更改时，将计划发回以供审阅，要求没有 ### Owner's words 部分的计划在这种情况下也确认其方向，并仅根据此存储库的批准记录检查所有者报价。 (#4441)
  • 当检查使用行号（例如 notes.md:8 或 notes.md:8:12）命名文件时，/ship 接受文档修复。 (#4437)
  • 一起启动的 Ubicloud 运行不能再超过项目的 vCPU 限制，新的 ubi-runner.sh room 命令会说明还可以容纳多少个虚拟机，并且 ID 共享前缀的两个所有者不再删除彼此过期的虚拟机。 (#4430)
  • 当 gstack 的夜间 Windows 测试运行失败或未完成时，每日稳定版本不再停止。 (#4400)
  • 每晚 Windows 测试运行再次在其时间限制内完成，分为八个具有最新计时的分片。 (#4409)
  • 现在，当拉取请求仅更改 bin/gstack-lock.sh 时，Windows 设置测试就会运行。 (#4433)
  • 当 zsh 在不带引号的 echo ==== 处停止时，/review 测试覆盖率评估不再使读取源文件的运行失败。 (#4364)
  • docs/skills.md 和 docs/review-policy.md 中的十六个文档链接再次到达其部分。由@Davmunrey 贡献。 (#4394)
  • 自述文件链接了两个新指南，安装和卸载文档正确计数和命名安装程序的挂钩。 (#4403)
  • docs/releases.md 表示稳定版本将失败的提交状态视为红色，并将待处理的状态视为仍在运行。 (#4436)

变化

  • /ship 打开的拉取请求在折叠部分之前最多显示三行，并且每次与 gstack-ship-queue land 的合并都会作为一个以 PR 标题为标题的提交。存储库的 .gstack/plain-titles.json 现在可以设置 body_since（较旧的 PR 只会收到警告）并扩展或替换 gstack 的默认内部单词列表。请参阅 docs/writing-prs.md。 (#4438)
  • /ship 计算每个拉取请求而不是每次运行的审核轮数，因此多次发布的 PR 仍然最多获得两轮审核，并且合并的版本始终获得完整审核。 (#4360)
  • /autoplan 的批准页面显示审阅者对计划的范围、顺序、方向、成本或包装的挑战，作为所有者的选择，建议审阅者进行更改，而不是默认“保持你的方向”。计划可以在 ### Owner's words 下引用其所有者，应用程序计划可以使用 ### Day one 表打开。 (#4431)
  • Claude Code 的技能列表现在说明了何时使用每个 gstack 技能，因此诸如“查看我的更改”之类的请求会加载/查看。每个会话列表会增加约 840 个令牌。 (#4387)
  • /ship 的测试步骤在超时时打印 PREGATE: time limit hit，并且 --step-timeout <seconds> 设置其预算（默认一小时）。 (#4429)
  • 现在，每项技能都告诉特工询问一次问题，并在移交之前打开并清理每个文件。 (#4383)
  • 现在，每一项技能都告诉代理永远不要打印整个环境、git 配置或进程列表，并通过一个 gstack-pr-wait 调用而不是轮询循环来等待 CI。 (#4382)
  • gstack 代理以三行打开每个状态报告：Failed or skipped:、Unverified: 和 Also changed:，并将报告控制在 250 个字以内。 (#4273)
  • /captain 的文档将 Failed or skipped: 和 Also changed: 行命名为 Failed or skipped: 和 Also changed: 行，并表示在后续行动中要求提供缺失的行，这绝不是拒绝报告的理由。 (#4432)
  • /eval-plan 检查过去留给判断的四件事：预注册的决定和评分部分、法官对手写标签的同意以及结果可能产生误导的三种常见方式。 (#4384)
  • gstack-runaway 报告线程的冷唤醒和空唤醒的成本，而不仅仅是有多少个唤醒，scan --wakes 列出每个唤醒。 (#4385)
  • 船舶政策指南解释了如何将任何拉取请求与 gstack-ship-queue land 合并，包括在具有一名维护者的存储库中，以及固定的 gh pr merge 后备。 (#4377)
  • 两个新指南：在其他人的存储库中进行修复，并与真人一起运行游戏测试。 (#4380)
  • ETHOS.md 在其“解释数字”部分的结尾提供了一个包含三项内容的检查清单。 (#4381)
  • docs/ship-policy.md 记录了 .gstack/approval-classes.json 架构、gstack-approval-classes 命令以及如何引用所有者的批准。 (#4355)

移除

  • 可选的 Stop 挂钩不再检查上次编辑后是否运行了测试； /verify 则用简单的语言来要求这一点。加载 /verify 后，Claude Opus 5.5 和 GPT-6.1 Sol 已经在 96% 和 89% 的运行中做到了这一点，并且检查将结果移动了 -0.5 到 +2 点，在噪音范围内。 (#4428)
