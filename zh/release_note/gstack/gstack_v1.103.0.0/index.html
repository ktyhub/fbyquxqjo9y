gstack v1.103.0.0

变更流程图

亮点

  • 破坏性变更：/verify 更名 — gstack 的构建检查 skill 现在叫 /build-check；只做检查用 /build-check quick。把 disabled_skills: verify 改成 disabled_skills: build-check，否则该 skill 会保持禁用。verify_before_commit 设置已退役并被忽略，但现有配置仍然有效。你自己的 verify skill 会被保留，而 Claude Code 内置的 /verify 不再被劫持。
  • 更强的安全检查 — /careful 和 /guard 现在能捕获对 main 的混淆强推，以及进入系统目录后或 /dev 下的危险删除，且对带引号参数误报更少。密钥检测现在处理 Rust 绑定、异常文件名和 Gemini AQ. 密钥；gstack-ship-queue land 还会在一次性 clone 中运行检查并禁用 hooks。全新安装还会移除 benchmark 提示词，不过旧提交仍可通过完整 git 历史访问。
  • 更可靠的 /ship 完成 — 此版本修复了大量评审卡住、审计过期、CI 闸门和锁恢复失败，包括堆叠分支、合并树的 CI、精确基础校验、可复用工作流和恢复的运行。CI 证据现在被更安全地复用，而非强制无谓重跑。如果 /ship 一直卡住 PR 或留下可恢复的锁，升级值得。
  • 评审与工作流改进 — 已对照固定上游版本验证的 vendored 文件可被排除；TypeScript NodeNext 和 Rails 测试映射改进；评审规划通过 GSTACK_REVIEW_CONSUMER_SCAN_CAP 和 GSTACK_REVIEW_PLAN_TIMEOUT_MS 支持超大仓库。/build-check 现在跨 worktree 信任仓库检查，有益于新 worktree 的 agent 会话。
  • 升级建议 — 推荐给使用 /ship、评审自动化、/careful 或 /guard、Gemini 密钥或基于 worktree 工作流的人。普通用户可以跳过这个密集版本，除非依赖更名后的 /verify 命令；没有证据表明这是重新打标签、仅元数据或空转发布。

gstack v1.103.0.0

此版本堵上了 gstack 两处安全检查和合并工具中的缺口，修复了导致 PR 无法完成的 /ship 失败，并将 /verify 更名为 /build-check，让 Claude Code 自带的 /verify 重新可用。用 /gstack-upgrade 升级。

gstack v1.103.0.0

此版本弥补了 gstack 的两个安全检查及其合并工具中的空白，修复了阻止拉取请求完成的 /ship 故障，并将 /verify 重命名为 /build-check，以便 Claude Code 自己的 /verify 再次工作。使用 /gstack-upgrade 升级。

需要采取的行动：/verify 现在是 /build-check

  • /verify 现在是 /build-check，因此输入 /verify 会再次打开 Claude Code 的内置 /verify。使用 /build-check 进行 gstack 的构建和检查循环，使用 /build-check quick 进行仅检查传递。 (#4714)
  • 如果您使用 disabled_skills: verify 关闭了该技能，请将该条目更改为 build-check。在此之前，gstack 将 verify 读取为 build-check，因此该技能在升级后会保持关闭状态。 (#4719)
  • gstack 不再在每次提交之前自行运行检查过程，因此 verify_before_commit 设置已停用。设置它会打印一条注释并且不会改变任何内容，并且仍然包含它的配置文件继续工作。 (#4714)
  • 有关验证更改的提示现在转到 Claude Code 自己的技能：gstack 的提示路由器和 /build-check 的描述不再声明它们。 (#4719)
  • 升级删除了 gstack 的旧 verify 技能条目（以及其他主机上或 --prefix 上的 gstack-verify），但永远不会删除您自己的 verify 技能。 (#4714)

安全

  • /careful 和 /guard 后面的破坏性命令检查现在会阻止强制推送到缩写 --no-dry-run、实际上是推送选项值的 -n 或带有数字的标志组 (-f4) 后面的主隐藏，并在 cd 之后相对删除到系统文件夹或删除 /dev 下的设备之前询问。 (#4604)
  • 相同的检查不再询问安全的未引用的引用路径，或者 gh issue 或 gh pr 命令的引用标题或正文。 (#4604)
  • gstack-ship-queue land 现在在一次性克隆中运行存储库的合并树检查，并且如果检查更改了 git 或 gh 配置、后续 git 和 gh 调用将使用的挂钩或二进制文件，则拒绝继续。它执行的每个 git 调用都在关闭钩子的情况下运行。 (#4649)
  • 秘密检查现在将密钥标记为 Rust let、const 和 static 绑定，并停止标记 Rust 类型注释和匹配臂。 (#4675)
  • 秘密检查现在读取名称包含空格、重音符号或其他字符 git 引号的文件； src/clé.rs中的一把钥匙曾经可以通过。 (#4701)
  • gstack 的秘密检查和浏览的 cookie 屏蔽可识别 Google AI Studio 现在发布的 Gemini 密钥，该密钥以 AQ. 开头。 (#4684)
  • 新的 gstack 安装不再包含从真实 SWE-rebench 基准测试任务复制的 63 个提示：路由器测试使用合成提示，如果基准任务 ID 再次出现，则测试失败。较早的提交仍然保留提示，因此具有完整 git 历史记录的安装仍然可以通过 git log 到达它们。 (#4642)
  • 对安全代码的审查发现，仅命名文件永远不会自动关闭，因此其位置无法到达公共拉取请求主体。 (#4700)

修复 /ship 和合并

  • 两轮限制后经批准的额外审核检查可使用一次；第二次索赔被 GRANT_SPENT 拒绝。 (#4722)
  • /ship’s finish 不再报告文档审核过时的文件，该文件经过干净的后续检查读取后没有任何变化。 (#4722)
  • 在拉取请求的第二轮审查后，所有者批准再进行一次检查现在可以让 /ship 完成，无论哪个命令记录了它。 (#4717)
  • 陈旧测试值检查不再标记共享已更改文件名的不同文件的测试；仅当测试的其中一个导入解析为该文件时，该测试才有效。 (#4723)
  • 堆叠在另一个分支上的分支上的 /ship 可以从绿色 CI 运行中清除其远程测试门。 (#4689)
  • /ship 的最终 CI 检查接受绿色运行，当 main 没有更改任何行或它们旁边的行时，测试您的分支合并到较新的 main 上，因此繁忙的存储库停止重新运行 CI。 (#4728)
  • 崩溃的 gstack-ship-queue land --pin 不再阻塞以后的每次合并：其锁在最后一步后 90 分钟到期，进程消失的锁将被接管。 (#4712)
  • 停止或终止的 /ship 运行不再阻止下一个 /ship，并且新的 gstack-ship-run 命令显示运行的状态并结束停止工作的运行。 (#4654)
  • review_exclude_paths 列表破坏策略架构的基础分支不再停止每个 /ship：审查涵盖每个文件并打印警告，因此修复拉取请求可以落地。 (#4637)
  • 跳过或中立的 CI 运行不再阻止在同一提交上重用传递运行。 （＃4695，＃4713）
  • 仅通过可重用工作流程运行的 CI 作业现在仅根据测试您的确切提交的调用者运行进行计数。 (#4713)
  • 本地测试门重用在您的确切代码上运行的每个绿色 CI，而不仅仅是它检查的第一个。 (#4671)
  • /ship 不再接受针对不同基础分支的测试门记录。 (#4706)
  • gstack-ship-queue ready 根据其目标分支（而不是存储库的默认分支）检查拉取请求。 (#4663)
  • gstack-ship-queue ready 一次性获取丢失的拉取请求头，打印进度并在 60 秒后停止，而不是沉默几分钟。 (#4668)
  • 当 /ship 的文档审核在最后一轮审核后更正已审核的文档时，/ship 即可完成。 (#4708)
  • /ship 可以在保存其快照之前停止的文档审核之后完成。 (#4693)
  • /ship 可以在从基础分支合并之前运行文档审核时完成。 (#4648)
  • /ship 在仅重新记录共享线束引脚的基础合并后保留拉取请求的已完成审查，并且 /ship 在其审查者在没有记录审查的情况下运行时发出警告。 (#4669)
  • 一旦剩余的调查结果得到裁决，确认其阻止程序已修复的后续检查现在就开始计算。 (#4691)
  • 后续检查读取已批准的修复轮清理现在结束该轮修复的结果。 (#4664)
  • 即使其简介是在审查开始之前编写的，对已批准的修复进行彻底的重新检查也很重要。 (#4698)
  • 修复提交的 Review-Finding: 预告片仅在全面审查并完成其范围内的修复后才会结束其发现。 (#4700)
  • /ship 的簿记在另外三种情况下仍然成立：变成符号链接的线束引脚需要重新审查，无法保存的声明如此说明，以及在新的描述后早期的运行仍被计数。 (#4703)
  • /ship 的审查计划在具有非常大的数据或试用文件的存储库上完成，并且 GSTACK_REVIEW_CONSUMER_SCAN_CAP 提高了数据文件扫描限制。 （＃4651，＃4643）
  • GSTACK_REVIEW_PLAN_TIMEOUT_MS 现在提高了 /ship 每一步的审查计划时间限制，因此大型存储库可以完成。 (#4632)
  • 存储库自己的 review_exclude_paths 测试不再将排除的文件拉回审查。 (#4699)
  • 代码审查现在读取前端更改的设计清单（它之前指出了丢失的文件），第二个模型审查现在读取存储库自己的 agents/ 文件夹中的代码。 (#4711)
  • /ship 的评论不再将“HIGH 分支”之类的代号视为 HIGH 发现。 (#4678)
  • 以编号标题形式书写的法典审查结果保持了其严重性。 (#4681)
  • 对 /ship 辅助工具的七个小修复，包括不再将 Review-Finding: 拖车变成 Refs 线路的问题链接。 (#4672)

  • /eval-plan 的试运行遵循计划自己的日期和声明的供应商模型，新计划命名了他们的分级机如何处理代理的存储库。 (#4673)

  • 声明 gbrain 上下文查询的技能在开始时加载它们； gstack-config set gbrain_context_load off 将其关闭。 (#4687)
