gstack v1.102.0.0

这个项目是干啥的：把 Claude Code 变成一支虚拟开发团队的配置集，内置 CEO、设计、审查、测试、发版等角色，给想单枪匹马做大项目的开发者和小团队用。

变更架构图

亮点

  • Codex 成为一等宿主 — ./setup --host codex（Codex 0.170+）会安装 hooks，在每条 shell 命令前建议 skill 并执行破坏性命令检查；风险命令在交互会话中被拦截，但在 codex exec 下只给警告。迁移/行为注意：Codex 启动时提示时请信任这些 hooks，并预期 skill 名称与 Codex 自身列表一致（$review，而非 $gstack-review）。Codex 用户特别值得升级——office-hours、plan-design-review 和 gstack-upgrade 在该环境原本是坏的，且 /review 现在会在缺少对抗性环节时拦一次（以 task_name 启动的 Sol 子 agent 算作该环节）。
  • 破坏性命令检查重建（/careful） — 在对 254,322 条真实 agent 命令的回放中，无害询问从 1.40% 降到 0.33%，而破坏性拦截从 948 条中的 443 条升到 930 条：scratch/cache/build 输出的删除被忽略，但项目外的删除、丢失未提交工作、历史重写、远程分支删除、数据库重置、云资源删除、向默认分支强推和擦盘都会被拦下。明确的破坏性变更：Agent SDK 程序现在收到警告而非询问（SDK 拒绝无人应答的询问）——设置 GSTACK_SESSION_KIND=interactive 可恢复询问。后续 #4525 进一步拓宽检测（静默 git clean -q、find -L … -delete、wipefs -a、cd 之后或带 --all/--mirror 的强推），代价是约多出 141 次无害询问（总计 0.39%）。
  • 安全修复：输出被截断现在改为失败关闭 — 输出被截断的命令现在判为失败，而不是基于部分输出做判断，堵上了一个缺口：diff 超过 64 MiB 的推送可能带着凭据绕过 pre-push hook（#4492、#4502）。单凭这一点，任何通过 /ship 发布的人都值得升级。
  • Hooks 与路由重新调校 — 辅助 hooks 默认开启，破坏性检查现在作为 hook 运行；提示词路由对长 bug 报告生效，会推荐用户自行安装的 skill，且不再把 bug 报告发给 /qa（60 条真实 bug 报告中，用 gstack 自带 skill 路由了 14 条，用已安装 skill 路由了 40 条）。没有迁移步骤，只是需要注意的行为变化。/ship 也获得一批可靠性修复——Capy 的 PR 交给 Capy 自己的工具处理，而不是用你的账号编辑；第二模型评审失败会给出具名原因，并把 402 记为预算停止；合并检查的修复会强制进行第二轮评审，而不是报告完成。
  • 结论 — 如果你用 Codex、依赖 /careful 或 /ship 的评审/安全流水线，或想堵上 64 MiB 凭据缺口，就升级。这些都不用则安全跳过：其余只是小维护，包括两个 GBrain 修复（/sync-gbrain 中超过 64 KB 的首页、跨仓库重新同步的唠叨提示）以及各类不稳定测试和 CI 修复。这是实质性发布，不是重新打标签或仅改元数据。

gstack 1.102.0.0 让 Codex 成为一等宿主：它现在能获得 gstack 的 skill 建议、破坏性命令检查和 /review 的清单拦截。破坏性命令检查经过重建，询问频率大幅降低，同时拦下更多真实破坏。

破坏性命令检查（/careful）

  • 它不再询问删除 scratch 文件（/tmp、mktemp 目录、缓存、构建输出），但会在删除你项目之外的东西、丢弃未提交工作、历史重写、远程分支删除、数据库重置和云资源删除前询问。递归删除 / 或你的主目录、向默认分支强推、擦除整块磁盘，无论怎么写都会被拦。在对 254,322 条真实 agent 命令的回放中，无害询问从占命令的 1.40% 降到 0.33%，拦截的破坏性命令从 443 条升到 948 条中的 930 条。（#4513）
  • 它读命令更仔细了：git push --repo=origin +main、cd 之后的强推或带 --all/--mirror 的强推、静默 git clean -q、find -L … -delete，以及所有拼写形式的 wipefs -a 都会被拦；git push -nf 的演练和对 SQL 文本的 grep 不再询问。在同一回放中，它拦下的破坏性命令只多不少，并新增 141 次无害询问（合计占命令的 0.39%）；后续修复正在处理这些。（#4525）
  • Agent SDK 程序收到警告而非询问，因为 SDK 拒绝无人应答的询问。设置 GSTACK_SESSION_KIND=interactive 可保留询问。（#4513）

Codex

  • ./setup --host codex（Codex 0.170+）新增 hooks，针对提示词建议合适的 gstack skill，并在每条 shell 命令前运行破坏性命令检查。Codex 无法就单条命令发问，因此风险命令在交互会话中被拦截，在 codex exec 下只给警告。Codex 启动时询问时请信任这些 hooks。（#4512）
  • Codex 上的 /review 在试图未完成对抗性环节或报告就结束时拦一次，和 Claude Code 一样。（#4522）它把以 task_name 启动的 Sol 子 agent 算作该环节。（#4526）
  • 当你的 Codex 目录路径含 shell 特殊字符时，Codex hooks 依然工作；卸载会保留你自己 hooks 的受信任状态；setup 更贴合 Codex 的 hook schema；/review 的清单能正确读取带引号的 ; 和失败的读取。（#4528）
  • Skill 建议、选择器提示和文档改为按 Codex 的列表方式命名 skill（$review，而非 $gstack-review）。（#4523、#4524）
  • office-hours、plan-design-review 和 gstack-upgrade 在 Codex 上重新能加载，codex exec 下的 skill 知道自己处于无人值守状态，Codex 评审人从干净上下文开始。（#4510）

Hooks 与路由

  • 辅助 hooks 默认开启，破坏性命令检查作为 hook 运行，提示词路由对长 bug 报告生效。用 gstack 自带 skill 时，路由 hook 路由了 60 条真实 bug 报告中的 14 条（此前 17 条）；文档现已与之一致。（#4503、#4505）
  • 路由 hook 现在还会推荐你自己安装的 skill，并停止把 bug 报告发给 /qa。用已安装 skill 时，它路由了 60 条真实 bug 报告中的 40 条。（#4506）

/ship、评审与 CI

  • 在 Capy 上，/ship 不再用你的 GitHub 账号编辑或评论 PR；它把文本交给 Capy 自己的 PR 工具。（#4518）
  • 输出被截断的命令现在判为失败，而不是基于部分输出做判断。这堵上了 diff 超过 64 MiB 的推送可能带凭据绕过 pre-push hook 的缺口。（#4492、#4502）
  • 第二模型评审失败会给出停止原因，把 402 记为预算停止，且绝不删除自己的提示词。（#4515、#4519）
  • 当某次修复触及合并检查时，第二轮评审现在会评审它，而不是报告完成。（#4520）
  • Ship policy 可把已发布数据标为内容，让 /ship 能评审大型数据 PR，且这样的目录不能把源码或 agent 文件藏起来不评审。（#4511、#4516）
  • 当被发布的 checkout 不是项目的默认 checkout 时，/ship 的评审也能工作。（#4507）
  • /ship 的状态机检查接受其读取器写出的头部行。（#4504）
  • 变更数字检查不再误报只共享 limit 之类单词的测试。感谢 @dtoelke。（#4496）
  • 合并了发布版本且仅重新生成了已声明文件的 PR，会复用其更早的测试运行。（#4483）
  • 当 Claude Code 在提交前运行 /verify 时，它得到的是快速检查而非完整修复循环（#4508），且该检查超时会干净失败。（#4527）
  • 评审收集器不再丢弃写成摘要 bullet 的真实 P0，也不再把评审人的范围列表当作发现。（#4527）
  • gstack-ship-queue ready 现在会填入针对其他开放 PR 的试合并，以及哪个第二模型检查了决策记录，外加六处 /ship 工具小修复，包括记录由另一个 agent 转达的裁定。（#4529）
  • worker 在各自会话中启动的测试运行不再被当作卡死而杀掉。感谢 @dtoelke。（#4533）
  • 免费套件 CI 能扛过缓慢的 Ubuntu 镜像，还修复了四个不稳定测试和 eval 检查。（#4530）

GBrain

  • /sync-gbrain 的读取检查在首页超过 64 KB 时能工作。（#4497）
  • 同步第二个仓库不再让第一个仓库反复要求你同步。感谢 @SatriaSuriaAriffin。（#4532）
