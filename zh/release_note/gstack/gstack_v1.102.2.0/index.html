gstack v1.102.2.0

gstack 1.102.2.0 修复了 Codex 上破坏技能的两件事，停止 /plan-tune 在没有记录的情况下将您键入的答案发送到模型，让大型存储库使用 /ship，使 /office-hours 从真实情况开始，并将技能路由从 CLAUDE.md 移到现在执行该工作的钩子中。 法典

  • 当清理临时文件时，Codex 0.170 上的技能不再停止：gstack 的 Codex 技能停止使用 Codex 拒绝的 rm -f 形式（之前拒绝 67 次，之后拒绝 0 次）。 (#4612)
  • /review on Codex with OpenAI 模型不再无法通过真正运行其安全通行证的审查。 Codex 会对发送给该审阅者的消息进行加密，因此 gstack 现在可以识别来自它启动的审阅者的传递，而不是从消息文本中识别。 (#4622) 隐私和遥测
  • /plan-tune 的答案摘要器现在会在将您键入的答案发送到模型之前写入自述文件承诺的机外发送记录，如果无法写入该记录，则不发送任何内容。任何不写入记录的模型调用的新测试都会失败。感谢@robbiesierra 的报告。 (#4621)
  • 在 Capy 安装上，只有所有者的选择发送使用数据，仅读取代码的审阅者不发送任何数据，并且错误报告带有错误类别。 (#4597) 技能
  • /office-hours 被重写：它首先要求基本事实，并且每个启动会话都以过时的测试结束。 (#4468)
  • gstack 不再提供将 ## Skill routing 部分添加到项目的 CLAUDE.md 中的功能。技能建议挂钩现在可以完成这项工作：有了它，Claude Code 在 60 个测试会话中的 45 个和 60 个测试会话中的 48 个中加载了正确的错误修复技能，而在没有 gstack 的情况下，60 个测试会话中只有 0 个加载了正确的错误修复技能。现有的 CLAUDE.md 文件保持不变。 (#4629)
  • 计划审查不再将 /design-review 审计摘要读取为分支机构的设计文档。感谢@robbiesierra 的报告。 (#4623)
  • /cso 在读取文件之前检查源文件上方的每个文件夹，因此它永远不会读取符号链接文件夹。 (#4592) /在大型存储库上进行交付和审查
  • GSTACK_REVIEW_PLAN_TIMEOUT_MS 现在在 /ship 使用它的地方提高了审查计划时间限制，因此拥有数十万个文件的存储库可以完成计划审查。超时消息命名该设置。 （＃4632，＃4637）
  • 当基础分支的审核策略仅在其排除列表中无效时（例如超过 64 个模式），/ship 现在会用响亮的警告来审核每个文件，而不是拒绝，因此修复策略的拉取请求本身可以被审核。拉取请求仍然无法更改其自身的审核策略。 (#4637)
  • Node 的内置测试文件现在在使用 vitest 或 jest 的存储库中与 node --test 一起运行。感谢@eoin-obrien 的报告。 (#4626)
  • /ship 不再因审核者已经清除的审核笔记而停滞，按照审核策略读取审核的方式计算审核轮次，并将安全结果保留在拉取请求主体之外。 (#4595)
  • 当 Capy 的驱动器同步数据库增长超过 100 MB 时，/ship 的审核不再停止。 (#4606)
  • /ship 的评论读者被告知永远不要停止他们没有启动的进程。 (#4607)
  • /ship 不再要求进行新的审查，因为 main 已经有一个堆叠的父级 (#4580)，在仅引入基础的合并中保持已审查的头当前状态 (#4577)，遵守存储库重新运行 CI 跳过的测试的时间限制，并表示何时需要安装新的工作树的软件包 (#4608)。
  • 提交准备好的拉取请求不再依赖于手写的门决定，准备好的注释、发布 PR 和压缩消息说明了正确的事情。 (#4596)
  • 可以审查包含大量捕获的代理会话的拉取请求的结果。 (#4574) 评估
  • /eval-plan 拒绝 gpt-4o 和任何被取代的模型作为手臂、法官、阅读器或模拟器，并指定替代者；当计划如此规定时，使用其供应商的默认模型进行测试的竞争对手可以豁免。从 2026 年 11 月 22 日起冻结的计划在模型评委计算数字之前需要 100 个人工标记的输出，而不是 40 个。 (#4630)
  • gstack 自己的 eval 助手从 Claude Haiku 4.5 迁移到 Haiku 5.5，这会重新启动每个付费案例的通过率历史记录。一名脚本测试演员留在 Haiku 4.5 上，因为 Haiku 5.5 在测试等待的事件之前表演。 （＃4630，＃4639）
  • /eval-plan 编写浪费更少金钱的计划。 (#4591) 文档
  • 自述文件和文档不再声称 gstack 可以让您的代理修复更多错误；他们说它做什么和不做什么。 (#4598)
  • 新页面：跨代理系统工作。 (#4583) 对于从事 gstack 工作的人
  • Free Tests 在 16 核运行器上运行其分片（中位数为 154 秒，低于前 5 次运行的 222 秒），并且分片完成时更加接近。 （#4600，#4578）
  • 跑步者跳过的隔离测试现在无法通过而不是通过。感谢@Huyvux12，他的 #4551 发现并首先修复了它。 (#4590)
  • 不稳定的修复：spawnSync 溢出检查 (#4613)；每周测试时间记录可以再次登陆（#4581）并且记录的测试时间是当前的（#4633）；对于真正的跑步者来说，作业日志睡眠时间足够长（#4589）。
  • 最慢的免费测试文件被分成六个 (#4588)，Windows 设置测试在安装更改时更快完成 (#4575)，并且拉取请求不再等待片状测试上传 (#4579)。
  • 九个团队运行评估的习惯，写入 gstack 自己的工作规则中（#4585，#4602）； gstack 自己在 Capy 上的使用与实际使用分开计算 (#4576)； Capy 上代理线程的令牌签入行减半以匹配 Capy 的新计数 (#4582)。
  • 一项关于 /ship 是否需要其辅助代理的实验得到了计划更新：每只手臂都有一名不计其数的飞行员，计划对一半的案件进行检查，在最终远程门拒绝时停止，并为其法官再标记一次尝试。 （#4587、#4605、#4609、#4611） 比较v1.102.1.0…v1.102.2.0
